# Ollama 与替代方案对比

## 全景概览

| 工具 | 定位 | 难易度 | 适合谁 |
|:----|:-----|:------|:-------|
| **Ollama** | 大模型"Docker" | 🟢 最简单 | 普通用户、开发者快速测试 |
| **LM Studio** | 图形化 Ollama | 🟢 最简单 | 非技术用户、Windows用户 |
| **llama.cpp** | 底层推理引擎 | 🟡 中等 | 追求极致控制和性能的开发者 |
| **vLLM** | 生产级推理服务 | 🔴 较复杂 | 高并发 API 服务、企业部署 |
| **llama-box** | 轻量级推理 | 🟡 中等 | 嵌入式、边缘设备 |
| **SGLang** | 结构化推理 | 🟡 中等 | 需要结构化输出、Agent 场景 |

---

## 一、Ollama

**本质**：对 llama.cpp 的高层封装，加了模型管理、API 服务、自动 GPU 检测

| 维度 | 评价 |
|:----|:------|
| ✅ 上手极快 | `ollama run xxx` 一条命令从零到跑 |
| ✅ 自动 GPU | 零配置，NVIDIA/AMD/Apple Metal 自动识别 |
| ✅ 模型管理 | `pull/list/rm` 管理模型，类似 Docker |
| ✅ 生态好 | 大量 GUI（Open WebUI, ChatGPT-Next-Web）直接对接 |
| ✅ API 兼容 | OpenAI 兼容格式，Cursor/VS Code 等工具直接连 |
| ❌ 自定义受限 | Modelfile 能调的不多，底层参数暴露有限 |
| ❌ 大模型管理笨重 | 所有层加载到 GPU，没有 vLLM 的 PagedAttention |
| ❌ 高并发弱 | 不是为高并发 API 设计的 |

**适用场景**：个人开发者测试、日常聊天、快速原型、单用户使用

---

## 二、LM Studio

**本质**：Ollama 的 GUI 版，Windows/Mac 原生桌面应用

| 维度 | 评价 |
|:----|:------|
| ✅ 图形界面 | 点几下就能下载运行模型 |
| ✅ 内置模型搜索 | 直接在 HuggingFace 搜，不用命令行 |
| ✅ 量化选择 | 图形化选择 Q4/Q5/Q6/Q8 |
| ✅ API 服务 | 也提供 OpenAI 兼容 API |
| ❌ Linux 不支持 | 只有 Windows 和 macOS |
| ❌ 不能脚本化 | 没有 CLI，不能自动化部署 |
| ❌ 资源占用 | GUI 本身也吃资源 |

**适用场景**：Windows 普通用户、不想碰命令行的用户

---

## 三、llama.cpp（Ollama 的底层引擎）

**本质**：C/C++ 写的高性能大模型推理引擎，Ollama/vLLM/LM Studio 底层都在用它的 GGUF 格式

| 维度 | 评价 |
|:----|:------|
| ✅ 性能最强 | CPU/GPU 混合推理优化到极致，Ollama 做不到的控制粒度它都能调 |
| ✅ GGUF 格式统治 | 社区最通用的量化格式，几乎所有模型都提供 GGUF |
| ✅ 极致的控制 | -ngl（GPU层数）、-tb（批处理）、-ctk/-ctv（KV Cache量化）全部可调 |
| ✅ 轻量 | 单二进制文件，嵌入式也能跑 |
| ❌ 没有模型管理 | 要自己下载 GGUF、写脚本调用 |
| ❌ 没有自动 GPU 检测 | 编译时要手动指定 CUDA/Metal/ROCm |

**适用场景**：需要精细调优性能的开发者、嵌入式设备、自己写脚本集成

---

## 四、vLLM

**本质**：高性能生产级推理引擎，核心创新是 **PagedAttention**（类似操作系统虚拟内存的显存管理）

| 维度 | 评价 |
|:----|:------|
| ✅ 吞吐量最高 | PagedAttention 让显存利用率提升 2-4 倍，同显卡服务更多用户 |
| ✅ 连续批处理 | 流式请求合并处理，比 Ollama 快几倍到几十倍 |
| ✅ 生产级 API | 原生 OpenAI 兼容，支持流式、函数调用、工具 |
| ✅ Prefix Caching | 共享前缀（如 System Prompt）的 KV Cache 复用，节省 50%+ 算力 |
| ❌ 配置复杂 | 设置模型路径、GPU 个数、tensor_parallel_size、max_num_seqs 等一堆参数 |
| ❌ 不支持 GGUF | 只支持原生 Safetensors（FP16/BF16），模型文件大 |
| ❌ 显存要求高 | 9B 模型 Q4 量化要 ~10GB，vLLM 要用原始 FP16 要 ~18GB |
| ❌ 不推荐单用户 | 为高并发设计的，一个人用杀鸡用牛刀 |

**适用场景**：多用户 API 服务（>10人同时使用）、企业级部署、需要低延迟高吞吐的生产环境

---

## 五、SGLang

**本质**：结构化推理引擎，针对 Agent/Function Calling/JSON 输出场景做了专门优化

| 维度 | 评价 |
|:----|:------|
| ✅ 结构化输出强 | 约束解码（Constrained Decoding）原生支持 JSON Schema |
| ✅ 多模态能力强 | 图片/视频输入支持好 |
| ✅ 推理加速 | RadixAttention（共享前缀树）比 vLLM 在某些场景还快 |
| ❌ 社区小 | 生态不如 Ollama 和 vLLM |
| ❌ 配置复杂 | 和 vLLM 类似，需要较多参数调优 |

**适用场景**：Agent 应用、需要强制 JSON 输出的场景、多模态推理

## 一句话选型建议

| 你的场景 | 选什么 |
|:---------|:-------|
| 我就想本地跑个模型聊聊天 | **Ollama** 🥇 最简单 |
| 我是 Windows 用户不想用命令行 | **LM Studio** 🥇 图形化 |
| 我是开发者要调性能参数 | **llama.cpp** 🥇 控制力最强 |
| 我搭个 API 给 100 个人用 | **vLLM** 🥇 高并发王者 |
| 我搞 Agent 要强制 JSON 输出 | **SGLang** 🥇 结构化推理最强 |
| 我在树莓派上跑 | **llama.cpp** 🥇 最轻量 |
| 我跑 70B+ 大模型但显存不够 | **llama.cpp** 🥇 量化最灵活 |

> 注意：Ollama 是 **入口工具**，llama.cpp 是 **底层引擎**，两者不冲突。Ollama 底层就是 llama.cpp，你也可以直接用 llama.cpp 获得更细的控制。
