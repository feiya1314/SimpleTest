## 一、系统架构与各服务特点分析

### 1.1 整体架构概述

内容审核平台（内容安全），采用五层微服务架构：

```
接入层 → 编排层 → 能力层 → 决策层 → 数据层
网关  →  中控(scas) → 审核服务 → 规则引擎 → 消息处理/Kafka
```

| 层 | 服务 | 职责 |
|---|---|---|
| 接入层 | 网关（Spring Cloud Gateway） | 统一入口、鉴权、限流、路由 |
| 编排层 | 中控编排服务（SCAS） | 加载配置、构建审核上下文、编排调用、处理结果通知业务 |
| 能力层 | 文本审核服务 / 多媒体审核服务 | 敏感词匹配 + 三方审核 / 三方审核转发 |
| 决策层 | 规则引擎 | 根据上下文与审核结果执行规则判断，返回风险结果 |
| 数据层 | 消息处理服务 + Kafka | 审核信息归档、统计分析、抽样人工复审 |

### 1.2 网关（Gateway，Spring Cloud Gateway）

**定位**：接入层，全系统唯一入口。

**特点**：
- 无业务逻辑，纯基础设施，只做流量治理和横切关注点
- 职责高度集中：接口鉴权（JWT/OAuth）、签名校验、限流、路由转发、统一接入日志
- 限流技术栈：Redis + Lua 脚本实现分布式限流（单脚本原子执行，避免竞态）
- 基于 WebFlux（响应式非阻塞），高并发下吞吐能力优于传统 Servlet 模型
- 路由配置化，新服务接入只需加路由规则

**优点**：横切逻辑集中、不侵入业务服务。

**风险点**：网关是单点，一旦故障全链路不可用，需要高可用部署（集群 + 前置 LB）。

### 1.3 中控编排服务（SCAS）

**定位**：编排层，架构的核心枢纽。

**特点**：
- 纯编排、无领域能力：不亲自做审核，只负责"串流程"——加载配置、组装上下文、编排调用顺序
- 持有全局审核上下文：把请求数据、配置、各环节结果聚合在一个上下文对象里贯穿全流程
- 职责边界清晰：
  1. 加载业务配置（审核规则、开关、策略）
  2. 构建审核上下文
  3. 编排调用审核服务
  4. 调用规则引擎做决策
  5. 处理结果并通知业务侧
- 适合用流程编排框架（Camunda、Flowable、自研状态机、策略模式 + 责任链）实现，流程可配置化
- 是唯一一个"懂全流程"的服务，也是故障的高风险汇聚点

**优点**：业务侧对接一个统一入口，不用感知内部多服务的复杂性。

### 1.4 审核服务（文本 / 多媒体）

#### 文本审核服务

**特点**：
- 流量大、独立拆分：避免影响其他内容审核，实现能力隔离（隔离故障 + 隔离扩容）
- 逻辑相对复杂：
  - 敏感词匹配（本地能力：DFA / Trie / AC 自动机 / 正则，可离线、低延迟、可热更新词库）
  - 调用三方 HTTP 服务（外部审核能力），外部依赖重
- 扩展方式：敏感词库可配置化/热加载；三方渠道可做多路冗余和降级

#### 多媒体审核服务

**特点**：
- 无复杂业务逻辑：基本是"透传 + 适配"
- 主要动作：转发给三方 HTTP 审核服务 → 接收结果 → 结果标准化处理
- 外部依赖占比极高：核心能力几乎完全托管给三方，自身是"适配器/门面"角色
- 技术重点在：HTTP 调用稳定性（超时、重试、熔断、幂等）、文件传输（OSS 预签名 URL 避免网关传输瓶颈）、三方接口协议适配

**文本与多媒体对比：**

| 维度 | 文本审核 | 多媒体审核 |
|---|---|---|
| 流量 | 大 | 相对小 |
| 业务逻辑 | 中（词库+三方） | 低（纯三方转发） |
| 外部依赖 | 中 | 极高 |
| 拆分配置 | 独立服务（能力隔离） | 独立服务（协议隔离） |
| 性能瓶颈 | CPU（敏感词匹配）+ 外部 IO | 外部 IO / 大文件传输 |

### 1.5 规则引擎服务

**定位**：决策层，系统的"大脑"。

**特点**：
- 完全无状态、纯计算：输入是请求上下文 + 审核结果，输出风险等级/风险结果，天然适合水平扩展
- 规则可配置化：规则以配置形式下发（Drools、Aviator、Groovy 脚本、自研 JSON 规则 DSL），业务改动不发布代码
- 与审核服务解耦：审核负责"查出事实"，规则引擎负责"做出判断"——把"取证"和"判决"分离
- 适合做成可热更新的规则版本控制（规则灰度、AB 测试、规则回滚）

**潜在风险**：规则多了以后，规则本身的管理（版本、测试、审计）会成为新难点，需要规则测试环境。

### 1.6 数据层（消息处理服务 + Kafka）

**定位**：数据层，异步数据通道。

**特点**：
- 完全异步、彻底解耦：审核结果通过 Kafka 异步通知，主链路与数据链路完全分离
- 业务用途多元：审核信息归档、统计分析、抽样人工复审
- 典型"削峰填谷"架构：高峰期数据量被 Kafka 缓冲，消息处理服务按自身能力消费
- Kafka 天然支持分区并行消费、消息重试、死信队列

**一致性注意点**：消息幂等（消费端去重）、顺序性（分区键设计）、最终一致性。

### 1.7 整体架构核心设计思想

1. **职责分离彻底**：接入/编排/能力/决策/数据五层各管一件事，单一职责贯彻到位
2. **"取证"与"判决"分离**：审核管取证，规则引擎管判决，策略变更不动代码
3. **同步与异步分离**：主链路同步保证实时性，数据链路异步保证稳定性
4. **能力隔离**：文本审核量大独立拆分；多媒体协议特殊单独成服务
5. **高内聚低耦合**：服务内部职责内聚，服务间通过明确接口（HTTP/Kafka）通信

### 1.8 潜在风险与改进建议

| 风险点 | 建议 |
|---|---|
| 中控服务是编排单点 | 流程配置化 + 版本化；编排的幂等和可重放 |
| 文本服务的三方 HTTP 调用是脆弱点 | 超时、熔断（Sentinel/Resilience4j）、多通道容灾、降级策略 |
| 多媒体服务核心能力全押在三方 | 双供应商冗余 + 抽象接口层，防止供应商锁定 |
| 异步链路的数据一致性 | 消费端幂等去重、消息追踪 ID、DLQ 监控告警 |
| 网关单点 | 集群部署 + 健康检查 + 自动摘除 |
| 规则引擎"规则变多后管理难" | 规则测试环境、规则灰度、上线审计 |

## 二、SCAS、文本服务、多媒体服务特点对比

### 2.1 核心定位

```
SCAS（编排层）     →  编排者：串流程、管上下文、调别人
文本服务（能力层） →  执行者：本地敏感词 + 三方审核
多媒体服务（能力层）→  转发者：纯透传三方结果
```

### 2.2 SCAS 中控编排服务

1. **纯编排，零业务能力**：自己不做审核、不判断、不存结果，只负责串流程
2. **持有全局审核上下文**：贯穿全流程，是流程状态的总持有者
3. **依赖复杂度最高**：依赖网关、文本/多媒体服务、规则引擎、Kafka；是全链路故障的汇聚点
4. **核心诉求是"可配置、可编排"**：流程变更理想情况下通过配置/流程定义实现
5. **技术画像**：计算量极小；IO 依赖极高；无状态但需共享上下文存储（Redis）；关键指标是编排延迟、下游可用性、超时/降级策略

### 2.3 文本审核服务

1. **逻辑最重的能力服务**：本地敏感词匹配（自有关键能力）+ 三方 HTTP 审核（借来的能力）
2. **流量大，独立拆分**：能力隔离 + 独立扩容 + 独立发布
3. **性能敏感**：敏感词匹配是 CPU 密集型，三方调用是 IO 密集型，属于"CPU + IO 混合压力"型
4. **技术画像**：计算量高；外部依赖中；无状态天然可水平扩展；关键点是词库热更新、匹配性能、三方超时/熔断/降级

### 2.4 多媒体审核服务

1. **逻辑最轻，典型"适配器/门面"**：接收内容 → 转发三方 → 结果标准化返回
2. **外部依赖占比极高**：核心能力几乎 100% 托管给三方；自身价值在外部调用的工程化（超时、重试、熔断、大文件处理、多供应商适配）
3. **对稳定性和成本敏感**：媒体文件大、传输慢；三方计费高，需要缓存、去重、异步批处理降成本
4. **技术画像**：计算量极低；外部依赖极高；关键点是文件传输、三方协议适配、双供应商容灾

### 2.5 三者对比总表

| 维度 | SCAS 中控 | 文本服务 | 多媒体服务 |
|---|---|---|---|
| 架构角色 | 编排者 | 执行者 | 转发者 |
| 业务逻辑复杂度 | 中（编排逻辑） | 高（算法+三方） | 极低 |
| 计算压力 | 极小 | 高（CPU） | 极低 |
| 外部依赖 | 高（调所有下游） | 中 | 极高（纯三方） |
| 流量特征 | 高（全量经过） | 高（文本量大） | 中 |
| 无状态可扩展 | 是（上下文需外置） | 是 | 是 |
| 核心能力 | 流程编排、上下文管理、降级兜底 | 敏感词算法 + 三方集成 | 三方协议适配 + 媒体传输 |
| 故障影响 | 全链路挂 | 只影响文本审核 | 只影响多媒体审核 |
| 主要风险 | 编排单点、流程变更 | 匹配性能、词库更新 | 供应商锁定、大文件传输 |

**一句话总结**：SCAS 是"指挥"（懂全流程但不干活）；文本服务是"主力"（既能本地打也能外包打，压力最大）；多媒体服务是"翻译"（自己不判断，把活包给三方，只做协议转换和稳定保障）。三者构成"编排—执行—转发"的完整链条。

## 三、SCAS 与多媒体服务的瓶颈分析

### 3.1 核心判断

这两个服务 CPU 压力不大，瓶颈**根本不在计算**，而在 IO 和外部依赖。两者都是 **IO/依赖密集型** 而非计算密集型——瓶颈不在自己算得慢，而在"等别人"和"受制于人"。

### 3.2 SCAS 中控编排服务的瓶颈

1. **下游调用延迟（最大瓶颈）**：RT ≈ 下游最长链路之和；吞吐上限 = 并发连接数 ÷ 单请求平均 RT，下游慢则 QPS 被锁死
2. **线程/连接资源耗尽**：同步阻塞调用下游时，大量请求阻塞等第三方，线程池被占满，即使 CPU 空闲也无法接收新请求
3. **上下文状态存储/访问**：Redis 的序列化/反序列化开销 + 网络往返在高并发下成为隐性瓶颈；上下文对象过大放大开销
4. **并发依赖和级联超时**：并行调用被最慢者主导；超时配置不合理引发重试风暴

**结论**：SCAS 的瓶颈 = 下游延迟 + 线程/连接资源。不是被 CPU 卡死，而是被"等"卡死。

**优化方向**：异步化（WebFlux/响应式、CompletableFuture 编排）、并行编排、连接池扩容、超时与降级策略、减少上下文存储往返。

### 3.3 多媒体审核服务的瓶颈

1. **三方接口的 QPS 配额（最大瓶颈）**：吞吐上限 = 三方配额；超配额即限流、拒单、加钱
2. **大文件/媒体传输带宽**：带宽和传输时间是硬瓶颈；应走 OSS 预签名 URL + 异步回调，避免文件在服务间流转
3. **网络 IO 与连接池**：长连接数受三方限制；单连接传输大文件占时久，连接池周转慢
4. **回调/异步处理通道**：依赖回调通道稳定性；回调积压、丢失、轮询周期长形成吞吐天花板
5. **成本约束**：三方按次/按量计费；需缓存、去重、批量提交压低成本

**结论**：多媒体服务的瓶颈 = 三方配额 + 大文件带宽 + 成本。是被"外包方"和"流量规格"卡死的。

**优化方向**：双供应商分流、预签名 URL 直传对象存储 + 异步回调、内容缓存/去重、批量提交、限流保护配额。

### 3.4 两者瓶颈对比

| 维度 | SCAS | 多媒体服务 |
|---|---|---|
| 瓶颈本质 | 等（下游延迟/线程耗尽） | 等 + 花钱（三方配额/带宽） |
| 瓶颈主体 | 自己的并发模型 + 下游性能 | 外部的三方能力 + 文件大小 |
| 资源型瓶颈 | 线程、连接池、上下文 IO | 连接池、带宽、三方配额 |
| 典型表现 | 线程池满、队列积压、RT 飙高 | 三方拒单/限流、传输超时、成本超支 |
| 最致命点 | 级联超时风暴 | 供应商故障/配额耗尽 = 审核能力归零 |
| 共性 | 都是 IO/依赖型瓶颈，CPU 空转但吃不上吞吐 | 同左 |

> 扩容这两个服务，单纯加 CPU 没有意义。SCAS 加线程/连接/实例 + 异步化 + 超时降级（扩大"等"的能力）；多媒体加配额/多供应商 + 对象存储直传 + 缓存去重（扩大"外包"的能力）。

## 四、线程、连接池瓶颈的解决方案

### 4.1 问题本质

> 同步阻塞模型下，一个线程只能同时处理一个请求，而大部分时间这个线程在睡觉（等 IO）。

解决思路三个层次：**换并发模型、管好连接、砍掉等待**。

### 4.2 方案一：换并发模型（治本）★核心方案

目标：让线程在等 IO 时被释放，去处理别的请求。

#### 方案 A：响应式编程（WebFlux）
- Spring WebFlux（Netty）替代 Spring MVC（Tomcat）
- 从"一个请求占一个线程"变为"少量线程 + 事件循环"
- 适用：SCAS 这种典型 IO 密集编排服务
- 注意：整个链路都要响应式（WebClient），不能混用阻塞式 RestTemplate
- 缺点：学习成本高、调试难

#### 方案 B：异步编排（CompletableFuture / Future）
- 不换框架，内部调用改为异步：
```java
CompletableFuture<AuditResult> text = CompletableFuture.supplyAsync(() -> callTextService());
CompletableFuture<AuditResult> media = CompletableFuture.supplyAsync(() -> callMediaService());
AuditResult r = text.thenCombine(media, this::merge).join();
```
- 适用：改动小、不想上响应式的团队
- 缺点：本质上有阻塞（join），需配置专门 IO 线程池

#### 方案 C：虚拟线程（Java 21+ Virtual Threads）★最推荐
- 百万级轻量线程，阻塞时自动让出平台线程，不需要改业务代码
- 同步代码 + IO 多场景性价比最高，几乎零重构
- 适用：SCAS、文本服务、多媒体服务全都适用

**三方案对比：**

| 方案 | 改造成本 | 提升效果 | 适用场景 |
|---|---|---|---|
| WebFlux 响应式 | 高（重写） | 最高 | 新项目、极致 QPS |
| CompletableFuture | 中 | 中 | 不想大改、并行编排 |
| 虚拟线程 | 极低 | 高 | 现有服务最推荐 |

### 4.3 方案二：管好连接池

#### 下游连接池
- HTTP 连接池（OKHttp / HttpAsyncClient / WebClient）：加大 maxConnections、设 idleTimeout、connectionTtl，每个下游目标独立连接池
- Redis 连接池（Lettuce）：线程安全的连接复用；正确配置 maxTotal、maxIdle
- Kafka 连接：生产者连接数匹配分区数；消费者并发由分区数决定

#### 关键参数（Little's Law）
```
连接池大小 ≈ (目标 QPS × 单次 RT 秒)
```
- 不够就加实例横向扩容，而不是无限调大单机参数
- 必须配合超时：connectTimeout、readTimeout、poolAcquireTimeout

#### 连接池监控
- 必须监控：活跃数、空闲数、等待获取的排队数、获取超时次数

### 4.4 方案三：砍掉等待

1. **同步 → 异步回调 / 消息队列（最重要）**：不要求实时返回的环节异步化（统计、归档 → Kafka）；三方慢操作改"提交 → 受理 → 回调/轮询 → 异步通知"
2. **超时与降级**：合理超时 + 快速失败 + 熔断（Resilience4j/Sentinel）+ 指数退避重试（防风暴）
3. **缓存**：相同内容/结果做本地或 Redis 缓存，命中则不调下游
4. **并行 → 减少调用次数**：合并多次下游调用（批量接口）

### 4.5 综合落地方案

**SCAS 中控服务：**

| 措施 | 具体做法 |
|---|---|
| 核心 | Java 21 虚拟线程（改动最小）或 WebFlux 异步化 |
| 编排优化 | CompletableFuture 并行编排，串行改并行 |
| 超时降级 | 每个下游独立超时 + Sentinel 熔断 + 快速失败 |
| 连接池 | 每个下游独立 HTTP 连接池，配置对齐 QPS×RT |
| 上下文 | Redis 上下文合并读写，或用本地线程上下文传递 |
| 异步化 | 非关键环节（日志、统计、归档）全部走 Kafka |

**多媒体服务：**

| 措施 | 具体做法 |
|---|---|
| 核心 | 大文件走 OSS 预签名 URL 直传 + 三方异步回调 |
| 提交即返回 | 提交审核 → 立即受理返回 → 结果异步通知 |
| 虚拟线程 | 同步调用三方时用虚拟线程，阻塞不占平台线程 |
| 双供应商 | 多供应商分流，避免单一连接池/配额打满 |
| 缓存去重 | 相同内容复用审核结果 |
| 连接池 | 大文件场景用信号量限流控制并发上传数 |

### 4.6 总结

> **治标：把连接池参数调大、监控补上；治本：换并发模型（虚拟线程/异步化）让线程不空等，用"异步回调 + 超时熔断 + 缓存"让请求少等待、连接少被占。**

优先级建议：先做超时/熔断/降级（立刻见效、风险最低）→ 再做虚拟线程（改动小收益大）→ 最后大文件和三方慢操作改异步回调（收益最大但改动大）。

## 五、CompletableFuture + Dubbo 异步：少量实例实现高吞吐

### 5.1 核心逻辑

> SCAS 用 CompletableFuture 异步编排 Dubbo 调用，多媒体用异步 HTTP 调三方——两个服务都可以用很少的实例扛住大吞吐。

原理：这两个服务都是 IO 密集，瓶颈在"等"不在"算"。异步化后，一个线程可以同时处理几百上千个请求（都在等 IO），实例数自然可以很少。

### 5.2 SCAS 为什么少量实例就能高吞吐

**关键：必须用 Dubbo 真正的异步调用（async=true + CompletableFuture / AsyncRpcResult 回调），不是"异步发起、同步等待"。**

| 方式 | 是否真异步 | 说明 |
|---|---|---|
| async=true + CompletableFuture | ✅ 真异步 | 发出去后线程立刻释放 |
| async=true + get() 立即阻塞 | ❌ 假异步 | 线程还是被占住 |
| Dubbo AsyncRpcResult 回调 | ✅ 真异步 | 底层 Netty IO 线程直接回调 |

**为什么实例可以很少：**
```
同步模型：单实例吞吐 = 线程数 / 平均RT
异步模型：单实例吞吐 = 并发数 / 平均RT（并发数轻松上万）
```
- 同步模型：实例数 = QPS ÷ 单实例线程能扛的 QPS
- 异步模型：单实例并发上限由连接数（Dubbo 客户端连接数）和内存决定，轻松上万
- SCAS 从"按 QPS 算实例"变成"按连接池和内存算实例"

**具体做法：**
```java
// Dubbo 异步调用 + CompletableFuture 并行编排
CompletableFuture<AuditResult> textFuture = textService.asyncAudit(context);
CompletableFuture<AuditResult> mediaFuture = mediaService.asyncAudit(context);
CompletableFuture<RiskResult> predictFuture = ruleEngine.asyncPredict(context);

CompletableFuture.allOf(textFuture, mediaFuture, predictFuture)
    .thenAccept(v -> {
        AuditResult finalResult = merge(textFuture.join(), mediaFuture.join(), predictFuture.join());
        notifyBiz(finalResult);
    });
```
要点：发起时用 Dubbo 异步（不 get），回调里再 get（此时已就绪，瞬时完成）。配合 `CompletableFuture.orTimeout` 设置超时。

**少量实例的边界条件：** Dubbo 客户端连接池够大（connections 调大）；下游本身扛得住并发；上下文不依赖重 DB/Redis 交互；注意 SCAS 是编排中心，总流量全系统最大。

### 5.3 多媒体为什么少量实例就能大吞吐

**关键：用异步 HTTP 客户端（WebClient / OkHttp async / HttpAsyncClient）。**

```java
// 异步 HTTP 调三方（WebClient）
Mono<ThirdPartyResult> mono = webClient.post()
    .uri(thirdPartyUrl)
    .bodyValue(request)
    .retrieve()
    .bodyToMono(ThirdPartyResult.class)
    .timeout(Duration.ofSeconds(10));

mono.subscribe(result -> {
    processAndNotify(result);
}, error -> {
    handleFailure(error);
});
```
要点：全程不阻塞，发起即释放，结果回调里继续。配合连接池（Netty maxConnections 调大）、超时、熔断。大文件走 OSS 预签名 URL 直传 + 三方异步回调。

**少量实例的边界条件：** 三方 API 配额足够（真正天花板）；连接池配够；提交和回调都是异步链路；若三方同步返回慢，确保用异步且连接池不打满。

### 5.4 对比总结

| 维度 | SCAS | 多媒体 |
|---|---|---|
| 调用方式 | Dubbo 异步 + CompletableFuture | 异步 HTTP（WebClient/OkHttp async） |
| 线程释放点 | 发起 RPC 后立即释放 | 发起 HTTP 后立即释放 |
| 单实例并发上限 | 客户端连接数 + 内存（上万级） | HTTP 连接池（几千级） |
| 实例数能不能少 | ✅ 能，大幅减少 | ✅ 能，大幅减少 |
| 真正天花板 | 下游扛得住 + 连接池 | 三方配额 + 连接池 |
| 必须配套 | 超时、降级、连接池参数 | 超时、熔断、连接池参数、预签名 URL |

**实例数建议**：两个服务实例数不再由 QPS 决定，而是由"单实例内存 + 连接池容量 + 故障冗余（至少 N+1）"决定。

## 六、异步 RPC 底层原理：NIO 与事件驱动

### 6.1 核心答案

> **是的，底层用的就是 NIO。** 数据不是"线程去等"拿回来的，而是"连接上有数据到达时，事件被触发，IO 线程回调你"拿回来的。业务线程从头到尾没参与等待。

- Dubbo 的传输层：基于 **Netty（NIO）**，负责收发字节
- Dubbo 的异步层：基于 **CompletableFuture**，把"数据到达"翻译成"你的回调执行"

### 6.2 一次完整的异步 RPC 生命周期

**第 1 步：业务线程发起调用（毫秒级，立即返回）**
```
SCAS 业务线程
   │  调用 textService.asyncAudit()
   ▼
Dubbo 客户端：序列化请求 → 分配唯一 RequestId（如 12345）
   │  注册：pendingFutures[12345] = 新的 CompletableFuture
   │  写入 Netty Channel（writeAndFlush）
   ▼
业务线程【立即返回】拿到 CompletableFuture（此时还没结果）
```

**第 2 步：业务线程去干嘛了？** 返回线程池，立刻处理下一个请求；或继续发起多媒体和 predict 的调用。

**第 3 步：数据在网络中传输**（字节流 + RequestId → 文本服务 → 响应字节流 → 回到 Netty Channel）

**第 4 步：数据到达，NIO 事件触发（关键）**
```
Netty Channel 上有数据可读
   → 操作系统内核通过 epoll 通知：Socket 可读（NIO 事件）
   → Netty 的 EventLoop（IO 线程）被唤醒
   → 读取数据 → 反序列化 → 按响应里的 RequestId=12345
   → 找到 pendingFutures[12345] → future.complete(结果)
```

**第 5 步：回调在哪个线程执行？**
```
future.complete(结果) → CompletableFuture 完成
   → 触发注册的回调，默认在【完成它的线程】上执行 = Netty 的 EventLoop（IO 线程）
```

整个流程：业务线程只做了"发出去"一件事，收回来是 Netty IO 线程 + epoll 事件驱动的，没有任何线程在"等"。

### 6.3 NIO 核心机制

**事件驱动：不是轮询，是"被通知"。** NIO 的核心是 Reactor 模型：

```
业务线程池（可少）
        │ 提交请求（不阻塞）
        ▼
┌─────────────────────────────────┐
│  EventLoop 组（IO 线程，如 2~4 个）  │
│  ├─ 每个 EventLoop 持有 Selector   │
│  ├─ Selector 调用 epoll_wait()     │
│  │   └─ 内核通知：哪些 Channel 有    │
│  │      数据可读/可写（事件）        │
│  └─ 处理事件：read/write/回调      │
└─────────────────────────────────┘
```

- **Selector（多路复用器）**：一个线程（EventLoop）同时"盯着"成千上万个 Socket 连接
- **epoll_wait()**：阻塞在这个系统调用上，内核发现有数据到达才返回通知
- 没有数据时，IO 线程就阻塞在 epoll_wait 上睡大觉，不消耗 CPU

**为什么一个 IO 线程能管几万连接：**
```
BIO：每个连接一个线程 → 1 万连接 = 1 万线程 → 线程切换爆炸、内存爆炸
NIO：每个 EventLoop 用 Selector 盯所有连接 → 1 万连接 = 几个 EventLoop 线程
```
本质：BIO 靠"线程数量"扛并发，NIO 靠"事件通知"扛并发。

**Netty 两级线程模型：**
- **Boss Group**：只管 accept 新连接，accept 后把 Channel 注册到某个 Worker EventLoop
- **Worker Group**：管已建立连接的 read/write、触发回调；一个 Worker 线程管几千个 Channel

**连接复用 + 多路复用**：一条 TCP 连接上同时并发多个请求（Dubbo 靠 RequestId 区分），不是"一个请求一条连接"。

### 6.4 事件注册与回调机制

```
内核（epoll）检测到数据
   → 通知 EventLoop（epoll_wait 返回）
   → EventLoop 调 Channel 的 read 回调
   → Dubbo 解码器反序列化
   → 按 RequestId 找到 CompletableFuture
   → future.complete(response)   ← "主动通知"，不是"被动等待"
   → 你注册的回调被调度执行
```

CompletableFuture 的角色：**"结果容器 + 回调注册表"**。调用时拿到空 Future；数据到达时 IO 线程 complete() 把结果塞进去；塞进去的瞬间自动唤醒所有回调。

**异步回调的本质：不是你去取数据，而是数据到了之后主动叫醒你。**

```
同步（BIO）：线程 park 在那里傻等数据 → 线程被占住
异步（NIO）：没有线程在等。数据到了 epoll 唤醒 EventLoop，
            EventLoop 把数据塞进 Future，Future 触发回调 → 无线程被占住
```

### 6.5 NIO vs BIO：本质区别

| 维度 | BIO（同步阻塞） | NIO（异步事件驱动） |
|---|---|---|
| 谁在等数据 | 一个线程等一个连接 | 没有线程等，内核通知 |
| 并发支撑 | 连接数 = 线程数（有限） | 一个线程管上万连接 |
| 线程利用率 | 大量线程空等 | 线程只在有数据时才干活 |
| 上下文切换 | 巨多 | 极少 |
| 拿数据方式 | 主动 read() 阻塞直到有数据 | epoll 通知 → 回调 |
| 结果获取 | 同步返回 / 阻塞 get | CompletableFuture 回调 |

> **一句话：BIO 是"派一个线程守一个门口死等"，NIO 是"一个保安用监控屏盯着所有门口，谁按门铃（事件）谁才动"。前者人多但效率低，后者人少但反应快。**

### 6.6 必须注意的坑：防止"假异步"

```java
// ❌ 假异步：虽然 async=true，但立刻 get() 阻塞，线程还是被占住
Future f = service.asyncAudit();
Object r = f.get();

// ✅ 真异步：发起后不 get，靠回调拿结果
Future f = service.asyncAudit();
f.thenAccept(r -> doSomething(r));
```

**判断标准**：发起调用后，业务线程是否立刻返回且不阻塞。如果有 get()/join()/阻塞等待，就是假异步，线程瓶颈依旧。

## 七、多媒体与 SCAS 服务的瓶颈观测指标

### 7.1 多媒体服务核心瓶颈点

| 优先级 | 瓶颈点 | 是谁的连接池/资源 |
|---|---|---|
| 1 | 三方 API 的 QPS/并发配额 | 三方那侧的限流（最常见瓶颈） |
| 2 | 本服务到三方的 HTTP 连接池 | 自己的 Netty/连接池（WebClient 底层） |
| 3 | 本服务的 EventLoop（IO 线程） | 自己的 Netty Worker 线程 |
| 4 | 大文件带宽/传输时间 | 网络链路 |
| 5 | 回调/通知链路 | 自己的生产连接 |

**关键认识**：多媒体是"外包"服务，真正的天花板通常在三方配额。观测要同时看"自己侧"和"三方侧"。

### 7.2 多媒体服务观测指标清单

**① 自己的连接池（首要）：**

| 指标 | 判断到瓶颈 |
|---|---|
| 连接池活跃连接数 | 接近 maxConnections → 连接池满了 |
| 等待获取连接排队数 | >0 持续 → 请求在等连接 |
| 获取连接超时次数 | 持续增长 → 明确瓶颈 |
| 连接池空闲连接数 | 接近 0 → 连接全被占 |

最佳观测：**inflight（在途请求数）= QPS × 平均RT**。inflight 接近"连接池容量 × 连接复用数"时即边界。

**② 三方侧（真正天花板）：**

| 指标 | 判断 |
|---|---|
| 三方限流错误码（429/配额超限） | 出现 → 撞到三方配额（最直接信号） |
| 三方 RT 变长 | 三方排队 |
| 三方成功率下降 | 三方在丢弃请求 |

**③ 本服务 EventLoop：**

| 指标 | 判断 |
|---|---|
| EventLoop 线程占用率 | 持续 >80~90% → 饱和 |
| EventLoop 任务排队数 | 增长 → 处理不过来 |
| 回调执行耗时 | 回调里做重活会阻塞 IO 线程 |

⚠️ 回调里绝对不能做阻塞操作（同步 DB、同步调服务），否则一个慢回调卡死整个 EventLoop。

**④ 端到端表现：** QPS 曲线是否平坦（平台期）、平均 RT 上涨（排队）、超时率、错误率（429/5xx）。

**⑤ 机器指标（辅助）：**
- CPU：通常不高（预期内），CPU 飙升反而不正常（说明写成同步/重计算）
- 内存：inflight = 大量 Future/Mono 对象 → 观察堆内存和 GC
- 网络带宽：大文件场景观察网卡吞吐
- 文件句柄数：接近 ulimit -n → 连接数撞 OS 限制

> **重要提醒**：多媒体"CPU 不高"是正常健康的（IO 密集），不能拿 CPU 判断瓶颈。CPU 高反而说明出了问题（假异步/同步代码）。

**边界判定：**
```
inflight ≈ 连接池容量 且 排队等待>0 且 超时率上升 → 本服务连接池到瓶颈
或
出现 429/三方限流 且 连接池还有空 → 三方配额到瓶颈（真天花板）
```
**观测顺序**：自己的连接池 → EventLoop → 三方响应码（429/5xx/超时）→ 机器指标（内存/带宽）。

### 7.3 SCAS 服务核心瓶颈点

| 优先级 | 瓶颈点 | 是谁的资源 |
|---|---|---|
| 1 | 下游服务（文本/多媒体/predict）的 TPS 和 RT | 别人的服务（最常见瓶颈） |
| 2 | 本服务到下游的 Dubbo 客户端连接池 | 自己的 Dubbo 连接 |
| 3 | 本服务业务线程池 | 自己的业务线程池 |
| 4 | 上下文存储（Redis） | 自己的 Redis 连接 |
| 5 | 回业务/通知链路 | 自己的下游通知连接 |

**关键认识**：SCAS 是"指挥"，几乎不干活，瓶颈绝大多数是"被下游拖死"。观测核心是"下游响应能力"。

### 7.4 SCAS 服务观测指标清单

**① 下游服务的 TPS 和 RT（首要）：**

| 指标 | 判断 |
|---|---|
| 下游 RT 变化 | SCAS RT = 下游 RT 之和（串行）或最慢者（并行） |
| 下游 TPS 是否达到上限 | 平台期 → 下游到瓶颈 → SCAS 被卡 |
| 下游超时率/错误率 | 下游超时/报错 → SCAS 被迫降级或失败 |
| 下游限流/拒绝 | ThreadPoolFullException → 下游爆了 |

**② 自己的 Dubbo 客户端连接池：** 每个下游的连接数是否打满 connections、inflight per provider、发送队列积压。

**③ 业务线程池：** 活跃线程数接近上限、队列积压、拒绝次数。注意：如果做对了"异步 + 立即返回"，业务线程池不应该成为瓶颈（占用 <1ms）。线程池满了往往是假异步。

**④ 上下文存储（Redis）：** Redis 连接池、Redis 延迟（每次读写都加 RT）、内存/大 key。

**⑤ 端到端 + 机器指标：** QPS 平台期、RT 分位数（P99 上涨）、线程切换、内存（Future 堆积）、**下游各服务的 RT/TPS/错误率（SCAS 观测核心就是这张表）**。

**边界判定：**
```
下游 RT 开始上涨 或 下游 TPS 触及平台期 或 下游出现超时/拒绝
→ SCAS 被下游拖到瓶颈（最常见）
或
自己对某下游的 inflight 接近连接池上限 且 该下游还能扛
→ SCAS 自己的 Dubbo 连接池到瓶颈（次要）
```
**观测顺序**：下游三兄弟的 RT/TPS/错误率（80% 瓶颈在这）→ SCAS RT 分位数 → 自己对各下游的 inflight/连接池 → 业务线程池（排除假异步）→ Redis。

### 7.5 两者对比

| 维度 | SCAS | 多媒体 |
|---|---|---|
| 核心瓶颈 | 下游 TPS/RT（别人的） | 三方配额（别人的）+ 连接池 |
| 自己连接池 | Dubbo 客户端连接池（到各下游） | Netty HTTP 连接池（到三方） |
| 第一观测指标 | 下游 RT/TPS/错误率 | inflight + 连接池活跃数 + 三方 429 |
| 自己的关键线程 | 业务线程池（应几乎空闲） | EventLoop（注意别阻塞） |
| 机器指标意义 | CPU 高=异常（假异步） | CPU 高=异常（同步代码） |
| 最直接边界信号 | 下游超时/拒绝出现 | 三方 429/超时出现 |
| 判断铁律 | 先查下游，再查自己 | 先查三方，再查连接池 |

> **判断铁律：CPU 指标在这两个服务里"无意义"（IO 密集，CPU 高反而说明写成了同步代码）。边界信号就两个：① 加压 TPS 上不去（平台期）；② RT/错误率开始上涨。顺着调用链往下找，谁先报错/超时，谁就是瓶颈。**

## 八、性能压榨：把资源利用压到极限

### 8.1 资源浪费的本质

异步化解决了线程瓶颈，但代价是"资源跑不满"。压榨极限的核心思路：

> **把"等待时间"变成"干活时间"——让每个单位资源同时处理更多请求，并消灭一切不必要的等待。**

四个方向：**提高并发度（填满等待）、消灭等待（异步到底）、降低单请求成本（减少干活量）、提升资源利用（让资源真正跑满）**。

### 8.2 方向一：提高并发度

1. **连接池容量 = 并发天花板，必须配够（最优先）**
   - 公式（Little's Law）：`并发度 = QPS × 平均RT`
   - 目标 5000 QPS、RT 1 秒 → 并发度 5000 → 连接池必须配到 5000+
   - 多媒体：WebClient maxConnections 拉到数千（同步调大 ulimit -n，如 65535）
   - SCAS：对每个下游的 Dubbo 客户端 connections 调大（如 10~50 条/实例）
2. **连接复用 + 多路复用**：一条连接上同时跑多个请求；不要为每个请求建新连接（建连+TLS 是纯浪费）
3. **增加单实例可处理的在途请求数**：由连接数 + 内存决定

### 8.3 方向二：消灭等待

1. **检查"假异步"，清掉所有同步阻塞（最高收益）**
```
❌ 阻塞点（必须改掉）：
   - get()/join() 立即阻塞取结果
   - 同步调用 DB/Redis（Jedis 同步、JdbcTemplate）
   - 同步 IO（文件读写、日志同步刷盘）
   - Thread.sleep / 锁等待
   - 同步调用其他 HTTP 服务（RestTemplate）
```
   - DB/Redis → 异步客户端（R2DBC、Lettuce 异步）；HTTP → WebClient；日志 → 异步日志
2. **回调里禁止重活**：慢回调卡死整个 EventLoop（管几千连接）。重活丢到独立业务线程池或继续链式异步
3. **非关键路径全部异步化**：统计、归档、日志 → Kafka/异步；大文件 → 预签名 URL + 异步回调

### 8.4 方向三：降低单请求成本

1. **缓存：让下游少被调用（对多媒体第一杠杆）**
   - 相同内容重复审核（图片 MD5/SHA、视频指纹）→ 结果缓存（本地 Caffeine + Redis 两级）
   - 缓存命中 → 不调三方 → 不占连接、不花钱、不吃三方配额
2. **批处理/合并调用**：多媒体批量提交三方；SCAS 合并上下文读写（一次 mget/mset）
3. **减少序列化/网络开销**：Dubbo 用 Kryo/FST 替代 Hessian（吞吐提升 30%~50%）；上下文瘦身；gzip 压缩
4. **减少不必要的下游调用**：SCAS 能并行的一定并行；裁剪不必要环节

### 8.5 方向四：提升资源利用

1. **正确配置线程池（IO 密集黄金配比）**
   ```
   线程数 = CPU核数 × (1 + 等待时间/计算时间)
   ```
   - 异步模型下业务线程池线程数应该极小（几十就够），线程只干"发起调用"的活
   - 并发承载在连接池，不在线程池——别用线程数硬撑并发，要用连接数
2. **网络参数调优**：`tcp_nodelay=true`（禁用 Nagle）、TCP buffer 调大、idleTimeout 合理设置、读超时精确（orTimeout/.timeout()）
3. **实例规格与部署匹配**：IO 密集服务分配"低 CPU 核数 + 大内存"实例；K8s HPA 按 inflight 指标（不是 CPU）伸缩
4. **内存与 GC 优化**：inflight = 大量 Future/Mono 对象；大内存 + ZGC/G1 低停顿；避免大对象和泄漏

### 8.6 压榨到极限的"终极组合拳"（按收益排序）

| 优先级 | 手段 | 收益 | 改动 |
|---|---|---|---|
| 1 | 缓存去重（重复内容不调三方） | 吞吐翻倍级别 | 中 |
| 2 | 清除全部假异步/同步阻塞 | 吞吐数倍 | 中 |
| 3 | 连接池配到 Little's Law 并发度 | 消除排队等待 | 低 |
| 4 | 序列化换 Kryo + 上下文瘦身 | 30%~50% | 低 |
| 5 | SCAS 并行编排（串行改并行） | RT 大降 | 低 |
| 6 | 异步日志/异步归档 | 释放线程 | 低 |
| 7 | TCP 调优 + 精确超时 | 连接周转加快 | 低 |
| 8 | IO 实例规格（低核大内存 + HPA 按 inflight） | 资源不浪费 | 低 |

### 8.7 必须警惕的"压榨陷阱"

> **IO 密集服务"资源不满"是健康状态。CPU 60% 可能是正常巅峰，CPU 90% 反而可能意味着出问题。**

真正"到极限"的标志：加连接/加 inflight 不再提升吞吐、P99 RT 开始恶化、错误率/超时率抬头。

> **压榨的方向是"让瓶颈逐个消失"，而不是"把 CPU 拉满"。每消除一个瓶颈，吞吐上一个台阶，直到下一个瓶颈（通常是三方配额/下游能力）成为新天花板。**

## 九、量化指标、扩容方案与配置需求

### 9.1 核心推导逻辑

**一切量化的根基：Little's Law**
```
并发度（inflight/在途请求数）= QPS × 平均RT（秒）
```

**"扛不住"的量化判据：**
```
① QPS 平台期：加压，TPS 不再上升
② RT 分位数恶化：P99 RT 持续上涨
③ 错误率抬头：超时/拒绝/429 比例开始上升
```
满足任一 → 到达瓶颈 → 触发扩容评估。

**扩容的本质 = 增加"瓶颈资源的容量"，而不是盲目加机器。**

各服务瓶颈资源：网关（线程/连接/限流配额）、SCAS（下游能力 + 自己到下游的连接）、文本服务（CPU + 三方配额）、多媒体（三方配额 + 连接池）、规则引擎（CPU + 内存）。

### 9.2 量化指标定义

**通用容量指标：**

| 指标名 | 含义 | 告警阈值 |
|---|---|---|
| inflight_requests | QPS × RT（在途数） | 上限 80% 告警 |
| qps | 每秒处理数 | — |
| p99_rt_seconds | 99 分位延迟 | 超过目标告警 |
| error_rate | 错误数/QPS | 超目标告警 |
| thread_active | 线程池活跃数 | maxThreads 80% |
| thread_queue | 线程池排队数 | >0 持续告警 |

**SCAS 专属：**

| 指标 | 含义 | 阈值 |
|---|---|---|
| dubbo_connections_* | 到各下游的连接数 | 打满告警 |
| dubbo_inflight_* | 到各下游在途请求数 | 80% 告警 |
| downstream_rt_* | 下游 RT | 目标 P99 告警 |
| downstream_tps_* | 下游吞吐平台期 | 平台期告警 |
| downstream_error_* | 下游错误率 | 告警 |
| context_redis_rt | 上下文 Redis 延迟 | 目标 P99 告警 |

**多媒体专属：**

| 指标 | 含义 | 阈值 |
|---|---|---|
| http_conn_pool_active | 到三方活跃连接 | 80% 告警 |
| http_conn_pool_pending | 等待连接排队数 | >0 持续告警 |
| http_inflight_* | 到三方在途请求数 | 80% 告警 |
| thirdparty_http_429/5xx | 三方限流/错误 | 出现即告警（关键） |
| thirdparty_rt | 三方 RT | 目标 P99 告警 |
| eventloop_utilization | EventLoop 占用率 | 80% 告警 |
| cache_hit_rate | 缓存命中率 | 低于目标（如 30%）提示加缓存 |
| large_file_bandwidth | 大文件传输带宽 | 80% 告警 |

### 9.3 量化容量模型

**单实例容量测算（压测得到两个常数）：**
```
① 单实例最大 inflight（并发承载上限）    → I
② 单实例最大 QPS（对应某 RT 目标）      → Q
```

**需要多少个实例（量化公式）：**
```
需要实例数 N = ceil(目标QPS ÷ 单实例QPS)
              = ceil(目标inflight ÷ 单实例inflight)（取两者大）
加冗余：N_final = N × 冗余系数（如 1.5~2）
```

**配置需求示例：**

多媒体服务单实例：
```yaml
max-connections: 3000          # = 目标并发度
connect-timeout: 3s
response-timeout: 10s
idle-timeout: 60s
tcp-nodelay: true
requests: { cpu: 2, memory: 4Gi }   # 低核大内存（IO 密集）
# OS: ulimit -n 65535
```

SCAS 单实例：
```yaml
dubbo.consumer.connections: 20   # 每个 provider 20 条连接
dubbo.consumer.timeout: 3000     # 精确超时快速释放
threads: 64                      # 异步下只需很小
requests: { cpu: 2, memory: 2Gi }
# 冗余：编排中心故障影响全链路 → 冗余系数 ≥2
```

文本服务单实例（CPU 密集，不同）：
```yaml
threads: 核数 × 2
requests: { cpu: 8, memory: 8Gi }  # 高核
```

### 9.4 扩容方案（三档）

**档位一：配置扩容（先不改实例）**
- 触发：`inflight/连接池上限 ≥ 0.8`（连接瓶颈，CPU/内存有余）
- 动作：调大连接池、调大 ulimit、调优超时、加缓存。零成本立刻生效

**档位二：垂直扩容（改单实例规格）**
- 触发：`堆内存 ≥80% 且 GC 频繁` 或 `CPU ≥80% 持续`（仅计算密集服务如文本）
- 注意：IO 密集服务垂直扩容收益低，优先横向

**档位三：水平扩容（加实例）★主要手段**
- 触发：QPS 平台期 + P99 上涨 + 错误率抬头
- 动作与量化：
```
新增实例数 = ceil(目标QPS/单实例QPS) - 当前实例数，再乘冗余
扩容后验证：QPS 是否线性上升？P99 是否回落？错误率是否归零？
```

### 9.5 "为什么要扩容"的完整推导逻辑

```
观测到：QPS 平台期 + P99 上涨 + 错误率抬头
   ↓
定位瓶颈资源：
   ├─ inflight ≈ 连接池上限 → 连接瓶颈
   ├─ EventLoop/CPU 打满 → 处理瓶颈
   ├─ 下游 RT/TPS 平台期 → 下游瓶颈（SCAS 常见）
   ├─ 三方 429 → 三方配额瓶颈（多媒体常见）
   ↓
判断扩容对象：
   ├─ 连接瓶颈 → 先配置扩容，无效则加实例
   ├─ 处理瓶颈 → 加实例或加资源
   ├─ 下游瓶颈 → 扩容下游服务（不是扩自己！）
   ├─ 三方瓶颈 → 加三方配额/双供应商/缓存去重（扩实例无效！）
   ↓
量化扩容规模：N = ceil(目标QPS/单实例QPS) × 冗余
   ↓
扩容后验证：QPS 线性上升？P99 回落？错误率归零？
   ↓
若仍扛不住 → 找下一个瓶颈（瓶颈逐层转移）
```

> **关键洞察：SCAS/多媒体扩容前必须先问"瓶颈在不在自己这"。如果是下游/三方瓶颈，扩自己实例是浪费钱、无效的——这正是量化指标的价值。**

### 9.6 告警分层触发扩容

| 告警 | 触发扩容动作 |
|---|---|
| inflight ≥ 80% 上限 | 先配置扩容（加连接池），2h 无效 → 水平扩容 |
| P99 RT > 目标值 | 定位瓶颈（自己/下游/三方），针对性扩 |
| 三方 429 出现 | 扩三方配额 / 双供应商 / 加缓存（不扩自己实例） |
| 下游 TPS 平台期 | 扩下游服务（不扩 SCAS 自身） |
| CPU ≥ 80%（仅文本类） | 水平扩容 |

**HPA 配置示例（按 inflight 而非 CPU）：**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  metrics:
  - type: External
    external:
      metric:
        name: http_inflight
        target:
          type: AverageValue
          averageValue: 1500   # 单实例承载 1500 在途，超了加实例
  minReplicas: 2
  maxReplicas: 20
```

### 9.7 量化指标 + 方案总结

| 环节 | 量化指标 | 扩容对象 | 为什么 |
|---|---|---|---|
| 瓶颈定位 | inflight/连接池/三方429/下游TPS | 取决于指标指向谁 | 避免扩错对象浪费资源 |
| 单实例容量 | 压测得 QPS 与 inflight 常数 | — | 一切量化的根基 |
| 扩容规模 | N = ceil(目标QPS/单QPS)×冗余 | 加实例 | 用公式代替拍脑袋 |
| 配置需求 | 连接池=并发度、线程=IO公式、实例=低核大内存 | 改配置 | 让配置匹配瓶颈资源 |
| 扩容验证 | QPS 线性上升？P99 回落？错误率归零？ | 验证闭环 | 确认扩容有效而非空转 |

> **量化扩容核心 = 用 Little's Law 把"扛不住"翻译成"哪个资源的 inflight 打满"，用压测得到的单实例容量常数算出"需要几个实例"，按瓶颈资源归属决定扩谁（自己/下游/三方配额/缓存），用"QPS 是否线性上升"验证扩容是否有效。SCAS 和多媒体最大的坑是——扩自己之前，先确认瓶颈不在下游和三方。**

## 十、响应慢但资源低的排查与调优

### 10.1 核心认识

> **CPU/内存/MySQL 低，说明瓶颈不在"算"和"存"，而在"等"。系统大部分时间在等待某个东西，而这个"等待"不消耗 CPU 也不消耗内存。**

### 10.2 响应慢的完整排查清单（按可能性排序）

**① 线程池队列积压（最常见）**
- 现象：请求进来后排队等空闲线程
- 为什么 CPU 低但慢：排队不消耗 CPU
- 排查：线程池指标（active、queue、拒绝数）；线程 dump 看线程卡在哪
- 为什么会打满：假异步残留（get()/同步DB/同步三方）；下游超时太长占住线程；下游变慢 → 线程池迅速打满

**② 下游/三方服务慢（IO 等待，第二大可能）**
- 现象：自己线程没满，但每个请求要等下游返回
- 排查：对下游的调用耗时分布；下游自己的 RT/P99；下游是否也有队列积压
- 关键：你测的 MySQL 没慢，但服务可能根本不查 MySQL，而是调下游 HTTP/RPC

**③ 连接池耗尽等待**
- 现象：请求在"获取连接"这一步排队
- 排查：各连接池活跃数、获取连接耗时；连接池满了 DB 本身可能不慢（慢在"等连接"）

**④ 锁竞争 / 死锁 / 资源争抢**
- 现象：请求被锁挡住
- 排查：线程 dump 大量 BLOCKED/WAITING；Redis 分布式锁、DB 行锁、缓存失效并发重建

**⑤ GC 停顿（Stop-The-World）**
- 现象：偶发大延迟，GC 停顿期间 CPU 是低的但系统像冻结了
- 排查：GC 日志 Full GC 频率、STW 时长；频繁 Minor/Full GC

**⑥ 网络层问题**
- 现象：RT 慢但内部一切正常
- 排查：TCP 重传率、RTT、跨区调用延迟

**⑦ 序列化/IO 阻塞在非业务代码**
- 现象：日志刷盘（同步日志）、磁盘 IO 慢、大对象序列化慢
- 排查：日志改异步日志看是否恢复；磁盘 IO（iostat）

### 10.3 为什么"进入线程池队列"是最可能的情况

典型链路（结合 SCAS 异步编排、多媒体异步 HTTP）：
```
请求进来 → 业务线程池（可能很小，如 64）→ 发起下游调用
                                    ↓ 下游慢/超时长
                          ↓ 线程被"等下游"占住不释放
                      ↓ 线程池迅速打满
                  ↓ 新请求只能进队列排队
              ↓ 表现为：RT 飙升，但 CPU/内存/DB 全低
```
**这就是"假异步"的典型表现**：用了 CompletableFuture 但代码里有 get() 阻塞等待，线程还是被占住，异步白做。

### 10.4 调优方案

**第一层：先定位（30 分钟内）**
```
① 看线程池：active、queue、拒绝数（queue 增长 + active=满 → 线程池瓶颈）
② 看线程 dump：线程卡在哪？
   - BLOCKED → 锁等待
   - WAITING (park) → 等连接/等下游
   - RUNNABLE 但多 → CPU 密集（但你 CPU 低，排除）
③ 看连接池：active、等待获取数
④ 看下游调用耗时分布
⑤ 看 GC 日志
```

**第二层：对症调优**

| 定位结果 | 调优方案 |
|---|---|
| 线程池队列积压 | ① 清假异步（根本解）② 调大线程池（治标，谨慎）③ 调低下游超时快速失败 ④ 加实例 |
| 下游慢 | 扩下游；加缓存；超时熔断降级；并行优化 |
| 连接池耗尽 | 调大连接池；缩短连接占用（异步化）；精确超时 |
| 锁竞争 | 减小锁粒度；无锁化/读写锁；singleflight 优化缓存重建 |
| GC 停顿 | 换 G1/ZGC；减少大对象；调堆大小 |
| 网络慢 | 就近部署；压缩传输；减少跨区调用 |

**第三层：线程池队列的专项调优（三个方向，别盲目调大）**

**方向 A：调大线程池（治标，需谨慎）**
```
适用：确认线程池太小、且下游正常
风险：线程太多 → 上下文切换成本 ↑ → CPU 反而飙高
规则：线程数 = 核数 × (1 + 等待/计算)
```

**方向 B：调大队列 + 限流（保护系统，优先级更高）★**
```
关键认知：队列积压 ≠ 一定要处理完，而是"系统已经过载"
正确处理：
  ① 用队列长度做限流信号（Sentinel/自研）：超阈值 → 快速失败/降级
  ② 合理队列容量（如 1000），拒绝策略 = 快速失败+降级，而非无限排队
  ③ 无限排队是灾难：请求越积越多，RT 越拉越长，最终拖垮系统
```

**方向 C：治本——消除"占线程"的根因 ★★**
```
① 清掉假异步（get() 改回调）→ 线程释放 → 队列自然不积压
② 下游超时调短 + 熔断 → 慢请求快速失败 → 线程不被占死
③ 非关键路径异步化（日志/Kafka）
→ 队列空了，线程池大小反而不重要了
```

**线程池调优的黄金顺序：**
```
1. 先清假异步/调短超时（治本，释放线程）
2. 再用队列长度做限流保护（防过载拖垮）
3. 最后才考虑调大线程池（仅当确认线程池确实太小）
```

### 10.5 完整排查决策树

```
响应慢，CPU/内存/MySQL 低
  │
  ├─ 看线程池：
  │   ├─ queue 增长? ──是──► 线程池队列积压
  │   │                        ├─ 看线程 dump：
  │   │                        │   ├─ BLOCKED → 锁竞争 → 减小锁粒度
  │   │                        │   ├─ WAITING → 等连接/等下游
  │   │                        │   │            ├─ 等连接 → 调连接池
  │   │                        │   │            └─ 等下游 → 扩下游/缓存/熔断
  │   │                        │   └─ RUNNABLE → 排除
  │   │                        └─ 清假异步 + 调短超时 + 队列限流
  │   └─ queue 正常? ──► 看连接池：
  │       ├─ 等待获取>0 → 连接池耗尽 → 调大连接池 + 异步化
  │       └─ 正常 → 看下游调用耗时：
  │           ├─ 下游慢 → 扩下游/缓存/降级
  │           └─ 正常 → 看 GC → 看网络 → 看磁盘/日志
```

### 10.6 为什么"MySQL 没慢"不能排除问题

> **你的服务响应慢，可能根本不查 MySQL。** SCAS 主要调下游 RPC（Dubbo）；多媒体主要调三方 HTTP。MySQL 慢查询只覆盖"数据库访问"这个点，覆盖不到"等待下游/等待连接/等待锁/GC"。MySQL 没慢只说明 DB 不是瓶颈，真正的瓶颈在等待路径上。

### 10.7 总结

> **响应慢但资源低 = 瓶颈在"等待"，不在"计算"。排查顺序：线程池队列 → 线程 dump 定位卡点（锁/连接/下游）→ 下游调用耗时 → GC → 网络。线程池队列积压时，先清假异步 + 调短超时（治本），再用队列长度限流保护（防过载），最后才考虑调大线程池（治标）。MySQL 没慢只说明 DB 不是瓶颈，等待路径才是主战场。**
