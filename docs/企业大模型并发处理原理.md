# 企业大模型并发处理原理

## 一、多个用户同时访问，为什么不会互相干扰？

### 核心机制：每个请求是"独立的数学运算"

一个 LLM 本质上是一个函数 f(x) = y。多个用户同时调用，就是同时计算 f(x₁) = y₁、f(x₂) = y₂、f(x₃) = y₃，各自独立，互不干扰。

```
用户1："法国的首都是"  ──→  模型 ──→  "巴黎"
用户2："1+1等于"      ──→  模型 ──→  "2"  
用户3："写一首诗"     ──→  模型 ──→  "春风拂柳绿..."

每个用户的计算过程完全独立：
  - 输入不同（不同的 prompt）
  - 计算路径各自独立（各自的 KV Cache）
  - 输出不同
  - 就像多个计算器同时算不同的算式
```

### 实际处理方式（以 vLLM 为例）

```
用户1 ───┐
用户2 ───┼─── [调度器] ─── [GPU 显存区] ─── [矩阵计算单元]
用户3 ───┘                      │
                           各用户有自己的 KV Cache 空间
                           （互不重叠的显存区域）

                    ┌──────────┬──────────┬──────────┐
                    │用户1 KV  │用户2 KV  │用户3 KV  │
                    │  Cache   │  Cache   │  Cache   │
                    ├──────────┼──────────┼──────────┤
                    │ token 1  │ token 1  │ token 1  │
                    │ token 2  │ token 2  │ token 2  │
                    │ token 3  │ token 3  │ ...      │
                    │ ...      │ ...      │          │
                    └──────────┴──────────┴──────────┘
                    每个框是独立的显存块，互不干扰
```

## 二、并发处理的核心技术

### 技术一：连续批处理（Continuous Batching）——最关键

这是提升并发量的**最重要的技术**。传统方式 vs vLLM 方式：

```
传统批处理（朴素方式）：
  
  时间 ──────────────────────────────────→
  
  用户1：    ████████░░░░░░░░░░  ← 用户1先跑完
  用户2：      ████████░░░░░░░░  ← 用户2等用户1到一半才开始
  用户3：        ████████░░░░░░  
  用户4：          ████████░░░░
  
  GPU 利用率：约 50%（很多时间在空等）

连续批处理（vLLM 方式）：

  时间 ──────────────────────────────────→
  
  用户1：  ████████
  用户2：   ██████
  用户3：     ██████████
  用户4：       ██████
  用户5：         ████████
  
  GPU利用率：~95%（一直有请求在算）
  
  原理：
    每当一个用户的生成结束（输出完整回答），
    立即分配显存给下一个等待的用户。
    不像传统方式要等整个 batch 全部完成才释放。
```

### 技术二：PagedAttention

```
传统方式：
  每个请求预先分配一块固定的显存给 KV Cache
  → 如果用户只生成了 100 token，但预分配了 2048 token 的空间
  → 浪费 95% 的显存

PagedAttention（vLLM 的核心创新）：
  类似操作系统的虚拟内存——按需分配
  每个用户的 KV Cache 由多个"页"（page）组成
  用多少就分配多少，不用提前预留
  
  效果：同一张显卡，多塞 2-3 倍的并发请求
```

### 技术三：Prefix Caching

```
多个用户可能使用相同的系统提示词（System Prompt）：
  
  用户1：System Prompt + "法国的首都是"
  用户2：System Prompt + "1+1等于"
                        ↑
             共享相同的 KV Cache 前缀
             不需要为每个用户重新计算

  效果：当用户的 System Prompt 很长（如 4K tokens）时，
         能节省 50-80% 的计算量
```

### 技术四：显存管理

```
多用户并发时，显存分配策略：

┌────────────────────────────────┐
│  模型权重（固定占用 ~10GB）     │  ← 所有用户共享
├────────────────────────────────┤
│                                │
│  用户1 KV Cache（动态增长）     │
│  用户2 KV Cache（动态增长）     │  ← 每个用户独立的
│  用户3 KV Cache（动态增长）     │     显存区域
│  ...                           │
│                                │
├────────────────────────────────┤
│  临时计算缓冲区                 │  ← 所有用户共享
└────────────────────────────────┘

KV Cache 是"越长越占显存"：
  上下文长度 × 2（K和V） × 层数 × 隐藏维度 × 2字节
  例如 4K 上下文：4096 × 2 × 80 × 8192 × 2 ≈ 10GB/用户
```

## 三、并发数量的限制因素

| 瓶颈 | 说明 | 典型极限（H100 80G，70B Q4） |
|:----|:-----|:-----------------------:|
| **显存** | 每个用户的 KV Cache 占用显存 | 约 3-5 个用户（4K context） |
| **算力** | GPU 的计算吞吐量（FLOPs） | 约 10-30 个用户（看任务长短） |
| **网络带宽** | 输入输出的数据传输 | >100 用户时可能成为瓶颈 |
| **CPU 调度** | 调度器处理请求队列 | >1000 用户时需要多机 |

**实际生产中，哪个先达到瓶颈？**

```
长上下文场景（如文档分析）：
  → 显存最先爆（每个用户占很大显存）
  → 限制并发数：~3-5 个/卡

短文本场景（如聊天）：
  → 算力最先饱和（GPU 利用率到顶）
  → 限制并发数：~10-30 个/卡
```

## 四、如果想增大并发，该怎么做？

### 方案一：单卡优化（成本最低）

```
效果：提升 ~2-5 倍并发

① 使用 PagedAttention（用 vLLM 而不是 llama.cpp）
② 启用 Prefix Caching（如果共享 System Prompt）
③ 量化到更低精度（FP16 → INT4 → 省出更多显存放 KV Cache）
④ 缩短上下文长度（限制 max_tokens，减少每个用户的显存占用）
⑤ 启用 KV Cache 量化（把 KV Cache 也从 FP16 降到 INT8）
```

### 方案二：增加 GPU（最直接）

```
效果：线性提升

1 卡 H100 → 并发 10 个用户
2 卡 H100 → 并发 20 个用户（数据并行，每卡独立处理不同用户）
8 卡 H100 → 并发 80 个用户

但是这 8 张卡是"各自为战"的：
  卡1：用户1,2,3
  卡2：用户4,5,6     ← 每张卡独立处理自己的用户
  ...
  
不是"8张卡一起算一个用户"（那是张量并行/模型并行，为的是减小延迟，不是增加并发）
```

### 方案三：多机部署（最大规模）

```
效果：理论上无限扩展

负载均衡器（如 Nginx / Envoy）
  │
  ├── 节点1：vLLM（8卡H100）
  ├── 节点2：vLLM（8卡H100）
  ├── 节点3：vLLM（8卡H100）
  └── 节点4：vLLM（8卡H100）
  
负载均衡器把用户请求分发到不同节点
每个节点上的 vLLM 实例独立处理各自的用户

并发量 = 单节点并发 × 节点数
```

### 各方案效果对比

| 方案 | 并发提升 | 成本 | 实现难度 |
|:----|:-------:|:----:|:--------:|
| 量化（FP16→INT4） | 2-3x | 免费 | 🟢 低 |
| PagedAttention | 2-3x | 免费 | 🟢 直接用 vLLM 就行 |
| Prefix Caching | 1.5-2x | 免费 | 🟢 vLLM 自带 |
| 加 1 张卡 | 2x | $30K+ | 🟡 需要配置分布式 |
| 加 1 台机器 | 8x | $250K+ | 🔴 需要负载均衡+运维 |

### 实际企业做法（以 1 张 H100 为例）

```yaml
场景：70B 模型 INT4 量化，4K context

不优化：最多 1-2 个用户并发
  → 每个用户独占总显存，其他人排队

启用 PagedAttention + Prefix Caching + KV Cache 量化：
  ↓
优化后：约 8-12 个用户并发
  → 显存按需分配，共享前缀不重复计算

再加 1 张 H100（数据并行）：
  ↓
约 16-24 个用户并发
```

## 五、两种部署方式架构对比

### Ollama（个人用） vs vLLM（企业用）

```
Ollama 架构（本地跑）：

  用户 ──→ ollama serve ──→ llama.cpp ──→ GPU
         ↑                           ↑
  一次只处理一个用户           朴素批处理，不优化并发

vLLM 架构（企业用）：

            ┌── 调度器（PagedAttention） ──┐
            │                              │
  用户1 ────┤                              ├──→ GPU ──→ 结果1
  用户2 ────┤                              ├──→ GPU ──→ 结果2
  用户3 ────┤  连续批处理 + Prefix Cache     ├──→ GPU ──→ 结果3
  用户4 ────┤                              ├──→ GPU ──→ 结果4
            │                              │
            └──────────────────────────────┘

  Ollama 适合 1 人用
  vLLM 适合 10-100 人用
  再多就要上负载均衡 + 多机了
```

## 一句话总结

> **多用户并发的核心不是"模型是否能同时处理多人"（数学上讲当然可以），而是"显存怎么分配、计算怎么批处理、调度怎么高效"。** PagedAttention（按需分配显存，减少浪费）+ 连续批处理（GPU 一直干活不停机）+ Prefix Caching（共享重复计算）这三项技术，让单卡并发从 1-2 提升到了 10-20。还不够就加卡。💰
