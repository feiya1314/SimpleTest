# 19. 开源大模型开源的是什么

**核心就是模型参数（权重）**。像 DeepSeek 开源的主要包括：

1. **模型权重/参数** - 这是最核心的，即神经网络训练好的参数文件（比如 DeepSeek-V2 的 236B 参数）。拿到这些参数，你就可以在自己的机器上运行推理。
2. **模型架构和配置** - 网络结构设计（如 MoE 架构、Attention 机制等）、超参数配置。
3. **Tokenizer/分词器** - 词汇表和分词策略。
4. **推理代码** - 通常附带基本的推理脚本。

**但通常不开源的部分**：

- **训练数据** - 数据集一般不公开（涉及版权和合规问题）
- **训练代码** - 分布式训练框架、数据清洗 pipeline 等通常不开放
- **训练过程** - checkpoint、日志等

所以开源的大模型可以理解为"**把训练好的脑子给你，但不会告诉你它是怎么被教出来的**"。这允许社区做推理、微调（Fine-tune）、量化压缩等二次开发，但要完全复现训练过程几乎不可能。


# **11. 什么是推理大模型和非推理大模型？有什么区别？**

**推理大模型**：在内部生成推理链条、自我纠错、验证答案后才输出最终结果。类比人类"System 2（慢思考）"——仔细计算27×38而非直接回答
**非推理大模型**：看到问题直接凭"直觉"（一次前向传播）生成答案。类比人类"System 1（快思考）"——直接回答2+2

**核心区别**：

|  | **维度** | **非推理模型** | **推理模型** |
| --- | --- | --- | --- |
| **回答方式** | 直接输出 | 先内部推理，后输出答案 |  |
| **自我纠错** | ❌ 不能 | ✅ 能（回溯、验证） |  |
| **响应速度** | 🟢 快（秒级） | 🔴 慢（几秒到几分钟） |  |
| **复杂推理** | 🔴 差（直觉式） | 🟢 **极强**（深思式） |  |
| **简单任务** | 🟢 高效 | 🔴 浪费（杀鸡用牛刀） |  |
| **总成本（复杂）** | 🔴 可能多次尝试 | 🟢 一次搞定更省钱 |  |
| **可解释性** | 🔴 黑箱回答 | 🟢 可查看推理过程 |  |
| **数学能力（AIME）** | \~10-16% | \~70-87%（质的飞跃） |  |
| **编程能力** | 🟡 中 | 🟢 强 |  |
| **创造性** | 🟢 好 | 🟡 可能"过度思考" |  |

**代表模型**：非推理——GPT-4o、Claude 3.5 Sonnet、LLaMA 3、Qwen 2.5；推理——**OpenAI o1/o3**（首个推理大模型，2024）、**DeepSeek-R1**（开源推理模型，2025，通过纯强化学习涌现推理能力）、Gemini 2.5 Pro

**推理能力从何而来**？核心是**思维链（Chain-of-Thought）**。DeepSeek-R1训练中通过强化学习，模型**自发涌现**出回溯（发现当前路径错误回到分歧点）、验证（得到答案后反过来验证正确性）、子问题分解（大问题拆小）、多路径探索（尝试多个解法）和反思（分析自己为什么错了）等策略——这些不是显式编程的，而是从RL奖励信号中自我进化出来的

**最佳实践**：**两者互补而非替代**。简单问答/翻译/创意写作用非推理模型（更快更便宜）；复杂数学/竞赛编程/科学推理用推理模型。最聪明的做法是**路由系统自动分配**

# **12. 大语言模型和 Transformer 是什么关系？**

**一句话**：**Transformer是大模型的"发动机"，大模型是Transformer的"终极形态"。** 所有现代大语言模型（GPT、Claude、DeepSeek、LLaMA）的底层架构都是Transformer

**核心关系**：没有Transformer就没有大模型。2017年前主流NLP用RNN/LSTM，参数量百万级，RNN的顺序计算无法并行且长序列梯度消失，根本上限制了规模。Transformer的**并行计算**能力使训练超大规模模型成为可能

**为什么Transformer能成为大模型的基石（五大原因）**：

- **1. 并行计算=规模化的前提**：RNN的串行特性决定了训练时间O(n)，扩展到百亿级参数时成本天文数字。Transformer的Self-Attention一次矩阵乘法处理整个序列，GPU利用率拉满。**没有并行就没有Scaling Law**
- **2. Scaling Law成立**：实验证明Transformer的loss随参数/数据/算力幂次下降，**可预测地变强**。RNN/LSTM的loss会先下降然后饱和，加参数没用。Transformer是第一个"增加算力就能稳定变好"的架构，这是大模型工业化的基石
- **3. 上下文长度的自然扩展**：RNN理论无限但实际100-200步就废；原始Transformer 512；GPT-4达128K；Gemini达1M。Transformer通过工程优化（Flash Attention、稀疏注意力、Ring Attention）不断拉长上下文，**RNN架构做不到**
- **4. 架构统一了模态**：Transformer不挑食——文本（GPT）、图像（ViT）、语音（Whisper）、视频（Sora）、多模态（CLIP/GPT-4V）。**同一个架构处理所有模态**意味着跨模态融合天然可行，RNN做不到
- **5. 硬件生态已经锁定**：GPU的Tensor Core就是为矩阵乘法优化的。Transformer的训练=大量矩阵乘法→硬件利用率极高。NVIDIA的cuDNN、Flash Attention都是专为Transformer优化的。RNN的小步循环运算完全不适合GPU架构

**大模型 = 超级大的Transformer解码器**。GPT系列本质上就是把Transformer解码器堆得极大极深加上一些改进。原始Transformer（2017）只有6层编码器+6层解码器，65M参数；LLaMA-3 70B有80层解码器+8192隐藏维度+8192×28672的FFN，720亿参数

**大模型对Transformer的改进**：

- **解码器取代编码器-解码器**：GPT证明只用解码器即可完成所有任务
- **注意力机制进化**：标准注意力→因果注意力→GQA/MQA（节省KV Cache）→FlashAttention（显存优化）
- **激活函数进化**：ReLU→GELU→**SwiGLU**（LLaMA使用，效果最好）
- **位置编码进化**：绝对位置编码（sin/cos）→**RoPE（旋转位置编码）**，可外推到更长序列
- **归一化改进**：Post-Norm→Pre-Norm（训练更稳定）、LayerNorm→**RMSNorm**（计算更快）
- **MoE（混合专家）架构**：传统Transformer所有参数参与所有计算；MoE只激活一部分专家，如Mixtral 8×7B总参数46.7B每次只用12.9B，DeepSeek V2/V3也是稀疏MoE

**涌现能力**：小型Transformer只有基础语言建模能力；中型Transformer（1B-10B）增加翻译和摘要能力；大型Transformer（>10B）增加多步推理和代码生成；**大模型（>100B）突然出现**零样本推理、上下文学习、思维链、指令遵循等能力——这些是Transformer原始架构没有的，是**规模放大带来的质的飞跃**

# 大模型如何调用工具的

好问题，这是理解 AI Agent 最核心的部分之一。
大模型调用工具的完整流程
大模型本身只是一个文本生成模型，输入一段文字，输出下一段文字。让它能 "调用工具"，需要在外层套一个专门的运行时。
整个流程分六步：
第 1 步：把工具的 "说明书" 写在系统 prompt 里
在模型看到你的问题之前，系统 prompt 里已经塞入了所有可用工具的说明。每个工具的描述包括：

工具名：get_weather
描述：查询指定城市的天气深度拆解 OpenCode 架构：这款 AI 编码工具的设计精髓全在这了
参数：
  city（字符串，必填）：城市名称
  unit（字符串，可选）：温度单位，celsius 或 fahrenheit
模型看到的不是真实的 API 接口，而是这段文字描述。对模型来说，"调用工具" 就是 "输出一段符合格式的文字"。
第 2 步：模型根据用户问题推断该用哪个工具
用户问："北京今天多少度？"
模型在推理时，把用户问题跟每个工具的 description 做语义匹配。它发现 get_weather 的 description 匹配 "查询城市天气"，于是决定用这个工具，参数填 city = 北京。
第 3 步：模型输出一个结构化的 "工具调用"
模型不是真的去调 API，而是输出一段特定格式的文本。OpenAI 格式的例子：

{
  "tool_calls": [{
    "id": "call_xxx",
    "type": "function",
    "function": {
      "name": "get_weather",
      "arguments": "{\\"city\\": \\"北京\\", \\"unit\\": \\"celsius\\"}"
    }
  }]
}
对于 Claude 的格式，输出的是 tool_use 类型的 content block。本质上都是模型输出一段结构化的 JSON 文本。
第 4 步：运行时拦截这个输出，去执行真实的 API 调用
模型输出文本后，外层的 Agent 运行时（比如 Claude Code 的 harness）检查输出内容。如果检测到工具调用格式，它不会把这段 JSON 直接返回给用户，而是拦截下来，自己去调用真实的 API。

模型输出 → 运行时检测到 tool call → 运行时执行真实 API → 拿到结果
第 5 步：把结果返回给模型，让模型继续推理
运行时把 API 返回的结果（比如 "北京，25°C，晴"）以 tool_result 的格式塞回给模型。模型看到结果后，像什么都没发生一样，继续基于这个信息生成最终的回复。
第 6 步：模型生成最终的文本回复
模型把工具返回的信息整合进自己的回答，输出给用户："北京今天 25 度，天气晴朗。"
为什么模型能准确生成调用指令
准确是相对的，不是绝对的。但大体上能做到的原因有几个。
原因一：模型是专门训练过的
基础的大语言模型（预训练阶段）并不会调用工具。工具调用能力是通过指令微调（instruction tuning）和函数调用微调（function calling fine-tuning）专门训练出来的。
训练数据里包含了大量这样的样本：

用户：北京的天气怎么样？
系统：以下是可用工具：[get_weather 描述...]
助手：（调用 get_weather，参数 city=北京）
系统：工具返回 25°C
助手：北京今天 25 度。
模型反复看到这种 "用户问问题 → 调用工具 → 拿到结果 → 生成回答" 的模式，学会了在什么情况下应该输出什么格式的工具调用。
原因二：工具描述的质量直接决定了准确性
这是最容易被忽视的一点。模型能不能准确调用工具，70% 取决于工具描述的清晰度。
好的描述：

工具：search_flights
描述：查询航班信息。当用户询问航班、机票、飞机出行时使用
参数：
  from（城市名）：出发地
  to（城市名）：目的地
  date（日期）：出发日期，格式 YYYY-MM-DD
差的描述：

工具：sf
描述：一个函数
参数：a, b, c
模型不是 "理解" 了这个工具的逻辑，而是通过语义相似度匹配用户的问题和工具的 description。description 写得越准确，匹配就越准。参数名和类型越明确，模型生成的参数值就越正确。
原因三：输出格式被强制约束
模型在微调时被训练成输出特定格式的 JSON。推理时，运行时可以进一步用 JSON schema 验证模型的输出，如果格式不对就要求模型重试。OpenAI 和 Anthropic 的 API 层面都支持对工具调用做 schema 校验，参数类型、必填字段不对会直接报错。
原因四：但模型确实会出错
工具调用并不总是准确的，常见的问题有：

问题类型 / 表现 / 原因

幻觉调用 / 用户没要求用工具，模型自己调了 / 模型过度关联
参数错误 / 参数名对但值错了 / 用户意图理解偏差
选错工具 / 有两个相似的 tool，选了错的 / description 不够区分
忽略工具 / 应该用工具但直接回答了 / 模型忘了或 training 不充分
格式错误 / 输出的 JSON 不合法 / 模型生成不稳定
所以 Agent 框架中通常都有重试机制和 fallback 逻辑。
一句话总结
大模型调用工具不是真的去 "调 API"，而是通过训练学会了 "在需要的时候，输出一段特定格式的 JSON，声明我要用哪个工具、参数是什么"。外层的运行时拦截这个 JSON，替它去执行真实的调用，再把结果喂回来。准确率取决于训练数据的质量和工具描述写得好不好，不是模型 "理解" 了 API 文档。

大模型的本质：下一个词的预测器
模型在推理时做的事情极其简单：

输入："北京的天气怎么样？"
模型内部：计算"下一个最可能是什么词"
输出概率分布：
  "北"    概率 0.001%
  "天"    概率 0.0005%
  "{"    概率 85%        ← 选了这个
  "北"    概率 0.002%
  ...

选择概率最高的 → 输出 "{" 
然后把这个字拼回输入，继续预测下一个：

输入：... + "{"
预测下一个：
  "\\n"   概率 1%
  "  "  概率 70%         ← 选了这个
  "t"   概率 20%
  其他  概率 9%
就这样一个字一个字地生成下去。模型没有意识，不知道自己在 "生成 JSON" 或 "调用工具"。它只是在做它最擅长的事：根据已看到的所有文字，猜下一个最该出现的文字是什么。
那为什么它总是猜对 JSON 格式？
因为在训练阶段，它看到了巨量的 JSON 文本。
训练数据里 JSON 的占比
一个标准的 100B\~1T token 的模型，训练数据中包含了：
大量 API 文档（OpenAI、Anthropic、Google 的 API 文档都大量使用 JSON）
GitHub 上的代码（大量项目使用 JSON 做配置）
函数调用微调数据（专门构造的 tool call 样本）
Stack Overflow 和技术论坛
模型可能看到了几十亿个 JSON 片段，它已经 "学会" 了 JSON 的统计规律。

JSON 的统计规律：
  "{" 之后 → 大概率是 '"'（字段名开始）
  '"' 之后 → 大概率是字母或数字（字段名内容）
  字段名后 → 大概率是 '":'
  '":' 之后 → 大概率是值（字符串/数字/布尔/数组/对象）
  值结束 → 大概率是 ',' 或 '}'
这些规律对模型来说，和 "我" 之后大概率是 "是"、"吃"、"想" 这些语言规律没有任何区别。模型不知道自己在遵守 JSON 语法，它只是发现历史上看到的所有 { 后面跟着的字符都有固定的统计模式，它照着这个模式走。
函数调用微调：专门强化了这种模式
在基础模型（预训练）之上，厂商会做指令微调和函数调用微调。他们会构造这样的训练样本：

用户：今天北京多少度？

系统消息中包含：
你是一个 AI 助手，你可以使用以下工具：
- get_weather: 查询天气，参数 city(string), unit(string)

助手期望的输出：
[工具调用开始标记]get_weather[参数开始]{"city":"北京","unit":"celsius"}[结束]
注意，这里不是靠 "理解"JSON 语法来输出的，而是通过数万个这样的样本，让模型记住了 "当用户问天气时，我的输出应该长这样"。
这是一个纯粹的模式匹配过程：

看到用户问"北京多少度" 
→ 激活了"get_weather"这个模式
→ 激活了"输出 JSON 参数"这个模式
→ 一个字一个字地生成出正确的 JSON

中间没有"理解JSON语法"这个步骤。
但模型确实会出错
即使训练充分，模型仍然会在工具调用上犯错。原因在于 token 级别的概率并不是 100%：

理论上：{ 之后 " 的概率是 99.9%
实际上：{ 之后 " 的概率可能是 99.5%

那 0.5% 的概率会输出什么？
  可能是换行符（模型在 JSON 里看到过换行）
  可能是空格
  可能是任何在训练数据中出现在 { 后面的字符

当模型"累了"（概率分布变平），这 0.5% 的概率就会冒出来。
所以你会看到这样的错误：

{                            ← 正确
  "city": "北京"            ← 正确
  "unit": "celsius"         ← 正确
}                            ← 正确
,                           ← 错误！多了一个逗号
模型在训练数据中看到过 }, 这个模式（对象后面还有更多字段），所以有时候会不自觉地多输出一个逗号。
为什么 API 层面很少出错
你实际使用 API 时很少看到 JSON 格式错误，是因为：
采样策略：API 的 temperature 设得很低（0 或接近 0），每次选概率最高的那个 token，大大降低出错概率
重复采样：如果输出的 JSON 格式不对，API 底层会自动重新生成
Schema 校验：API 会校验工具调用的参数格式，不符合要求就报错，不会返回给用户
推理增强：像 o1、R1、DeepSeek V4 这类模型有更强的思考能力，在输出前内部已经做过多轮验证
一句话总结
模型能准确输出 JSON 格式的 tool call，不是因为它 "理解" 了 JSON 语法，而是因为它在训练数据中看到过几十亿次这种模式，已经把 { → " → : → , → } 的统计规律学得极其牢固。这跟它学会 "我" 后面通常跟动词是同一个原理 —— 纯粹的统计模式匹配，没有理解。
