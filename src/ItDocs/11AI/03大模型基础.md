# 1. 开源大模型开源的是什么

**核心就是模型参数（权重）**。像 DeepSeek 开源的主要包括：

1. **模型权重/参数** - 这是最核心的，即神经网络训练好的参数文件（比如 DeepSeek-V2 的 236B 参数）。拿到这些参数，你就可以在自己的机器上运行推理。
2. **模型架构和配置** - 网络结构设计（如 MoE 架构、Attention 机制等）、超参数配置。
3. **Tokenizer/分词器** - 词汇表和分词策略。
4. **推理代码** - 通常附带基本的推理脚本。

**但通常不开源的部分**：

- **训练数据** - 数据集一般不公开（涉及版权和合规问题）
- **训练代码** - 分布式训练框架、数据清洗 pipeline 等通常不开放
- **训练过程** - checkpoint、日志等

开源的大模型可以理解为"**把训练好的脑子给你，但不会告诉你它是怎么被教出来的**"。这允许社区做推理、微调（Fine-tune）、量化压缩等二次开发，但要完全复现训练过程几乎不可能。

# 2. 权重到底是什么？

## 权重的本质

权重就是**神经网络中所有的参数（Parameters）**，包括连接权重 w 和偏置 b。模型训练的过程，本质上就是**从海量数据中不断调整这些参数的值**，最终让它们"记住"了语言规律和知识。

把大模型想象成一个**超大规模的信息处理系统**：

- **输入**：Token 序列（"中国的首都是"）
- **权重**：系统内部数千亿个"旋钮"，每个旋钮控制信息如何流动和变换
- **输出**：下一个最可能的 Token（"北京"）

权重就是这些"旋钮"的最终状态，是模型**所有知识的载体**。

## 权重的物理存储

权重在计算机里就是**一个巨大的浮点数数组**：

```
LLaMA-3 70B 的权重构成（简化）：
- 80 层 Transformer 层
- 每层有：注意力权重 + FFN 权重
- 总共约 700 亿个浮点数

存储大小：
- FP32（32位浮点）：70B × 4字节 = 280GB
- FP16/BF16（16位）：70B × 2字节 = 140GB
- INT4（4位量化）：70B × 0.5字节 = 35GB
```

所以"70B 模型"的 70B 指的就是**权重数量**——700 亿个参数。你下载模型文件时下载的就是这些浮点数。

## 怎么理解权重——三个类比

**类比一：大脑的突触连接**

人脑有约 860 亿个神经元，每个神经元通过突触连接。权重就像突触的**连接强度**——有些连接强（权重值大），有些连接弱（权重值接近 0），有些连接是抑制的（负值）。学习就是调整这些连接强度的过程。

**类比二：乐谱，不是演奏**

权重就像**乐谱**，而不是演奏本身。乐谱记录了音乐的所有信息（音符、节奏、力度），但它自己不会发出声音。只有演奏者（推理代码）照着乐谱演奏，音乐才会响起。同样，权重记录了知识，但只有加载到推理框架中运行前向传播，才会产生输出。

**类比三：压缩的知识库**

大模型把整个互联网的文本知识"压缩"到了这几十 GB 的权重里。原始训练数据可能有几十 TB 甚至 PB 级，但权重只有几十到几百 GB。这个压缩过程会丢失细节，但保留了**统计规律和模式**。所以权重本质上是一个**极致的压缩器**——把海量数据压缩成一组参数。

## 权重怎么使用

**1. 推理（Inference）——最常用的方式**

加载权重，输入文本，模型通过**前向传播**计算输出。权重是**只读**的，不会改变：

```
加载权重 → 输入"中国的首都是" → 前向传播计算 → 输出"北京"
                                  ↑
                          权重参与计算但不更新
```

你使用 ChatGPT、Claude 时，背后的模型权重就是在做推理。**同一个权重文件，无论谁用、在哪用、用多少次，推理结果是一样的**（不考虑随机采样差异）。

**2. 微调（Fine-tuning）——在权重基础上继续学习**

在特定领域数据上继续训练，**更新权重**。微调后权重发生了变化，模型"学会"了新的知识或能力：

```
原始权重 → 在医疗数据上微调 → 医疗版权重
原始权重 → 在代码数据上微调 → 代码版权重
```

常见的微调方法：

- **全参数微调**：更新所有权重，效果好但成本极高
- **LoRA（Low-Rank Adaptation）**：冻结原始权重，在旁边加一个小矩阵，只训练这个小矩阵。训练完成后得到的是一个"LoRA 权重文件"（通常只有几 MB 到几十 MB），推理时合并到原始权重上使用

**3. 量化（Quantization）——压缩权重**

把高精度浮点数映射到低精度，减少存储和加速推理：

```
FP32（4字节）→ FP16/BF16（2字节）→ INT8（1字节）→ INT4（0.5字节）
精度越高          ←              →  速度越快、存储越小
```

量化会带来**轻微的性能损失**，但对大部分任务影响不大。这就是为什么消费级显卡也能跑大模型——通过量化把 70B 模型从 140GB 压缩到 35GB（INT4），RTX 4090 的 24GB 显存通过 CPU offloading 也能运行。

**4. 权重合并/模型融合（Model Merging）**

把多个微调后的权重按比例混合，产生同时具备多种能力的模型：

```
merged_weight = α × 权重_A + (1-α) × 权重_B
```

比如把"代码版"和"数学版"权重合并，得到一个既懂代码又懂数学的模型。这是开源社区常用的技巧。

## 权重的关键特性

1. **权重不是代码**——你不能打开权重文件阅读它存储的"知识"。权重是数值矩阵，不是人类可读的文本
2. **权重是分布式的**——知识不是存在某个特定的权重里，而是**分布存储**在数十亿个权重的组合中。删除单个权重对模型能力几乎没有影响
3. **权重是统计性的**——权重不是精确的事实数据库，而是"统计规律"的编码。所以模型会"幻觉"——它不是在查字典，而是在猜最可能的回答
4. **权重决定了能力上限**——同样的推理代码，加载不同的权重，产生完全不同的能力。代码只是骨架，权重才是灵魂

## 一句话总结

权重就是大模型"脑子"里的**全部记忆和经验**，以**数千亿个浮点数**的形式存储。你可以直接用它做推理（只读），也可以在特定数据上微调（更新部分权重），或者量化压缩（减小体积）。理解权重就是理解"大模型开源到底开源了什么"的关键——开源的是**训练好的参数**，不是训练过程或数据。

# 3. 什么是推理大模型和非推理大模型？有什么区别？

**推理大模型**：在内部生成推理链条、自我纠错、验证答案后才输出最终结果。类比人类"System 2（慢思考）"——仔细计算27×38而非直接回答
**非推理大模型**：看到问题直接凭"直觉"（一次前向传播）生成答案。类比人类"System 1（快思考）"——直接回答2+2

**核心区别**：

|  | **维度** | **非推理模型** | **推理模型** |
| --- | --- | --- | --- |
| **回答方式** | 直接输出 | 先内部推理，后输出答案 |  |
| **自我纠错** | ❌ 不能 | ✅ 能（回溯、验证） |  |
| **响应速度** | 🟢 快（秒级） | 🔴 慢（几秒到几分钟） |  |
| **复杂推理** | 🔴 差（直觉式） | 🟢 **极强**（深思式） |  |
| **简单任务** | 🟢 高效 | 🔴 浪费（杀鸡用牛刀） |  |
| **总成本（复杂）** | 🔴 可能多次尝试 | 🟢 一次搞定更省钱 |  |
| **可解释性** | 🔴 黑箱回答 | 🟢 可查看推理过程 |  |
| **数学能力（AIME）** | \~10-16% | \~70-87%（质的飞跃） |  |
| **编程能力** | 🟡 中 | 🟢 强 |  |
| **创造性** | 🟢 好 | 🟡 可能"过度思考" |  |

**代表模型**：非推理——GPT-4o、Claude 3.5 Sonnet、LLaMA 3、Qwen 2.5；推理——**OpenAI o1/o3**（首个推理大模型，2024）、**DeepSeek-R1**（开源推理模型，2025，通过纯强化学习涌现推理能力）、Gemini 2.5 Pro

**推理能力从何而来**？核心是**思维链（Chain-of-Thought）**。DeepSeek-R1训练中通过强化学习，模型**自发涌现**出回溯（发现当前路径错误回到分歧点）、验证（得到答案后反过来验证正确性）、子问题分解（大问题拆小）、多路径探索（尝试多个解法）和反思（分析自己为什么错了）等策略——这些不是显式编程的，而是从RL奖励信号中自我进化出来的

**最佳实践**：**两者互补而非替代**。简单问答/翻译/创意写作用非推理模型（更快更便宜）；复杂数学/竞赛编程/科学推理用推理模型。最聪明的做法是**路由系统自动分配**

# 4. 大语言模型和 Transformer 是什么关系？

**一句话**：**Transformer是大模型的"发动机"，大模型是Transformer的"终极形态"。** 所有现代大语言模型（GPT、Claude、DeepSeek、LLaMA）的底层架构都是Transformer

**核心关系**：没有Transformer就没有大模型。2017年前主流NLP用RNN/LSTM，参数量百万级，RNN的顺序计算无法并行且长序列梯度消失，根本上限制了规模。Transformer的**并行计算**能力使训练超大规模模型成为可能

**为什么Transformer能成为大模型的基石（五大原因）**：

- **1. 并行计算=规模化的前提**：RNN的串行特性决定了训练时间O(n)，扩展到百亿级参数时成本天文数字。Transformer的Self-Attention一次矩阵乘法处理整个序列，GPU利用率拉满。**没有并行就没有Scaling Law**
- **2. Scaling Law成立**：实验证明Transformer的loss随参数/数据/算力幂次下降，**可预测地变强**。RNN/LSTM的loss会先下降然后饱和，加参数没用。Transformer是第一个"增加算力就能稳定变好"的架构，这是大模型工业化的基石
- **3. 上下文长度的自然扩展**：RNN理论无限但实际100-200步就废；原始Transformer 512；GPT-4达128K；Gemini达1M。Transformer通过工程优化（Flash Attention、稀疏注意力、Ring Attention）不断拉长上下文，**RNN架构做不到**
- **4. 架构统一了模态**：Transformer不挑食——文本（GPT）、图像（ViT）、语音（Whisper）、视频（Sora）、多模态（CLIP/GPT-4V）。**同一个架构处理所有模态**意味着跨模态融合天然可行，RNN做不到
- **5. 硬件生态已经锁定**：GPU的Tensor Core就是为矩阵乘法优化的。Transformer的训练=大量矩阵乘法→硬件利用率极高。NVIDIA的cuDNN、Flash Attention都是专为Transformer优化的。RNN的小步循环运算完全不适合GPU架构

**大模型 = 超级大的Transformer解码器**。GPT系列本质上就是把Transformer解码器堆得极大极深加上一些改进。原始Transformer（2017）只有6层编码器+6层解码器，65M参数；LLaMA-3 70B有80层解码器+8192隐藏维度+8192×28672的FFN，720亿参数

**大模型对Transformer的改进**：

- **解码器取代编码器-解码器**：GPT证明只用解码器即可完成所有任务
- **注意力机制进化**：标准注意力→因果注意力→GQA/MQA（节省KV Cache）→FlashAttention（显存优化）
- **激活函数进化**：ReLU→GELU→**SwiGLU**（LLaMA使用，效果最好）
- **位置编码进化**：绝对位置编码（sin/cos）→**RoPE（旋转位置编码）**，可外推到更长序列
- **归一化改进**：Post-Norm→Pre-Norm（训练更稳定）、LayerNorm→**RMSNorm**（计算更快）
- **MoE（混合专家）架构**：传统Transformer所有参数参与所有计算；MoE只激活一部分专家，如Mixtral 8×7B总参数46.7B每次只用12.9B，DeepSeek V2/V3也是稀疏MoE

**涌现能力**：小型Transformer只有基础语言建模能力；中型Transformer（1B-10B）增加翻译和摘要能力；大型Transformer（>10B）增加多步推理和代码生成；**大模型（>100B）突然出现**零样本推理、上下文学习、思维链、指令遵循等能力——这些是Transformer原始架构没有的，是**规模放大带来的质的飞跃**

# 5. 大模型token会映射成id，ID会变的吗？

**核心答案**：在**同一个模型 + 同一个分词器（Tokenizer）版本**下，token 到 ID 的映射是**固定的、确定的**。但跨模型、跨分词器版本时会变化。

## 为什么同一个模型下 ID 是不变的？

Tokenizer 在训练完成后会生成一个**固定的词汇表（Vocabulary）**，本质上就是一个 **"词 → ID" 的哈希映射表**：

```
词汇表示例（简化）：
"我"    → ID 1234
"是"    → ID 5678
"中国"  → ID 9012
"人"    → ID 3456
```

这个映射表在模型训练完成后就**冻结了**，不会动态变化。同一个词（严格说是同一个 subword 单元）每次经过 tokenizer 都会得到同一个 ID。这是 Tokenizer 设计的基本原则——**确定性映射**。

## 什么情况下 token 的 ID 会变化？

1. **不同模型使用不同的 Tokenizer**：GPT-4 使用 GPT-4 的 Tokenizer，LLaMA 使用 LLaMA 的 Tokenizer（基于 SentencePiece），DeepSeek 也有自己的 Tokenizer。同一个中文句子在不同 Tokenizer 下会分成不同的 token 片段，ID 也完全不同。
2. **同一个模型的不同版本更新 Tokenizer**：例如 GPT-3.5 到 GPT-4 可能升级了 Tokenizer，支持更多语言或特殊字符，词汇表发生了变化。
3. **自定义 Tokenizer 训练数据不同**：如果自己训练 Tokenizer，训练语料不同会导致词汇表不同，同一个词的 ID 不同。
4. **特殊 Token 的 ID 是预定义的**：每个模型都有一些特殊 token，它们的 ID 是固定的：
   - `<PAD>` → ID 0
   - `<UNK>` → ID 1（未知词统一映射到这个 ID）
   - `<BOS>` / `<SOS>` → ID 2（序列开始）
   - `<EOS>` → ID 3（序列结束）
   - `<SEP>`、`<CLS>` 等视模型而定

## 实际影响

- **Token 计数是确定的**：同一段文本用同一个 Tokenizer 编码，得到的 token 数量是固定的。这就是 API 计费可以精确计算的原因
- **KV Cache 依赖 ID**：推理时缓存的 Key-Value 是基于 token ID 的，ID 不变才能复用缓存
- **Prompt Cache 命中**：连续请求中相同的 token 序列（相同的 ID 序列）才能命中缓存，节省延迟和成本
- **不同模型间不能混用**：不能把 GPT-4 的 token ID 直接给 LLaMA 用，词汇表完全不同

## 一句话总结

Token 到 ID 的映射在**同一个 Tokenizer 版本内是绝对确定的**，一个词永远映射到同一个 ID。但**不同模型 / 不同 Tokenizer 版本之间**，词汇表不同，ID 映射也不同。开发者需要记住的是：**同一个 API（如 GPT-4 API）的 Tokenizer 是固定的，你每次发送相同文本得到的 token ID 序列完全一样**。

# 6. 大模型工作的步骤是什么

大模型从接收输入到生成输出，核心是一个**自回归（Autoregressive）**的循环过程：每次只预测**下一个 token**，然后把新生成的 token 拼回去继续预测，直到完整输出。

完整流程分为以下 7 个步骤：

## 第 1 步：Tokenizer 分词——把文本变成 Token ID 序列

用户输入的文本，模型是看不懂的。第一步是用 Tokenizer（分词器）把文本切分成 token，再映射成模型能处理的数字 ID：

```
输入文本："中国的首都是哪里？"
                    ↓ Tokenizer 分词
Token 序列：["中国", "的", "首都", "是", "哪里", "？"]
                    ↓ 查词汇表映射为 ID
Token ID 序列：[1234, 567, 8901, 2345, 6789, 111]
```

每个 Tokenizer 维护一个**词汇表（Vocabulary）**，本质上是一个"词片段→ID"的映射表。中文通常按字或词切分，英文按 subword（子词）切分。

## 第 2 步：Embedding 嵌入层——把 Token ID 变成向量

每个 Token ID 查 Embedding 矩阵，得到一个**高维向量**（通常 4096 或 8192 维）：

```
Token ID: [1234, 567, 8901, 2345, 6789, 111]
                    ↓ Embedding 查表
向量序列（形状：[6, 4096]）：
[[0.12, -0.34, 0.56, ...],  ← "中国" 的向量
 [0.78, 0.91, -0.23, ...],  ← "的" 的向量
 [0.45, -0.67, 0.89, ...],  ← "首都" 的向量
 ...]
```

Embedding 矩阵本身也是**可训练的参数**（权重的一部分），训练过程中每个 token 的向量表示会不断调整，使得语义相近的 token 在向量空间中也相近。

## 第 3 步：位置编码——告诉模型 token 的顺序

Attention 机制本身**没有顺序感**，它看到的是"一堆 token"，不知道哪个在前哪个在后。必须显式地注入位置信息：

- **RoPE（旋转位置编码）**：目前主流方案（LLaMA、Qwen、DeepSeek 都用这个）。通过对 Query 和 Key 向量施加旋转变换来编码位置。好处是支持**外推**——训练时只见过 4096 长度，但推理时可以处理更长的文本
- **绝对位置编码**：早期方案（GPT-2、原始 Transformer），直接加一个位置向量到 Embedding 上

## 第 4 步：Transformer 层——核心计算，逐层处理

这是最核心的步骤。向量序列会依次通过 N 层 Transformer 解码器层（LLaMA-3 70B 有 80 层），**每层结构完全相同但权重不同**：

每一层包含两个子模块：

**子模块 A：多头自注意力（Multi-Head Self-Attention）**

让每个 token "看" 到其他所有 token，聚合上下文信息：

```
输入："中国" 的向量、"的" 的向量、"首都" 的向量、"是" 的向量、"哪里" 的向量、"？" 的向量
                    ↓ Self-Attention
"中国" 的向量 → 融合了上下文信息：关注到了"首都"、"哪里"
"首都" 的向量 → 关注到了"中国"、"是"
"哪里" 的向量 → 关注到了"首都"、"是"
```

**注意力计算的本质**：每个 token 生成 Query（查询）、Key（键）、Value（值）三个向量。Query 去匹配所有 Key 得到注意力分数（相似度），然后用分数加权求和所有 Value。数学上就是：

```
Attention(Q, K, V) = softmax(Q × K^T / √d) × V
```

**子模块 B：前馈神经网络（FFN）**

对每个 token 独立做**非线性变换**，相当于"思考"这一步提取到的信息：

```
FFN(x) = SwiGLU(x × W1) × W2
```

每个 token 通过 FFN 时，同一层内所有 token **共享同一套权重**，但每个 token 独立计算互不影响。

**残差连接（Residual Connection）**：每个子模块后，会把**输入和输出相加**，然后做 Layer Normalization。公式：

```
输出 = LayerNorm(输入 + 子模块(输入))
```

这样做的好处是让梯度可以直接流过，训练更稳定。

**逐层递进**：第 1 层输出的向量可能只捕捉到基础的语法关系，第 10 层开始理解短语语义，第 30 层以上能捕捉长距离依赖关系，到第 80 层（最后一层）输出的向量已经包含了**整个上下文的高度抽象语义信息**。

## 第 5 步：输出投影层（LM Head）——向量变回概率分布

最后一层 Transformer 输出的向量，经过一个线性变换（LM Head），映射到**词表大小**的向量，每个位置对应词表中的一个 token：

```
最后一层输出的向量（[4096] 维）
                    ↓ LM Head 线性变换
词表大小的向量（[128000] 维）  ← 每个值代表对应 token 的"分数"
                    ↓ Softmax 归一化
概率分布：
  "北京"     → 概率 85%    ← 选这个
  "上海"     → 概率 5%
  "南京"     → 概率 3%
  "广州"     → 概率 2%
  ...其他   → 概率 5%
```

LM Head 的权重矩阵形状是 `[词表大小, 隐藏维度]`，它也是可训练参数。有些模型（如 LLaMA）会**共享** Embedding 层和 LM Head 的权重（Weight Tying）。

## 第 6 步：采样策略——决定选哪个 token

概率分布出来后，不能简单地每次都选概率最高的 token（贪心解码），那样会让输出变得单调和死板。常用的采样策略：

- **Top-k 采样**：只从概率最高的 k 个 token 中采样（如 k=40），排除概率很低的 token
- **Top-p（Nucleus）采样**：从累计概率超过 p 的最小 token 集合中采样（如 p=0.9）
- **Temperature**：控制概率分布的"尖锐程度"。temperature 越低，越倾向于选高概率 token（确定性高）；越高，低概率 token 也有机会被选中（创造性高）
- **贪心解码（Greedy Decoding）**：每次都选概率最高的 token，适合需要确定性答案的任务（如数学计算）

实际应用中通常组合使用：Top-k + Top-p + Temperature 调整。

## 第 7 步：自回归循环——重复直到停止

大模型是**自回归**的——每次只生成一个 token，然后拼回去继续：

```
第一轮输入："中国的首都是"
        ↓ 前向传播（步骤 1-6）
输出 token："北京"    ← 概率最高的

第二轮输入："中国的首都是" + "北京"
        ↓ 前向传播
输出 token："是"

第三轮输入："中国的首都是" + "北京" + "是"
        ↓ 前向传播
输出 token："中国"

第四轮输入："中国的首都是" + "北京" + "是" + "中国"
        ↓ 前向传播
输出 token："的"

...继续直到生成 <EOS>（结束标记）或达到最大长度限制
```

这就是为什么大模型生成速度不是恒定的——生成的 token 越多，输入序列越长，注意力计算量越大（KV Cache 优化除外）。

## KV Cache——关键优化

在第 7 步的自回归循环中，如果每轮都重新计算所有 token 的注意力，会产生大量重复计算。KV Cache 缓存了之前所有 token 的 Key 和 Value 向量，新的一轮只需要计算**新 token** 的 Query、Key、Value：

```
第一轮（无缓存）：
  计算所有 token 的 Q、K、V → 保存 K、V 到缓存

第二轮及以后（有缓存）：
  只计算新 token 的 Q、K、V
  Attention 计算：新 Q × (缓存 K + 新 K) → 注意力分数
  缓存中存入新 K、新 V
```

KV Cache 是推理优化的核心手段，但它**消耗大量显存**——对于 70B 模型，每个 token 的 KV Cache 约 2MB，生成长度为 4096 的序列，KV Cache 需要约 8GB 显存。

## 完整流程图

```
用户输入文本："中国的首都是"
    │
    ▼
① Tokenizer：["中国", "的", "首都", "是"] → [1234, 567, 8901, 2345]
    │
    ▼
② Embedding：Token ID → 向量序列 [4, 4096]
    │
    ▼
③ RoPE 位置编码：注入位置信息
    │
    ▼
④ Transformer 层（×N层）：
   ├ 自注意力：每个 token 聚合上下文
   └ FFN：非线性变换
    │
    ▼
⑤ LM Head + Softmax：向量 → 概率分布
    │
    ▼
⑥ 采样：从概率分布中选一个 token → "北京"
    │
    ▼
⑦ 拼回输入 → 重复②~⑥ → 直到遇到 <EOS>
    │
    ▼
最终输出文本："北京是中国"
```

## 一句话总结

大模型的工作流程就是"**分词 → 向量化 → 逐层注意力处理 → 概率预测 → 采样输出 → 拼回去再来一次**"的循环。每步只生成一个 token，把新 token 拼到输入末尾继续生成下一个。这就像一个**逐字造句**的过程——每次只看已经写好的内容，决定下一个字写什么，直到句子完整。

# 7. Function Call介绍？

## Function Call 是什么

Function Call 是大模型在训练和推理时的一种**特殊输出格式**。它不是真的去调用函数，而是模型输出一段特定格式的文本，声明"我想调用某个函数，参数是什么"。

本质上就是：

```
模型输出 → 一段结构化的 JSON → 声明"我要用 X 工具，参数是 Y"
```

---

**Function Call、Tool Call、Tools 参数 三者的关系**

这三者是**同一件事的不同发展阶段和叫法**：

```
tools 参数（API 请求时传的） → 告诉模型"你有这些工具可用"
                              ↓
模型根据 tools 参数决定是否调用 → 输出 function call / tool call
                              ↓
系统拦截这个输出 → 去执行真实的 API → 把结果塞回给模型
```

**具体来说：**

| 术语 | 谁在用 | 本质 | 说明 |
| --- | --- | --- | --- |
| **Function calling** | OpenAI 最早提出 | API 中的一个功能名称 | OpenAI 在 2023 年 6 月首次推出的功能，允许模型输出结构化的函数调用。是最早的叫法 |
| **Tools 参数** | OpenAI / Anthropic / 几乎所有厂商 | API 请求中的参数名 | 你传工具定义的地方。OpenAI 叫 `tools`，Anthropic 也叫 `tools` |
| **Tool call** | Anthropic 的叫法 | 模型输出的格式 | Anthropic API 中，模型输出的是 `tool_use` 类型的 content block。对应 OpenAI 的 `tool_calls` |
| **Function call** | OpenAI 的叫法 | 模型输出的格式 | OpenAI 的 `tool_calls[].function` 里包含 name 和 arguments |

**它们的关系图：**

```
API 请求：
  tools: [                        ← 这是参数名
    {                              ← 这是 tool 定义
      "name": "get_weather",
      "description": "...",
      "input_schema": {...}        ← Anthropic 叫 input_schema，OpenAI 叫 parameters
    }
  ]

模型输出（OpenAI 格式）：
  tool_calls: [                    ← OpenAI 叫 tool_calls
    {
      "id": "call_xxx",
      "type": "function",          ← type = function
      "function": {                ← OpenAI 叫 function
        "name": "get_weather",
        "arguments": "{\"city\": \"北京\"}"
      }
    }
  ]

模型输出（Anthropic 格式）：
  content: [
    {
      "type": "tool_use",          ← Anthropic 叫 tool_use
      "name": "get_weather",
      "input": {"city": "北京"}    ← Anthropic 叫 input
    }
  ]
```

所以：

- **Function calling** = OpenAI 给这个功能起的营销名字
- **Tools 参数** = 你传工具定义给模型的 API 参数
- **Tool call / Function call** = 模型输出中表示"我要调用工具"的那段 JSON

**三者说的是同一件事**——只是不同厂商叫法不同，但底层原理完全一样。

---

**Function Call 的原理**

第 1 步：你把工具描述放在 `tools` 参数里传给模型

```json
{
  "model": "gpt-4",
  "messages": [{"role": "user", "content": "北京天气"}],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "查询天气",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {"type": "string"}
          },
          "required": ["city"]
        }
      }
    }
  ]
}
```

第 2 步：模型在推理时，看到用户说"北京天气"，匹配到 get_weather 的 description。然后模型在生成 token 时，不走正常文本生成路径，而是**切换到一个特殊模式**——输出 tool call 格式的 JSON。

OpenAI 的实现是：模型在训练时学会了一个特殊 token，表示"接下来我要输出工具调用"。这个 token 触发模型进入"工具调用模式"，输出结构化的 JSON 而不是自然语言。

第 3 步：API 返回的 response 里，不是普通的 `content` 文本，而是 `tool_calls` 字段

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,                    ← 没有文本内容
      "tool_calls": [{                    ← 而是 tool_calls
        "id": "call_abc123",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\": \"北京\"}"
        }
      }]
    }
  }]
}
```

第 4 步：你的代码检测到 `tool_calls`，拦截它，去调用真实的天气 API。

第 5 步：把 API 返回的结果以 `tool` role 塞回给模型：

```json
{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "北京，25°C，晴"
}
```

第 6 步：模型看到这个结果，继续推理，最终用自然语言回复："北京今天 25 度，天气晴朗。"

---

**关键区别：OpenAI 和 Anthropic 的实现差异**

| 维度 | OpenAI | Anthropic (Claude) |
| --- | --- | --- |
| API 参数名 | `tools` | `tools` |
| 工具定义中的参数名 | `parameters` | `input_schema` |
| 模型输出的字段 | `tool_calls[].function` | `content[].tool_use` |
| 输出中参数名 | `arguments` (JSON string) | `input` (JSON object) |
| 结果回传 | `role: tool` | `role: user` + `content[].tool_result` |

但底层原理完全一样——都是把工具定义传给模型，模型输出结构化的调用指令，系统拦截执行，结果喂回去。

---

**那 Agent 框架在这中间做了什么？**

Agent 框架（如 Claude Code、LangChain、AutoGen）做的事情就是**自动化这个循环**：

```
没有 Agent 框架：
  你写代码手动传 tools 参数
  → 你写代码检测 tool_calls
  → 你写代码调真实 API
  → 你写代码把结果塞回去
  → 你写循环

有 Agent 框架（如 Claude Code）：
  Claude Code 自动传 tools 参数（Read、Edit、Bash 等）
  → Claude Code 自动拦截 tool_use
  → Claude Code 自动执行真实的 Read/Edit/Bash
  → Claude Code 自动把结果塞回去
  → Claude Code 自动循环

你看不到这个循环，因为框架替你做了。
```

## 为什么模型能准确生成调用指令

准确是相对的，不是绝对的，但大体上能做到的原因有几个。

**原因一：模型是专门训练过的**

基础的大语言模型（预训练阶段）并不会调用工具。工具调用能力是通过**指令微调（Instruction Tuning）和函数调用微调（Function Calling Fine-tuning）**专门训练出来的。训练数据里包含了大量"用户问问题 → 调用工具 → 拿到结果 → 生成回答"的样本，模型反复看到这种模式后，学会了在什么情况下应该输出什么格式的工具调用。

**原因二：工具描述的质量直接决定了准确性**

模型能不能准确调用工具，**70% 取决于工具描述的清晰度**。模型不是"理解"了这个工具的逻辑，而是通过语义相似度匹配用户的问题和工具的 description。description 写得越准确，匹配就越准，参数名和类型越明确，模型生成的参数值就越正确。

**原因三：输出格式被强制约束**

模型在微调时被训练成输出特定格式的 JSON。推理时，运行时可以进一步用 JSON schema 验证模型的输出，如果格式不对就要求模型重试。OpenAI 和 Anthropic 的 API 层面都支持对工具调用做 schema 校验，参数类型、必填字段不对会直接报错。

**原因四：但模型确实会出错**

工具调用并不总是准确的，常见的问题有：

| 问题类型 | 表现 | 原因 |
| --- | --- | --- |
| 幻觉调用 | 用户没要求用工具，模型自己调了 | 模型过度关联 |
| 参数错误 | 参数名对但值错了 | 用户意图理解偏差 |
| 选错工具 | 有两个相似的 tool，选了错的 | description 不够区分 |
| 忽略工具 | 应该用工具但直接回答了 | 模型忘了或 training 不充分 |
| 格式错误 | 输出的 JSON 不合法 | 模型生成不稳定 |

所以 Agent 框架中通常都有重试机制和 fallback 逻辑。

**一句话总结**

Function calling / Tool calling / Tools 参数，本质是**同一件事的三个侧面**：

- **Tools 参数**：告诉模型有哪些工具可用
- **Tool call / Function call**：模型输出中表示要调用工具的那段 JSON
- **底层原理**：模型在训练时学会了在某些情况下输出结构化 JSON，外层系统拦截这个 JSON 去执行真实操作

整个过程就是：**告诉模型工具有哪些 → 模型决定用哪个 → 输出调用指令 → 系统执行 → 结果喂回去 → 模型继续推理**。准确率取决于训练数据的质量和工具描述写得好不好，不是模型"理解"了 API 文档。

# 8. Skill和Tool有什么区别？

这个问题问到 Skills 和 Tools 最核心的架构区别了。

**Skill 不是直接通过** `tools` 参数传给模型的，而是通过一个统一的 Skill 工具作为"入口"。

## Skill 的调用机制

**第 1 步：系统 prompt 里有一段文字描述所有可用的 skill**

```plaintext
系统 prompt 中包含：
"你还可以使用以下技能（Skills），当用户的问题匹配时自动加载：
  - summarize-changes: 总结未提交的代码变更
    - docker-debug: 排查 Docker 容器问题
    - deploy: 部署应用到生产环境
当用户说'看看我改了啥'，你应该加载 summarize-changes 技能。"
```

这是一段自然语言文字，不是 JSON schema。

**第 2 步：**`tools` 参数里只有一个统一的 `Skill` 工具

```json
{
  "tools": [
    // ... Read, Edit, Bash 等其他工具
    {
      "name": "Skill",
      "description": "执行一个技能。当用户的问题匹配某个技能的描述时，调用此工具加载并执行该技能。",
      "input_schema": {
        "type": "object",
        "properties": {
          "skill_name": {
            "type": "string",
            "description": "要执行的技能名称"
          }
        },
        "required": ["skill_name"]
      }
    }
  ]
}

```

**注意**：这里只有一个 `Skill` 工具，不是每个 skill 一个工具。所有的 skill 共用一个入口。

第 3 步：模型通过系统 prompt 里的描述决定用哪个 skill

用户说："帮我看看我改了什么"

模型在系统 prompt 中看到：

- `summarize-changes: 总结未提交的代码变更` ← 匹配！

于是模型调用 `Skill` 工具：

```json
{   "tool_use": {     "name": "Skill",     "input": {       "skill_name": "summarize-changes"     }   } } 

```

第 4 步：Claude Code 框架拦截这个调用，去磁盘上找到对应的 SKILL.md，把内容加载到上下文里

```plaintext
框架检测到 Skill("summarize-changes")
→ 去 .claude/skills/summarize-changes/SKILL.md 读取内容
→ 把内容注入到对话上下文中（作为 tool_result 返回）

```

第 5 步：Claude 看到 SKILL.md 的指令，像读普通文档一样理解并执行

```plaintext
SKILL.md 内容： "## 总结变更 1. 运行 git diff HEAD 获取变更 2. 用三到五个要点总结 3. 标记任何风险点" 

Claude 读到这些 → 用自己的工具去执行
→ 调用 Bash("git diff HEAD")
→ 分析输出
→ 用自然语言回复总结

```

**Skill 不通过 tools 参数传，而是通过系统 prompt 的文字描述 + 一个统一的 Skill 工具入口来实现。**

---

**Tool 和 Skill 的架构对比图**

```plaintext
Tool 的机制：
  tools 参数中：                  模型看到：
  [                               [
    {name: "Read", ...},           → 一个可调用的函数
    {name: "Edit", ...},           → 一个可调用的函数
    {name: "Bash", ...},           → 一个可调用的函数
  ]                               ]
                                  模型输出：
                                  tool_use(name="Read", input={...})

Skill 的机制：
  系统 prompt 中：                模型看到：
  "可用技能：                      → 一段文字描述
   - summarize-changes: ...        → 另一个技能名
   - docker-debug: ..."            → 另一个技能名
  
  tools 参数中：                  模型看到：
  [{name: "Skill",                 → 一个可调用的函数
    input_schema: {                 → 参数是 skill_name
      skill_name: string
    }
  }]
                                  模型输出：
                                  tool_use(name="Skill", input={skill_name: "summarize-changes"})
                                  → 系统加载 SKILL.md → 模型读到指令 → 用其他工具执行

```

---

**为什么这么设计？三个原因**

原因一：**按需加载，节省 token**

如果每个 skill 都像 tool 一样传完整 schema，10 个 skill 每个几千字 SKILL.md，那就是几万 token 的固定开销。Skill 只在需要时才加载内容，不占用每次请求的 token 预算。

```plaintext
10 个 tool 的 schema：约 3000 token（每次请求都传） 10 个 skill 的完整内容：约 30000~50000 token（如果全量传） → Skill 的按需加载机制省掉了这个开销 

```

原因二：**Skill 是 "指令" 不是 "函数"**

Tool 是结构化的：参数名、类型、必填 / 可选，模型严格按照 schema 生成 JSON。

Skill 是自然语言的：一段 Markdown 指令，Claude 读完后自己决定怎么做。它不需要结构化的 schema。

```plaintext
Tool 的典型定义：
{
  "name": "get_weather",
  "input_schema": {
    "city": {"type": "string", "description": "城市名"}
  }
}
→ 模型输出：{"city": "北京"}

Skill 的典型内容：
"## Docker 调试步骤
1. 运行 docker ps 查看运行中的容器
2. 运行 docker logs  查看日志
3. 检查端口是否被占用"
→ 模型读完后，用自己的工具一步步执行

```

原因三：**自动匹配不是模型做的**

当用户说 "我的 Docker 起不来了"，是 Claude Code 的框架（不是模型）去匹配这个输入和 skill 的 description，决定是否自动加载 skill。框架可以读到所有 skill 的 meta 信息（因为它们在磁盘上），然后决定在系统 prompt 里注入哪些 skill 描述，甚至直接调用 Skill 工具加载。

这个匹配逻辑不需要经过模型 —— 框架自己判断，然后再决定要不要告诉模型。

**那手动** `/skill-name` **呢？**

当你手动输入 `/summarize-changes` 时，流程更直接：

```plaintext
用户输入 "/summarize-changes" → Claude Code 框架识别出这是 skill 调用 → 直接去磁盘加载 SKILL.md 内容到上下文 → 框架在系统 prompt 中告诉模型"用户要求执行 summarize-changes 技能" → Claude 看到 skill 内容后开始执行 

```

这就不需要经过 "模型先调用 Skill 工具" 那一步了。框架直接帮你把 skill 内容塞进去。

**一句话总结**

Skill 不是像 Tool 那样通过 `tools` 参数传入 JSON schema 给模型的。而是在系统 prompt 里用文字列出可用的 skill，同时在 `tools` 参数里放一个**统一的** `Skill` **入口工具**。模型想用 skill 时，调用 `Skill("skill_name")`，框架去磁盘加载 SKILL.md 内容到上下文，Claude 读完后用 Read、Edit、Bash 等工具按指令执行。手动 `/skill-name` 则跳过 "模型调用 Skill 工具" 这一步，框架直接加载内容。

# 9. 大模型的本质是什么？

大模型从本质上来说，就是一个**下一个 Token 的预测器**。模型在推理时做的事情极其简单：根据已看到的所有文字，猜下一个最该出现的文字是什么。

## 模型在推理时做什么

模型接收输入文本后，内部计算"下一个最可能是什么词"，输出一个概率分布：

```
输入："北京的天气怎么样？"
模型内部：计算下一个 token 的概率分布
输出概率分布：
"北"    概率 0.001%
"天"    概率 0.0005%
"{"    概率 85%        ← 选了这个
...
```

选择概率最高的 token 输出，然后把这个 token 拼回输入，继续预测下一个。模型没有意识，不知道自己在"生成 JSON"或"调用工具"，它只是在做最擅长的事：**根据上下文猜下一个最该出现的 token**。

## 为什么模型能准确输出 JSON 格式

因为在训练阶段，模型看到了巨量的 JSON 文本。一个标准的 100B\~1T token 的模型，训练数据中包含了大量 API 文档、GitHub 代码（JSON 配置）、函数调用微调数据和 Stack Overflow 等技术论坛内容。模型可能看到了**几十亿个 JSON 片段**，已经"学会"了 JSON 的统计规律。

**JSON 的统计规律：**

```
"{" 之后 → 大概率是 '"'（字段名开始）
'"' 之后 → 大概率是字母或数字（字段名内容）
字段名后 → 大概率是 '":'
'":' 之后 → 大概率是值（字符串/数字/布尔/数组/对象）
值结束 → 大概率是 ',' 或 '}'
```

这些规律对模型来说，和"我"之后大概率是"是"、"吃"、"想"这些语言规律没有任何区别。模型不知道自己在遵守 JSON 语法，它只是发现历史上看到的所有 { 后面跟着的字符都有固定的统计模式，照着这个模式走。

## 函数调用微调强化了这种模式

在基础模型（预训练）之上，厂商会做指令微调和函数调用微调，构造大量这样的训练样本：

```
用户：今天北京多少度？

系统消息中包含可用工具：
- get_weather: 查询天气，参数 city(string), unit(string)

助手期望的输出：
[工具调用标记]get_weather{"city":"北京","unit":"celsius"}
```

模型通过数万个这样的样本，记住了"当用户问天气时，我的输出应该长这样"。这是一个纯粹的**模式匹配过程**：

```
看到用户问"北京多少度"
→ 激活了"get_weather"这个模式
→ 激活了"输出 JSON 参数"这个模式
→ 一个字一个字地生成出正确的 JSON
```

中间没有"理解 JSON 语法"这个步骤。

## 但模型确实会出错

即使训练充分，模型仍然会在工具调用上犯错。原因在于 token 级别的概率并不是 100%：

```
理论上：{ 之后 " 的概率是 99.9%
实际上：{ 之后 " 的概率可能是 99.5%
```

那 0.5% 的概率可能输出换行符、空格，或任何在训练数据中出现在 { 后面的字符。当模型概率分布变平时，这 0.5% 的概率就会冒出来。例如：

```json
{
"city": "北京",
"unit": "celsius"
},
```

模型在训练数据中看到过 `},` 这个模式（对象后面还有更多字段），所以有时候会不自觉地多输出一个逗号。

## 为什么 API 层面很少出错

实际使用 API 时很少看到 JSON 格式错误，原因如下：

- **采样策略**：API 的 temperature 设得很低（0 或接近 0），每次选概率最高的 token，大大降低出错概率
- **重复采样**：如果输出的 JSON 格式不对，API 底层会自动重新生成
- **Schema 校验**：API 会校验工具调用的参数格式，不符合要求就报错
- **推理增强**：像 o1、R1 这类推理模型有更强的思考能力，在输出前内部已做过多轮验证

**一句话总结**

模型能准确输出 JSON 格式的 tool call，不是因为它"理解"了 JSON 语法，而是因为它在训练数据中看到过几十亿次这种模式，已经把 { → " → : → , → } 的统计规律学得极其牢固。这跟它学会"我"后面通常跟动词是同一个原理——**纯粹的统计模式匹配，没有理解**。
