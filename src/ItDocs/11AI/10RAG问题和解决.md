# 1. RAG 系统有哪些典型的痛点和失败点？为什么 RAG 会答错？

一个 RAG 系统的完整链路是：**文档加载 → 切分 → 嵌入 → 存储 → 检索 → 重排 → 组装上下文 → LLM 生成 → 输出**。任何一个环节出问题，最终答案都可能出错。业界把 RAG 常见问题整理为 **12 个痛点**，其中 **前 7 个**来自 Barnett 等人的论文《设计检索增强生成系统的七个失败点》（基于 AI 导师、认知审查员、BioASQ 三个真实案例，包含上万份文档、1000 个问题的实证），**后 5 个**是工程实践补充的痛点。这 12 个痛点可以按链路分成三个阶段：

- **数据接入与检索前**：知识库压根没有答案（痛点 1 内容缺失）、海量数据入库难（痛点 8）、复杂文档解析难（痛点 10）
- **检索中**：有答案但没被捞出来（痛点 2 漏掉 Top-K、痛点 3 检索到但没进上下文、痛点 9 结构化数据检索）
- **生成与系统**：检索对了但 LLM 没答好（痛点 4 未提取、痛点 5 格式错误、痛点 6 详细程度不当、痛点 7 不完整），以及基础设施与安全（痛点 11 后备模型、痛点 12 LLM 安全）

用一句话概括核心：**RAG 效果 = 检索质量 × 生成质量。检索错了，LLM 再强也白搭；检索对了，LLM 也可能答不好。** 排错时第一步永远是先区分「问题出在检索层还是生成层」。

## 12 个痛点速览

| 编号 | 痛点 | 一句话描述 | 所在环节 | 来源 |
| --- | --- | --- | --- | --- |
| 1 | 内容缺失 Missing Content | 知识库没有答案，硬编一个貌似合理的回答 | 检索前 | 论文 FP1 |
| 2 | 漏掉排名靠前的文档 Missed Top-K | 答案在库里，但排名不够靠前没被展示 | 检索 | 论文 FP2 |
| 3 | 检索到但没进上下文 Not in Context | 文档被检索到，但没进入 LLM 的上下文 | 上下文组装 | 论文 FP3 |
| 4 | 答案没被提取 Not Extracted | 上下文里有答案，但 LLM 没抽出来 | 生成 | 论文 FP4 |
| 5 | 格式错误 Wrong Format | 要求输出表格/列表，LLM 没按格式来 | 生成 | 论文 FP5 |
| 6 | 详细程度不当 Incorrect Specificity | 答案过于笼统或过于具体 | 生成 | 论文 FP6 |
| 7 | 回答不完整 Incomplete | 答案没错，但漏了该给的信息 | 生成 | 论文 FP7 |
| 8 | 数据摄取可扩展性 Data Ingestion Scalability | 海量数据入库慢、系统过载 | 数据接入 | 工程痛点 |
| 9 | 结构化数据 QA | 表格查询翻译难、文本到 SQL 不灵活 | 检索/生成 | 工程痛点 |
| 10 | 复杂 PDF 数据提取 | 内嵌表格等复杂结构检索不到 | 数据接入/检索 | 工程痛点 |
| 11 | 后备模型 Fallback Model | 主模型限流/故障，系统不可用 | 基础设施 | 工程痛点 |
| 12 | LLM 安全性 | 提示注入、不安全输出、信息泄露 | 全链路 | 工程痛点 |

**面试要点**：先说出「RAG 有 12 个常见痛点，前 7 个来自论文、后 5 个来自工程实践」，再按「数据接入/检索/生成/系统」归类，体现对链路的整体把握。

# 2. 痛点 1：内容缺失（Missing Content）如何解决？

**内容缺失**：用户问的问题，知识库里根本没有对应的内容。理想情况下 RAG 应该回答「对不起，我不知道」，但现实中它往往会编造一个看起来合理、实际错误的答案，误导用户。

## 为什么会发生

- **知识库覆盖不全**：私有文档没入库，或入库范围太小
- **问题超出知识范围**：用户问的根本是知识库外的问题
- **LLM 的「讨好」倾向**：它没有「承认不知道」的机制，宁可硬编也不说不知道

## 解决方案

1. **数据清理（治本）**：垃圾进垃圾出。源数据质量差（相互矛盾、过时、错误），RAG 管道再好也救不回来。干净数据是所有 12 个痛点的先决条件
2. **更好的提示（治标）**：在 prompt 里明确要求「**如果你不确定答案，请直接告诉我你不知道**」，鼓励模型承认局限、透明表达不确定性。这无法保证 100% 准确，但是清理数据后最有效的兜底手段之一
3. **检索答案校验（兜底）**：给检索结果与问题的相关性打分，低于阈值就拒绝回答，返回「知识库没有相关内容」，而不是硬答
4. **持续扩充知识库**：把高频未覆盖的问题对应的内容补进知识库

**面试要点**：先讲「内容缺失的本质是库里没有答案」，再讲「治本靠数据清理、治标靠提示约束、兜底靠相关性校验」，最后强调「宁可说不知道，也不能乱说」。

# 3. 痛点 2：漏掉排名靠前的文档（Missed Top-K）如何解决？

**漏掉排名靠前的文档**：答案确实在知识库里，但检索时该文档的相似度排名不够靠前，被 Top-K 截断漏掉了，LLM 自然答不出来。注意它和痛点 1 的区别——**痛点 1 是「库里没有」，痛点 2 是「库里有但没被捞上来」**。

## 为什么会发生

1. **切分不合理**：chunk 太大或太小，导致答案被拆散或语义被稀释
2. **嵌入模型不够强**：语义相似度算得不准，相关文档得分低
3. **Top-K 设置太小**：为了性能只取前几个，相关文档排在 K 名之外
4. **只用向量检索**：没有结合关键词检索等多路召回，单一检索方式有盲区

## 解决方案

1. **超参数调优**：核心是两个参数——
   - `chunk_size`（切分大小）：影响语义完整性和检索精度
   - `similarity_top_k`（召回数量）：影响召回率与噪音的平衡
   - 做法：准备一小批标注好的问题-答案对，用语义相似度等指标遍历参数组合，选分数最高的一组（如 LlamaIndex 的 ParamTuner）
2. **Rerank 重排序（业界最有效）**：
   - 先多召回候选（如 Top-10），再用重排模型（如 Cohere Rerank）精排，只把 Top-2 交给 LLM
   - 原理：向量检索是「粗排」，只算语义相似度；重排模型能把问题与每个候选拼接起来做更精细的相关性判断，属于「精排」
3. **多路召回 + 混合检索**：向量检索 + 关键词检索（BM25）并行召回后合并去重，弥补单一检索的盲区
4. **替换或微调嵌入模型**：换更强的嵌入模型，或在领域数据上微调开源嵌入模型，从源头提升语义相似度计算的准确性

**面试要点**：强调「检索层是 RAG 调优的主战场」，先讲痛点 2 本质是「召回不全」，再讲核心解法是业界标配的「**多召回 + 重排精排**」。

# 4. 痛点 3：检索到但没进上下文（Not in Context）如何解决？

**整合策略的局限**：文档明明被数据库检索出来了，但最终没有进入生成答案的上下文。多发生在数据库返回了大量文档、需要经过「整合（Consolidation）」流程时——受上下文窗口和成本限制，只有部分内容能被塞进 prompt。

## 为什么会发生

1. **上下文窗口限制**：LLM 一次能处理的内容有限（如 8K/32K token），检索到的内容放不下
2. **整合策略过于简单**：只截取、丢弃或压缩部分内容，恰好把含答案的内容丢了
3. **检索返回大量文档**：Top-K 设置偏大，但整合环节只来得及处理一部分

## 解决方案

1. **调整检索策略**：使用更精准的检索策略，减少无效内容——如基础检索、高级检索（句子窗口、递归检索等）、知识图谱检索、组合/分层检索
2. **上下文压缩（Prompt Compression）**：检索后用压缩模型（如 LongLLMLingua）把上下文压缩成只保留关键信息的短文本再交给 LLM，一次能塞进更多有效信息
3. **重排序 + 精选**：重排后只保留最相关的少量 chunk（如 Top-3），保证精华能进上下文
4. **微调嵌入模型**：让检索结果更准，从源头减少「检索到但用不上」的内容
5. **增大上下文窗口**：换支持更长上下文的模型，配合更大的 Top-K（同时要注意痛点 4 的「迷失在中间」问题，见下题）

**面试要点**：痛点 3 的核心矛盾是「**检索到的内容 > 模型能读的内容**」，解法主线就是「压缩 or 精选」两条路。

# 5. 痛点 4：答案没被提取出来（Not Extracted）如何解决？

**未提取**：上下文里确实含有答案，但 LLM 没有正确地把答案抽取出来。多发生在**上下文信息太杂乱、或存在相互矛盾的信息**时——关键细节被淹没或互相打架，模型无从下手。

## 为什么会发生

1. **上下文噪音大**：塞进了大量无关内容，关键信息被淹没
2. **信息相互矛盾**：知识库里同一件事有不同说法，LLM 无所适从
3. **prompt 指令不清**：没明确要求「从给定材料中提取，不要自行发挥」

## 解决方案

1. **数据清理（治本）**：清除矛盾、过时、无关的数据，从源头减少噪音
2. **Prompt 压缩（LongLLMLingua）**：检索后把上下文压缩，只保留与问题最相关的部分，减少噪音、聚焦答案
3. **长上下文重排序（LongContextReorder）**：研究发现模型对上下文**开头和结尾**的内容利用最好，中间的内容容易「迷失在中间（Lost in the Middle）」；重排把最相关的 chunk 放到开头或结尾，提高它被正确读取的概率——在需要大 Top-K 的场景尤其有用
4. **更好的提示指令**：明确「只从给定材料中提取答案」并要求给出依据来源

**面试要点**：痛点 4 的关键词是「噪音」，解法主线是「清理数据 + 压缩上下文 + 把关键内容放到开头结尾」，能讲出「迷失在中间」现象是加分项。

# 6. 痛点 5：格式错误（Wrong Format）如何解决？

**格式错误**：用户要求以特定格式（表格、列表、JSON 等）返回信息，但 LLM 没有按要求输出。

## 解决方案

1. **更好的提示**：
   - 澄清指令，把格式要求写清楚
   - 简化请求，用关键词表达
   - **举例说明**：在 prompt 中给一个期望输出的示例（Few-shot）
   - 迭代追问：生成不对就追问修正
2. **输出解析（Output Parsing）**：给 LLM 附加「输出解析器」——先定义输出结构（如 ResponseSchema），让 LLM 按结构生成，再把输出解析成程序可用的对象（如 LangChain 的 StructuredOutputParser）
3. **Pydantic 程序（Pydantic Program）**：定义 Pydantic 模型作为输出 Schema，LLM 的输出直接转成结构化对象，保证字段完整、类型正确。有文本补全、函数调用、预打包三种形式
4. **JSON 模式（JSON Mode）**：部分接口支持强制输出合法 JSON（如 OpenAI 的 `response_format={"type":"json_object"}`），模型只会生成可解析的 JSON 字符串。注意：它只保证格式合法，不保证内容符合 Schema，需要再做校验

**面试要点**：从「提示约束 → 输出解析 → 结构化 Schema → 强制 JSON」逐层递进，强调「格式问题要用工程手段兜底，不能只靠提示」。

# 7. 痛点 6：详细程度不当（Incorrect Specificity）如何解决？

**不恰当的详细程度**：回答要么过于笼统、要么过于具体，不符合用户预期。例如教师问学生问题，期待的是「具体的教育内容」而不是「直接给答案」；用户问题本身太宽泛、不知道该怎么问时，也容易出现回答粒度不对。

## 为什么会发生

1. **问题太宽泛**：query 本身模糊，检索和生成都失去方向
2. **内容粒度不对**：chunk 切得太大或太小，检索到的参考内容粒度直接决定了答案粒度
3. **场景预期不匹配**：系统设计者没在 prompt 里约束回答的深度和角度

## 解决方案

- **高级检索策略（调整内容粒度）**：
  - **从小到大检索（Small-to-Big）**：先用小块精确匹配定位，再返回包含该小块的更大上下文，兼顾「精确」和「完整」
  - **句子窗口检索（Sentence Window）**：按句子级别检索，命中后扩展成句子所在窗口的上下文
  - **递归检索（Recursive Retrieval）**：把文档分层（摘要层 → 章节 → 细节），先命中摘要，再沿层级递归下钻到细节
- **在 prompt 中约束详细程度**：明确「用一句话/一段话/列表回答」「面向专家/面向新手」等粒度要求
- **Query 澄清**：对模糊问题先反问澄清，或让 LLM 自动补全、生成子问题后再检索

**面试要点**：痛点 6 的本质是「内容粒度」问题，解法是「控制检索到的内容粒度 + 在 prompt 里规定回答粒度」两条线。

# 8. 痛点 7：回答不完整（Incomplete）如何解决？

**不完整**：回答本身没错，但漏掉了部分该有的信息，即使这些信息就在上下文里可以提取。典型例子：问「文档 A、B、C 分别讲了哪些关键点？」——如果只给出一个笼统回答，就是典型的痛点 7，这类问题把子问题拆开一个个问会更有效。

## 为什么会发生

1. **一个问题包含多个子问题**，LLM 只答了其中一个
2. **跨多文档的问题**，检索时只召回了部分文档
3. **对比类、罗列类问题**在朴素 RAG 下表现最差

## 解决方案：查询转换（Query Transformation）

在实际查询向量库之前，加一层「查询理解」，把用户问题转成更适合检索和回答的形式，主要有四种：

1. **路由（Routing）**：保留原问题，先判断它属于哪个知识子集/工具，再路由到合适的工具
2. **查询重写（Query Rewriting）**：把原问题改写成多种表述，用多个改写后的查询检索同一组工具，提高召回
3. **子问题（Sub-questions）**：把大问题拆成多个小问题，每个小问题检索对应文档，最后汇总
4. **ReAct Agent 工具选择**：让 Agent 根据原问题决定用什么工具、以及在这个工具上执行什么查询

另一种高频考察的查询重写技术是 **HyDE（Hypothetical Document Embeddings，假设文档嵌入）**：

- **思路**：先用 LLM 根据问题生成一个「假设性的答案/文档」，再用这个假设文档的向量去检索，而不是用原始问题向量
- **原理**：假设文档和真实文档都是「陈述句」形态，语义上比「问题句」更接近，检索命中率更高
- **注意**：效果依赖 LLM 生成假设文档的质量，有失败的可能，需要评估后再决定是否使用

**面试要点**：痛点 7 的核心解法是「查询转换」，要能说出路由、重写、子问题、ReAct 四种方式，再补上 HyDE 这个高频考点。

# 9. 痛点 8：数据摄取可扩展性（Data Ingestion Scalability）如何解决？

**数据摄取可扩展性**：系统难以高效管理和处理海量数据时出现的问题——海量文档入库时**处理慢、耗时过长、系统过载**，甚至导致摄取失败、数据质量问题和可用性受限。这是 RAG 从「小数据量 Demo」走向「生产系统」时第一个会撞上的痛点。

## 为什么会发生

1. **串行处理**：文档加载、切分、抽取、嵌入等步骤一条流水线逐个处理，文档一多就慢
2. **单机瓶颈**：嵌入模型调用、向量入库都是耗时操作，没有并行和水平扩展
3. **全量重建**：每次新增文档都重新索引全部数据，浪费大量算力

## 解决方案

1. **并行化摄取管道（核心）**：把切分、抽取、嵌入等变换步骤**并行执行**——多文档同时处理（如 LlamaIndex 的 IngestionPipeline 设置 `num_workers`），文档处理速度可提升数倍到十余倍
2. **增量摄取**：只处理新增/变更的文档，避免全量重建
3. **数据质量治理**：摄取前清洗数据，避免垃圾进垃圾出，也避免脏数据拖慢管道

**面试要点**：抓住「并行化摄取 + 增量摄取」两个词，说明这是把 RAG 从小规模 Demo 推向生产的必经环节。

# 10. 痛点 9：结构化数据 QA 怎么做？如何让 LLM 理解表格？

**结构化数据 QA**：表格数据（Excel、SQL 结果等）对 RAG 是难点——准确翻译用户查询去检索相关结构化数据很困难，尤其是复杂或不明确的查询；**文本到 SQL 不灵活**，LLM 对「一行行单元格」的理解远不如对文本，直接把整张表塞进 prompt 又容易超限、定位困难。业界主流是「文本推理 + 符号推理」两条路，进阶有链式转换和自洽聚合两种方案。

## 两条推理路径

1. **文本推理**：把表格转换成文本描述，直接提示 LLM 推理——适合概括性、语义性问题
2. **符号推理（程序综合，Program Synthesis）**：让 LLM 写代码（Python/SQL）对表格做精确计算，再根据执行结果回答——适合精确计算、聚合统计问题

## 两种高级解法

1. **Chain-of-Table（表链）**：把「思维链」和表格转换结合——LLM 通过一组受限操作（切行、切列、聚合等）**逐步转换表格**，每一步都把变换后的表格呈现给 LLM，直到定位到合适的子集。优点：能处理「包含多条信息的复杂单元格」问题，避免一次给整张表带来的噪音
2. **MixSelfConsistency（混合自洽）**：同时采样多条「文本推理路径」和「符号推理路径」，通过自洽机制（多数投票）聚合两类结果，取「文本和符号推理一致同意」的答案，达到当时的最优效果

**面试要点**：记住「表格 QA 有文本推理和符号推理两条路」，进阶是「Chain-of-Table 链式转换表格」和「MixSelfConsistency 混合自洽投票」两个方案名。

# 11. 痛点 10：复杂 PDF（内嵌表格、多栏排版）怎么检索？

**复杂 PDF 数据提取**：复杂 PDF 的难点在于——**检索的是「整页文本」，而答案藏在「内嵌的表格」里**，纯文本切分拿不到表格结构，也就检索不到表格里的数据。

## 主流方案：先结构化解析，再构建节点图检索

1. **解析出表格**：用工具（如 unstructured.io）从文档中解析出内嵌表格；如果源是 PDF，先转成 HTML（如 pdf2htmlEX，保留文本和格式）再解析
2. **构建节点图**：把解析出的表格作为独立节点，与正文建立关联关系（节点图结构）
3. **递归检索**：用递归检索——先命中相关正文节点，再沿节点关系找到对应的表格节点——根据用户问题索引并检索表格
4. **生成答案**：把命中的表格内容交给 LLM 生成回答

（工具落地：LlamaIndex 的 `EmbeddedTablesUnstructuredRetrieverPack` 封装了上述「解析 → 节点图 → 递归检索」流程。）

**面试要点**：抓住「复杂 PDF 要先做结构化解析（把表从页面里抠出来），再做节点图/递归检索」，而不是直接把整页文本向量化。

# 12. 痛点 11：主模型限流或故障时怎么办？（后备模型设计）

**后备模型**：RAG 系统重度依赖 LLM API，主模型一旦**限流（Rate Limit）或故障**，整个系统就不可用。需要在架构上设计「后备模型（Fallback）」机制。

## 两种主流方案

1. **模型路由（Neutrino Router）**：
   - 通过一个「路由器」聚合多家 LLM，用预测器模型智能地把每次查询路由到最适合的模型，在保证质量的同时优化成本和延迟
   - 可自定义路由器选择偏好的模型，或使用包含所有支持模型的默认路由器
2. **统一 API（OpenRouter）**：
   - 一个统一 API 访问任意 LLM，自动查找多家提供商中的最低价格，**主模型故障时自动切换后备模型**
   - 好处：模型/提供商之间切换无需改代码；多提供商冗余，单点故障不影响
   - 支持用户通过 OAuth 为自己的模型付费

## 设计要点

- **分级降级**：主模型 → 备选模型 → 兜底答案（如「暂时无法回答」）
- **限流缓解**：配合语义缓存——高频问题命中缓存直接返回，不调主模型，既降成本又缓解限流
- **监控切换**：主模型错误率/延迟超标时自动切到后备模型，并告警

**面试要点**：核心答案是「多模型冗余 + 统一 API + 自动路由/降级」，能补一句「用语义缓存缓解限流」更佳。

# 13. 痛点 12：LLM 安全性如何保障？

**LLM 安全性**：RAG 系统暴露给用户后，主要面临三类安全问题：

- **提示注入（Prompt Injection）**：用户输入恶意指令，诱导模型越权操作或泄露数据——这是最大的风险点
- **不安全的输出**：模型生成了违规、危险内容
- **敏感信息泄露**：无权限用户通过提问拿到了私密文档内容

## 核心方案：LLM 输入输出的双向审核（Llama Guard）

**Llama Guard**（Meta 基于 Llama 2 的安全分类模型）：

1. **输入审核（Prompt Classification）**：用户提问先过一遍 Llama Guard，判断是否安全
2. **输出审核（Response Classification）**：LLM 生成的回答再过一遍，判断是否安全
3. **策略化分类**：Llama Guard 内置一套安全策略（暴力、色情、仇恨言论等），会指出内容违反了哪个子类别；也支持自定义安全策略（custom_taxonomy）适配业务
4. **不安全处理**：输入不安全就拒绝；输出不安全就返回「无法回答」，而不是把危险内容放给用户

## 其他安全措施

- **权限与隔离**：检索层做访问控制，用户只能检索自己有权限的文档（元数据级过滤），从源头防止越权泄露
- **数据脱敏**：入库前对敏感信息脱敏
- **微调后重新安全测试**：研究发现对 LLM 微调可能削弱其安全训练，所有微调过的模型都必须重新做安全测试

**面试要点**：答出「输入 + 输出双向审核」的结构 + Llama Guard 这个工具名 + 「提示注入是最大风险点」，再补权限隔离，就够深入了。

# 14. 构建 RAG 系统有哪些工程经验教训？

基于三个真实案例研究（AI 导师、认知审查员、BioASQ），论文总结了以下关键经验：

1. **更大上下文通常更好**：8K 上下文比 4K 得到更准确的反馈。注意这与早期 GPT-3.5 时代「检索内容放得越多效果越差」的结论不同——在新模型上，把相关上下文给足反而更好，但要配合去噪（见痛点 4），不能盲目堆内容
2. **语义缓存能显著降本增效**：RAG 多用户场景面临限流和高成本，把高频问题及对应答案预先填充到语义缓存，命中就直接返回，减少 LLM 调用
3. **元数据注入提升检索**：检索时给 chunk 加上文件名、段落编号等元数据，方便定位和过滤，对多轮聊天场景尤其有效
4. **开源嵌入模型对短文本足够好**：处理短文本时，开源句子嵌入模型（如 Sentence-BERT 系）效果与闭源模型相当，不必迷信闭源
5. **RAG 系统必须持续监控和调优**：真实运行会遇到各种未预料的输入，需要持续监控、根据线上反馈迭代调整
6. **精确配置是效果分水岭**：块大小、嵌入策略、分块策略、检索策略、整合策略、上下文大小、提示这七个环节都需要精确调整
7. **组件拼装不一定最优**：用开源组件「组合定制」的 RAG 未必最好，端到端训练（把检索与生成作为整体训练）能更好地适应不同领域需求
8. **系统性能只能在实际运行中验证**：离线评估（如 G-Evals）看起来有希望，但前提是有标注好的问题-答案对，真实场景很难提前备齐，很多性能特征必须上线后才知道

**面试要点**：这题考「工程体感」，能背出「更大上下文、语义缓存、元数据注入、开源嵌入够用、持续监控、端到端训练可能更优」这些点，说明不是只会背书。

# 15. 如何系统性排查和优化一个 RAG 系统？

把 12 个痛点对应到链路上，形成排查清单——从前往后逐段排查，定位问题出在哪一段。

## 按链路逐段排查

1. **数据质量与接入**：源数据是否干净、无矛盾？海量数据摄取是否并行化？（对应痛点 1/4 的治本、痛点 8）
2. **切分与嵌入**：chunk 大小是否合适？嵌入模型是否匹配领域？（对应痛点 2/6）
3. **检索召回**：Top-K 是否够？有没有多路召回？有没有重排？（对应痛点 2/3/9）
4. **上下文组装**：关键 chunk 是否真的进了 prompt？是否被压缩或截断？（对应痛点 3/4）
5. **生成与输出**：prompt 是否约束了「不知道就说不知道」、格式、详细程度？（对应痛点 1/5/6/7）
6. **系统与安全**：有没有后备模型？输入输出是否做了安全审核？（对应痛点 11/12）

## 排查方法论

- **逐段定位（最关键）**：把检索结果打印出来人工看——「答案在不在检索结果里」：
  - 答案在检索结果里但答错 → 生成层问题（痛点 4-7）
  - 答案不在检索结果里 → 检索层问题（痛点 2-3）
  - 库里根本没有答案 → 数据问题（痛点 1）
- **先治本再治标**：先清理数据，再调检索，最后才考虑换模型、加提示
- **小规模评估集**：准备一小批标注好的问题-答案对，用语义相似度等指标量化调优前后的效果，避免拍脑袋
- **线上监控**：上线后持续监控错误模式，按痛点归类，针对性修复

**面试要点**：这题展示方法论。最体现工程能力的一句话是「**先看检索结果里有没有答案，来区分检索层问题和生成层问题**」，务必讲出这个定位思路。
