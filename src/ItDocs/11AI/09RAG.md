# 1. 什么是RAG

RAG 全称 **Retrieval-Augmented Generation（检索增强生成）**，核心思路是：**在生成答案之前，先从外部知识库检索相关内容，把检索结果和用户问题一起交给 LLM，让它基于这些上下文回答**。它解决的核心问题是 LLM 知识冻结——模型训练完之后知识就固定了，无法覆盖私有数据和最新信息。本质上相当于给 LLM 开了一场「开卷考试」，不再靠死记硬背。

## 为什么 LLM 需要 RAG

LLM 训练完之后，知识以参数形式固化在模型里，这带来两个先天缺陷：

- **知识时效性差**：训练数据截止日期之后的信息它一无所知
- **私有知识缺失**：公司内部文档、行业专有数据没有进过训练集，模型对这些内容完全空白

理论上可以用微调更新知识，但成本高、耗时长，而且知识一旦写进参数，更新就要重新训练。RAG 走了一条完全不同的路：**不把知识塞进模型参数，而是在用户提问时实时去外部知识库检索，把相关内容放进 prompt 给 LLM 读**。LLM 有很强的阅读理解能力，只要把内容放进上下文，它就能基于这段内容回答问题。

## 完整工作流程

一个完整的 RAG 系统分**离线**和**在线**两个阶段。

### 离线阶段：建库（只做一次）

1. **文档加载**：把 PDF、Word、Markdown、网页、数据库记录等原始数据读取进来，常用 LlamaIndex / LangChain 的 DocumentLoader，支持几十种数据源格式
2. **文档切割（Chunking）**：把文档切成小片段。原因有两个：
   - 向量模型有输入长度限制，整篇文档塞不进去
   - 整篇文档压缩成一个向量，细节信息会被「平均掉」，检索不精准
   - 实践中通常每个 chunk 500～1000 token，并做一定重叠（如前后各 100 token），避免切断完整语义
3. **向量化（Embedding）**：把每个 chunk 转成高维数字向量（如 1536 维浮点数列表）。语义相近的文本向量距离近，语义不相关的距离远，这是语义检索的基础
4. **入库**：把每个 chunk 的向量 + 原始文本一起存进向量数据库（Chroma、Milvus、Qdrant、Weaviate 等）

### 在线阶段：检索 + 生成（每次提问都执行）

1. **Query 处理**：用户问题往往口语化、带指代，直接检索效果差，需要 LLM 改写（Query Rewrite）或从对话历史补充上下文
2. **向量检索（粗排）**：把问题转成向量，在向量库做相似度搜索，找出距离最近的 Top-K 个 chunk，百万量级也能几十毫秒返回
3. **Rerank（精排）**：用 Cross-Encoder 模型把问题与每个候选 chunk 拼接，深度理解相关性重新排序，过滤掉不相关结果，通常对 Top-20 精排后保留 Top-3～Top-5
4. **生成**：把「用户问题 + 精排后的 chunk」拼成 prompt 交给 LLM。Prompt 中明确要求「只根据资料回答，资料里没有就说不知道」，抑制幻觉

## RAG 与微调的本质区别

- **微调**：把新知识写进模型参数，更新知识需要重新训练
- **RAG**：把知识放在外部实时检索，不动模型本身，更新知识只需更新知识库

## 核心价值

1. **知识可热更新**：往知识库加文档即可，不需要重新训练，成本极低
2. **答案可溯源**：每条回答都能追溯到来源 chunk，可解释性强，答错了也知道是哪条知识出了问题

这是企业落地 AI 问答系统首选 RAG 的根本原因。

# 2. RAG用来解决什么问题

RAG 主要解决三个问题：**知识时效性、私有知识覆盖、幻觉**。这三个问题的根源是同一件事——**知识被固化在模型参数里**。RAG 的解法是把知识存到外部，用时实时检索注入，彻底绕开参数里的知识限制。

## 三个问题的根源：知识冻结

LLM 在预训练阶段把海量文本的知识编码进参数权重，训练完成后参数不再更新。这个「知识冻结」特性直接导致三个连锁问题：

### 问题一：知识过期（时效性）

- 训练数据有截止日期，之后的信息模型不知道
- 模型不会说「我不知道」，而是用历史规律「推测」出一个听起来合理的答案
- 例：金融场景分析某公司最近一季度财报，模型基于过期数据，参考价值大打折扣

### 问题二：私有知识空白

- 公开互联网知识模型或多或少见过，但公司内部文档（产品手册、客服知识库、合同模板）根本不在训练集里
- 时效性说的是「旧了」，私有知识说的是「压根没有」
- 例：客服机器人回答「我们产品的退款政策」，这条信息没进过训练集，回答了就是在编

### 问题三：幻觉（知识缺失的副产品）

- LLM 的核心机制是「预测下一个词」，没有「不确定就停下来」的开关，也没有「知道自己不知道」的能力
- 当参数里知识不够时，它只能硬着头皮往下生成，把相关、不相关的知识拼凑成一个「听起来合理」的答案
- **关键认知**：幻觉不是独立的 bug，而是知识缺失的副产品。知识过期导致幻觉，知识缺失也导致幻觉，根源都是参数里没有对应知识
- 幻觉是整个 LLM 应用最核心的可信度问题，在医疗、法律、金融等容错率低的场景可能造成实际损失

## RAG 的解法

既然知识冻在参数里是根源，那就不把知识放在参数里：

- 知识整理成文档，预处理后存入向量数据库
- 用户提问时，先检索最相关的内容片段，把片段和问题一起塞进 prompt
- LLM 基于「参考资料」回答，而不是凭记忆发挥

这一招对三个问题都有效：

1. **知识过期**：新内容随时入库，不需要重新训练，知识库更新即生效
2. **私有知识缺失**：公司文档入库后，LLM 就能「看到」并回答私有问题
3. **幻觉**：LLM 有真实参考依据，是在「复述」检索内容而不是凭记忆发挥，幻觉率显著降低；且每条答案可溯源，用户能核实原文

**本质**：RAG 是给 LLM 开卷考试，知识存在外面、用时翻出来看。这个设计让知识管理和模型能力解耦——更新知识不碰模型，扩充领域知识只需扩充知识库。

# 3. RAG 解决了什么问题？微调和 RAG 各自的优劣势是什么？

微调和 RAG **解决的不是同一层面的问题，不是谁替代谁的关系**：

- **微调**是把新知识直接烧进模型参数，适合改变行为风格、培养深度专业能力
- **RAG** 是在推理时实时检索注入知识，适合知识频繁更新、需要溯源的场景

知识库类问答系统首选 RAG（成本低、可随时更新）；要让模型学会特定输出格式或行业语气，微调更合适。**两者也可以组合使用：先微调再套 RAG**。

## 本质：都是在补模型没学到的知识

LLM 的知识训练时固化在参数里，训练完不再成长，不知道新事、不知道私有数据。微调和 RAG 本质上都在解决同一个问题——**怎么把模型训练时没学到的知识补上**，只是思路完全不同：一个直接改参数，一个不改参数、推理时现查。

## 微调（Fine-tuning）：把知识直接烧进模型

**优势：**

- 效果彻底，模型从内部改变，专业词汇、输出格式、回答风格都能深度定制
- 推理时不需要额外检索步骤，响应延迟低

**劣势：**

1. **成本高**：需要标注数据、GPU、跑训练，时间和金钱成本不低
2. **知识更新难**：业务数据每周在变，不可能每周重调一次；每次微调几小时到几天
3. **不透明**：回答来自参数，不知道模型从哪条知识推出，出错难定位；模型只是记住了训练数据里的模式，记了什么、记错了什么无从得知

## RAG：不改参数，推理时现查

**优势：**

- 知识库更新只是加文档，不需要重新训练，加完即生效
- 回答可附来源 chunk，出错能定位是哪个知识的问题
- 成本低，小团队用 OpenAI Embedding + Chroma 就能跑起来

**劣势：**

1. **检索延迟**：多一次检索步骤，响应延迟增加几百毫秒到一秒
2. **检索质量卡住上限**：相关 chunk 没被检索回来，LLM 再强也答不出来。**生成层只能基于检索到的内容作答，检索质量决定效果上限的主要部分**——所以 RAG 调优的主战场通常是检索层，而不是一上来就换更贵的 LLM（当然生成层的 Prompt 约束、指令遵循对最终效果也有独立贡献）
3. **复杂推理能力提升有限**：RAG 只提供参考资料，对领域深度推理能力有限制，还是需要微调

## 组合使用：微调解决「怎么说」，RAG 解决「说什么」

实际工程最常见做法：**先对基础模型微调**，学会输出格式、语气风格、行业术语；**再用 RAG 提供具体知识内容**。微调解决「怎么说」，RAG 解决「说什么」，各司其职。

## 选型对比表

| 维度 | 微调（Fine-tuning） | RAG |
| --- | --- | --- |
| 知识更新 | 需要重新训练，成本高 | 更新知识库即可，实时生效 |
| 推理延迟 | 低，无额外检索步骤 | 较高，多一次检索耗时 |
| 实现成本 | 高，需要 GPU 和标注数据 | 低，向量库 + Embedding 即可 |
| 答案可溯源 | 不支持，来自模型参数 | 支持，可追溯到具体 chunk |
| 适合场景 | 定制输出风格、深度专业能力 | 私有知识问答、动态更新数据 |
| 知识上限 | 受限于训练数据质量和规模 | 受限于检索质量和 context 长度 |

**面试要点**：先讲清本质区别（微调改参数、RAG 注入知识），再各说优劣，最后必须提到两者可组合使用——能讲出组合思路，说明理解了工程选型。

# 4. RAG 中的文档是怎么存的？粒度是多大？详细说说文档切割（Chunking）策略？

文档不能直接存进向量库，**必须先切成小块（chunk），每个 chunk 分别向量化后存成一条记录**。每条记录有三个核心部分：**向量**（用于相似度检索）、**原始文本**（检索命中后给 LLM 读的内容）、**metadata**（来源文件、页码等，用于过滤和溯源）。切割粒度没有固定答案，通常 **500～1000 token** 是合理起点，但更重要的是**根据文档类型选策略**。

## 为什么不能整篇存储

1. **向量模型有输入长度限制**：一般最多几百到几千 token，整篇文档塞不进去
2. **细节被平均掉**：整篇压缩成一个向量，信息太密集，检索到的是笼统的文档而不是精确的段落。例：想找「退款政策」，但向量里混着「配送时效」「积分规则」，结果召回整篇文档

## 每条 chunk 记录的存储结构

- **向量**：一串浮点数，只有检索系统会用到，负责「找到」
- **原文**：纯文字，LLM 真正阅读的内容，检索命中后塞进 prompt，负责「阅读」
- **metadata**：来源文件名、页码、章节等，用于过滤（「只搜客服部门的文档」）和溯源（「这个答案来自哪个文件的第几页」）

类比：向量是索引卡，原文是书页，metadata 是书签。查询流程：用户问题 → 向量化 → 找相似 chunk → 取出原文 → 塞进 prompt → LLM 生成。

## 粒度选择的取舍

- **chunk 太大**：向量把太多语义压缩在一起，检索易召回部分相关的内容，且可能超 Embedding 输入长度限制
- **chunk 太小**：单个 chunk 语义不完整、上下文丢失，LLM 看不懂，检索噪音多

**500～1000 token 是起点，关键是根据文档结构选策略。**

## 文档切割策略

### 策略一：固定大小切割（Fixed Size Chunking）

- 按固定字符数或 token 数切割，不管语义边界
- 优点：实现简单、chunk 大小可控；缺点：可能在句子中间截断
- **通常配合重叠（overlap）使用**：如 chunk_size=500、overlap=100，前一个 chunk 的末尾和后一个的开头有重叠，确保跨边界语义被至少一个 chunk 完整覆盖
- 适合纯文本、无明显结构的文档，是最基础最保底的选择

### 策略二：语义边界切割（Semantic/Structure Based Chunking）

- 按文本的自然语义边界切：段落、句子、标题层级
- 核心思想：**不要在语义中间截断**。句子是表达意思的最小完整单位，按段落切则每个 chunk 都是围绕同一话题的完整段落，语义独立性最好
- 常见做法：维护分隔符优先级列表，先按段落切，太大再按句子切，再大按标点切，直到满足 chunk_size
- 对 Markdown/HTML 文档按标题层级切更好：每个 chunk 对应一个完整章节，metadata 自动带上标题（如「产品手册 > 退款政策 > 申请流程」）

### 策略三：特殊内容专项处理

- **代码**：以函数或类为单位切割，函数是最小的语义完整单元；用 AST 语法解析工具识别边界
- **表格**：整块保留，转成 Markdown 存储，不能按行截断（每一行依赖表头才有意义）

### 策略四：父子切割（Parent-Child Chunking）

一句话概括：**检索时用放大镜（小块精准定位），返回时用全景图（大块上下文完整）**。

- 同一段内容存两份：细粒度小 chunk（如 200 token）用于检索，精度高；包含上下文的大 chunk（如 1000 token）通过 ID 关联
- 检索时用小 chunk 找精准命中点，按关联 ID 取出大 chunk 交给 LLM
- 代价：存储量翻倍、索引构建复杂，但对召回质量要求高的场景值得

### 补充：Late Chunking（Jina AI 2024）

- 传统做法：先切块再编码，每个 chunk 独立过 Embedding，跨块上下文在编码阶段丢失
- Late Chunking：**先编码后切分**——把整篇文档丢给支持长上下文的 Embedding 模型做一次完整前向传播，得到每个 token 的向量（通过注意力机制彼此感知），再按 chunk 边界对 token 向量做 mean pooling 得到 chunk 向量
- 效果：chunk 向量天然融入全文语境，跨块的代词、背景、对比关系都保留
- 代价：需要模型支持长上下文（如 jina-embeddings-v2 支持 8192 token），且要保留 token 级中间结果，开销较大

## 策略选型表

| 策略 | 适用文档类型 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定大小 + 重叠 | 纯文本、无明显结构 | 实现简单、chunk 大小可控 | 可能在语义中间截断 |
| 语义边界切割 | 段落分明的文章 | 语义完整，召回质量好 | 实现稍复杂，chunk 大小不均 |
| 标题层级切割 | Markdown、HTML 文档 | 天然语义独立，带结构 metadata | 依赖文档有清晰标题结构 |
| 代码按函数切割 | 代码文件 | 保留代码逻辑完整性 | 需要 AST 解析，限定语言 |
| 父子切割 | 各类文档（追求高质量） | 检索精准 + 上下文完整两全 | 存储量翻倍，索引构建复杂 |
| Late Chunking | 各类文档 | chunk 向量保留全文上下文 | 需要模型支持长输入 |

**面试要点**：先说清为什么不能直接存（输入长度限制 + 细节丢失），再说怎么切（固定大小加重叠做兜底、语义边界更智能、代码表格特殊处理、父子切割兼顾精度与完整性），最后给出一句扎实的组合话术：「固定大小加重叠兜底，结构化文档用语义边界切割，高质量要求场景用父子切割」。

# 5. 怎么规避语义被切割掉的问题

从两个方向规避：**一是切的时候不要在语义中间截断**（重叠切割、语义边界切割）；**二是切完之后用检索策略把上下文补回来**（句子窗口检索、父子切割）。还有一个从根本解决问题的方案——Anthropic 提出的 **Contextual Retrieval**，向量化之前先让 LLM 为每个 chunk 生成背景说明。

## 问题本质：语义截断

假设文档有「...企业用户享有优先客服通道，响应时间不超过 2 小时，并可申请专属技术顾问服务...」，如果 chunk 边界恰好切在「2 小时，」处，「企业用户享有优先客服通道」和「可申请专属技术顾问服务」被分到两个 chunk。单独看每个 chunk 相关度都不高，都可能不被召回，答案就断了。

**核心问题不是信息丢了，而是信息被拆散后，每一半都不够强，检索时全军覆没。**

## 方向一：切的时候不要截断

### 方案一：重叠切割（Overlap）

- 相邻 chunk 之间有一段内容重叠，边界切在语义中间时，跨边界内容也一定完整出现在某个 chunk 里
- 重叠量通常设为 chunk_size 的 10%～20%（如 chunk_size=800，overlap=150）
- **注意**：重叠只是兜底，只能保证跨边界文字不丢失，解决不了「完整语义被拆散」的根本问题，不能只靠它

### 方案二：语义边界切割

- 找到文本中自然的语义边界再切（句子、段落）
- 句子是表达意思的最小完整单位，从句子中间截断，前后半截都是残缺的，向量化后语义也是扭曲的
- 实操：用 NLP 工具（spacy / nltk）识别句子结束位置，以句子为单位填充 chunk，加满就封存开新 chunk；段落分明的文档优先在段落边界切

## 方向二：切完之后补回上下文

### 方案三：句子窗口检索（Sentence Window Retrieval）

- 存储时切成单个句子，每句单独向量化用于精准检索
- 检索命中一个句子后，把该句**前后各 N 个句子一起返回**，形成上下文窗口给 LLM
- 两全其美：检索粒度细（单句）定位准确，但给 LLM 的是完整上下文
- 缺点：每句都要单独向量化，存储量较大

### 方案四：父子切割（Parent-Child Chunking）

- 思路与句子窗口相近，但更结构化：**用小 chunk 检索，用大 chunk 生成**
- 存储时同一段内容存两份：小 chunk（如 200 token）用于检索，大 chunk（如 1000 token）通过 ID 关联用于生成
- 对比：句子窗口是检索命中后动态扩展上下文，父子切割是提前把父子关系存好。父子切割更灵活（父 chunk 大小可精确控制），句子窗口实现更简单（不需维护父子 ID）

### 方案五：命题化切割（Propositions-based Chunking）

- 不按文本位置切割，**用 LLM 把文档分解成一条条独立的命题（Proposition）**
- 每个命题是完整、自包含的陈述句，包含表达该事实所需的全部上下文，单独拿出来就能看懂
- 例：「企业用户享有优先客服通道，响应时间不超过 2 小时，并可申请专属技术顾问服务」→ 分解为「企业用户享有优先客服通道。」「企业用户的客服响应时间不超过 2 小时。」「企业用户可以申请专属技术顾问服务。」
- 优势：每个 chunk 语义密度最高、最独立，检索精度好
- 代价：需要额外 LLM 调用，成本高，适合质量要求极高的场景

## 方案六：Contextual Retrieval（Anthropic）

换一个角度：**不改变 chunk 本身，而是在向量化之前把缺失的上下文补进去**。

- **要解决的根本问题**：chunk 单独拿出来就失去语境。Embedding 模型只能看到 chunk 文字本身，不知道它来自哪篇文档、讲什么主题。如「此条款自 2024 年 1 月 1 日起生效」单独向量化完全丢失「这是企业版客服条款」的关键信息
- **核心做法分两步**：
  1. **生成 Context**：让 LLM 看着整篇原始文档，为每个 chunk 生成 1～2 句背景说明（说明该 chunk 在文档中的位置和主题）
  2. **拼接再向量化**：把 Context 前置拼到 chunk 前面，整体做 Embedding 和 BM25 索引
- 效果示例：原 chunk「此条款自 2024 年 1 月 1 日起生效，适用于所有企业版订阅用户」→ 加上 Context「这段内容说明了企业用户专属客服和技术顾问服务条款的生效日期和适用范围」→ 向量里包含「企业用户」「客服条款」「生效日期」等关键语义，召回率大幅提升
- **成本控制**：用 Prompt Caching 可把 LLM 调用成本降低 80%～90%。同一篇文档的所有 chunk 请求共享相同前缀，第一次调用把文档缓存到 KV Cache，后续请求只算 chunk 部分。综合下来文档部分成本降到原来的 10%～20%
- **实测效果**：Contextual Retrieval 结合 BM25 混合检索，可将检索失败率（Top-20 召回未命中目标 chunk 的比例）降低约 49%

## 方案对比表

| 方案 | 核心思路 | 适合场景 | 代价 |
| --- | --- | --- | --- |
| 重叠切割 | 相邻 chunk 有内容重叠 | 所有场景，基础兜底 | 存储轻微增加 |
| 语义边界切割 | 在句子/段落边界处切 | 段落结构清晰的文档 | 需要 NLP 工具 |
| 句子窗口检索 | 精细检索 + 扩展返回窗口 | 追求高召回精度 | 存储量大 |
| 父子切割 | 小块检索、大块返回 | 通用场景，效果均衡 | 存储翻倍、索引复杂 |
| 命题化切割 | LLM 拆解为独立命题 | 高质量要求、重要知识库 | LLM 调用成本高 |
| Contextual Retrieval | 向量化前为每个 chunk 补全背景上下文 | 文档语境强、chunk 孤立感严重 | LLM 调用成本（Prompt Caching 可降） |

**面试要点**：先说清问题本质（chunk 孤立后失去语境，语义被拆散导致召回不到），再分两个方向讲方案——「切的时候别截断」（重叠、语义边界）和「切完补上下文」（句子窗口、父子、命题化、Contextual Retrieval）。实际工程组合使用：重叠做兜底，语义边界保证切割质量，高质量场景加父子切割或 Contextual Retrieval。

# 6. Embedding 是什么？如何选择评估 Embedding 模型？

Embedding 是把一段文本转成一串数字向量的过程，关键特性是**语义相近的文本，向量在数学空间里的距离也近**。RAG 的语义检索就靠这个实现——不是关键词匹配，而是看两段内容意思相不相近。

选模型主要看三个维度：**中文支持、向量维度、最大输入长度**。评估不要只看通用排行榜，**一定要在自己的业务数据上跑召回测试**（Hit@K）。

## Embedding 是什么

- Embedding 模型本质是「语义压缩」：把任意长度的文本映射成一个固定长度的浮点数向量（如 1024 维）
- 关键性质：语义相近的文本，向量余弦相似度高
- **为什么用余弦相似度而不是直线距离**：高维空间里向量长度受文本长度、表达强度等非语义因素影响，直接比距离会把「长短」和「语义」混在一起；余弦只看方向（夹角），方向一致则值接近 1，正好把「意思相近」从「文本长短」里剥离出来

与关键词匹配的本质区别——示例：**「苹果手机怎么截图」和「iPhone 如何截屏」** 字面完全不同但语义相同，关键词匹配完全无效，而 Embedding 后余弦相似度可能高达 0.95；「苹果手机」和「苹果汁」都有「苹果」但语义相差远，向量距离会拉开。**这是从「意思」层面做匹配，能处理同义词、近义词和不同表达方式。**

## 常见 Embedding 模型对比

- **OpenAI text-embedding 系列**：text-embedding-3-small 性价比高，1536 维、支持降维到 256 维省存储，英文效果好；缺点是 API 收费、数据要发到 OpenAI 服务器，有数据出境合规问题
- **BGE 系列（北京智源）**：bge-large-zh-v1.5 是经典中文开源模型，1024 维，可本地部署数据不出境；bge-m3 是多语言版本（中英日），1024 维，支持稠密向量、稀疏向量、ColBERT 式多向量三种检索模式，适合中英混排
- **新一代高性能模型**：Qwen3-Embedding（阿里通义）多语言基准表现突出、中文很强；Voyage-3-large 英文检索精度超过 OpenAI；Cohere embed-v4 支持 128K 超长上下文；Gemini Embedding 表现均衡。2025-2026 做新项目建议关注这些新模型，在自己数据上测评后再选型

## 如何选择 Embedding 模型

1. **中英文比例**：中文为主选 bge-large-zh-v1.5 或 Qwen3-Embedding；中英混合选 bge-m3；纯英文或追求省事选 text-embedding-3-small
2. **数据合规要求**：数据不能出境就必须用可本地部署的开源模型（BGE 系列、Qwen3-Embedding）
3. **向量维度**：维度越高精度越好，但存储空间和检索时间增加。百万量级知识库 1024 维是合理平衡点；规模小 1536 维无所谓。部分新模型（如 text-embedding-3-small）支持 Matryoshka 降维，可灵活调整维度平衡精度和成本

## 如何评估 Embedding 模型

- **常见误区**：只看 MTEB 通用排行榜分数。MTEB 是权威通用排行榜，但它用通用数据集，你的业务场景（医疗问诊、法律文档、客服知识库）和通用数据分布差异很大，排行榜第一不一定适合你
- **正确方法**：在**自己的业务数据**上跑召回测试——准备几百条业务相关的「问题 + 正确答案 chunk」对，用候选模型做检索，看正确 chunk 是否出现在前 K 条结果里，指标叫 **Hit@K**。Hit@5 = 0.8 表示 80% 的问题答案出现在前 5 条里。**Hit@5 低于 0.7 就要考虑换模型或改进 Chunking 策略**

| --- | --- | --- | --- | --- |
| text-embedding-3-small | 1536（可降维） | 一般 | 否（API） | 英文为主、快速上手 |

| bge-large-zh-v1.5 | 1024 | 很好 | 是 | 中文知识库经典选择 |

**面试要点**：讲三点——Embedding 关键是语义相近向量距离近；选模型看场景（中文 BGE/Qwen3，中英混合 bge-m3，合规要求开源本地部署）；评估不要只看 MTEB，要跑业务数据上的 Hit@K。被追问「用的什么模型」可以说「中文场景用 bge-large-zh-v1.5 或 Qwen3-Embedding，业务数据上 Hit@5 达到 0.8 以上，按测评结果选的」。

# 7. Embedding 有哪几种算法

Embedding 算法经历了**三代演进**，每一代都在补上一代的坑：

1. **第一代静态词向量**（Word2Vec / GloVe）：把每个词映射成固定向量，但同一个词不管上下文都一个向量，处理不了多义词
2. **第二代上下文相关向量**（ELMo / BERT）：同一个词在不同语境有不同向量，但检索时要两两拼接，百万条文档要跑百万次，检索速度不可接受
3. **第三代句子级对比学习 Embedding**（SBERT / SimCSE / BGE）：专为「两段文本有多相似」优化，能提前算好所有文档向量存库，查询时只算一次，是 RAG 场景的标配

## 第一代：静态词向量（Word2Vec / GloVe / FastText）

- **Word2Vec（2013，Google）**：用周围词预测中心词（CBOW）或用中心词预测周围词（Skip-gram）。Skip-gram 从一个词产生多个训练样本，对低频词更友好，更常用；CBOW 大数据集收敛更快。「国王 - 男人 + 女人 ≈ 女王」的著名类比就是它做的
- **GloVe（斯坦福）**：对整个语料库的词共现矩阵做分解，全局统计信息利用更充分，实际效果与 Word2Vec 相近
- **FastText（Facebook）**：解决「未登录词」问题——把词拆成字符级 n-gram 子词，每个子词有自己的向量，词向量是子片段向量的平均，遇到没见过的词也能估算合理向量
- **共同局限：静态**。「我吃了苹果」和「苹果手机发布了」里的「苹果」向量完全相同，只记住了「哪些词经常一起出现」，不是真正的语义理解

## 第二代：上下文相关向量（ELMo / BERT）

- **ELMo（2018，Allen NLP）**：用双向 LSTM 从左往右和从右往左扫描，拼接两个方向的隐藏状态作为词的上下文向量，第一个实用的上下文 Embedding
- **BERT（2018，Google）**：用 Transformer 替代 LSTM，引入 Masked Language Model 预训练任务，用 [CLS] token 表示整个句子，同时看到前后文，效果全面超越 ELMo
- **致命缺陷**：比较两个句子相似度必须把两句拼在一起喂给 BERT 让 [CLS] 判断。每次检索都要把查询和每个候选 chunk 拼接跑一遍，百万条文档就要跑百万次，一次前向传播几十毫秒，检索完全不可用

## 第三代：句子级对比学习 Embedding（SBERT / SimCSE / BGE）

核心理念：**让每个句子独立生成一个向量，直接用余弦相似度比较**。

- **SBERT（Sentence-BERT，2019）**：用 bi-encoder 结构，两个句子分别独立过 BERT 得到各自句子级向量，用余弦相似度衡量距离。代价是精度略降（编码时看不到两句话 token 的交叉交互，不如 Cross-Encoder），但速度提升几个数量级——文档向量提前算好存库，检索时只算一次查询向量，毫秒级返回，在 RAG「速度优先」场景完全值得
- **SimCSE（2021，普林斯顿）**：对比学习，把同一句话做两次 dropout 得到两个向量作为正样本对拉近，同一 batch 其他句子的向量作为负样本推远。无需人工标注，解决 BERT 原生句子向量「各向异性」（向量挤在窄小锥形区域、没有充分利用向量空间）的问题
- **BGE（北京智源）**：中文 RAG 场景非常流行的开源模型，基于对比学习在中英大规模数据上训练，支持 bi-encoder 和 reranker 两种形态；E5（微软）是另一个常用英文对比学习 Embedding

**第三代的新趋势（2025-2026）**：

- **指令感知 Embedding**（如 Qwen3-Embedding）：模型根据检索指令动态调整向量表示，同一段文本在「找相似问题」和「找答案」两种意图下产生不同向量
- **Matryoshka 表示学习（MRL）**：训练时让向量前 N 维就能表达有意义语义，可灵活截断维度平衡精度和存储
- **多模态 Embedding**：同一模型既能编码文本也能编码图片，支持跨模态检索

这些是第三代基础上的增强，不是独立第四代。

## 三代演进总结表

| 世代 | 代表模型 | 核心特点 | 主要局限 | RAG 适用性 |
| --- | --- | --- | --- | --- |
| 第一代 | Word2Vec、GloVe、FastText | 词级静态向量 | 无法处理多义词，词级非句子级 | 不适用 |
| 第二代 | ELMo、BERT | 上下文动态向量 | 检索需两两拼接，速度极慢 | 不适用于实时检索 |
| 第三代 | SBERT、SimCSE、BGE、E5 | 句子级 bi-encoder，对比学习 | 精度低于 cross-encoder | 标配，性能和精度平衡最优 |

**面试要点**：按三代演进逻辑讲——第一代解决「词变向量」但处理不了多义词；第二代解决多义词但检索要两两拼接不可用；第三代用 bi-encoder 独立编码、提前算好向量存库，检索只算余弦相似度，是 RAG 标配。被追问项目用什么模型，答「中文场景用 BGE，业务数据上评估选型」。

# 8. 什么是向量数据库？如何对比选型

向量数据库是**专门用来存储和检索高维向量的数据库**，核心能力是**近似最近邻搜索（ANN）**，能在百万甚至亿级向量里快速找出最相似的几条。普通关系型数据库的索引结构对高维向量基本失效，所以需要专门的数据库。

选型经验：本地开发用 **Chroma**（零配置上手极快）；生产中小规模推荐 **Qdrant**（性能好、API 简洁）；超大规模考虑 **Milvus**（字节、小米在用）；不想自己运维用 **Pinecone**（云托管）；已有 PostgreSQL 可直接用 **pgvector** 插件。

## 什么是向量数据库

- 向量数据库存的是 Embedding 模型把文本、图片、音频转成的浮点数数组（如 768 维或 1024 维），每个向量代表内容的「语义含义」，语义越相近向量距离越近
- 核心操作是 **近似最近邻搜索（ANN）**：给一个查询向量，找出库里最相似的 K 个向量，返回对应原始内容，这是 RAG「检索」那一步的底层支撑
- **与关系型数据库的本质区别**：MySQL 擅长精确匹配（WHERE id = 123），向量数据库擅长语义相似（找和这个意思最接近的内容），两者解决不同问题，不是互相替代

## 为什么需要专门的向量数据库

- 高维向量相似度搜索如果暴力遍历，百万条数据要算一百万次余弦相似度，延迟不可接受
- **B-tree 索引失效**：B-tree 只能处理一维有序索引，「近」是高维空间的综合判断，不是某个维度上的排序，无法对 1024 维向量建 B-tree 找最近邻
- 向量数据库用专门的索引结构加速，在可接受的精度损失下把延迟降到毫秒级

## 核心索引算法：HNSW 和 IVF

### HNSW（Hierarchical Navigable Small World）

- 目前召回率最高的 ANN 算法之一，构建多层图结构，查询时从最上层稀疏图开始导航，逐层收窄，最终在底层找到最近邻
- 类比：在地图上找最近餐厅，不是遍历全国所有餐厅，而是先定大致方向，再逐层锁定到省、市、区
- **优点**：召回率高（相同延迟下可达 95%+）、查询速度快
- **缺点**：建索引内存消耗大，不适合内存极度受限场景
- Qdrant、Milvus、Chroma 默认都用 HNSW

### IVF（Inverted File Index）

- 先对向量做聚类，把相似向量分进同一个「桶」，查询时只搜最相关的几个桶，不全量遍历
- 类比：找编程书不用翻整个图书馆，先到「计算机科学」区域再找
- **优点**：内存占用小、适合超大规模
- **缺点**：精度比 HNSW 略低，需要调参（聚类数量 nlist、搜索桶数量 nprobe）
- Milvus 超大规模场景用 IVF 系列

**为什么需要 IVF**：HNSW 内存消耗和向量数量成正比，亿级规模内存扛不住；IVF 用聚类换内存，牺牲一点精度处理超大规模。

## 向量数据库的核心能力

1. **Metadata 过滤（混合检索）**：给每个向量挂 metadata 字段，检索时加过滤条件（如「只搜技术部文档」），只在符合条件的子集里做 ANN。先过滤再 ANN 能保证召回的都是真正想要的，避免 Top-K 名额浪费
2. **实时更新**：支持在线增量写入，新数据进来增量构建索引，不需要停服重建
3. **与关键词检索融合**：纯向量检索对精确词语（产品型号、专有名词）效果不好，部分向量库同时支持向量检索 + BM25 关键词检索做混合召回

## 选型对比表

| 数据库 | 部署方式 | 适合规模 | 混合检索 | 主要优势 | 主要劣势 |
| --- | --- | --- | --- | --- | --- |
| Chroma | 本地/Client-Server/云 | 中小规模 | 是（BM25/SPLADE） | 零配置上手极快，生态集成好 | 超大规模稳定性待验证 |
| Qdrant | 自托管/云（支持分布式） | 中大规模（亿级） | 是 | 性能好，API 简洁，Rust 高性能 | 超大规模需调优 |
| Milvus | 自托管（分布式） | 大规模（亿级） | 是 | 可水平扩展 | 部署运维复杂 |
| Pinecone | 全托管云服务 | 中大规模 | 是 | 无需运维 | 费用高，数据出境 |
| pgvector | PostgreSQL 插件 | 中小规模 | 是（配合全文检索） | 无需新组件，可 JOIN 业务数据 | 性能弱于专用向量库 |

**面试要点**：不要理解成「普通数据库加个向量字段」——向量数据库是为高维向量相似度搜索设计的，核心是 ANN，B-tree 对高维向量检索失效。选型从数据规模、部署方式、是否需要混合检索三个维度回答。索引算法至少要能讲清 HNSW 和 IVF 的区别和适用场景。

# 9 数据量级是多大？性能如何？性能瓶颈？

生产环境用 **Milvus**，数据量级在 **150 万条左右**的 1024 维向量，用 **HNSW 索引**，单次查询延迟 **P50 约 20ms、P99 约 60ms**。选 Milvus 是因为它支持分布式部署和读写分离，适合数据量大、并发高的场景。

遇到过两个典型瓶颈：**一是内存压力**（百万级 1024 维向量原始数据就要好几个 GB，开启标量量化 SQ8 后内存降到四分之一）；**二是大批量写入触发后台 Segment 合并影响查询延迟**（解法是错峰批量写入、分批小批次写入）。

## 为什么选 Milvus

- 普通数据库存结构化数据、精确匹配；向量库存语义向量、相似度搜索
- 100 万条记录逐一算距离是 O(N)，太慢；向量数据库通过 HNSW 索引把查询时间压缩到接近 O(log N)，用少量精度损失换极大速度提升
- 选 Milvus 的原因：**数据量级上去了单机撑不住，需要分布式部署**；**知识库每天增量更新，读写分离让写入不影响查询稳定性**

## Milvus 核心概念

- **Collection（集合）**：类似关系库的「表」，存储一类向量数据。每条记录包含 chunk ID、向量、原文内容、来源文档等 metadata
- **Segment（段）**：Milvus 管理数据的基本单位。新写入数据先进「增量段」（临时接收缓冲区），积累到一定量触发合并变成「封存段」（建好索引、查询快）。合并动作本身消耗 CPU 和磁盘，会抢资源
- **Index（索引）**：向量检索的加速结构，最常用 HNSW。关键参数：
  - **M**：每个节点最多认识的邻居数，越大图越密、精度越高、建索引内存和时间越多，通常 16～32
  - **ef_construction**：建图时每个节点考察的候选数，越大越精确、建索引越慢，通常 100～200
  - **ef（search_ef）**：查询时搜索的候选集大小，越大召回越准、延迟越高，按需求在 50～200 之间调

## 数据规模和实测性能

- 数据：约 150 万条 chunk，BGE-large-zh 生成 1024 维向量，HNSW 索引（M=16，ef_construction=128）
- **内存计算**：150 万 × 1024 维 × 4 字节（float32）≈ 6GB 纯向量；完整进程跑起来约 10～12GB（HNSW 图结构、metadata、Collection 管理、OS 缓存）
- **量化 SQ8**：把每个 float32 压成 int8（1 字节代替 4 字节），内存从 10GB 降到约 3GB，召回率基本无损（通常下降 1 个百分点以内），是最划算的优化
- **实测查询性能**（单机 16 核 32G、本地千兆网、HNSW 在内存、ef=100）：单次 top-5 查询 P50 约 20ms，P99 约 60ms，并发 100 QPS 稳定
- **关键提醒**：报数字必须带硬件和参数背景——同样 Milvus，跑在 8 核机上、跨机房调用、ef 设到 200，数字可能差一个量级

## 遇到的性能瓶颈

### 瓶颈一：内存不足，查询延迟飙升

- 最开始没开量化，8GB 内存的机器加载向量索引后频繁 swap，查询延迟从 20ms 飙到 2s+。**这是一个易误诊的点：看起来像索引算法问题，实质是内存不够被系统强行 swap**
- 解法：SQ8 量化，内存从 10GB 降到 3GB 左右彻底解决；辅助手段是 Milvus 支持原始向量存磁盘（mmap），只把索引放内存，原始向量只在精排时才读

### 瓶颈二：批量写入触发 Segment 合并，查询抖动

- 一次性写入几十万条新数据时，后台触发 Segment 合并（把多个小增量段合并成大封存段并建索引），耗 CPU 和磁盘 IO，期间查询 P99 从 60ms 涨到 300ms+
- 解法一（错峰）：批量写入改到业务低峰期（如凌晨），让合并在用户不活跃时静默完成
- 解法二（化整为零）：每批写入控制在 500～1000 条以内，分多批、每批间隔几秒，把合并冲击变成多次小冲击

**面试要点**：不能说「Chroma，几万条，感觉挺快」。先说清选型（Milvus，百万级需要分布式和读写分离），给出具体数字（150 万条 1024 维、HNSW、P50 20ms、P99 60ms、100 QPS 稳定），最后讲一个真实踩过的瓶颈及解法（SQ8 量化 / 错峰分批写入）。

# 10 使用 RAG 给大模型一个输入，系统是怎样的工作流程？

一个问题输入 RAG 系统后，**不会直接丢给大模型，而是先经历一套「检索 → 整理 → 生成」的流水线**：先对问题做预处理（改写成适合检索的形式），再把问题向量化，去向量库找最相关的文档片段，经过精排筛掉噪音，最后把筛选出的片段和问题拼成 Prompt 交给大模型生成答案。整个流程的核心目标只有一个：**让大模型在回答时有真实知识作为依据，而不是凭空发挥**。

## 为什么不能直接丢给大模型

- 大模型上下文窗口有限，不可能把整个知识库塞进去
- 没有外部知识依据时，模型靠参数记忆回答，容易出现幻觉
- 所以 RAG 在线流程本质是「精准取件」：从海量知识里找到与问题最相关的几段，再让模型在「小范围」里作答

## 完整流程（六大步骤）

### 第一步：Query 预处理（Query Rewrite）

用户原始提问质量决定后续所有环节的天花板。用户提问往往口语化、带指代（如「上次那个方案怎么样」），或与文档用词差异大，直接检索命中率低。常见技术：

- **简单改写**：把口语化问题改写成更正式、独立完整的检索句
- **HyDE（假设文档嵌入）**：让 LLM 先假设一个可能的答案，用假设答案的向量检索。因为假设答案和真实答案用词更接近，语义空间更匹配，命中率更高
- **多角度扩写**：把同一问题扩展成 3-5 种表述分别检索后合并结果，覆盖面更广

### 第二步：Query Embedding（问题向量化）

用 Embedding 模型把处理后的 query 转成向量。**关键细节：必须用和离线建库时完全相同的 Embedding 模型**。不同模型的向量空间语义不对齐——维度数可能不同（A 是 1024 维、B 是 1536 维），即使维度相同，各自向量空间里的方向含义、距离分布也不同，两个模型产出的向量直接算距离没有意义。所以**一旦换 Embedding 模型，整个知识库必须重建**。

### 第三步：向量检索（ANN 搜索）+ 多路召回

拿问题向量去向量库做 ANN 搜索，找余弦相似度最高的 Top-K 个片段，百万量级几十毫秒返回。但工程上通常同时做**多路召回**：

- **向量检索**：捕获语义相似性
- **BM25/全文检索**：捕获关键词精确匹配（产品型号、专有名词、错误拼写）
- 多路结果用 **RRF（互倒排名融合）** 合并，覆盖面比单路更广、质量更高

### 第四步：Rerank 精排

- 向量检索是「粗排」，Top-20 结果里混有相关度不高的干扰片段
- **Rerank 模型（Cross-Encoder 结构）**把用户问题和每个候选片段拼在一起输入，深度理解语义匹配程度，重新打分排序，最终保留 Top-3～Top-5 高质量片段
- **为什么两阶段**：Rerank 是 Cross-Encoder，要把查询和每个候选拼在一起过模型，计算量远大于向量检索，对百万条逐一算分延迟不可接受。所以「粗排筛到几十条，精排再挑最好的几条」，兼顾速度和质量

### 第五步：Prompt 拼装

把精排后的片段和用户原始问题组装成 Prompt。典型模板：

```
你是一个专业助手，请根据以下参考资料回答用户的问题。
如果参考资料中没有相关信息，请回答「根据现有资料无法回答」，不要自行猜测。

参考资料：
[1] {chunk_1}
[2] {chunk_2}
[3] {chunk_3}

用户问题：{user_query}
```

**每条指令都有工程意图**：

- 「只根据资料回答」：抑制 LLM 凭记忆发挥的倾向
- 「资料没有就说不知道」：防止信息不足时强行补全出幻觉
- 参考资料带编号：方便后续引用溯源

### 第六步：大模型生成 + 溯源

大模型基于参考资料生成答案。工程上通常要求模型**在答案里标注每句话来自哪个片段**（如「根据资料[1]...」），用户可以追溯到原始文档验证准确性。**溯源非常关键**——模型即使在有参考资料时依然可能过度发挥或误读，溯源让用户能判断哪些内容可靠、哪些需要再确认。

## 链路耗时分布与优化

- 耗时大致：Query 改写几十毫秒，向量检索几十毫秒，Rerank 几百毫秒，Prompt 组装可忽略，大模型生成 1-10 秒（按输出长度）
- 常见优化：缓存高频 Query 的检索结果；向量检索和 BM25 检索并行执行，延迟从串行叠加变成取最大值

**面试要点**：按顺序把六步讲清楚，每步干什么、为什么需要、有什么工程细节。尤其注意第二步必须用相同 Embedding 模型（换模型要重建库）、第四步两阶段检索的原因、第五步 Prompt 约束的意图。

# 11、介绍一下向量检索和关键词检索的区别

**关键词检索（BM25 这类）靠词频统计**，看查询词在文档里出现了多少次，擅长精确命中；**向量检索靠语义空间里的距离**，能理解「换了种表达方式的同一个意思」，擅长模糊语义匹配。两者各有盲区：**BM25 遇到同义词就没辙，向量检索遇到专有名词、产品型号这类精确词就容易漏**。所以 RAG 系统通常两路都跑，用 **RRF** 算法合并结果。

## 关键词检索（BM25）：字面匹配，靠统计

- BM25 是 Elasticsearch、Lucene 等传统搜索引擎的核心算法
- 底层是**倒排索引**：记录「每个词出现在哪些文档里」（不是每篇文档有哪些词）
- 打分核心看两个因素：
  - **词频（TF）**：词在文档中出现次数越多越相关
  - **稀缺度（IDF）**：词在所有文档里越罕见越有区分力。「的」「是」「在」这类词在哪都高频，只看词频区分不出相关性，IDF 给常见词降权、给罕见词加权
- BM25 在 TF-IDF 基础上加了**饱和度限制**，防止某词重复太多次权重无限叠加
- **优势**：对精确词汇命中率极高——产品型号「iPhone 15 Pro Max」、专有名词「LSTM」、缩写「RAG」，只要文档里有这个词就能精准找到
- **劣势**：遇到同义词束手无策。用户查「手机截图」，文档写「iPhone 截屏教程」，词汇零重叠分数为零，哪怕它正好是最相关的答案

## 向量检索：语义匹配，靠 Embedding

- 用 Embedding 模型把每段文本转成高维向量（语义空间坐标），语义相近的文本坐标靠近，用户查询也转成向量找最近的几个
- 「苹果手机怎么截图」和「iPhone 如何截屏」一个字都不一样，但余弦相似度可高达 0.95
- 通过 **ANN** 在向量库找最近的 Top-K 条，百万量级几十毫秒返回
- **优势**：语义理解能力强，能跨越同义词、近义词、不同表达方式
- **劣势**：对精确词汇不敏感——产品型号「Pro Max 256GB」、人名、版本号在 Embedding 空间里可能距离不远，容易混淆，反而不如 BM25 直接命中准确

## 核心区别对比表

| 维度 | 关键词检索（BM25） | 向量检索 |
| --- | --- | --- |
| 匹配方式 | 词汇重叠统计 | 语义空间距离 |
| 索引结构 | 倒排索引（稀疏） | 向量库（稠密） |
| 同义词处理 | 无法处理 | 天然支持 |
| 精确词命中 | 极好 | 容易漏 |
| 计算方式 | 基于统计，可解释 | 黑盒，向量距离 |
| 适合场景 | 专有名词、代码、精确查询 | 语义问答、模糊表达 |

## 混合检索：两路都跑，取长补短

既然两种方式盲区互补，工程标准做法是**混合检索（Hybrid Search）**：同时跑向量检索和 BM25 各自召回一批候选，用 **RRF（Reciprocal Rank Fusion，互倒排名融合）** 合并排序。

- **RRF 思路**：不看原始分数只看排名。因为向量相似度（0-1 余弦值）和 BM25 分数（任意正数）量纲完全不同，不能直接加权平均
- 公式：对文档在某路的排名 rank，贡献分 1/(rank + k)，k 是平滑参数通常取 60；把文档在所有路的贡献分相加得综合分
- 效果：两路都认为相关的排最前，只有一路认为相关的也不会被完全丢掉
- 工程好处：两路可并行执行，总延迟取两路最大值而非相加，几乎无额外时间代价

**面试要点**：不要简单说「向量检索更好」——两者是互补关系。讲清 BM25 靠词频精确匹配强但同义词没辙，向量检索靠语义理解强但精确词易漏，正确做法是混合检索两路并行 + RRF 融合。

# 12. 如何润色用户的 Query（Query Rewrite）？目的是什么

Query Rewrite 的核心目的是**弥补用户提问方式和知识库文档表述之间的语义鸿沟**。用户的问题往往口语化、模糊、带缩写，而文档写的是正式书面语，向量相似度天然偏低，导致该召回的内容没被召回。

我接触过的四种主要方法：**直接改写**（口语化转精准表述）、**Query 扩展**（补充相关关键词）、**HyDE**（先生成假设答案、用答案向量检索）、**Step-back Prompting**（把具体问题向上抽象一层，检索更通用的背景知识）。

## 为什么需要 Query Rewrite

用户和文档写作者之间有天然的表述鸿沟。用户可能问「这东西坏了咋整」，文档里写的是「产品故障排查与维修指南」，即便语义相关，向量相似度也可能低到召回不了正确文档。Query Rewrite 就是在检索前对用户问题做加工，让它在向量空间里离正确文档更近。

## 方法一：直接改写（Query Rewriting）

- **解决**：口语化表达、指代不清、上下文丢失
- 把口语化、模糊的问题改写成更精准、书面的检索表述，同时补全上下文、处理代词指代（「这个功能」改写为具体功能名），让多轮对话中的模糊引用变成检索可识别的具体词汇
- 示例：「上次说的那个退款的事，流程是啥」→「申请商品退款的完整操作流程是什么」
- **局限**：直接改写主要解决指代、口语化问题，对「问句 vs 陈述句」这种全局文体差异收效有限——现代 Embedding 模型虽大多经过问答对训练，但问题以疑问句表达时，与文档陈述句表述的语义距离仍可能偏大，这正是引入 HyDE 的动机

## 方法二：HyDE（Hypothetical Document Embeddings）

- **解决**：问题和文档文体风格差异大
- 核心思路：**正常用问题的影子找答案的样子，HyDE 先描绘出答案可能长什么样子，再去找长得像它的文档**。先让 LLM 根据问题生成一段「假设性答案」，再用假设答案的向量检索。假设答案不需要准确，只需要「风格像文档」
- 原理：**在向量空间里，答案到答案的距离比问题到答案的距离近得多**。假设答案的作用不是回答问题，而是「扮演文档的角色」
- 示例：问题向量「退款政策是什么」和文档「申请售后退款须知」距离较远；而假设答案向量「用户可在购买后 14 天内申请退款...」和文档距离很近，能被正确召回
- **注意**：如果 LLM 生成的假设答案方向错了，反而会把检索带偏，一般在知识库领域明确的场景效果更稳定

## 方法三：Step-back Prompting（后退提问）

- **解决**：问题太具体，知识库里没有直接答案但有背景原理
- 把具体问题「后退一步」提升到更抽象层次，先检索背景知识，再结合背景知识回答具体问题
- 类比：做数学题不是一上来硬套公式，而是先想「这道题用的是哪种定理」，再用定理解题
- 示例：「Qdrant 的 HNSW ef 参数设多少合适」→「HNSW 索引的参数调优原则是什么」，能命中更多通用背景文档

## 方法四：多 Query 扩展（Multi-Query）

- **解决**：问题角度单一、覆盖不全
- 用 LLM 把用户原始问题改写成 3～5 个不同角度的版本分别检索，合并结果去重
- 核心思路：只要有一个改写版本和文档表述对上了，就能召回正确内容，就像拦截网越宽捕到鱼的概率越高
- **注意**：原始问题本身要保留在检索列表里，不能只用改写版本——改写可能丢失原始细节，原始问题反而最精准
- 代价：多几次 LLM 调用

## 方法对比表

| 方法 | 解决的核心问题 | 额外开销 | 适合场景 |
| --- | --- | --- | --- |
| 直接改写 | 口语化、指代不清、上下文丢失 | 1 次 LLM 调用 | 多轮对话场景 |
| HyDE | 问题和文档文体风格差异大 | 1 次 LLM 调用 | 专业知识库、文体差异明显 |
| Step-back | 具体问题需要背景知识辅助 | 1 次 LLM 调用 | 技术文档、需要原理支撑的场景 |
| 多 Query 扩展 | 单一角度覆盖不全 | N 次 LLM 调用 | 答案涉及多个维度的复杂问题 |

**面试要点**：核心是把「为什么要做 Query Rewrite」和「四种方法各自解决什么问题」讲清楚——口语化用直接改写，文体差异用 HyDE，问题太具体用 Step-back，角度单一用多 Query 扩展，让面试官看到你理解不同场景需要不同策略。

# 13. 什么是多路召回？具体怎么做

多路召回就是**同时用多种不同的检索方式去捞候选内容，然后合并排序**，而不是只靠单一的向量检索。核心出发点是**向量检索和关键词检索各有盲区，互为补充**：向量检索擅长语义相似但对精确词语（产品型号、缩写、数字）效果差；BM25 关键词检索正好相反，精确匹配强但不理解语义。项目里常用组合是**向量检索 + BM25 混合检索 + 多 Query 扩展**，多路结果用 **RRF 算法融合**，最后送进 Rerank 精排。

## 为什么单路召回不够用

- 单纯依赖向量检索是大多数 RAG 系统早期做法，短板是**对精确词语召回效果差**。例：用户问「M4 Pro 芯片的性能参数」，「M4 Pro」是专有名词，向量模型可能把它和「苹果最新处理器」拉近，却找不到含字符「M4 Pro」的记录。**单纯换更强的纯向量 Embedding 模型改善有限**——对精确词不敏感是「只看语义不看字面」的固有特性，这正是需要 BM25 混合检索的原因
- 反过来 BM25 对同义词无能为力：用户问「怎么退货」，文档写「申请售后」，词不重叠，完全召回不到
- 两种方式的盲区恰好互补，这就是多路召回的出发点

## 常见的三路召回组合

### 第一路：向量检索（Dense Retrieval）

- 文档和查询都用 Embedding 模型转成向量，用余弦相似度在向量库找最近的 Top-K
- 擅长语义匹配（同义词、不同表达方式），短板是精确词语——正好是第二路的强项

### 第二路：BM25 关键词检索（Sparse Retrieval）

- BM25 是 TF-IDF 改进版，根据词频和文档频率打分，本质是问「这个词有没有『代表』这篇文档」
- 中文场景先做分词（jieba 切词），对分词后的词列表建索引和检索
- 纯文本匹配速度极快，对精确词语、数字、专有名词召回效果非常好

### 第三路：多 Query 扩展召回

- **为什么需要**：用户提问角度和文档表述角度不一致，不是同义词问题而是整个视角差异。例：用户问「产品多久能送到」，文档写「配送时效说明」，向量相似度不高、BM25 也匹配不到关键词
- 做法：用 LLM 把原始问题改写成 3～5 个不同角度版本分别检索，合并去重（同一 chunk 被多版本召回只保留一份）
- 代价是多几次 LLM 调用，但提问风格多变场景下召回覆盖率可提升 10%～20%

## 结果融合：RRF 算法

三路各自返回排序结果，但分数单位不同（余弦相似度 vs TF-IDF 分数），没法直接加权平均。**RRF（Reciprocal Rank Fusion，倒数排名融合）只用排名不用原始分数**：

- 公式：`score(chunk) = Σ 1/(k + rank)`，k 是平滑参数通常取 60，rank 是文档在某一路的排名
- 直觉：不管各路分数怎么算（本就不具可比性），只看排名，多路都排名靠前的 chunk 综合分高，就像多位评委都给高分的选手综合排名高
- 不需要训练、计算量极小、工程落地成本低
- **注意**：RRF 本质还是粗排，适合在 Rerank 前做候选集合并；对召回精度要求高还要接 Cross-Encoder 精排模型（如 bge-reranker-v2-m3）

## 实战建议

- **专有名词、产品型号、数字多的场景**（电商、IT 文档）：向量 + BM25 双路是标配，收益明显
- **用户提问方式多变、与文档表述差异大的场景**（客服问答）：加多 Query 扩展，覆盖率提升 10%～20%
- **召回质量要求极高的场景**：三路全上，最后接 Rerank 精排

## 召回方式对比表

| 召回方式 | 擅长 | 短板 | 适合场景 |
| --- | --- | --- | --- |
| 向量检索 | 语义相似、同义词、不同表达 | 精确词语、数字、专有名词 | 通用语义检索 |
| BM25 关键词 | 精确词匹配、专有名词 | 同义词、语义相关但词不重叠 | 有大量精确词语的知识库 |
| 多 Query 扩展 | 覆盖不同表述角度 | 增加 LLM 调用开销 | 用户提问风格多变的场景 |

**面试要点**：把「为什么单路不够」（向量检索对精确词天然不敏感，不是模型问题而是检索方式本身局限）和「多路怎么组合、怎么融合」（向量管语义、BM25 管精确词、多 Query 管表述差异、RRF 融合）两条线讲清楚。

# 14. RAG 检索优化策略有哪些

RAG 检索优化从四个层次来看：**索引层**决定知识怎么存，**查询层**决定问题怎么转换，**召回层**决定从哪些路径去找，**重排序层**决定最终哪些内容进入 prompt。单独优化一个层次往往效果有限，线上系统要**组合使用**——先靠索引优化和多路召回的保证覆盖率，再用 Rerank 保证精度，用户提问质量差时再加查询优化。

## 为什么检索优化最重要

LLM 只能根据送进去的 context 回答，**检索召回的内容就是整个系统的天花板**。生成层做得再好，检索没把相关内容找回来，LLM 也是巧妇难为无米之炊。生成层优化（调 prompt、换模型）是锦上添花，检索层优化是从根本上提升系统能力上限，是投入产出比最高的环节。

## 四层优化的全貌

- **索引层**：决定知识怎么「存」——文档切割的粒度和方式，直接影响向量语义质量
- **查询层**：决定问题怎么「转」——检索前对 query 加工，让它更容易命中知识库
- **召回层**：决定知识从哪里「找」——多条检索路径并行捞取候选，互补盲区
- **重排序层**：决定候选里谁「最相关」——对粗召候选集精排，保证进 prompt 的都是真正有用的内容

比喻：索引层决定「仓库里放了什么」，查询层决定「用什么钥匙开门」，召回层决定「从哪几扇门进去找」，重排序层决定「把找到的东西里最好的几件带出来」。

## 第一层：索引优化

聚焦一个核心矛盾：**检索用的粒度和 LLM 读的粒度天然矛盾**。

- chunk 承担两个角色：检索时被找到（要求语义聚焦、小粒度）；被 LLM 读懂（要求上下文完整、大粒度）
- 直接切小会让 LLM 拿到碎片化信息，回答质量反而下降；切大则检索时语义稀释
- **核心解法：Small-to-Big（小块检索、大块使用）**，三种实现方式：

1. **Parent-Child Chunking**：切成细粒度子 chunk（150 token）和粗粒度父 chunk（500 token），子 chunk 通过 parent_id 关联父 chunk。入库只给子 chunk 建向量索引（检索精度高），命中后按 parent_id 取出父 chunk 给 LLM（上下文完整）
2. **摘要索引（Summary Index）**：让 LLM 为每段内容生成摘要，用摘要建向量索引。摘要是对核心意思的提炼，语义更聚焦、和问题更接近，命中后把原始段落给 LLM
3. **多粒度分层索引**：同时建章节级、段落级、句子级三层索引。宽泛概念性问题用章节级，细节性（如「退款申请需要几个工作日」）用句子级，系统按问题类型自动选粒度

## 第二层：查询优化

即使索引建得好，用户提问方式和知识库表述之间仍有鸿沟。例：用户问「苹果手机咋截图」，库里写「iPhone 截图操作方法」，口语和书面语表达差异会拉开向量距离。四种方法：

- **Query 改写**：把口语化、有歧义的 query 转成正式、精准的书面表达。例：「它为什么这么贵」结合对话历史改写成「iPhone 15 Pro Max 定价偏高的原因是什么」
- **多 Query 扩展（Multi-Query）**：把一个问题扩展成 3～5 个不同角度问法分别检索合并去重。**注意原始问题必须保留**——改写可能丢失原始细节，原始问题反而最精准
- **HyDE**：先让 LLM 生成「假设答案」，用假设答案向量检索。假设答案和文档都是陈述性文字、风格更接近、向量距离更近。**注意**：假设答案方向错了会把检索带偏，领域明确的场景效果更稳定
- **Step-back Prompting**：把具体问题抽象一层生成更通用的背景问题检索。例：「为什么 transformer attention 要除以 sqrt(d_k)」→「attention 机制的数学原理」，先检索背景知识再结合回答

## 第三层：召回优化

- 单一向量检索只擅长语义相似，对精确词匹配效果差（「M4 Pro」这类型号不如 BM25 准）；BM25 只会数词频不理解语义（「怎么退货」vs「申请售后」召不到）
- **多路召回**：同时打开多扇门，向量检索 + BM25 + 多 Query，覆盖更多可能性
- 各路分数量纲不同，用 **RRF 融合**：不看原始分数只看排名，`score(chunk) = Σ 1/(k + rank)`，k 通常取 60（加「保底分」，不让排名靠后的候选因偶尔失误被完全淘汰）。优点：实现简单、不需要训练、计算量极小

## 第四层：重排序（Rerank）

多路召回后候选有 20～30 个，直接全塞给 LLM 有两个问题：**token 消耗暴涨、成本上升**；**上下文太长 LLM 出现「Lost in the Middle」**（只关注开头结尾，中间内容被忽略）。所以需要精排挑出最相关的 3～5 个。

- **为什么 Rerank 比向量检索准**：两种模型结构不同
  - **Bi-encoder**（向量检索用）：query 和 chunk 各自独立编码成向量再算余弦。优点是快（chunk 向量提前算好存库，检索只算一次 query 向量）；缺点是看不到两段文字的具体词语关联，相关性判断不够精准
  - **Cross-encoder**（Rerank 用）：把「query + chunk」拼成一对输入整体看相关性，能看到 query 中每个词对 chunk 的影响，判断精度远高于 Bi-encoder。代价是每个候选都要单独跑一次，速度慢，只适合对小规模候选集精排
  - 类比：Bi-encoder 像只看两人简历判断合不合适合作，Cross-encoder 是把两人放一个房间观察怎么交流配合
- 常用开源 Rerank 模型：**BGE-Reranker-v2**（中英双语效果好）、**BCE-Reranker**；不想自己部署可用 Cohere Rerank、Jina Reranker 的 API

## 四层优化怎么组合

| 层次 | 解决的核心问题 | 推荐程度 |
| --- | --- | --- |
| 索引优化（Parent-Child） | 检索粒度 vs 上下文完整性的矛盾 | 推荐，效果稳定 |
| 查询优化（Multi-Query / HyDE） | 用户提问和知识库表达不对齐 | 视场景，提问质量差时必做 |
| 多路召回（向量 + BM25） | 单路检索漏召 | 推荐，低成本高收益 |
| Rerank 精排 | 粗召精度不足 | 强烈推荐，提升精度最直接 |

**典型生产级搭配：Parent-Child 索引 + 向量 BM25 多路召回 + Rerank 精排**，基本覆盖大多数检索质量问题；用户提问质量差（口语化、指代不清）再加 Query 改写。

从另一个角度记这四层：索引层保证「存进去的知识可以被找到」，查询层保证「搜索的姿势是对的」，召回层保证「不漏掉该找到的内容」，Rerank 层保证「送进 LLM 的是真正有用的内容」。

**面试要点**：不要只罗列优化手段，要讲清四层逻辑关系——每层解决什么问题、为什么需要、怎么和其他层配合，最后给出一套典型组合方案（Parent-Child 索引 + 多路召回 + Rerank）。

# 15. 有哪些更复杂的 RAG 范式

RAG 的发展经历三代演进：**Naive RAG** 是基础的检索加生成；**Advanced RAG** 在检索前后都加了优化（Query 改写、Rerank、混合检索）；**Modular RAG** 把各个环节做成模块可以任意组合。

在这之上还有几个值得关注的高级范式：**Self-RAG** 让 LLM 自己决定要不要检索及评估检索质量；**CRAG** 在检索质量差时自动降级到网络搜索；**GraphRAG** 是微软的方案，用知识图谱的社区发现和层次摘要增强全局理解；**Agentic RAG** 把 RAG 做成 Agent，支持多轮动态检索。

## 为什么需要不同的 RAG 范式

朴素 RAG 的问题随场景复杂度增加越来越明显：

1. **检索质量参差不齐**：有些问题一次检索就能找到答案，有些完全召不到，但系统不区分，一律把结果喂给 LLM，导致模型在低质量上下文上胡说
2. **所有问题走同一套流程，太死板**：有些问题根本不需要检索（如「1+1 等于几」），有些需要多轮检索才能拼出完整答案，朴素 RAG 一律只检索一次
3. **知识库覆盖有盲区**：知识库不可能有所有答案，找不到时朴素 RAG 要么让 LLM 编造，要么返回风马牛不相及的回答

Advanced RAG 的手段能缓解这些问题，但它们有一个共同假设：**流程是固定的，只是每个环节做得更好**。真正复杂的场景需要「流程本身能根据情况调整」——什么时候该检索、检索结果不行怎么办、需不需要再检索一次，这些决策要系统自己做。

## 三代 RAG 演进

- **Naive RAG**：用户提问 → 向量检索 → 拼 prompt → LLM 生成。逻辑直白、两天能跑 Demo，但什么都没优化——检索召回什么送什么，用户提问差就找得差，全部一股脑塞给 LLM，幻觉和偏差由此而来
- **Advanced RAG**：在「检索前」和「检索后」各加一道工序。检索前加 Query 改写和扩展，检索后加 Rerank 精排和内容压缩。不用改框架，工程改动小、效果提升明显，目前大多数生产系统用的都是这个形态
- **Modular RAG**：不再是固定流程上打补丁，而是**把 RAG 各环节拆成可独立替换的模块，像乐高一样按需组合**。检索模块可选向量检索、BM25 或图检索；改写模块可选 HyDE、Step-back 或多 Query；生成模块可带引用结构化输出。LlamaIndex 的 Workflow 和 LangGraph 都是这个设计思路的实现

## 高级范式

### Self-RAG：LLM 自己决定要不要检索

解决「所有问题都走同一套流程，太死板」的痛点。Self-RAG 训练一个特殊 LLM，自主决定：

- 当前问题需不需要检索？（Retrieval token）
- 检索回来的内容和问题相不相关？（Relevance token）
- 生成的答案有没有幻觉？（Support token）
- 最终答案质量够不够好？（Utility token）

执行流程：

1. **判断是否需要检索**：常识性问题或不需要外部信息就直接生成
2. **检索并逐条评估相关性**：对每个召回 chunk 独立判断是否相关，不相关的跳过
3. **基于相关 chunk 生成候选答案**：每个相关 chunk 各自生成一个候选
4. **评估答案质量**：对每个候选打两个分——有没有文档支撑（防幻觉）、对用户有没有用
5. **选出最优答案返回**

**重要前提**：那四种 reflection token 不是现成 LLM 自带的，需要在一个专门构造的数据集上对基础 LLM 做监督微调，把这些特殊 token 作为新词表的一部分训练进去。Self-RAG 不能拿普通 GPT-4 直接「套用」，要么用论文开源的微调版本（基于 Llama2-7B/13B），要么自己造数据微调。这是它和 CRAG、Agentic RAG 不一样的地方（后两者可在通用 LLM 上直接跑）。

### CRAG（Corrective RAG）：检索质量差时自动纠错

解决「知识库覆盖有盲区」的痛点。CRAG 在检索后加质量评估环节：

- **质量评估**：用轻量级检索评估器（专门训练的分类模型，或 Rerank 模型分数近似）判断检索结果和问题的相关程度
- **三级路由决策**：
  1. 评估为「相关」：直接用本地结果生成
  2. 评估为「不相关」：知识库没覆盖，丢弃本地结果，降级走网络搜索
  3. 评估为「模糊」：本地结果和网络搜索结果合并使用，两者互补
- 判断阈值需按业务场景调，没有固定数值
- **核心价值在于「兜底」**：知识库覆盖不到的问题不会直接乱答，自动去网上找答案，把知识库当主力、网络搜索当备胎

### GraphRAG：用知识图谱增强全局理解

解决「需要全局理解」的问题。普通向量检索只能召回「和问题直接相关的文档片段」，对于「这批文档的核心主题是什么」「A 公司和 B 公司有什么关联」这类问题，只能找到局部信息，无法把散落多处的知识串联起来。GraphRAG 是微软 2024 年提出并开源（论文 2024 年初发布）的方案，组合了知识图谱、社区发现和层次摘要：

- **预处理阶段**：先用 LLM 从文档抽取实体和关系建成知识图谱 → 用 Leiden 等社区发现算法对实体聚类成「社区」→ 对每个社区生成 LLM 摘要（描述实体间关系、整体内容）→ 形成多层级摘要结构
- **检索阶段**，支持两种查询模式：
  - 局部问题（如「A 公司 CEO 是谁」）：在知识图谱中做实体查找和关系遍历
  - 全局问题（如「这些文档的主要主题」）：用 Map-Reduce 方式，先让 LLM 分别阅读各社区摘要提取信息，再汇总生成答案
- **为什么向量检索搞不定**：向量检索是「一对一匹配」，擅长找局部片段，无法理解知识库宏观结构和跨文档关联。GraphRAG 通过预建社区摘要把全局信息提前「蒸馏」好
- 适合：知识关联性强、需要全局视角的场景（金融企业关系分析、医疗药物-疾病-症状关联、大规模文档主题归纳）
- 代价：构建图谱和社区摘要需要大量 LLM 调用，预处理成本较高

### Agentic RAG：把 RAG 做成 Agent

解决「复杂问题需要多轮动态检索」的问题。普通 RAG 是固定的「检索一次 → 生成」，但有些问题需要多轮检索：第一次检索信息不够要追加；结果互相矛盾要再检索验证；问题本身多步骤，每步检索不同内容。

Agentic RAG 把 RAG 嵌入 Agent 循环，LLM 自主决定：要不要再检索一次、用什么关键词检索、检索结果够不够、什么时候生成答案。

执行流程：

1. **接收问题，进入循环**：LLM 拿到问题开始 Agent 决策循环
2. **LLM 决定下一步动作**：根据已收集的上下文判断——信息够了吗？不够下一步搜什么？
3. **执行检索，累积上下文**：按 LLM 指定关键词检索，把新召回的 chunk 追加到已有上下文
4. **重复判断，直到信息充分**：每轮重新评估「现在能回答了吗」，不够继续检索，够了就生成
5. **生成最终答案**：退出循环，基于所有累积上下文生成；设置最大迭代次数防止死循环

适合多步骤推理的复杂问题（如「分析 A 公司最近三年财报，找出营收增速放缓的根本原因」）。

**与前面范式的区别**：Self-RAG 是给 RAG 加「要不要检索」的开关，CRAG 是加「检索不好怎么办」的兜底，Agentic RAG 是把整个检索流程变成可不断循环、不断调整的智能体。

## 范式对比表

| 范式 | 核心创新 | 适合场景 | 工程复杂度 |
| --- | --- | --- | --- |
| Advanced RAG | Query 改写 + Rerank | 大多数生产场景 | 低 |
| Self-RAG | LLM 自主决策检索 | 问题类型多样、部分不需要检索 | 高（需特殊训练模型） |
| CRAG | 检索质量差时降级网络搜索 | 知识库覆盖不全的场景 | 中 |
| GraphRAG | 社区发现 + 层次摘要，支持全局查询 | 实体关系复杂、需要全局理解的场景 | 高（图构建 + 摘要成本大） |
| Agentic RAG | 多轮动态检索 | 复杂多步骤问题 | 中（Agent 框架） |

**面试要点**：不要只罗列名字。要讲清楚每种范式解决了什么痛点、核心机制是什么、适合什么场景。主线是：Self-RAG 解决「不是所有问题都需要检索」、CRAG 解决「检索质量差时怎么办」、GraphRAG 解决「全局理解和跨文档关联」、Agentic RAG 解决「复杂问题需要多轮动态检索」。

# 16. 在什么场景使用图数据库来增强传统的向量检索

当业务问题**涉及多个实体之间的关联推理**时，就需要考虑引入图数据库增强。向量检索有一个根本局限：**无法沿实体关系链做多跳推理**，只能召回与 query 直接相似的文档片段，没办法沿着实体之间的关系链往下追。比如问「公司 A 的投资方和公司 B 有什么交集」，答案不在某一段文档里，而是藏在多个节点之间的关系上，单纯向量检索很难处理。典型场景有企业关系分析、医疗知识图谱、代码依赖关系查询、供应链溯源。

## 向量检索能做到什么、做不到什么

- 向量检索把问题转成向量，找「向量最接近」的文档片段。对「什么是 Transformer」「Python 的 GIL 是什么」这类答案在某段文档里的问题，一跳就找到了
- **根本限制：单跳**。它每次只能找和问题直接相关的内容，无法沿实体关系链往下追
- **为什么多检索几次不行**：多检索的前提是你知道「下一步该搜什么」，但向量检索没有「关系」概念，不知道实体 A 和实体 B 之间有边，更不知道该沿哪条边走。就像在陌生城市问路，别人只告诉你「附近有家店」，不会告诉你「往东走 200 米还有一家」

向量检索答不上来的问题示例：

- 「小米的主要竞争对手的 CEO 是谁」：需要先找竞争对手，再拿名字找 CEO，两步之间有实体跳转，第二跳就断了
- 「治 A 疾病的药和治 B 疾病的药有没有相互作用」：答案藏在「药物 → 作用靶点 → 相互作用」多节点路径上，没有一篇文档直接写出结论
- 「这个函数直接和间接依赖的所有第三方库有哪些漏洞」：需沿代码依赖链一层层展开，每一跳都是新查询

**共同特征**：答案不在某一个文档里，而是藏在多个节点之间的「关系」上，要沿边一跳一跳走才能拼出完整答案。

## 图数据库为什么能解决

- 图数据库专门存「实体和关系」，把世界表示成一张网：每个节点是一个实体（公司、人、疾病、药物），每条边是一种关系（投资、竞争、治疗、副作用）
- 可以做**图遍历**：从一个节点出发沿关系边一跳一跳走，把路径上所有相关节点的信息都收集回来，正好补上向量检索的短板
- **注意**：图数据库不是向量检索的「升级版」，不能替代。传统图查询语言（Cypher）擅长精确关系查询，对「语义相似」这种模糊匹配不擅长（现代图数据库如 Neo4j 虽在加向量索引，但那是把向量检索嫁接进图，不是图遍历本身）。用户问「手机充电慢怎么办」没有明确实体关系可遍历，图数据库帮不上忙，向量检索却能找到语义相近的故障排查文档。**两者是互补关系，不是替代关系**

## 向量检索 + 图数据库的组合用法

1. **向量检索做入口**：用户问「小米的竞争对手 CEO 是谁」，先向量检索找到和「小米」相关的文档片段，识别出关键实体，定位到「小米」节点
2. **图数据库接力做关系遍历**：拿到入口实体后沿关系边走：「小米」→ 竞争关系 →「OPPO、vivo、荣耀」→ CEO 关系 → 对应人名，收集沿途节点信息
3. **合并上下文**：把向量检索结果和图遍历结果合并，一起给 LLM 生成回答

类比：向量检索像「导航定位」帮你找到出发点，图遍历像「沿路线一站一站走」收集沿途站点信息。前者解决「在哪」，后者解决「能到哪」。

## 哪些场景值得用图数据库

- **企业关系分析**（最典型）：金融、投资领域股权关系、任职关系错综复杂。「X 基金投资的公司里有哪些跟 Y 集团存在竞争」这类问题纯向量检索答不上来，图里一趟遍历几秒就出来
- **医疗知识图谱**：疾病、症状、药物、基因有大量关联。「某个基因突变会导致哪些疾病，这些疾病有哪些共同治疗方案」这种多层关系链追溯，图遍历很自然
- **代码知识库**：函数调用关系、模块依赖关系建成图，「这个接口被哪些上游服务直接和间接调用」走一遍就出来
- **供应链溯源**：原材料 → 供应商 → 成品 → 分销商，层级关系天然适合图结构，追溯某批次产品的所有上下游环节，图遍历是最自然的解法

## 什么时候不值得上图数据库

- 图数据库代价不小：需要用 LLM 做实体抽取和关系抽取把非结构化文档转成图结构，成本高、易出错，维护图结构比维护向量库复杂得多
- 如果问题大多数是「找某个概念的解释」「某个功能怎么用」，向量检索 + Rerank 已够用，强行上图是过度设计
- **判断原则**：问题里是否同时出现多个具体实体名，并在问这些实体之间「有什么关系」或「通过关系能找到什么」。是，就值得考虑图增强；主要是找某段描述性内容，向量检索就够

**面试要点**：先讲清向量检索是「单跳」的、没有实体关系概念，不知道往哪跳；图数据库核心价值是沿关系边做多跳遍历，补上关联信息。组合方式是向量检索做入口定位实体、图接力做关系遍历、合并上下文给 LLM。判断标准是问题是否涉及多实体关联推理。

# 17. 如何规避 RAG 系统中大模型的幻觉

RAG 里的幻觉主要有两类来源：

1. **检索没召回到相关内容**：LLM 没有可用上下文，靠自身知识编造答案
2. **检索到了但 LLM 没严格遵循**：在文档内容基础上加了自己的推断

规避策略主要有四个方向：**Prompt 强约束**（明确告知只能根据资料回答）、**检索质量门控**（Rerank 分数低于阈值直接拒答）、**生成后引用核查**（每个关键声明都要在 chunk 里找到依据）、**结构化输出强制溯源**（输出 JSON，每条结论附来源编号）。其中 **Prompt 强约束 + 检索质量门控是成本最低、收效最快的组合**，生产系统上线前必须做。

## 幻觉的两个来源

**第一个误区要先破除**：做了 RAG 不代表没幻觉。塞进 prompt 不等于 LLM 一定「老老实实照着说」。LLM 有自己的预训练知识储备，当资料和它「学到的」不一致，或 prompt 里根本没召回相关内容，它就可能绕开资料自己发挥。

- **来源一：检索层没找到，LLM 靠「猜」回答**。检索失败时 prompt 里是空的或不相关内容，LLM 不会说「我不知道」，而是用训练时见过的知识编一个看起来像答案的东西，说得还很自信。例：知识库记录「7 天无理由退款」，某次没召回到这个 chunk，LLM 给出「30 天退款」的错误答案
- **来源二：检索到了，但 LLM 没有严格照着说**。更隐蔽更常见。相关 chunk 被召回，但 LLM 在生成时「超发挥」——在资料基础上加推断、补充原文没有的细节、把两段不相关信息拼在一起

两种幻觉根源不同，解法不同。下面四个方案从「成本最低」到「机制最严格」递进。

## 方案一：用 Prompt 告诉 LLM「只准照着资料说」

成本最低、最容易上手、效果立竿见影。很多人搭 RAG 只把 chunk 塞进 prompt 然后问「请回答这个问题」，LLM 就会觉得「资料只是参考，可以结合自己知识一起回答」，幻觉由此产生。修复方法是在 system prompt 里立规矩：

```
回答规则：
- 只能使用【参考资料】中的信息来回答，不得引入资料之外的知识
- 如果参考资料中没有足够信息，必须明确回答：「根据现有资料，无法回答该问题」
- 回答时标注信息来源（来自哪条参考资料）
- 不要推断、不要猜测、不要补充资料中没有明确说明的内容
```

每条规则的作用：

- 第一条让 LLM「知道自己的边界」——只是传话人，不是百科全书
- 第二条给 LLM「合法的逃生出口」——资料里没答案时说「不知道」比编一个合理答案好得多
- 第三条让 LLM 主动对照原文，相当于加了一个自检动作

**局限**：能压制「生成层幻觉」，但对「检索层幻觉」帮助有限——prompt 里根本没有相关内容，再强约束也顶不住 LLM 瞎编。

## 方案二：检索质量差时，直接拒绝回答

方案一解决「LLM 超发挥」，但检索这一步就失败时，prompt 里全是无关内容，光靠 Prompt 约束拦不住。与其让 LLM 在低质量上下文强行生成「可能是错的答案」，不如直接告诉用户「知识库里没有这个信息」。

- **怎么判断检索质量**：用 Rerank 模型打分。流程：召回 Top-K 候选 → Rerank 对每个候选打 0-1 相关度分 → 看最高分
- 最高分低于阈值：返回「知识库无相关信息，建议联系人工」，不让 LLM 强行回答
- 最高分达标：把所有达标 chunk 筛出来喂给 LLM
- **阈值怎么定**：没有通用数字，按业务数据调。拿一批「已知答案在库里」和「已知答案不在库里」的测试集跑一遍，看 Rerank 分数分布找切点。经验值 0.3～0.6：精度要求高（金融、医疗）偏高，召回率宽松（闲聊问答）偏低
- **为什么拒答是好的**：用户问知识库覆盖不到的问题，最好的答案是「我不知道，请联系人工」，而不是一个听起来合理但实际错误的答案——**答错比不答更危险**

方案一 + 方案二组合能同时压制两类幻觉：方案二负责「检索质量差时不让 LLM 胡说」，方案一负责「检索质量还行但 LLM 超发挥时把它框住」。这是上线前的基础配置，成本也最低。

## 方案三：答案生成后，逐条核查有没有「凭空捏造」

前两个方案在「生成之前」防控，方案三是「生成之后」校验。思路：LLM 生成答案后，再用另一个 LLM（或同一个 LLM）回头检查，**答案里每条关键信息在 chunk 里有没有对应依据**，没有依据的标注「无法核实」或直接删掉。就像文章写完要请编辑审阅，方案一是事前约束作者行为，方案三是事后审稿。

- 代价：多一次 LLM 调用，响应延迟增加、成本翻倍
- 适用：对准确性要求极高的场景（医疗问诊、法律咨询），答错了代价很大
- 普通企业知识库问答，方案一 + 方案二通常已够用

## 方案四：强制 LLM 输出时带上来源编号

在格式层面做约束，和方案一的 Prompt 约束配合使用效果更好。让 LLM 输出结构化 JSON，每个结论必须填写来自哪条参考资料的编号：

```json
{
  "answer": "完整回答",
  "statements": [
    {"claim": "具体结论1", "source_ids": [1, 2]},
    {"claim": "具体结论2", "source_ids": [3]}
  ],
  "confidence": "high/medium/low"
}
```

**为什么有效**：

1. LLM 构建 JSON 时必须主动想「这条结论我从哪条资料里找到的」，这个过程本身减少瞎编概率——就像让学生写论文必须标注参考文献，自然不敢随便编
2. 系统拿到 JSON 后可以做程序化验证：source_ids 对应的 chunk 和 claim 明显不相关，就自动过滤掉这条结论

## 四个方案怎么组合

- **普通企业知识库和客服问答**：方案一 + 方案二是必须做的基础配置，成本极低，幻觉解决大半
- **可信度要求高的场景**（金融分析、法律文档）：加方案四，让每条答案带来源编号，用户可自行核实
- **准确性要求极高、容错率低**（医疗问诊、合规审核）：四个方案全上，用延迟和成本换最高级别的准确性

**核心认知**：规避幻觉没有一劳永逸的银弹，但**检索质量是幻觉的最大来源**——检索到了正确内容，Prompt 再稍微约束，幻觉就少很多；检索这一步烂，再多的生成层约束也填不了坑。**治幻觉，先治检索。**

**面试要点**：先破除「检索做好了就不会幻觉」的误区，讲清两个来源（检索层没召回 + 生成层超发挥），再给整套防控策略：Prompt 强约束压制生成层幻觉、检索质量门控在检索失败时拒答、生成后引用核查做二次校验、结构化输出强制溯源。成本最低收效最快的是 Prompt 约束 + 检索门控。

# 18. 怎么量化你的 RAG 效果

评估 RAG 效果分两层：**检索层**看该召回的有没有召回到（**Hit@K、MRR**）；**生成层**看答案对不对、有没有幻觉、和问题相不相关（用 **RAGAs 框架**，核心是 Faithfulness、Answer Relevancy、Context Recall 三个指标）。**一定要在自己的业务数据上跑，不能只看通用排行榜**。另外线上指标（用户点踩率、追问率、转人工率）才是最终衡量标准，离线指标只是辅助。

## 为什么需要系统化评估

- 靠「人工抽查几条觉得还行」就上线，问题明显：**靠感觉调优没方向**（改了 Chunking、换了 Embedding 有没有提升，抽查几条说明不了问题）；**出了问题不知查哪里**（不知道是检索没召回、召回但 LLM 编造、还是 Prompt 设计问题）；**优化后无法验证收益**（没有数字，技术决策没说服力）
- RAG 评估比普通任务难：答案是自然语言没有唯一标准答案；出问题不知道是检索层还是生成层的锅；人工标注成本高
- 正确做法是**拆成两层分别评估**，精确定位问题

## 第一层：检索层评估

单独评估检索有没有把正确的 chunk 召回来。需要准备「问题 + 对应正确 chunk ID」的测评数据（从历史问答标注或领域专家整理）。

- **Hit@K**：把 Top-K 检索结果摆在面前，要找的在里面就算命中。回答「找到没」的问题，不关心第几名。**Hit@5 低于 0.7 说明检索层有问题**（考虑换 Embedding 或优化 Chunking）；高于 0.8 说明检索层 OK，答案还不好就是生成层问题
- **MRR（Mean Reciprocal Rank，平均倒数排名）**：关心「要找的东西排在第几名」。对每个问题算 1/排名再求平均：第一名 1 分、第二名 0.5、第三名 0.33。回答「多快找到的」。**MRR 低于 0.5 通常说明 Rerank 效果不够好**（召回了但没排前面）
- 两者配合：Hit@5 = 0.9 说明 90% 的问题前 5 条能找到，但 MRR 只有 0.3 说明相关内容虽然找到但排得很靠后

## 第二层：生成层评估（RAGAs 框架）

RAGAs（Retrieval Augmented Generation Assessment）是广泛使用的 RAG 端到端评估框架，核心思路是 **LLM-as-a-Judge**（用 LLM 当裁判自动打分，不需要人工标注每条）。四个核心指标：

- **Faithfulness（忠实度）**：答案里每件事在检索到的 chunk 里有没有出处。衡量幻觉程度——逐句问「这句话你从哪条资料找到依据」，没有依据的句子越多分越低。**目标 > 0.8**
- **Answer Relevancy（答案相关性）**：答案有没有回答用户问的问题。和 Faithfulness 是两回事——Faithfulness 问「说的是不是真的」，Answer Relevancy 问「说的是不是用户想要的」。答案可以字字有据但完全跑题（问北京天气答北京历史），就是 Faithfulness 高、Answer Relevancy 低。**目标 > 0.8**
- **Context Recall（上下文召回率）**：回答问题所需的信息有多大比例在检索结果里覆盖到。需要有标准答案（ground_truth）作参照，衡量检索层有没有「漏掉该找到的内容」。**目标 > 0.7**
- **Context Precision（上下文精确率）**：检索结果里「有用的内容」排名是否靠前。召回 10 个 chunk，相关的有没有排在前面。Context Recall 关注「该找的有没有找全」，Context Precision 关注「找到的里面相关的是不是排在前面」

**成本控制**：RAGAs 每次评估都要调用 LLM 打分，几千条测试集 token 消耗可观。缓解方式：核心测试集抽样（只跑最有代表性的 200～500 条）；评判模型从 GPT-4o 降级到 GPT-4o-mini（按官方定价便宜约 25 倍以上，精度损失可接受）。

## 用指标定位问题

| 指标 | 低了说明 | 优化方向 |
| --- | --- | --- |
| Context Recall | 检索层没召回正确内容 | 换更强 Embedding、调整 Chunking、加多路召回 |
| Context Precision | 召回太多噪音，不相关混进来 | 加强 Rerank、调低送 LLM 的 chunk 数量 |
| Faithfulness | LLM 在编造，幻觉多 | 加强 Prompt 约束、引用核查、检索质量门控 |
| Answer Relevancy | 答案跑题 | Prompt 指令更明确，要求严格回答问题本身 |

## 线上指标：最终衡量标准

离线指标再好，最终看线上用户反应：

- **点踩率（thumbs_down_rate）**：用户主动点踩，最真实的负反馈
- **追问率（followup_rate）**：用户说「你没回答我的问题」或追问同一问题，反映「答非所问」
- **转人工率（escalation_rate）**：RAG 放弃回答的频率。太高说明知识库覆盖不足；但若因质量门控上升不一定是坏事——宁可转人工也不要给错误答案
- **空回答率（answer_empty_rate）**：系统主动说「我不知道」的比例，过高说明知识库亟需扩充
- **会话解决率（session_resolution_rate）**：最综合的指标，「一次对话能不能解决用户问题」，最贴近用户体验

**注意**：离线指标好不代表线上一定好——离线测试集可能不能完整代表真实用户分布，或离线优化过头损害线上体验（如为追求 Faithfulness 把 Prompt 收太死，模型回答过于保守）。两者要定期交叉对照，发现偏差时往往是测试集需更新或指标权重需调整。

**评估闭环**：离线评估（Hit@K + RAGAs）用来快速迭代和定位问题，线上指标（踩率、转人工率）是最终验收标准。两者结合形成「离线测评 → 上线 → 线上观测 → 发现问题 → 离线复现 → 修复 → 再上线」的完整闭环。

**面试要点**：不能靠「用户投诉」或「人工抽查」这种事后手段。检索层用 Hit@K 和 MRR，生成层用 RAGAs 的 Faithfulness、Answer Relevancy、Context Recall，线上用点踩率、转人工率等业务指标做最终验收。通过指标组合精确定位问题出在检索层还是生成层。

# 19. RAG 知识库如何实现动态与持续更新

知识库更新的核心挑战是：**文档变了，对应的 chunk 和向量都要跟着变，而且要做增量处理，不能每次全量重建**。通用方案是给每个文档算一个内容 hash，通过轮询或监听数据源变更检测到新增、修改、删除，先清掉旧向量再重新切割入库。实时性要求高的场景用消息队列（如 Kafka）做变更事件驱动，实现秒级入库。

## 为什么更新 RAG 知识库比更新普通数据库麻烦

普通数据库更新一条记录直接 UPDATE 就行，数据独立、改一条不影响别的。但 RAG 知识库的麻烦在于：**原始文档和向量库之间不是一对一，而是一对多**。一篇文档切成几十上百个 chunk，每个分别 Embedding 后入库。文档内容一改，切割结果可能完全不同——chunk 数量、边界、内容都变，无法简单「更新一条记录」。

所以 RAG 知识库最可靠的更新逻辑是**「先删后增」**：先删掉旧文档对应的所有 chunk，再重新切割入库，而不是在原有 chunk 上局部更新。理论上 Chunking 策略完全稳定时（如固定 token 窗口切）可做局部更新，但生产环境 chunk 边界一变就全乱套，与其博弈不确定性，不如走「先删后增」简单可靠。

## 三种变更操作

- **新增**：最简单。文档以前不存在，走一遍完整的「切割 → Embedding → 写入」流程，没有历史包袱
- **修改**：最容易踩坑。很多人直觉认为「只改了一段文字就更新那个 chunk」，这个思路行不通——内容一改切割边界就变，原来第 3 个 chunk 的内容可能分散到第 3、4 个 chunk，无法一一对应做局部打补丁。**正确做法是推倒重来**：把这篇文档之前入库的所有 chunk 全部删掉，重新按新内容切割入库。操作暴力但可靠，是唯一不出 bug 的做法
- **删除**：最直接。文档下线就把对应所有 chunk 从向量库清除，不能留「僵尸 chunk」，否则用户仍会检索到失效内容

## 如何检测文档是否变化

最常用方案是**内容 hash**：每次入库时计算文档内容的 MD5 或 SHA256 摘要，把 hash 值和文档 ID、对应 chunk ID 列表一起存下来（Redis 或数据库）。下次检测时重新计算对比：

- hash 相同 → 内容没变，跳过
- hash 不同 → 有更新，触发重处理

hash 运算非常快，哪怕只改一个标点符号 hash 就完全变化，不会漏掉任何变更。

**优化**：先用「最后修改时间」这个轻量字段做粗筛，只对时间戳变化的文档算 hash。如数据源每晚同步一次，上百万篇文档真正改过的可能只有几千篇，能把 99% 的文档过滤掉。

## chunk ID 和文档 ID 的关联设计

删除一篇文档的所有 chunk 时，需要快速找出「这篇文档对应哪些 chunk」。两种常见做法：

1. **chunk ID 带文档 ID 前缀**：如 `product_manual_v3_chunk_001`，按前缀批量查找删除
2. **在 chunk 的 metadata 里存文档 ID 字段**：如 `source_doc_id: "product_manual_v3"`，向量库支持按 metadata 字段过滤批量删除

关键是从一开始就把文档和 chunk 的关联关系设计好，等需要更新时再临时想办法会很狼狈。

## 两种主流的变更感知方式

### 定时轮询（Polling）

- 系统按固定时间间隔（如每天凌晨、每小时）扫描所有文档，对比 hash，把有变化的重新处理
- **优点**：实现简单，不依赖外部系统
- **缺点**：有延迟（文档改完要等下一个轮询周期才生效）；文档量大时全量扫描是开销（大多数文档没变却每次算 hash）
- 适合：文档更新频率低、实时性要求不高的场景（内部知识库、产品文档）

### 事件驱动（Event-Driven）

- 数据源有变更时主动发消息（Kafka、RabbitMQ、Webhook），知识库更新服务订阅消息立即处理
- **优点**：延迟低，文档变更后几秒内生效
- **缺点**：需要数据源支持发消息能力，架构更复杂
- 适合：实时性要求高的场景（客服知识库运营刚更新退款政策要求立刻生效、新闻资讯类新文章发布就入库）
- **轻量方案**：Confluence、Notion、语雀等都支持 Webhook，文档保存时自动推送 HTTP 请求，天然适合事件驱动更新，不需要引入消息队列这么重的组件

## 全量重建：最后的手段

定期把整个知识库推倒重建（所有文档重新切割、Embedding、写入）。**优点**是逻辑最简单：不需要维护文档和 chunk 对应关系、不需要 hash 检测、不用担心旧 chunk 漏删。**缺点**：文档量大时重建消耗大量时间和 Embedding API 费用；重建过程中知识库不可用。

适用场景：知识库规模很小（几十篇文档，重建几分钟搞定）；或做了重大架构调整（换了 Embedding 模型、改了 Chunking 策略），新旧向量不兼容必须全量重建。平时不推荐依赖。

## 灰度更新：稳妥地切换新版本

对于核心生产知识库，直接删旧数据风险太大，万一新切割内容有问题想回滚都来不及。更稳妥的做法：

1. 新版本 chunk 写入时打上 `version=new` 标签，旧版本保留 `version=old`
2. 验证阶段：用一批测试问题同时跑新旧两个版本，对比答案质量，确认没有引入退化
3. 验证通过后：把检索时的版本过滤条件从 old 切换到 new
4. 最后清理旧版本 chunk

类似软件发布的蓝绿部署，好处是：出了问题立刻回滚（切回过滤条件），切换秒级完成，不需要重新入库。对金融、医疗等领域质量要求很高的知识库，这种谨慎策略很有必要。

## 更新方案对比表

| 方案 | 延迟 | 实现复杂度 | 适用场景 |
| --- | --- | --- | --- |
| 定时轮询 | 分钟-小时级 | 低 | 文档更新频率低，实时性要求不高 |
| Webhook 触发 | 秒级 | 中 | 数据源支持 Webhook，如 Confluence、Notion |
| 消息队列 | 秒级 | 中高 | 大规模、高并发更新，生产环境首选 |
| 全量重建 | 分钟-小时级 | 低 | 文档量小，或知识库结构大改，不推荐常用 |

**总结**：生产环境推荐「事件驱动 + hash 变更检测 + 先删后增」的组合方案，兼顾实时性和数据一致性。新增和删除相对简单，修改记住一个原则——**永远先删掉旧的所有 chunk 再重新入库，不要尝试局部更新**，这是最可靠也最不容易出 bug 的做法。

**面试要点**：知识库更新绝对不能尝试「只更新变了的那个 chunk」——文档内容一变 chunk 切割边界就完全不同，没法局部更新。正确做法是 hash 检测变更 + 先删后增；低频场景定时轮询、高频场景 Kafka/Webhook 事件驱动；同时做好 chunk ID 与文档 ID 的关联设计。

# 20. RAG 最难的地方是哪里

RAG 最难的不是把它跑起来（一个基础 Demo 一两天就能搭起来），**难的是把它调好**。工程上最头疼的有三块：**文档预处理**（原始数据格式五花八门，处理不好就是垃圾进垃圾出）、**检索质量调优**（向量召回不准是整个系统的天花板，但问题来源很多，排查费劲）、**效果评估**（答案对不对很难系统性衡量，不知道哪个环节出问题，优化就变成瞎猜）。

## 第一难：文档预处理

文档预处理是最前面的一环，做不好后面所有 Chunking、Embedding、检索、生成优化再牛也难救回来——**给系统喂的原料本身就是烂的**。这是「地基型」瓶颈：地基歪了，上面盖得再漂亮也容易塌。看起简单，实际是最脏最累的工程活。

- **PDF 解析**是最常见问题。pypdf 这类通用 PDF 库做的是文本流提取，遇到带表格、双栏、嵌套的 PDF 会把内容顺序搞乱。例：产品规格表原本三列「型号、内存、价格」，解析出来变成一串乱码「型号内存价格iPhone 158GB5999」，行列关系全没了。这样的内容存进向量库，检索出来也是废的。表格和复杂版面应交给 pdfplumber、unstructured 这类专门优化结构化提取的库
- **扫描版文档**需要 OCR
- **包含大量图片的文档**：图片里的关键信息文本提取不到
- **代码文档**：代码块切割不当会破坏逻辑完整性
- **高价值复杂文档**（合同、财报、专利）：可用多模态模型（如 GPT-4o Vision）理解 PDF 截图，但代价比普通 Embedding 高几十到上百倍，只适合单价高、内容复杂、数量可控的文档

真正的生产系统，文档预处理的代码量往往比 RAG 核心逻辑还多。

## 第二难：检索质量调优

检索质量是整个 RAG 系统效果的天花板——检索召回不到相关内容，后面 LLM 再强也没用。但检索质量差的原因可能来自好几个地方，定位特别麻烦：

1. **Chunking 策略**：chunk 切得不好，问题和相关内容语义对不上。例：用户问「退款流程是什么」，但文档按产品分类组织，退款相关内容被切散在十几个 chunk 里，每个单独看相关度都不高，召回的都是边缘内容
2. **Query 和文档的语义鸿沟**：用户提问口语化，文档是正式技术语言。例：「这个功能怎么用不了」vs 文档「系统故障排查指南」，向量相似度可能不高。解法是 Query 改写，或在存文档时也为每个 chunk 生成几个可能的提问形式一起存（假设性问题增强）
3. **向量检索对精确词语效果差**：产品型号「Pro Max 256GB」、专有名词、缩写，纯向量检索往往不如 BM25。生产环境要做混合检索（向量 + 关键词各召回一批合并去重），效果比单独用任何一种都好

## 第三难：效果评估

检索质量调优费劲，但更头疼的是：**你怎么知道调完之后变好了还是变差了**。单条答案对错人工判断成本高、不同人标准不一样；端到端指标（用户满意度、解决率）反馈周期太长，出问题不知道是 Chunking、检索还是 LLM 生成的锅。

工程上比较实用的做法是**把评估拆成两层**：

1. **检索层评估**：不看 LLM 输出，只看「该召回的文档有没有被召回到」。指标 **Hit@K**——正确答案有没有出现在前 K 条检索结果里。Hit@5 = 0.8 表示 80% 的问题答案出现在前 5 条。可自动化批量跑，快速定位检索是否是系统瓶颈
2. **端到端评估**：用 RAGAs 框架自动打分，三个核心维度：
   - **Faithfulness（忠实度）**：答案有没有编造知识库里没有的内容，高说明模型在复述检索内容没有瞎编
   - **Answer Relevancy（答案相关性）**：答案和问题是否对应，防「答非所问」
   - **Context Recall（上下文召回率）**：检索内容是否覆盖回答问题所需全部知识，低说明检索层遗漏关键信息

三个指标结合基本能定位是检索层还是生成层的问题。

## 总结

RAG 落地最大的感受：**原型 Demo 一两天能跑起来，但调到生产可用的质量水平，往往需要几周甚至几个月的迭代**。每个环节都可以是瓶颈（文档预处理、Chunking 策略、Embedding 选型、检索方式、Rerank、Prompt 设计），任何一个做得差都会拖累整体效果，而且各环节相互影响，没有捷径。

**面试要点**：系统说有三大难点——文档预处理（PDF 表格、扫描件、复杂排版解析不好，垃圾进垃圾出）、检索质量调优（Chunking、语义鸿沟、精确词召回三个问题交织）、效果评估（没有量化指标就不知道该优化哪里）。关键是要能分层、有体系地说明难点，而不是东一榔头西一棒槌地罗列问题。

# 21 为什么Code agent不用RAG而用grep

**Code agent（如 Claude Code）不用 RAG 检索而用 grep，本质是两种不同的设计哲学**：RAG 假设「LLM 不够强，要用工程手段帮它把材料准备好」；Code agent 假设「LLM 已经足够强，工程的角色是给它准备好工具，把决策权还给它」。代码场景是动态、结构化、需要精确的，与 RAG 擅长的「静态文档、自然语言、模糊匹配」正好相反。因此 Claude Code 采用 Grep / Glob / Read 三件套 + 子 agent 探索 + LLM 多轮迭代循环的方案，而不是建索引做向量召回。

## 为什么代码检索必须有这一步

用户让 Code agent「把 UserService 里登录方法改一下」，模型要完成任务，第一件事是找到 UserService 文件、找到登录方法的具体代码——代码都没看到怎么改。但模型不能直接「看」磁盘上的代码，只能看到塞进上下文里的文字。

**为什么不能把整个项目代码全塞进去**：LLM 上下文窗口有限。就算用支持 1M token 的超长上下文模型（约 200 多万字），一个像样点的项目动辄几百万行代码，再算上依赖库源码，远超模型承载量，更别说还要留位置给系统提示、对话历史、工具调用结果。所以代码检索这一步就出来了：**从一堆代码里精准捞出和当前任务相关的几个片段，再塞给模型**。

## RAG 在代码场景的做法（为什么不行）

RAG 在代码场景的工作流四步：

1. **切片（Chunking）**：按函数、类或固定行数（如每 100 行）把代码切成小片段
2. **向量化（Embedding）**：每个片段过 Embedding 模型转成高维向量（语义指纹）
3. **建索引（Indexing）**：所有向量存进向量数据库（Faiss、Pinecone、Milvus）
4. **召回（Retrieval）**：把问题向量化，去库里找最相似的 Top-K 片段，拼进 prompt 给 LLM

RAG 把「找代码」转成了「算相似度」——所有检索逻辑归结为「在向量空间找最近的几个邻居」。在客服问答、FAQ 文档这类场景很好使，但放到代码上有一堆坑：

### 痛点 1：代码不像散文，切不动

- 文章是流式的，拦腰切一刀损失不大，前后段还能独立读；代码有严格结构
- 一个 200 行函数按 100 行切，上半段是 if 开头、下半段是 else 结尾，两个片段都没法用
- 函数 A 调用函数 B，A 和 B 在不同片段时，模型只看到 A 不知道 B 是干嘛的，幻觉概率拉满

### 痛点 2：精确匹配的活，向量干不了

- 向量召回本质是「找相似的」不是「找对的」
- 让 agent「看下 getUserById 函数的实现」，向量召回会找一堆「跟用户相关的查询函数」：getUserByName、getUserByEmail、fetchUserInfo……但你要的就是 getUserById 这一个具体的函数
- 向量擅长「模糊」，代码很多时候要的就是「精确」

### 痛点 3：代码每天在变，索引咋办

- 建好索引后，开发一个 commit 改了 20 个文件、新增 3 个函数，索引怎么办？
- 重建：整个项目重新切片重新 embedding，成本不低，频繁 commit 直接性能爆炸
- 不重建：模型查到的全是旧版本，用过期信息写新代码，不写 bug 都难
- 增量更新：听着合理，但实现一堆边界情况（哪些 chunk 要删、哪些要重算、跨文件引用关系怎么同步），简单事情搞复杂了

### 痛点 4：冷启动慢

- 百万行代码库上跑 RAG，建索引要十几分钟甚至更久
- 用户打开工具看着进度条转、等几分钟才能用，体验直接劝退
- Code agent 的设计理念是「打开就能用」，RAG 不答应

### 痛点 5：黑盒，不可解释

- 向量召回回来 5 个片段，问为什么是这 5 个？没人答得上来
- 出了 bug 不知道从哪儿查起：是召回错了？还是召回对了但模型理解错了？追溯链路非常痛苦

**总结**：RAG 在「静态文档、自然语言、模糊匹配」场景是利器，但代码恰好是反过来的——动态、结构化、需要精确。RAG 在代码上不是不能用，是用得很别扭。

## Claude Code 的反向思路：让模型自己找

程序员定位代码的工作流是：先看目录结构（ls），再 grep 全局搜关键字，grep 出候选文件挨个看，找到后再看上下文。整个过程是「找文件 → 找内容 → 看具体代码」三件套，循环往复。**程序员没有提前给整个项目建索引、做向量化，就是「现用现找」。**

Claude Code 的检索哲学：**让模型像程序员一样自己去找**。不预处理、不建库、不算向量，每次需要代码就实时去现场查。工具就给三个：

- **Glob**：按文件名 pattern 找文件（对应 find）
- **Grep**：按内容关键字找代码（对应 grep -r）
- **Read**：按需读文件内容（对应 cat 和编辑器跳转）

看似原始，但本质是把「找代码」的决策权还给了 LLM——不需要提前猜模型会问什么，模型自己想搜什么就搜什么，搜完看一眼结果再决定下一步。

### Grep：基于 ripgrep，但不是简单封装

既然模型能跑 Bash，为啥还要单独包一个 Grep 工具？三层考虑：

1. **权限统一管控**：Bash 是万能工具，模型理论上能跑任何命令（rm、curl、git push）。把 grep 单独包成工具，相当于在这个高频操作上画一道权限闸门，更安全
2. **输出格式可控**：直接跑 bash grep 输出是一坨纯文本；Grep 工具提供结构化输出——行号、上下文行、按文件分组、支持「只返回匹配文件名」「只返回匹配数量」「返回匹配内容」三种粒度，模型按需选择，token 浪费少
3. **性能**：底层用 ripgrep（Rust 写的），多线程并行、自动尊重 .gitignore（不去搜 node_modules 这类垃圾目录），性能甩老牌 grep 几条街

工具描述里甚至有强硬指令：搜索任务永远使用 Grep，绝不要用 Bash 调用 grep 或 rg——用 system prompt 强制模型走专用工具。

### Glob：按文件名找，按修改时间排序

- 按文件名 pattern 找文件，如 `**/*.tsx`
- 两个小巧思：
  1. **结果按修改时间倒序排列**：大部分时候「最近改过的」就是「跟当前任务最相关的」，是很朴素但有效的启发式
  2. **100 文件硬上限**：超出截断，避免输出爆炸把上下文塞满；模型想看更多可收紧 pattern 再搜

### Read：按需读取，绝不贪心

- 默认只读 2000 行，超出截断。文件 5000 行怎么办？模型可指定 offset 和 limit 参数分段读取：先读 1～2000 行看结构，确定位置后 `offset=3500, limit=500` 精准读那一段
- 核心思想：**模型应该按需读取，不要贪心**——引导模型形成节约 token 的习惯
- 关键细节：每次直接 stat 磁盘文件、读取最新内容，**不缓存、不索引、不预处理**。刚改的文件下一次 Read 立刻能看到新内容，这是实时性的来源——没有索引层就没有索引滞后

### 三件套的组合用法

举例「这个项目登录功能在哪实现的」：

1. **Glob** 找候选文件，如 `**/*login*.{ts,tsx,js}`，可能拉回 5 个候选
2. **Grep** 在这些文件里搜关键字（passport|auth|login），定位到具体命中行
3. **Read** 读命中文件的相关行段，看具体实现

整个过程是模型一步步推进的：**每一步看到上一步的结果，决定下一步搜什么、读什么**。没有「一次性召回所有相关代码」的步骤，这是和 RAG 范式最大的不同。

## 当三件套不够用：派子 agent 去探索

「调研一下整个项目的认证模块流程」这类任务需要看的东西多——grep 好几个关键词、读好几个文件、来回比对、最后总结结论，整个过程十几个工具调用。如果让主 agent 自己干，**主 agent 的上下文很快被一堆 grep 输出和文件片段塞满**，真正要解决的问题被检索过程的中间结果挤到角落，模型注意力被分散，质量直线下降——这就是大型探索任务的最大敌人：**上下文污染**。

Claude Code 的解决办法：**派一个子 agent 出去探索**。类比：老板要做战略决策要看大量市场数据，不会自己一头扎进 Excel 翻几个小时，而是派秘书「你帮我调研一下，明天给我一份精简报告」。秘书看了一堆资料，最后只把结论给老板，老板的注意力（主 agent 的上下文）就被保护起来了。

子 agent 派遣机制：

1. 主 agent 通过 Agent 工具派子 agent，子 agent 是独立运行实例，有自己的对话上下文，与主 agent 完全隔离
2. 子 agent 拿到精简的工具池——通常是只读工具（Grep、Glob、Read、只读 Bash），但不能 Edit、不能 Write、不能再派子 agent（防止层层嵌套递归），这种 agent 在源码里叫 **Explore agent**
3. 子 agent 在自己的上下文里多轮迭代，grep 几十次、read 几十次，中间结果都留在自己上下文里
4. 子 agent 完成后只把最终结论返回主 agent——主 agent 上下文里只多了一段精简结论，所有搜索过程都被压缩没了

这就是**上下文压缩的精髓**：用一个隔离的子 agent 把脏活儿干了，主 agent 只接收干净的结论。

**使用原则**（工具描述里的引导规则）：简单、明确目标的代码搜索直接用 Grep/Glob/Read；范围更广的代码库探索和深度研究用 Agent 工具 + subagent_type=Explore。临界点大概是「预期超过 3 次查询」：少于 3 次别折腾派 agent，多于 3 次就别污染主 agent 上下文。

**加分项**：子 agent 可以并行派多个——同时调研「认证模块」「支付模块」「订单模块」三块，一次派出三个子 agent 各干一块，干完同时回来报告，并发探索极大缩短整体时延。

## LLM-driven 的多轮迭代循环

什么让 Code agent 能「自己探索」？是**多轮迭代**这一层。

- RAG 的范式是「考试发卷子」：用户提问 → 系统一次性召回 Top-K → 模型一次性生成答案。中间没有循环、没有反悔，是一次性的、不能中途调整
- Code agent 的范式是「现场探案」：用户提问 → 模型说「我先 Grep 一下」→ 系统执行返回结果 → 模型看到结果说「UserService 比较像，我 Read 一下」→ 系统执行 → 模型说「找到了」。是循环、是边查边推理

这个循环本质是 query 主流程里的 while 循环：模型每轮说话（可能带 tool_use）→ 执行工具 → 把结果回填到对话历史 → 模型继续，直到模型自己说「我搞定了」循环才停下。**它给了模型在每一步根据上一步结果调整方向的能力**：

- Grep 结果是空的？改个关键字再搜
- Read 出来的代码逻辑不像以为的？再 Grep 几个相关函数
- 发现这个文件引用了另一个文件？跟过去看下那个文件

这种「走一步看一步」的能力，是 RAG「一次召回」给不了的：**RAG 召回错了就是错了，模型只能将错就错；Agent 召回错了，下一轮自己就调整了**。grep 本身不强，但「让 LLM 自己决定每一轮 grep 什么」就强了。

## 回到原题：为什么 Code agent 不用 RAG

Claude Code 不用 RAG 主要有六个原因：

1. **冷启动**：grep 毫秒级响应、开箱即用；RAG 要先建索引、分钟级冷启动
2. **实时性**：grep 每次现读磁盘最新版本；RAG 索引会滞后，文件改了得重建
3. **精确性**：grep 是确定性的字符正则匹配，要找 getUserById 就只有它；RAG 是向量近似匹配，会把一堆相似函数糊在一起
4. **Token 经济**：grep + Read 按需读取，模型只看真正需要的几行；RAG 一上来就要给整个代码库做 embedding，存储和计算成本都不小
5. **可解释性**：grep 每一步检索过程对用户透明可审计；RAG 的 Top-K 召回是黑盒，出 bug 没法 debug
6. **决策权**：grep 让 LLM 自己决定每一轮搜什么读什么，多轮迭代逐步逼近答案；RAG 一次性把材料丢给模型，模型只能将错就错

再升一层，两种方案代表两种设计哲学：

- **RAG 派**：LLM 不够强，要用工程手段帮它把材料准备好——chunking、embedding、向量召回，本质都是「替模型做决定」
- **Claude Code 派**：LLM 已经足够强，工程的角色是给它准备好工具、把决策权还给它——grep 不替模型做任何决定，只是个工具，用不用、什么时候用、怎么用全是模型说了算

Anthropic 押注「模型会越来越强」，选择信任模型的判断能力，是长期主义的选择。

## 那 RAG 是不是该被淘汰了

不是。RAG 仍然有它的舞台，只是不在 Code agent 这种场景里：

1. **巨型代码库 + 跨仓库检索**：大公司有几十个 monorepo、上千万行代码，靠 grep 在整个公司代码库搜性能扛不住，建好索引的 RAG 有用武之地
2. **纯语义查询**：「找一下处理用户认证相关的代码」这种描述性、模糊性问题，用关键字 grep 不好搜，向量召回有优势
3. **多人协作的知识库类查询**：代码 + 文档 + Wiki 全部混合检索，这种场景 RAG 合适

而 Claude Code 这套方案，最适合单项目、探索式开发、需要精确性、要求实时性的场景——恰好是大部分 AI 编程工具的主战场。**工具是为场景服务的，没有银弹。**

**面试要点**：不要只回答「grep 快 RAG 慢」。主线是：代码场景需要精确、动态、实时，与 RAG 擅长的模糊匹配、静态文档相反；Claude Code 的核心不是「用 grep 代替 RAG」，而是「让 LLM 自己在多轮循环里决定每一步搜什么读什么」——把检索决策权还给模型。最后要能说出 RAG 仍然适合的场景（巨型代码库、语义查询、知识库混合检索），体现辩证理解。

# 22 RAG全链路优化

RAG 全链路优化，就是**从「文档入库」到「答案生成」的整条流水线上，逐环节定位瓶颈并做系统性优化**。RAG 系统的效果是「短板效应」——任何一个环节弱都会拖垮整体，所以不能只盯着检索或只盯着 Prompt，而是要把**离线建库、在线检索、生成输出**三段全链路都优化到位。我的做法是：先建立评估体系量化每个环节，再按「链路图上每一点都能说出优化手段」的方式逐段排查。

## 全链路优化框架

完整的 RAG 链路分为三个阶段，每段都有自己的优化点：

1. **离线建库阶段**：文档预处理 → 文档切割（Chunking）→ 向量化（Embedding）→ 索引入库
2. **在线检索阶段**：Query 处理 → 向量/关键词多路召回 → 精排（Rerank）
3. **生成输出阶段**：Prompt 拼装 → LLM 生成 → 输出校验/溯源

## 阶段一：离线建库优化

### 文档预处理

- 用专门的结构化解析工具（pdfplumber、unstructured）处理表格、双栏、扫描件（OCR），保证进库的是干净文本——**垃圾进垃圾出**，这一步是地基
- 高价值复杂文档（合同、财报）可用多模态模型理解 PDF 截图，但成本高，只对少量高价值文档用

### 文档切割（Chunking）

- 按文档结构选择策略：纯文本用固定大小 + 重叠兜底，结构化文档用语义边界切割，代码按函数切，高质量场景用父子切割（小块检索、大块返回）
- 用 **Small-to-Big** 思想解决「检索粒度 vs 上下文完整性」的矛盾
- 用 Contextual Retrieval 在向量化前给每个 chunk 补背景上下文，解决孤立 chunk 失去语境的问题

### 向量化（Embedding）

- 选型：中文场景 BGE / Qwen3-Embedding，中英混合 bge-m3，数据不能出境必须开源本地部署
- 在**自己的业务数据上跑 Hit@K 测试选型**，不只看 MTEB 排行榜
- 注意：在线查询必须用与建库完全相同的 Embedding 模型，换模型要全量重建库

### 索引入库

- 向量数据库选型（Chroma/Qdrant/Milvus/Pinecone/pgvector）按数据规模、部署方式、混合检索需求定
- 索引参数调优：HNSW 的 M、ef_construction、查询 ef 在「召回率 vs 延迟 vs 内存」间平衡
- 数据量级大时开启量化（SQ8）降低内存占用

## 阶段二：在线检索优化

### Query 处理

- 口语化、带指代的问题做 **Query Rewrite**（直接改写、HyDE、Step-back、多 Query 扩展）
- 目的是弥合用户提问和文档表述之间的语义鸿沟

### 多路召回

- **向量检索 + BM25 关键词检索**并行召回，互补「语义」和「精确词」盲区
- 用户提问风格多变时再加**多 Query 扩展**，扩大覆盖
- 多路结果用 **RRF 融合**（只看排名不看原始分数，k 取 60）

### 精排（Rerank）

- 用 **Cross-Encoder** 模型（如 BGE-Reranker-v2）对粗召的 Top-20\~30 精排，选出 Top-3\~5
- 解决「Lost in the Middle」（上下文太长时模型忽略中间内容）和 token 浪费问题

## 阶段三：生成输出优化

### Prompt 拼装

- 明确约束：**只根据资料回答、资料没有就说不知道、回答标注来源**，抑制幻觉
- 控制送入 LLM 的 chunk 数量和长度（过长会增加延迟和成本、引入噪音）

### 生成与校验

- 幻觉防控四件套：Prompt 强约束 → 检索质量门控（Rerank 分低拒答）→ 生成后引用核查 → 结构化输出强制溯源
- 需要溯源时让 LLM 输出 JSON，每条结论附 source_ids，系统可程序化验证

### 性能优化（延迟）

- **缓存**：高频 Query 的检索结果和生成结果缓存，命中直接返回
- **并行化**：向量检索和 BM25 并行执行，延迟取最大值而非相加
- **流式输出**：用 SSE 流式返回首 token，提升用户体感
- **模型降级**：简单问题用快速小模型，复杂问题用大模型（路由）

## 全链路优化怎么落地

1. **先量化**：建立两层评估体系（检索层 Hit@K/MRR，生成层 RAGAs 的 Faithfulness/Answer Relevancy/Context Recall），上线后看线上指标（点踩率、转人工率）
2. **逐环节排查**：指标低了定位到具体环节——Context Recall 低查 Chunking/Embedding/多路召回，Context Precision 低加强 Rerank，Faithfulness 低加强 Prompt 约束和检索门控
3. **组合优化**：单独优化一个环节效果有限，要组合——典型生产配置是「Parent-Child 索引 + 向量 BM25 多路召回 + Rerank 精排 + Prompt 强约束 + 检索质量门控」
4. **迭代闭环**：离线测评 → 上线 → 线上观测 → 发现问题 → 离线复现 → 修复 → 再上线

**面试要点**：不要把 RAG 优化理解成「调 Prompt 或换模型」的单点操作，而要给出全链路的框架——离线建库（预处理、Chunking、Embedding、索引）、在线检索（Query 处理、多路召回、Rerank）、生成输出（Prompt、幻觉防控、性能优化）三段各有优化手段，并且要用评估指标驱动、组合优化、迭代闭环。

# 23 检索召回量如何平衡精度、延迟与成本

在 RAG 里，检索召回量、上下文窗口、精度、延迟、成本之间存在根本矛盾：**召回量越大，越可能覆盖正确答案（精度高），但送入 LLM 的上下文越长，token 成本越高、延迟越大，还可能因为「Lost in the Middle」反而降低精度**。平衡的思路不是「一刀切定死一个数」，而是**分层控制、动态调整、按需取舍**。

## 先看清矛盾

- **精度 vs 成本**：Top-K 越大，正确答案被召回的几率越高，但塞进 prompt 的 token 越多，成本线性上升
- **精度 vs 延迟**：K 大 → 要读的上下文长 → LLM 生成延迟高；且 Rerank 要对更多候选打分，耗时增加
- **上下文长 vs 精度**：上下文过长时 LLM 出现「Lost in the Middle」——只关注开头结尾，中间的有效信息被忽略，精度反而下降
- 所以**不是 K 越大越好**，关键是把「有限上下文预算」花在刀刃上

## 第一层控制：召回端分阶段「先粗后精」

核心思路是**把召回分成粗排和精排两段，粗排广撒网、精排收窄**：

1. **粗排阶段放宽 K**：向量检索 + BM25 多路召回，每路召回 Top-50\~100，保证覆盖（不送 LLM）
2. **精排阶段收窄 K**：用 Cross-Encoder Rerank 只对粗排候选（Top-50\~100）打分，选出 Top-3\~5 送 LLM

这样既保证了「正确答案没被提前丢掉」（粗排放宽），又控制住了「进 prompt 的只有最相关的几条」（精排收窄）。**把精度保障放在粗排，把成本/延迟控制放在精排**，两个目标各由一段承担。

## 第二层控制：检索质量门控 + 动态 Top-K

- **检索质量门控**：Rerank 分数低于阈值直接拒答「知识库无相关信息」，避免用低质量上下文浪费成本还给出错误答案
- **动态 Top-K**：不是所有问题都要 5 条上下文——简单问题 2\~3 条就够，复杂问题才需要更多。可以让 LLM 或规则判断问题复杂度，动态决定送入的 chunk 数量。也可以用 Rerank 分数的分布来判断：分数断崖式下降处就是 K 的合适取值（只保留分数明显高的那批）

## 第三层控制：上下文压缩与精炼

在把 chunk 送进 LLM 之前做压缩，用更少的 token 承载同样的信息：

- **基于摘要压缩**：先让 LLM（或抽取式方法）把每段 chunk 压缩成摘要/要点，只送摘要。代价是多一次 LLM 调用，但送入主模型的 token 大幅减少
- **只送关键片段**：用句子窗口/父子切割思想，检索命中后只送最相关的段落而不是整块大 chunk
- **去重与合并**：多路召回中重复、高度重叠的 chunk 先合并去重，避免同样的信息占两份 token
- **引文压缩**：对带引用的输出，只保留必要来源

## 第四层控制：缓存与并行（压延迟）

- **结果缓存**：高频 Query 的检索结果、甚至最终生成结果缓存，命中直接返回，零延迟零成本
- **检索并行**：向量检索和 BM25 并行执行，延迟取最大值而非相加
- **流式输出**：首 token 快速返回，长生成也不影响体感
- **模型分层**：简单问题走小模型（快、便宜），复杂问题走大模型，成本弹性控制

## 平衡决策的落地方法

1. **量化权衡**：用评估指标（Hit@K、RAGAs 分数）配上线指标，确定基准——在精度达标（如 Faithfulness > 0.8、Hit@5 > 0.8）的前提下，尽量压 K 和上下文长度
2. **做消融实验**：分别测 K=3/5/8/10、不同上下文长度下的精度、P50/P99 延迟、单次成本，画出「精度-成本-延迟」曲线，找拐点
3. **按场景给预算**：对延迟敏感的场景（对话式）K 取小、优先缓存流式；对精度敏感的场景（金融医疗）K 适当放大、接受更高延迟成本

**面试要点**：先讲清矛盾本质——不是 K 越大越好，上下文过长还会因 Lost in the Middle 降精度。再给四层平衡手段：粗排放宽精排收窄的「先粗后精」、检索质量门控 + 动态 Top-K、上下文压缩精炼、缓存并行压延迟。最后强调要用消融实验和量化指标找精度-延迟-成本的平衡点。

# 24 如何提升问答准确率、优化链路降低推理延迟

**重排（Rerank）优化是提升 RAG 问答准确率最直接的手段**，链路优化则是降低推理延迟的工程重点。准确率的关键是「送进 LLM 的都是最相关的少数几条」；延迟的关键是「该并行的并行、该缓存的缓存、该提前算的提前算」。两者不是互相拆台——**好的重排能减少送入 LLM 的噪音，反而降低无效上下文带来的延迟和成本**。

## 一、重排策略优化（提升准确率）

### 为什么需要独立的重排层

- 向量检索（Bi-encoder）把 query 和 chunk 分开编码再算余弦，快但看不到两段文字的具体词级交互，相关性判断粗糙
- 重排（Cross-encoder）把「query + chunk」拼在一起整体编码，能看到 query 中每个词对 chunk 的影响，判断精度远高于 Bi-encoder，但慢，只适合对小候选集做精排
- 所以流程是：向量检索粗排召回 Top-20\~50 → Cross-encoder 精排 → 取 Top-3\~5 送 LLM

### 重排模型选型与优化点

- **选型**：开源用 BGE-Reranker-v2（中英双语效果好）、BCE-Reranker；API 用 Cohere Rerank、Jina Reranker
- **与 Embedding 模型匹配**：重排模型建议选和业务数据同域、和 Embedding 模型兼容的版本；中文场景 bge-reranker 系列配 bge 系列 Embedding 效果更稳
- **候选集规模权衡**：精排候选太少（如只排 5 条）可能把正确答案挡在外面；太多（如 200 条）精排耗时线性增长。通常 20\~50 是合理区间，可用 Rerank 分数分布判断（分数明显断层的点之后可以截断）
- **分数门控**：重排最高分低于阈值直接拒答，避免低质量上下文进入生成

### 提升重排精度的技巧

- **拼接质量**：给重排模型拼接时，用「query + chunk」的标准格式，有些模型支持加指令（instruction）提升效果
- **多路重排融合**：可以综合「语义重排分数」和「关键词相关分数」，或用多个重排模型投票，稳定性更好（成本更高）
- **迭代反馈**：把线上 bad case（正确答案没排到前面）收集起来重训或微调重排模型，或调整阈值
- **与 Prompt 配合**：重排只保证「进 prompt 的相关」，生成质量还要靠 Prompt 约束（只根据资料回答）+ 溯源

## 二、链路优化（降低推理延迟）

### 检索阶段压延迟

- **并行化**：向量检索和 BM25 关键词检索并行执行，延迟从串行叠加变成取最大值
- **缓存**：高频 Query 的检索结果缓存（内存/Redis），命中直接返回；文档向量预计算好存库（查询只算 query 向量）
- **索引调优**：HNSW 的查询 ef 参数调小可加快查询（召回率略降），用「粗排放宽、精排收窄」保证精度不损

### 生成阶段压延迟

- **模型分层路由**：简单问题走快速小模型，复杂问题走大模型；或用 LLM 路由器判断
- **减少送入的上下文**：重排只送 Top-3\~5（重排也帮了延迟），配合上下文压缩（摘要、关键片段）减少生成输入长度
- **流式输出（SSE）**：首 token 快速返回，长内容边生成边推送，体感大幅提升
- **生成缓存**：完全相同的 Query 直接命中历史生成结果
- **Prompt 精简**：固定指令部分用 Prompt Caching，减少重复计费；动态部分最小化

### 工程级优化手段

- **预计算与预处理前置**：把能提前算的都提前算——文档向量离线算好、Query 改写可预生成高频问题变体
- **异步化**：非关键路径（如日志、指标上报）异步处理，不阻塞主链路
- **服务架构**：检索服务和生成服务分开部署，检索服务水平扩展扛并发；读写分离（Milvus）保证写入不影响查询
- **指标监控**：分环节埋点（检索延迟、精排延迟、生成 TTFT/TBT、单次成本），持续观测定位瓶颈

## 准确率与延迟的协同优化

- **重排帮助延迟**：高质量重排减少送入 LLM 的噪音 chunk，token 少了生成就快、成本就低
- **门控帮助质量**：检索质量门控既提升准确率（不答错），又省成本（不浪费在低质量上下文）
- **评估闭环**：用 RAGAs 指标 + 线上点踩率/转人工率验证优化是否真的提升了准确率；用 P50/P99 延迟和单次成本验证链路优化效果。**优化一定要用数字验证，不能靠感觉**

**面试要点**：分两块讲——重排策略（为什么需要 Cross-encoder 独立精排、模型选型、候选集规模权衡、分数门控、bad case 迭代）和链路优化（检索并行、结果缓存、模型分层路由、流式输出、预计算前置）。最后点出两者协同：重排减少噪音既提升准确率又降低延迟成本，用指标闭环验证。
