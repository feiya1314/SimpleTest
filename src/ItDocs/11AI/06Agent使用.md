# AI的边界

AI 可以放大开发者的能力，但软件原有的设计，决定了这种放大最终能够到达哪里。

AI 最擅长的并不是替你决定系统应该如何设计，而是在设计已经清晰、约束已经明确之后，快速复制正确的模式，把剩下的业务代码补齐。人负责建立正确的模型和约束，AI 负责高速展开实现。

AI 对我而言，至少有两个已经非常明确的价值：加速理解，以及加速代码生成。前者让我更快地读懂已有系统、讨论方案、验证设计；后者则是在模型和约束确定以后，迅速把设计展开成代码。这样，开发效率和代码质量才有可能同时得到保证。

如果不想理解，只想让 AI 生成代码，代码质量其实非常容易失控。好在随着大模型越来越强，人和 AI 之间的对齐成本也会逐渐降低：你表达出的设计意图越准确，AI 实现出来的结果就越接近你的预期。


不断问自己：为什么要这样设计？有没有更简单的方式？这个抽象以后能不能站得住？这些问题不是单纯生成代码能解决的。它们需要你在真实项目里反复碰撞。


AI 编程的一个核心原则是：先做最小、核心、可验证的东西。软件开发本质上是在对抗复杂性。

编程不是一次性把目标完整实现出来，而是在构建一个系统，并且一步步逼近目标。

所以不管是目标设计，还是实现过程，我都会先收敛到一个最小的核心闭环，并且保证它可以被验证。后面的打磨和扩展，都围绕这个闭环继续推进。

那人类工程师到底在干啥？从他们这套实践里，你能看到工程师的工作重心其实都压在了三件事上面：

把产品目标拆解成 Agent 能力边界内的小任务，确保每一件事都是 Agent 接得住的

当 Agent 反复失败时，不是去催它「再努力一点」，而是去看它「环境里缺了什么能力」，然后把那个能力补进环境里

建立反馈链路，让 Agent 真正能看到自己工作的结果，而不是两眼一抹黑地瞎跑

你看出第二条的意思了吗？这其实是一次思维方式的根本转变。

以前遇到 Agent 写代码有 bug，传统做法是加一句提示词「请仔细检查代码不要有 bug」，然后祈祷模型这次听话。

而 Codex 团队的做法是：给 Agent 接上 lint、单测、运行环境，让它自己写完自己跑，看见 bug 自己改。同样一个问题，前者是在求模型发挥，后者是在改造环境，彻底决定了 Agent 下次会不会再犯。


你会发现一个很微妙的变化：你花在「亲手写代码」上的时间越来越少，花在「写规则、写流程、设计环境」上的时间越来越多。

OpenAI Codex 团队那几个工程师能撬动百万行代码，靠的就不是键盘敲得快，而是把 Agent 的运行环境设计到位。

写代码这件事本身会越来越多地交给 Agent，但设计一个能让 Agent 高质量产出的环境，这件事在很长一段时间里都得是人来做。这可能就是未来程序员真正的主战场。


### 注意力稀释

当上下文达到大约 10 万 token 时（无论上下文窗口是 20 万还是 100 万，这个拐点大致相同，约占 40%），LLM 开始变"笨"。持续向同一上下文添加内容，它会越来越笨，直到做出愚蠢的决定。

**应对方法：** 把任务控制在智能区内，不要让 AI"贪多嚼不烂"。这对应着 Martin Fowler 在《重构》和《程序员修炼之道》中的经典建议：保持任务足够小，让人类开发者也不至于慌乱、掉入愚蠢区。

**大任务如何拆分：**

- 一种方式是不断继续，进入愚蠢区后压缩上下文，再继续。这种方式效果不佳。
- 另一种方式是使用多阶段计划（multi-phase plans），把大任务拆成小块，每块都在智能区内完成。
- 更进一步，任何有经验的开发者都会意识到：多阶段计划本质上是一个循环。与其写死阶段一、二、三、四，不如设定"阶段 n"——在后台维护一份计划，然后在计划之上循环，直至完成。

这引出了 Ralph Wiggum 实践：只需指定旅程的终点——创建一份 PRD（产品需求文档）描述目的地，然后让 AI 每次做一个小改变，逐步接近终点。Matt 认为 Ralph 模式可行，但他个人更喜欢多一些结构。


### 持续遗忘

LLM 会不断"忘记"之前的对话，就像电影《记忆碎片》（Memento）的主角一样，总是重置回基础状态。

每个 LLM 会话都会经历相同阶段：

1. **系统提示（system prompt）**：始终存在于上下文中。它应尽可能小——如果有人往里面塞 25 万 token，就会直接掉入愚蠢区，什么都做不了。
2. **探索阶段**：编码代理去探索代码库。
3. **实现阶段**：编写代码。
4. **测试阶段**：运行反馈循环，确保代码正常工作。

**清除上下文（clear）与压缩（compact）：** 清除上下文会回到最初的系统提示状态；压缩则会把整个对话历史挤压成一份书面记录。很多开发者喜欢压缩，但 Matt 讨厌它——他更喜欢 AI 像《记忆碎片》主角一样，每次状态都完全相同。如果能做到这一点并围绕它优化，就会处于很好的状态。

**关键信息：** 每次会话都要知道当前消耗了多少 token（Claude Code 的状态栏会显示精确数字），以便知道离愚蠢区有多近。


### Spec驱动的问题

Grill Me 技能非常小，作用是防止与 AI 协作时最重要的问题之一：**目标错位（misalignment）**。

**反对的实践——"从规格到代码"（specs to code）：** 一些人主张：要构建应用，先写规格文档，然后把文档交给 AI 转成代码。如果代码有问题，不看代码，回去改规格，如此循环。这本质上是另一种形式的"vibe coding"——完全忽略代码。Matt 尝试过，发现行不通，因为**你必须掌控代码**——理解其中的内容、塑造它，因为代码是你的战场。

**Grill Me 的做法：**

1. 清除上下文。
2. 调用 grill me 技能，传入客户需求（如 Slack 消息）。
3. LLM 先派一个子代理（sub-agent）探索代码库。子代理拥有独立的上下文窗口，探索后把重要信息以摘要形式回传给主代理，本质上是一种委托。
4. 然后开始逐一提问（一次一个问题），每个问题同时给出推荐答案。问题可能多达 40、80 甚至 100 个。

**设计概念（design concept）：** Frederick P. Brooks 在《设计的设计》中提到：当一群人共同构建新事物时，参与者之间会共享一个"设计概念"。Matt 意识到，他与 Claude 协作时需要的不是一个计划、一个产物，而是与 AI 达成共同的"波长"（shared understanding）。Grill Me 就是达成这种对齐的高效方式。

**Grill Me 的扩展用法：** 与领域专家（如客户 Sarah）开会后，可以把会议记录喂给一个"拷问会话"，检验那些你没想到的假设。这能把来自外界的输入转化为经过验证的资产。

**适用场景：** 有听众提问说，Grill Me 提的许多问题更适合产品经理（PO）而非开发者。Matt 认为，这种"拷问"式协作可以类比结对编程——房间里多了一个不断追问你的第三方。关于实现的问题，应该是你、同行开发者与 AI 三方讨论；关于领域知识的问题，应该是你、领域专家与 AI 三方讨论。关键决策需要大量人类参与，甚至可以变成"群体编程"（mob programming）式的 AI 协作。

**停止时机：** Grill 会话可能异常密集，AI 会没完没了地问。这些技能是可调优的——如果 AI 逼得太紧，可以直接告诉它收敛一点、设定停止点。


### PRD维护

PRD 的功能就是记录"目的地"。具体格式无所谓，可以用自己偏好或公司使用的模板。**整个过程只是在总结已有的设计概念。**

PRD 的典型结构：

- 问题陈述（problem statement）：用户面临的问题
- 解决方案（solution）
- 一组用户故事（user stories）
- 已做出的实现决策（implementation decisions）
- 关键的测试决策（testing decisions）

Matt 通常先做 Grill 会话，再写 PRD。写 PRD 时 AI 会：先要一份对问题的详细描述 → 探索代码库 → 再次拷问用户 → 套用 PRD 模板。

**Matt 通常不读 PRD：** 因为 LLM 非常擅长总结。既然已经通过 Grill 会话与 LLM 达成了共享的设计概念，再读 PRD 只是在检验 LLM 的总结能力。但他会关心 AI 提出的"拟修改模块清单"——因为这不是 specs to code，在整个过程中都要把代码放在心上。

**负决策的保留：** 关于如何保留"决定不做的事"，PRD 中有专门的"范围之外（out of scope）"部分，这对定义"完成"（definition of done）非常重要。

**PRD 文档的保存：** Matt 倾向于不把 PRD 长期保存在仓库里，因为代码演化后文档会腐烂（doc rot），过时的文档反而会误导 AI。他使用 GitHub Issues 管理，完成后直接标记为 closed（已关闭）——AI 仍可获取，但能直观看到它已过期。

### 5 **、code review，** 根据需求的编号或者问题单号，进行代码review

AI 一分钟能吐出几百上千行代码，你还一行一行盯着看，最后只会把自己变成整个开发流程的瓶颈。

人类读代码太慢了，如果还逐行审查，就丧失了用 AI 的意义。

以前最看重的是读代码、写代码，现在可能正在变成写测试、定约束、设指标。

#### **一、三方面 通过三个subagent 去执行**

1. **业务方面：** 需求实现是否符合spec要求，满足业务要求
2. **质量方面：** 代码可读性、可维护性、异常处理、日志打印、注释是否合理、命名、与现在代码风格是否一致、圈复杂度
3. **技术方面：** 是否考虑并发安全、资源生命周期、性能、事务、网络、降级、容错等方面

agent执行流程：

```plaintext
Step 1：读取需求
Step 2：读取变更代码
Step 3：读取相关上下文
Step 4：建立检查项
Step 5：逐项审查
Step 6：只报告有证据的问题
Step 7：给出风险等级
Step 8：给出修复建议
```

#### **二、Reviewer 必须“基于证据”，** 不允许 **可能存在并发问题** 。

#### **三、review agent 执行完后，主agent根据审核结果，继续修改，循环**

这里每次subagent执行完后把报告展示，涉及到 **高风险的情况，比如并发安全、数据库事务、性能等由人工确认后继续执行。**给出修复建议，而不是直接自己改代码

#### **四、限制**

- **定义PASS标准** ，AI 很容易吹毛求疵，可以分级别，比如 阻塞、严重、一般、普通。如果把一般以上修复即可结束
- **限制循环次数** ，比如最多三次，不过agent由于可能上下文疑问，控制不准，实现精准控制比较复杂，目前是人工确认

### 6、bug修复

1. 根据错误现象，给出正确的标准，什么是正确的
2. 尽可能先复现bug，**和用户描述完全一致**，不能是碰巧出现的其他问题
3. 在缺失关键信息时，明确要求需要提供哪些方面的信息，而不是靠瞎猜
4. 给出修复方案
5. 先写回归测试，再实现修复代码。

结果呢？Agent 更糊涂了。

为啥？因为上下文窗口是稀缺资源。这个文件被当作系统提示词每次都注入进去，当它变得越来越长的时候，模型的注意力被严重稀释。它看到的东西太多，反而抓不住当前任务真正需要的那部分。

这其实就是我们前面讲过的「上下文腐化」在规则文件这个场景的具体表现。

OpenAI 后来怎么改的？他们把 AGENTS.md 从一本「百科全书」改成了一个「目录页」：

主文件只保留 100 行左右的核心索引。你没看错，OpenAI 原文博客里特地写明了这个数字：整个 AGENTS.md 控制在大约 100 行，它不告诉 Agent 每条细节规则，只告诉 Agent「你想看什么，去哪儿看」

详细的内容拆到具体的子文档里：架构文档一份、设计原则一份、产品规格一份、执行计划一份、质量评分一份，每份都有清晰的主题

Agent 平时只看目录，只有真的需要某一部分的时候，才钻进对应的子文档

图片
这套做法其实就是我们前面讲的渐进式披露（Progressive Disclosure）。

我特别喜欢这个思路，因为它和我们做软件设计里的「按需加载」「懒加载」一脉相承：上下文优化的本质，不是「给得越多越好」，而是「该给的时候给，不该给的时候藏起来」。

这一点其实和我们前面讲的 Agent Skills 是同一回事，前后呼应上了。如果你现在在写 CLAUDE.md 或者 Cursor Rules 这种文件，强烈建议你回头看看自己写的有没有「百科全书化」。如果有，赶紧拆。


AGENTS.md 是给 AI Coding Agent 看的**项目指令文件**，相当于给 AI 的 README——README.md 是给人看的项目说明，AGENTS.md 是给 AI Agent 看的项目上下文指令，包含构建命令、编码规范、测试要求、安全注意事项等 AI 需要知道的信息。它与 CLAUDE.md **等价**，内容格式完全通用，一个软链接即可兼容。

## 2.1 官方建议的使用方式

官方推荐的使用方式非常简单：

1. **在仓库根目录创建一个 AGENTS.md 文件**
2. **写上对 Agent 有用的内容**——项目概述、构建测试命令、代码风格、安全注意事项
3. **补充额外指引**——commit 规范、部署步骤、安全陷阱，任何你会告诉项目新成员的东西
4. **Monorepo 嵌套**——大型 monorepo 可以在子目录放嵌套的 AGENTS.md，Agent 会自动读取最近的那个（OpenAI 自己的仓库有 88 个 AGENTS.md）

格式上没有强制要求，就是标准的 Markdown，用什么标题、写什么内容完全自由。

## 2.2 哪些应该写进 AGENTS.md 中

AGENTS.md 的第一原则是**渐进式披露**——它是一张**地图，不是一本手册**。建议控制在 **200 行以下**。什么都要写等于什么都没写，文件膨胀到 5000 行，AI 的注意力被稀释，关键规则反而被忽略。

只有**两类内容**应该直接写入：

1. **AI 理解项目全貌的必要信息**——技术栈、仓库结构、核心模块、分层架构
2. **违反会直接导致问题的硬性规则**——编码规约、命名约定、禁止项

### 不写进 AGENTS.md 的内容

其他详细信息通过文档链接引用，不要在 AGENTS.md 中展开：

```
AGENTS.md（地图）
  → docs/architecture.md          分层架构详细说明
  → docs/development.md           开发环境搭建
  → docs/design-docs/*.md         组件使用模式
```

**判断标准**：如果 AI 不知道这条信息就会写出**错误**的代码，放 AGENTS.md；如果只是写出**不够好**的代码，放详细文档，AGENTS.md 里放链接。

## 2.3 注意事项

### 2.3.1 通过 Bad Case 驱动迭代

不要试图一次写完 AGENTS.md。从 **实际使用中发现的 bad case 出发** ：

1. AI 犯了一个错误（用了错误的命名风格、在错误的层级引入了依赖）
2. 思考：如果 AGENTS.md 里多写一条规则，AI 是不是就不会犯这个错
3. 判断改哪里：全局规则→AGENTS.md，模块细节→对应的 docs/

这是最高效的迭代方式。 **AGENTS.md 需要随着项目演进持续调整。**

### 2.3.2 规则要有执行力

重要的规则必须有对应的**自动化检查**。AGENTS.md 中写"禁止跨层依赖"，如果没有 lint 脚本来检查，AI 和人都会违反。

**规则优先级**： **能自动化检查的** > **写在 AGENTS.md 中的** > **口头约定的**

### 2.3.3 团队共建

鼓励团队成员在遇到 AI bad case 时主动补充规则，但要遵循"地图"原则：

| 改动类型 | 维护位置 | 举例 |
| --- | --- | --- |
| 全局性的架构约定或编码规约 | **AGENTS.md** | 所有 Controller 统一 POST |
| 某个模块的具体开发规范 | 对应的 **docs/** 文档 | 某个 Service 的调用约定 |
| 前端组件的使用模式 | 组件模式文档 | ProTable 的某个 prop 必须传特定值 |
| 参考项目的架构说明 | 对应的 **ref-**\* 文档 | 某个开源项目的架构分层介绍 |

如果细节规则都怼进 AGENTS.md，上下文会膨胀，重要的规则反而被淹没。

### 2.3.4 标注给谁看

团队中不是所有人都用 AI 工具。明确标注每个文件的目标读者：

| 文件 | 读者 | 说明 |
| --- | --- | --- |
| **README.md** | 人 | 项目介绍、快速开始，给人类看的入口 |
| **AGENTS.md** | AI 为主，人可浏览 | AI 工具自动读取的项目指令 |
| **docs/\*.md** | AI 为主，人可参考 | 各模块的开发手册 |
| **scripts/\*.sh** | 人和 AI 都用 | 构建、启动、部署脚本 |

README.md 和 AGENTS.md 是互补的——README.md 聚焦快速开始和贡献指南；AGENTS.md 聚焦构建命令、编码规范和验证流程。脚本是人和 AI 共用的，AGENTS.md 和 docs/ 下的文档主要是给 AI 的上下文。

## 2.4 实践经验

### 2.4.1 仓库聚合——解决上下文割裂

采用 **monorepo** 结构，前后端代码放在同一个仓库中：

```
project-root/
  server/                        # 后端（Spring Boot）
  web/                           # 前端（React + TypeScript）
  user-guide/                    # 用户手册（Markdown）
  reference-projects/            # 参考项目（git submodule）
  scripts/                       # 构建、启动、检查脚本
  docs/                          # 架构文档、设计文档
```

**好处**：AI 在同一个窗口中就能看到 Controller 接口定义和对应的前端 API 调用，实现真正的全栈编码。AI 还可以直接基于代码变更同步更新用户手册。

### 2.4.2 统一环境配置——让 AI 能启动项目

每个人的本地环境配置方式不统一（IDE JVM 参数、shell export、.bashrc），AI 工具不知道环境变量在哪。解决方案：

1. 所有本地环境变量统一配置在 **\~/.\_env** 文件中（纯 KEY=VALUE 格式），启动脚本自动 source
2. 放在 \~ 下而非项目目录，避免意外提交到 Git
3. AGENTS.md 中写明优先级：先查 \~/.\_env，不存在则回退到 application.yml 缺省值
4. 配套一键启动脚本，封装 JDK 检测、优雅关闭旧进程、健康检查轮询等逻辑

AI 不需要理解这些细节，只需要调用一个命令。这是 AGENTS.md 中"快速命令"章节的核心价值——把复杂的环境操作封装成一条命令，降低 AI 的认知负担。

### 2.4.3 验证闭环——改完代码不算完，跑通接口才算完

**curl 验证规范**：

1. 每个 curl **独立执行**——禁止串联多个 curl，一个命令只做一件事
2. 用**临时文件传递数据**——curl 输出写入 /tmp/ 下的临时文件，后续用 python3 独立解析
3. **Token 获取模板化**——登录→写文件→提取 token→后续请求携带
4. **排查路径明确**——日志文件位置、数据库连接方式
5. **最好开子Agent去验证，1、**上下文隔离（最核心原因）通常会产生海量的终端日志和输出。污染主上下文  2、AI 生成模型与人类程序员一样，存在“自我审查盲区”。 3、权限与安全边界隔离，在复杂系统中，验证阶段可能需要运行编译脚本、启动沙箱环境或执行集成测试。可以限制为只读或仅允许执行测试命令（Read, Bash），防止在验证过程中误触修改代码的逻辑

为什么这么严格？因为 AI Agent 在 shell 中执行命令时经常遇到兼容性问题。比如 zsh 下管道 + 方括号的 glob 问题，会导致 `curl | python3 -c "print(data['key'])"` 直接报错。用临时文件中转虽然多了一步，但稳定性高得多。

**示例流程**：

```
# Step 1: 登录，结果写文件
curl -s -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin"}' > /tmp/login.json

# Step 2: 提取 token（独立命令）
python3 -c "import json; print(json.load(open('/tmp/login.json'))['data']['token'])" > /tmp/token.txt

# Step 3: 业务接口调用
TOKEN=$(cat /tmp/token.txt)
curl -s -X POST http://localhost:8080/providers/list \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"page":0,"size":10}' > /tmp/result.json
```

**验证不止于编译通过**。

### 2.4.4 自动化检查——规则的执行力

AGENTS.md 中写的规则，如果没有自动化检查，AI 和人都会违反。

**分层依赖检查示例**：

```
L0 - entity/          → 只允许依赖 common
L1 - repository/      → 只允许依赖 entity, common
L2 - core/            → 横切关注点，不允许依赖业务包
L3 - config/          → 允许依赖 core, service
L4 - service/         → 业务核心层
L5 - controller/      → 只允许依赖 service, core, common
```

用一个 shell 脚本扫描所有 Java 文件的 import 语句，按包路径判断所属层级，检查是否违反依赖方向。违规时输出可操作的错误信息：

```
✗ service/client/impl/SomeService.java 导入了 entity.SomeEntity
  原因: 客户端实现禁止直接依赖业务 Entity，须通过 DTO 传递数据
  修复: 在编排层完成 Entity→DTO 转换，客户端只接收 DTO
```

错误信息格式：**WHAT**（违规了什么）+ **WHY**（为什么不允许）+ **HOW**（怎么修复）。AI 读到这条错误信息后，能直接按照 HOW 的指引去修复，不需要额外的上下文。

通过 Makefile 提供统一入口：

```
lint-arch:    ./scripts/lint-deps.sh      # 分层依赖检查
lint-format:  mvn spotless:check          # 格式检查
format:       mvn spotless:apply          # 格式修复
build:        mvn package -DskipTests     # 构建
test:         mvn test                    # 测试
```

AI Agent 不需要记住每个检查命令的具体写法，只需要知道 `make lint-arch` 和 `make lint-format`。

### 2.4.5 参考项目引入——给 AI 喂够上下文

AI 不认识闭源组件，维护使用文档又总是滞后于实现。解决方案是**直接引入源码**：

```
reference-projects/
  higress/                # 开源 Higress 网关内核源码
  nacos/                  # 开源 Nacos 注册配置中心源码
  pro-components/         # 私域组件库源码（TypeScript）
  other-product-backend/          # 其他产品后端（Go）
  other-product-frontend/         # 其他产品前端（React）
  himarket/               # 开源 HiMarket AI 开放平台（Spring Boot）
```

源码永远不会过时，它就是最准确的文档。AI 不会写私域组件的代码时，可以直接读源码里的 TypeScript 定义和实现。

同时，为每个参考项目维护一份架构说明文档（docs/design-docs/ref-\*.md），帮助 AI 快速理解参考代码的结构。ref 文档是"地图"，告诉 AI 参考项目的整体结构和关键模块在哪里；reference-projects 是"源码"，AI 需要细节时直接去读。

**为什么不只写文档**：

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 只写使用文档 | 轻量、聚焦 | 滞后于实现、覆盖不全、边界情况缺失 |
| 引入源码 + 架构说明 | 永远准确、覆盖完整 | 仓库体积增大、需要管理 submodule |

`to-spec` 会把规格文档发布为工单，因此必须先通过 `setup-matt-pocock-skills` 为本仓库配置好任务追踪工具以及工单评审标签词汇表。 两种模式均支持：GitHub 这类线上追踪平台，或是存放在 `.scratch/` 目录下的本地 Markdown 文件（开箱即用）。

#### 规格文档 = 决策记录

设置规格文档的根本原因：大模型上下文窗口存在上限。 你在深度质询（grilling）过程中敲定的所有内容 —— 最终方案形态、反复权衡得出的选择、明确决定不做的需求 —— 全都保存在一段即将被清空的对话里。规格文档用来永久留存这些结论。

因此，它不会校验方案，也不会做出任何新决策。它使用项目自有术语记录已定方案，保证新开会话时无需你重复讲解需求。 如果规格文档中出现了你从未确认过的内容，那属于文档缺陷。

#### 先确定测试边界，再撰写正文

在输出任何文字之前，`to-spec` 会先梳理该功能对应的**测试边界（seams）**，并与你确认。 优先复用现有边界，尽可能选用层级最高的边界；一次改动理想情况下只定义一处边界。

确认后的测试边界会贯穿后续流程： `tdd` 只会在双方约定好的边界开展测试；`code-review` 对照规格文档评审代码变更。一旦出现未经确认的边界，评审阶段就会标记出来。 这种关联是间接依托这份规格文档建立的。正因如此，测试边界的讨论应当在此处落实，不要推迟到开发阶段。

在一个陌生的城市,你站在十字路口,不知道该往哪
走。你随机问了一个路人,他说:"往前走,第二个路
口左转。"你走了,又问下一个路人,他又给你指了一
个方向。你就这样走了一段又一段。最后,你到了某
个地方,但你说不清那是哪里,也不知道离目的地有
多远。
换一种方式:你提前做了功课,知道你要去的店在"淮
海路"上。你到了淮海路,但不知道具体是哪一栋。然
后你挨栋去找。终于找到,满意离开。
这两个场景,分别对应了
grill-me 和
brainstorming两个skills在理论层面上的区别。
两种误用模式
这两种误用模式,在Al对话里非常普遍。

误用一:把brainstorming当grill-me用
你带着一个模糊的念头去找grill-me,心想"你帮我
完善完善"。但Al不断追问你:"你的目标用户是谁?
你的差异化是什么?你的商业模式是?"你越来越烦
躁。"我就是不知道才来问你的啊!"结果:被问太多
问题,对话变成审讯。
误用二:把grill-me当brainstorming用
你只有一个"也许可以做这个东西"的念头,连方向都
不确定。你去找Al说"帮我设计一下这个产品"。AI
说:"好的,请告诉我你的核心功能、目标用户、竞品
分析。"你更懵了。"我要是知道还要问你?"结果:细
节补得很累,对话变成填表。
这两种误用,有一个共同的原因:你对两个skill的前
提假设一无所知。
grill-me和brainstorming不是可以互换的工具,
而是分别对应了两种完全不同的认知准备状态。
打过一个比方:
brainstorming帮我在陌生城市里定大致方位,
grill-me是在已经选好的街区里挨栋敲门找那一间。

前者解决"往哪儿走",后者解决"这家店具体怎么装修
到能开业"。反过来用的话,不是被问太多,就是最后
细节补得很累。
grill-me的假设是:你脑海里已有方案,只是缺少细
节。他会在树干的基础上通过与你不断讨论延伸出树
枝,完成态是一棵完整的designtree。
brainstorming的假设是:你只有模糊的想法,他就
你的想法给你指方向。
这两个假设是完全相反的。不是强度上的差异,是认
知阶段的差异。
这么看的话,grill更适合技术人员,因为通常拿到需
求都会有技顶方案。brainstorming更适合产品或者
非技术背景的人。因为他们的工作往往是从模糊想法
出发,需要先找到方向。
grill-me和brainstorming是互补的两极。一个负
责指路,一个负责长树。选哪个,不取决于你的个人
偏好,而取决于你现在有多少。
grill-me完成态是一棵完整的designtree。每个枝
干都有方向、有细节、可执行。

brainstorming完成态是"到达目的地"。你知道往哪
走了,但门店还没装修、货还没进、团队还没搭。
显然,后者完成态的细节没有前者丰富。
所以:
grill-me后续流程更简洁。tree完整,可以直接进
入执行阶段。
brainstorming后续流程更重。不管是tospec,还
是spectoplan,都会花很多精力补细节。
就像你拿到了完整的建筑图纸,施工队可以直接开
工。但如果你只拿到一个地址,施工队还需要从零开
始设计。
三步操作法:念头阶段如何用grill-me
如果你只有念头,但又想用grill-me(因为它能产出
完整的design tree),有三个办法。
第一步:交流前就有个主干
不要空手去问"帮我设计一个产品"。先自己搞清楚:
你的产品要解决什么问题,目标用户是谁。grill-me
需要的不是完整方案,而是一个可以延伸的主干。



一、上下文与记忆管理
想要让记忆在不同会话之间互通流转，最优方案是编写一套技能 / 斜杠命令：定期汇总开发进度、写入进度日志，保存至 \~/.claude/ 下的 .tmp 临时文件，全程追加写入直至会话结束。
次日重启会话时，直接读取这份日志作为初始上下文，无缝接续昨日工作；每一次会话单独生成一份日志文件，避免新旧项目上下文互相污染。日积月累会生成大量会话日志，可定期备份至云端，或是清理无用的历史会话记录。
整套流程：Claude 生成一份记录当前项目整体状态的汇总文档，你通读一遍，按需提出修改意见，随后开启全新对话，直接传入这份文件路径即可加载过往进度。这种方式在触及上下文上限、需要继续推进复杂开发任务时尤为好用。
日志文件必须包含这些关键信息：
经过验证、切实可行的技术方案（附带落地证据）
尝试过但最终失败的思路
尚未探索的备选方案
剩余待完成工作清单
策略性清空上下文
梳理完整开发计划后，便可清空冗余上下文（如今 Claude Code 规划模式已内置该默认选项），后续全程依照既定方案执行。适合场景：前期大量调研探索产生了海量无关对话内容，正式编码阶段不再需要这些冗余信息。
上下文压缩实操技巧：
关闭自动压缩功能，在逻辑节点处手动触发压缩；也可以编写专属压缩技能，由 AI 自动判断时机发起压缩。
还可将压缩逻辑绑定至PreToolUse钩子（文件编辑 / 写入前触发）：当上下文冗余度过高时，钩子会主动提醒你执行压缩优化。
进阶：动态注入系统提示词
绝大多数人会把所有约束规则统一写进全局CLAUDE.md（用户维度）或项目目录.claude/rules/（项目维度），每次开启会话都会完整加载全部内容。我摸索出一套试验性优化方案：通过命令行参数动态按需注入上下文，精准控制每一轮会话加载哪些规则内容，根据当前开发任务切换专属约束。
对比 @文件引用 优劣
写法 @memory.md 或是写入 rules 目录：会话过程中 Claude 会调用读取工具拉取文件内容，内容以工具返回结果形式汇入对话
--system-prompt 参数注入：对话启动前，内容直接写入顶层系统提示词
二者核心差异是指令优先级层级：
系统提示词 > 用户输入消息 > 工具返回内容。
日常开发差距并不明显；但对于硬性行为约束、项目专属边界、必须让 AI 优先遵守的规则，通过系统提示词注入能保证权重最高，执行效果更稳定。
落地配置方案：
.claude/rules/ 存放项目通用基础规则，再通过终端别名绑定不同场景专属系统提示文件，一键切换：
dev.md：业务代码实现专属约束
review.md：代码质量、安全审计专属规则
research.md：前期调研探索阶段规范
多数场景下两种方式差距微弱；CLI 动态注入优势：无需调用文件读取工具、加载更快；系统层级指令约束力更强；小幅节省代币开销。但属于细微优化，对很多人而言维护成本大于收益。
进阶：持久记忆钩子系统
大部分用户知晓但极少活用三类生命周期钩子，完美解决跨会话记忆留存问题：
PreCompact 钩子：上下文压缩前，把核心项目状态保存至文件
SessionComplete 钩子：会话结束后，沉淀本次踩坑经验、技术收获写入文档
SessionStart 钩子：新会话启动时，自动加载近期历史上下文
整套钩子配套脚本功能拆解：
pre-compact.sh：记录每一次压缩事件，给活跃会话日志打上压缩时间戳
session-start.sh：检索近 7 天历史会话文件，提醒可接续的过往进度、已沉淀技能
session-end.sh：依照模板生成 / 更新每日会话日志，记录会话起止时间
三套钩子串联运行，全程无需手动操作即可实现不间断跨会话记忆，在第一篇基础钩子（PreToolUse/PostToolUse/Stop）之上，聚焦完整会话生命周期做了拓展。
二、持续学习与记忆沉淀
前文讲过通过技能自动更新代码图谱实现记忆迭代，这套逻辑同样适用于复盘错误、沉淀经验。
如果你反复给 Claude 下达相同指令，AI 却屡次踩同一个坑、给出重复无效回复，就必须启用持续学习机制：你总要二次提示纠正 AI 方向，这类纠偏范式应当固化为可复用技能。
实现方式：可以直接告知 Claude 记住经验、写入规则库；也可以编写专用自动化技能完成沉淀。
现存痛点
反复消耗代币、挤占上下文空间、浪费开发时间；一次次提醒 AI 不要重复犯错却收效甚微，极大降低开发心态。
解决方案
当 Claude 攻克复杂问题（调试技巧、兼容变通方案、项目专属编码范式）后，自动将这套经验打包为全新技能存入目录。下次遇到同类场景，技能会自动加载，AI 直接沿用成熟解法。
为何选用 Stop 钩子，而非每轮消息触发钩子？
UserPromptSubmit 钩子会在你发送任意一句话时都执行，开销极大、拉高每轮对话延迟，完全没必要；
Stop 钩子仅在整段会话收尾时运行一次，轻量化无运行损耗，并且可以通读完整会话全过程，碎片化复盘效果远优于逐句校验。
运行逻辑：会话结束触发钩子，脚本扫描全程对话，提取可复用内容（报错解决方案、调试思路、兼容方案、项目定制规范等），自动生成技能文件存入 \~/.claude/skills/learned/。
手动提取经验：/learn 命令
不必等到会话结束。中途攻克棘手难题后，随时输入 /learn，工具会引导你提炼这套解决范式，自动生成技能文档并等待你确认保存。
会话日志统一规范
日志存放路径：\~/.claude/sessions/YYYY-MM-DD-项目主题.tmp
一日一会话一份日志，内容包含：当前项目状态、已完成事项、阻塞卡点、关键技术决策、可供下次会话接续的全部上下文。仓库示例文件夹内附有标准模板。
其他自主迭代记忆方案
复盘日志记忆法（@RLanceMartin）
每次会话结束后，复盘智能体梳理全过程：顺利落地的方案、失败尝试、你做出的所有纠正指令，汇总写入记忆文档，后续会话自动加载，逐步贴合你的编码习惯。
定时主动优化建议（@alexhillman）
每 15 分钟 AI 主动复盘近期交互记录，提出记忆规则优化方案，由你审批通过 / 驳回；久而久之 AI 会根据你的偏好自主迭代约束。
三、代币开销优化
很多重度使用者受模型计费、调用额度限制困扰，下面是全套降本实操技巧：
核心方案：子智能体分层调度架构
按照任务难度分配不同价位模型，用最低成本的模型完成力所能及的工作，杜绝高端模型资源浪费：
Haiku：简单重复任务、纯执行类工作（成本最低）
Sonnet：绝大多数常规编码开发（均衡性价比）
Opus：架构设计、复杂多文件重构、安全核心代码、多次尝试仍未解决的难题
量化基准测试方案（进阶）
搭建标准化测试仓库，设定清晰任务清单与开发计划；每一个 Git 工作树固定整套子智能体全部使用同一款模型，完整跑完所有开发任务，记录耗时、通过率。
最终通过单元测试、集成测试、E2E 全量测试对比三套模型交付结果，用通过率数值量化各模型优劣；若全部模型均可完美交付，就继续增加边界测试用例提升难度。这套方案耗时较长，按需取舍即可。
模型选型速查表
90% 编码场景默认选用 Sonnet
升级 Opus：初次开发失败、修改 5 个以上文件、系统架构设计、安全敏感代码编写
降级 Haiku：机械重复工作、指令极度清晰、多智能体架构里的执行工人角色
价格对比参考：
Sonnet 4.5 输入 3 美元 / 百万代币、输出 15 美元 / 百万代币；相较 Opus 可节省约 66.7% 开销；
Haiku 与 Opus 差价高达 5 倍，远高于 Sonnet 和 Opus 的 1.67 倍价差，高低搭配是性价比最优解。
你可以在子智能体配置文件中直接指定每一个代理使用的模型。
工具调用层面优化
替换默认检索工具：将系统自带 grep/ripgrep 更换为 mgrep，各类代码检索场景下可平均缩减一半代币消耗。
后台进程分流
不需要 AI 实时读取完整终端日志流时，把耗时命令放到 Tmux 后台运行；仅把最终需要的关键内容摘抄汇总后再发给 AI。
输入代币是主要计费开销大头（Opus 输入 5 美元 / 百万代币，输出 25 美元 / 百万代币），此举能大幅削减日志灌入上下文带来的无谓消耗。
模块化代码库降本
代码拆分越细致、单文件行数越少（数百行而非数千行），代币开销越低，同时 AI 首次编写正确率更高。
巨型长文件会迫使 AI 反复分段读取、频繁调用文件工具，极易丢失细节，中途中断重读还会叠加额外代币损耗；模块化拆分从根源规避该问题。
搭配清理冗余代码技能定期重构删减无效代码，持续精简仓库体积。闲暇时通读项目，提炼重复逻辑交由 AI 统一抽象封装，进一步压缩代码体量。
高阶：精简系统提示词
极致压缩开销玩家可选：Claude Code 默认系统提示词约 18000 代币，占据 200k 上下文窗口 9% 空间；通过补丁精简至 10000 代币，可削减 7300 静态开销（降幅 41%）。可参考 YK 发布的系统提示词补丁，个人并不推荐改动底层提示词。
四、校验闭环与效果评估
依托可观测手段、标准化评估体系把控交付质量，避免 AI 堆砌无效代码堆积技术债。
可观测落地方式
Tmux 绑定日志追踪：触发任意技能时，全程抓取 AI 思考过程、输出日志留存归档
PostToolUse 钩子日志：记录每一步 AI 执行的操作、代码改动详情
基准测试工作流
会话分叉 + Git 工作树对照测试：
一份会话启用自定义技能，另一份空白环境不加载任何技能，完成相同任务后对比两份最终代码差异，量化技能带来的效率提升；可联动前文持续记忆模块迭代优化规则。
两类主流评估模式
基于检查点的阶段性校验（线性流程首选）
开发流程设置明确里程碑节点；每完成一段就对照验收标准校验；校验不通过必须修复完毕才可继续推进。适合需求清晰、分阶段落地的功能开发。
持续性全量评估（探索重构 / 日常维护首选）
每间隔固定时长、每次大规模代码修改后自动执行：完整测试套件、项目构建、代码格式校验；一旦出现功能退化立刻告警，暂停开发修复问题。适合无明确节点的重构、长期项目维护工作。
三类打分评审机制（Anthropic 官方标准）
代码自动评审器
字符串匹配、单元测试、静态代码扫描、运行结果核验；速度快、成本低、结果客观；缺点是无法兼容合理的代码写法变体，容错性差。
大模型评审器
按照评分细则打分、自然语言断言、两两方案横向对比；灵活适配各类细节场景；缺点是结果具备随机性、代币成本更高。
人工评审
领域专家抽检审核；质量天花板，但耗时久、成本最高。
核心评估指标
pass@k：只需功能可用即可，获取反馈迭代优化场景使用
pass^k：追求代码风格、逻辑高度统一，需要近乎固定输出结果场景使用
评估搭建步骤
尽早落地：从过往失败场景提取 20\~50 个简易测试用例
将你踩过的坑全部转化为标准化测试用例
编写无歧义任务需求，两位开发者执行结果需完全一致
均衡设计正向、反向测试场景
搭建干净测试环境，每轮评测初始化仓库状态
只评判最终交付产物，不拘泥 AI 中间思考过程
复盘大量会话日志持续优化规则
通过率达到 100% 时，新增更难用例防止能力停滞
五、并行开发策略
多会话分叉并行工作时，务必给每一份会话划定清晰边界，代码修改范围尽量零重叠；选择互不干扰的正交任务，杜绝代码改动冲突。
个人惯用并行范式
主会话负责核心代码编写；分叉会话专门做三件事：
研读代码库梳理整体架构
查阅第三方服务官方文档
检索开源参考项目、技术调研

Claude Code 创作者 Boris 提出过同时运行 5 个本地 + 5 个云端实例的方案，我并不认同。并行实例数量必须贴合真实需求：能用脚本解决的绝不新开 AI 会话；可在 Tmux 后台运行命令交由主会话统一汇总的，不必拆分多实例。
核心原则：用最少的并行会话完成全部工作。
新手务必先吃透单会话上下文管理，再逐步尝试并行；即便熟练后，日常最多同时开启 3\~4 个 Claude 会话足矣，绝大多数场景 2\~3 个就可以覆盖。
多实例协同必备：Git 工作树
多 AI 同时修改同一项目不同分支时，Git 工作树是唯一稳妥方案：
彻底规避 Git 提交冲突
每一份目录都是干净独立工作区
方便横向对比不同实现方案
可用来对照测试各模型交付效果
级联排布工作法
多标签页从左至右依次新建任务，按时间顺序从最早到最晚流转跟进；单次聚焦不超过 3\~4 项任务，过多任务会带来巨大心智负担，反而降低效率。
六、新项目启动基础搭建
代码仓库体量越大，技术债累积速度越快；规范初始化项目，能极大降低后续维护成本。
双智能体启动范式（个人专属工作流）
新开空白仓库，同时启动 2 个 Claude 实例分工协作：

搭建项目目录结构、全套配置文件（CLAUDE.md、规则、子智能体等），统一编码规范，搭建项目基础骨架。

示例链接：https://www.helius.dev/docs/llms.txt
七、核心理念：沉淀可复用工作流
开发者 @omarsar0 的观点我十分认同：前期花费时间打磨可复用流程、范式，过程枯燥繁琐，但随着大模型迭代升级，这套沉淀会带来指数级复利收益。
值得投入精力打磨的内容：
子智能体体系、自定义技能、斜杠命令、开发规划范式、MCP 工具集、上下文工程技巧

八、智能体编排最佳实践
前文罗列过规划师、架构师、TDD 助手、代码评审等角色子智能体，本节讲解多智能体调度协作逻辑。
子智能体固有痛点：上下文信息断层
子智能体只会收到调度主代理下发的字面任务指令，无法知晓这项任务背后的开发目的、整体项目上下文；返回精简总结时，极易丢失关键隐性信息。
类比：领导派你参会只让你带回会议总结，你只能复述表面内容，不清楚会议背后的整体规划，领导必然会接连追问细节。
迭代式召回补全方案
主调度代理审阅每一份子智能体返回结果
信息不全时发起追问
子智能体回到源码 / 文档重新调取内容补充
循环往复最多 3 轮，避免无限迭代
下发任务时，不仅要写明具体操作，还要附带整体开发目标，方便子智能体判断信息优先级。
串行分阶段编排规范
每个智能体仅接收一类输入，产出一类标准输出
上一阶段结果作为下一阶段输入，流程不可逆跳步
阶段切换执行 /clear 清空冗余上下文
中间产出全部存入文件持久化，不只依赖会话内存
智能体难度分级梯队
一级：入门必学（上手简单，收益稳定）

前期充分提问对齐需求：减少后期反复修改成本
二级：高阶进阶（门槛高，需大量调试打磨）
长周期独立智能体：把控数小时跨度开发节奏，试错成本极高
并行多智能体：方差极大，仅适合高度拆分的超复杂项目
角色固化多智能体：大模型迭代速度过快，固定角色规则极易失效
计算机调用智能体：尚处于早期探索阶段，调试成本很高
学习路线：吃透一级全部技巧，产生真实效率提升后，再逐步钻研二级内容。

# **Matt Pocock：AI 编程工作坊内容整理**

## **一、核心论点：软件工程基本功同样适用于 AI**

Matt 认为，AI 是一个新范式，但我们在讨论 AI 时，往往忽略了那些与人类协作至关重要的软件工程基本功——它们与 AI 协作时同样极其有效。本次工作坊的目的，就是把这些基本功应用到 AI 协作之中。

## **二、LLM 的两个奇特约束**

### **1. 智能区与愚蠢区（Smart Zone & Dumb Zone）**

这一观点出自 Human Layer 公司的创始人 Dex Hy。当你刚开始与 LLM 对话、从零开始时，LLM 处于"智能区"，表现最好，因为此时注意力关系（attention relationships）的负担最小。每向 LLM 增加一个 token，注意力关系就会平方级增长——就像足球联赛每增加一支球队，比赛场次会平方级增加。

因此，当上下文达到大约 10 万 token 时（无论上下文窗口是 20 万还是 100 万，这个拐点大致相同，约占 40%），LLM 开始变"笨"。持续向同一上下文添加内容，它会越来越笨，直到做出愚蠢的决定。

**应对方法：** 把任务控制在智能区内，不要让 AI"贪多嚼不烂"。这对应着 Martin Fowler 在《重构》和《程序员修炼之道》中的经典建议：保持任务足够小，让人类开发者也不至于慌乱、掉入愚蠢区。

**大任务如何拆分：**

- 一种方式是不断继续，进入愚蠢区后压缩上下文，再继续。这种方式效果不佳。
- 另一种方式是使用多阶段计划（multi-phase plans），把大任务拆成小块，每块都在智能区内完成。
- 更进一步，任何有经验的开发者都会意识到：多阶段计划本质上是一个循环。与其写死阶段一、二、三、四，不如设定"阶段 n"——在后台维护一份计划，然后在计划之上循环，直至完成。

这引出了 Ralph Wiggum 实践：只需指定旅程的终点——创建一份 PRD（产品需求文档）描述目的地，然后让 AI 每次做一个小改变，逐步接近终点。Matt 认为 Ralph 模式可行，但他个人更喜欢多一些结构。

### **2. 像《记忆碎片》的主角一样持续遗忘**

LLM 会不断"忘记"之前的对话，就像电影《记忆碎片》（Memento）的主角一样，总是重置回基础状态。

每个 LLM 会话都会经历相同阶段：

1. **系统提示（system prompt）**：始终存在于上下文中。它应尽可能小——如果有人往里面塞 25 万 token，就会直接掉入愚蠢区，什么都做不了。
2. **探索阶段**：编码代理去探索代码库。
3. **实现阶段**：编写代码。
4. **测试阶段**：运行反馈循环，确保代码正常工作。

**清除上下文（clear）与压缩（compact）：** 清除上下文会回到最初的系统提示状态；压缩则会把整个对话历史挤压成一份书面记录。很多开发者喜欢压缩，但 Matt 讨厌它——他更喜欢 AI 像《记忆碎片》主角一样，每次状态都完全相同。如果能做到这一点并围绕它优化，就会处于很好的状态。

**关键信息：** 每次会话都要知道当前消耗了多少 token（Claude Code 的状态栏会显示精确数字），以便知道离愚蠢区有多近。这一信息至关重要。

## **三、对齐：Grill Me 技能**

Grill Me 技能非常小，作用是防止与 AI 协作时最重要的问题之一：**目标错位（misalignment）**。

**反对的实践——"从规格到代码"（specs to code）：** 一些人主张：要构建应用，先写规格文档，然后把文档交给 AI 转成代码。如果代码有问题，不看代码，回去改规格，如此循环。这本质上是另一种形式的"vibe coding"——完全忽略代码。Matt 尝试过，发现行不通，因为**你必须掌控代码**——理解其中的内容、塑造它，因为代码是你的战场。

**Grill Me 的做法：**

1. 清除上下文。
2. 调用 grill me 技能，传入客户需求（如 Slack 消息）。
3. LLM 先派一个子代理（sub-agent）探索代码库。子代理拥有独立的上下文窗口，探索后把重要信息以摘要形式回传给主代理，本质上是一种委托。
4. 然后开始逐一提问（一次一个问题），每个问题同时给出推荐答案。问题可能多达 40、80 甚至 100 个。

**设计概念（design concept）：** Frederick P. Brooks 在《设计的设计》中提到：当一群人共同构建新事物时，参与者之间会共享一个"设计概念"。Matt 意识到，他与 Claude 协作时需要的不是一个计划、一个产物，而是与 AI 达成共同的"波长"（shared understanding）。Grill Me 就是达成这种对齐的高效方式。

**Grill Me 的扩展用法：** 与领域专家（如客户 Sarah）开会后，可以把会议记录喂给一个"拷问会话"，检验那些你没想到的假设。这能把来自外界的输入转化为经过验证的资产。

**适用场景：** 有听众提问说，Grill Me 提的许多问题更适合产品经理（PO）而非开发者。Matt 认为，这种"拷问"式协作可以类比结对编程——房间里多了一个不断追问你的第三方。关于实现的问题，应该是你、同行开发者与 AI 三方讨论；关于领域知识的问题，应该是你、领域专家与 AI 三方讨论。关键决策需要大量人类参与，甚至可以变成"群体编程"（mob programming）式的 AI 协作。

**停止时机：** Grill 会话可能异常密集，AI 会没完没了地问。这些技能是可调优的——如果 AI 逼得太紧，可以直接告诉它收敛一点、设定停止点。

## **四、目标文档：PRD**

对齐阶段结束后，你拥有了一段宝贵的对话历史（示例中用了 2.5 万 token），其中大部分内容都是"黄金"。需要把它总结成一份**目标文档（destination document）**——即 PRD（产品需求文档）。

PRD 的功能就是记录"目的地"。具体格式无所谓，可以用自己偏好或公司使用的模板。**整个过程只是在总结已有的设计概念。**

PRD 的典型结构：

- 问题陈述（problem statement）：用户面临的问题
- 解决方案（solution）
- 一组用户故事（user stories）
- 已做出的实现决策（implementation decisions）
- 关键的测试决策（testing decisions）

Matt 通常先做 Grill 会话，再写 PRD。写 PRD 时 AI 会：先要一份对问题的详细描述 → 探索代码库 → 再次拷问用户 → 套用 PRD 模板。

**Matt 通常不读 PRD：** 因为 LLM 非常擅长总结。既然已经通过 Grill 会话与 LLM 达成了共享的设计概念，再读 PRD 只是在检验 LLM 的总结能力。但他会关心 AI 提出的"拟修改模块清单"——因为这不是 specs to code，在整个过程中都要把代码放在心上。

**负决策的保留：** 关于如何保留"决定不做的事"，PRD 中有专门的"范围之外（out of scope）"部分，这对定义"完成"（definition of done）非常重要。

**PRD 文档的保存：** Matt 倾向于不把 PRD 长期保存在仓库里，因为代码演化后文档会腐烂（doc rot），过时的文档反而会误导 AI。他使用 GitHub Issues 管理，完成后直接标记为 closed（已关闭）——AI 仍可获取，但能直观看到它已过期。

## **五、把 PRD 拆成看板与垂直切片**

拿到目的地后，需要把它拆成不会掉入愚蠢区的任务。Matt 偏好的方式是把 PRD 转成**看板（Kanban board）**——一组带有阻塞关系的工单。

例如，PRD 被拆成五个任务：

1. 数据模型（schema）与游戏化服务——不被任何任务阻塞
2. 连续打卡（streak）追踪——不被任何任务阻塞
3. 把积分和连续打卡接入课程/测验完成流程——被任务 1 和 2 阻塞
4. 追溯性回填（retroactive backfill）——只被任务 1 阻塞
5. 最后的整合任务——被所有任务阻塞

这种结构的意义：

- **可并行化：** 依赖关系明确的工单可以由多个代理同时抓取。多阶段顺序计划只能被一个代理执行（只有一条循环），而看板本质上是有向无环图（DAG），可以划分成多个阶段并行推进。
- **类型标注：** 每个任务还可以标注类型，比如 AFK 任务（人类可以离开键盘）。

**为什么需要人工参与拆分？** 因为这一步成本很低（PRD 做完后很快就能完成），而且人能立刻看出问题。最关键的技术出自《程序员修炼之道》中的**曳光弹（tracer bullets）／垂直切片（vertical slices）**。

**问题：AI 喜欢水平编码。** AI 倾向于一层层地写：阶段一做完所有数据库/schema，阶段二做所有 API，阶段三再做前端。问题在于：**直到阶段三你才得到完整反馈**——你一直没有可测试的集成系统，无法验证各层是否协同工作。

**正确做法是垂直切片：** 薄的、横跨所有需要层面的功能切片。每个切片结束时（甚至进行中），AI 就能获得关于完整流程的反馈。否则 AI 就像夜间防空炮手发射普通子弹——能看到目标却看不到弹道，只能在后期阶段"盲写"。（曳光弹在弹头附着荧光物质，让射手看到弹道、即时调整瞄准。）

**AI 的切片跑偏时需要纠正。** 例如第一刀被拆成了"创建游戏化服务"——这太水平了。理想的第一个垂直切片应该是：包含部分 schema 变更、新建某个服务、前端有最小展示。比如"在仪表盘上显示完成课程获得的积分"就是一个漂亮的垂直切片：它承载了大量用户故事，但结束时你能看到可见的东西，AI 之后可以在其上持续叠加。

## **六、AFK 代理循环（Ralph loop）**

整个流程的定位：

- **规划阶段（白天班）：** 人类负责——Grill 对齐 → 写成 PRD → 拆成看板。这些步骤全部需要人工审查。
- **实现阶段（夜班）：** 人类离开键盘，让一个或多个代理 AFK（away from keyboard，离开键盘）地处理看板。

AFK 循环本质上是 Ralph loop 的自动化。关键脚本（[once.sh](http://once.sh)）的工作方式：

1. 把 issues 目录下所有 markdown 工单文件读入一个变量——这就是代理的全部积压任务。
2. 抓取最近五次提交（用于反馈循环）。
3. 用 Claude Code 以"仅编辑"的权限模式运行，传入提示词和所有工单。

这是"人仍在循环"的单次版本，是迭代调优的基础——运行它，观察代理行为，必要时调整提示词。

AFK 循环的提示词要点：

- 只处理 AFK 类工单
- 若所有 AFK 任务已完成，输出"没有更多任务"
- 自己挑选下一个任务，按优先级排序：关键缺陷修复 → 开发基础设施 → 曳光弹（垂直切片）→ 打磨/速胜 → 重构
- 完成方式：探索仓库，用 TDD 完成任务，然后运行反馈循环

本质上，前面所有设置（Grill、PRD、看板）都是为了给"夜班"维护一份积压任务清单（backlog）。

## **七、TDD 的关键作用**

TDD（测试驱动开发）的核心是**红-绿-重构（red-green-refactor）**循环：先写一个失败的测试（红），再实现让它通过（绿），然后重构。仓库里有对应的技能文件教 AI 这么做。

**为什么 TDD 对 AI 极其重要：**

- 为代码库增添测试，而且是质量不错的测试。
- **防止 AI 作弊：** 不用 TDD 时，AI 倾向分层完成——先写完整实现，再补一层测试，测试很容易变成自说自话的空转。TDD 让 AI 在写代码之前先"插桩"（编写验证手段），作弊难度大大增加。

**反馈循环是 AI 输出的天花板：** 反馈循环（测试、类型检查）对 AI 产出合格代码至关重要。没有反馈循环，AI 完全是"盲写"。代码库反馈循环的质量直接决定 AI 编码的上限——如果 AI 输出糟糕，往往需要提升反馈循环的质量。例如，代理跑完 `npm run test` 和类型检查，捕获了一个类型错误并修复（把 "level thresholds number" 改成正确的类型标注），这正是反馈循环在起作用。

## **八、QA：人类品味的作用**

实现完成后（Ralph loop 会产出一份摘要，如"Issue 2 已完成、做了什么事"），必须进行人工 QA。QA 是人类把**品味和观点**施加回代码库的方式。

**为什么要人工 QA 而不完全自动化：** 有些团队试图把流程每一步都自动化——自动生成想法、自动 QA、自动研究、自动原型。结果往往做出缺乏品味、甚至无法正常工作的应用。构建软件需要人的参与，否则只会产出"垃圾"（slop）。

**QA 与看板的循环：** QA 阶段的产出是更多看板工单——在实现的同时可以 QA，不断补充新的（阻塞型）工单，看板可以无限容纳阻塞关系。

**代码评审的人工环节：** 评审时先看测试（是否测试了合理的东西），再看代码本身（是否做了太离谱的事）。不可避免的是，把编码委托给代理后，人类的代码评审工作量会增加——这是一个尚无完美答案的难题，但应该做好准备。

**关于让 AI 评审自己的代码：** 当然可以让 AI 做自动化评审步骤。但要注意：如果实现刚消耗了大量 token（接近愚蠢区），让同一上下文里的 AI 评审，评审会发生在"愚蠢区"，结果评审者比实现者更笨。正确做法是**清除上下文**，让评审在"智能区"进行。自动化评审很划算（token 便宜，AI 擅长评审），能捕获大量 bug。

## **九、深度模块与浅度模块（Deep vs Shallow Modules）**

引用 John Ousterhout《软件设计的哲学》（A Philosophy of Software Design）中的概念。

**浅度模块（shallow modules）：** 文件很小、导出很多东西、依赖关系纷乱。对 AI 而言很难导航——它需要手动跟踪整张依赖图。测试边界也很难划定：是给每个模块单独画测试边界，还是把成组模块一起测？坏测试往往就是这种形态：AI 试图给每个微小函数包一个测试边界，结果无法验证模块间的调用是否正确。

**深度模块（deep modules）：** 内部功能庞大、但只暴露小而简单接口的模块。优点：

- **容易测试：** 在一个大模块外包一个大测试边界，能捕获大量功能问题；调用方只面对简单接口。
- **对 AI 友好：** AI 能理解整个流程、作用于整个流程、测试整个流程。

**不加引导时，AI 自然产出的是浅度模块代码库**，所以指导 AI 时必须非常小心。在 PRD 中明确列出拟修改的模块（如"游戏化服务是一个新的深度模块，围绕它测试"），并在规划与实现的整个过程中始终记住这张模块图。

**另一个好处——保住你的"心智地图"：** 使用 AI 后，人们常发现自己对代码库的熟悉度下降。解决方案：**为模块设计接口，但把实现委托出去。** 模块变成"灰盒"——你只需知道它的形状（做什么、什么条件下表现什么行为），不必了解内部每个细节，也不必逐一共同评审内部实现。这让你既保持对代码库的整体把握，又保留心智空间。

**如何把浅度模块代码库改造成深度模块？** 使用 "improve codebase architecture"（改进代码库架构）技能：它会扫描代码库，寻找可以加深模块的地方。示例：Matt 的课程视频管理应用里有浏览器端视频编辑器，他用判别联合（discriminated union）把整个前端到后端包成一个巨型模块，从外部测试"前端按某个按钮一路到后端"的完整流程。这使 AI 能看到、操作并测试整个流程——对视频编辑器这种复杂模块，没有好测试时 AI 几乎无法改动，有了之后效果天差地别。

## **十、编码规范：推送与拉取**

要让 AI 按你期望的方式编码，有两种途径：

- **推送（push）：** 把指令推给 LLM，比如放在 [CLAUDE.md](http://CLAUDE.md) 里，每次都会随上下文发送给代理。
- **拉取（pull）：** 给代理自主拉取信息的机会，比如技能（skills）——技能文件放在仓库里，带有描述头，代理需要时可自行拉取。

Matt 当前的实践：

- **实现阶段：编码规范走"拉取"**——代理有问题时能查到规范。
- **自动化评审阶段：编码规范走"推送"**——把规范直接推给评审者，让它把"已写代码"和"编码规范"放在一起对照检查。

**模型选型：** 实现用 Sonnet，评审用 Opus——评审更需要"聪明"。

## **十一、并行化：Sand Castle**

Sand Castle 是 Matt 编写的 TypeScript 库，用于运行这些循环：

1. **规划器（planner）：** 查看积压工单（看板的阻塞关系），选出若干可并行处理的工单。
2. 为每个工单创建沙箱（Docker 容器 + git worktree/分支）。
3. 在沙箱中运行实现代理（传入工单号、标题、分支）。
4. 如果产生了提交，交给**合并代理（merger）**：传入合并提示词、分支和工单，执行合并；若类型、测试出问题则解决。
5. 稍后可以合回主干。

这实现了从"顺序循环"到"并行循环"的升级：多个代理在不同沙箱中同时工作，之后再合并评审。

## **十二、总结：整个流程**

- **全程保持对代码库形态的觉察：** 这不是 specs-to-code 编译器，不是无脑吐代码的 AI。我们有意识地设计想要的模块和代码库形态。
- **用 Grill 会话最大程度对齐**，把想法锤实。
- **不过度投入 PRD：** 不试图逐字读它，甚至不必太在意它。
- **把 PRD 转成可并行化的工单**，由多个代理并行处理。
- **实现后全力 QA 和代码评审**，再回到实现。QA 的产物就是给看板新增工单，如此循环。
- 全部完成后与团队共享，进行完整评审。此时通常由一两个开发者管理这个流程，并负责合回主干。
- **一切都可以自定义：** 这只是 Matt 发现行之有效的方式，不是标准答案。

**最后建议：** 如果只带走一点，那就是去读那些"AI 时代之前"的经典著作（《程序员修炼之道》《软件设计的哲学》等）。里面每一页都有有用的内容——这些书已经用自然语言把最好的软件工程实践表述出来了，可以直接放进提示词里使用。
