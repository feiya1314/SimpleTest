
# 1. JDK1.6 对 synchronized 做了哪些锁优化？

JDK1.6在锁方面做了哪些改进？高效并发体现在什么技术上？

**原理分析**

JDK1.6之前，`synchronized`直接调用`ObjectMonitor`的`enter`和`exit`，这种锁称为**重量级锁**。从JDK1.5到JDK1.6，HotSpot团队对Java中的锁进行了重要优化，主要包含以下几项技术：

- **适应性自旋锁**：避免线程被挂起阻塞，让线程在CPU上"稍等一下"
- **锁消除**：JIT通过逃逸分析，取消不存在竞争的同步
- **锁粗化**：将多次对同一对象的加解锁合并为一次
- **轻量级锁**：无竞争时通过CAS操作避免互斥量
- **偏向锁**：同一线程重复获取锁时，消除同步操作

这些优化对开发者透明，**只需使用synchronized，虚拟机根据竞争情况自行决定采用哪种锁**。

# 2. 什么是自旋锁？和阻塞锁有什么区别？

自旋锁的原理是什么？为什么需要自旋锁？

**原理分析**

自旋锁的核心思想：当线程请求锁时，如果锁已被持有，**线程不放弃CPU执行时间**，而是循环等待（自旋），不断检查锁是否释放。

**为什么需要自旋锁：** 共享数据的锁定状态一般只会持续很短时间，为了这段时间去挂起和恢复线程并不值得。Java线程映射到操作系统原生线程，阻塞或唤醒需要从**用户态切换到内核态**，开销很大。

**自旋锁 vs 阻塞锁的区别：**

- **阻塞锁**：线程放弃CPU时间，进入等待区，等待被唤醒
- **自旋锁**：线程不放弃CPU时间，保持运行状态，时刻检查共享资源是否可访问
- **响应速度**：自旋锁更快，因为不涉及线程状态切换
- **适用场景**：自旋锁适合**锁持有时间短、线程竞争不激烈**的情况；如果锁持有时间长或线程数多，自旋会浪费大量CPU时间

自旋锁在JDK1.4中引入，JDK1.6中**默认开启**。

# 3. 什么是锁消除？JIT 如何判断可以消除锁？

JIT编译器如何优化不必要的同步？

**原理分析**

**锁消除**是JIT编译器在动态编译同步块时，通过**逃逸分析（Escape Analysis）**判断同步块所使用的锁对象是否只能被一个线程访问。如果锁对象**不会逃逸到其他线程**，JIT编译时会取消这部分代码的同步。

例如以下代码中，`hollis`对象的生命周期只在`f()`方法内，不会被其他线程访问，JIT会将同步消除：

```java
public void f() {
    Object hollis = new Object();
    synchronized(hollis) {
        System.out.println(hollis);
    }
}
```

优化后等效为：

```java
public void f() {
    Object hollis = new Object();
    System.out.println(hollis);
}
```

典型的应用场景是**局部变量使用StringBuffer**这种线程安全的类做字符串拼接，开发者可能忽略了append方法上的synchronized，JIT可以帮忙消除不必要的同步。

锁消除是JIT编译阶段的功能（非javac编译），无法通过反编译直接观察，需要使用`-XX:+PrintEliminateLocks`参数在Server模式下查看。

# 4. 什么是锁粗化？和减小锁粒度是否矛盾？

锁粗化的原理是什么？它和锁粒度控制有什么联系？

**原理分析**

**锁粗化**：当JIT发现一系列连续操作都对同一个对象反复加锁和解锁（甚至出现在循环体中），会将加锁同步的范围**扩散（粗化）到整个操作序列外部**，减少频繁加解锁的开销。

例如：

```java
for(int i=0;i<100000;i++){
    synchronized(this){
        do();
    }
}
```

会被粗化为：

```java
synchronized(this){
    for(int i=0;i<100000;i++){
        do();
    }
}
```

**锁粗化与减小锁粒度并不冲突：**

- **减小锁粒度**：强调将无关的准备工作放在锁外，锁内只处理并发相关的内容，好比去银行办业务前先准备好资料，不在柜台前占用时间
- **锁粗化**：建议同一个线程要执行多个同步操作时，一次性完成所有操作，而非反复取号排队，好比办理多个业务时在同一个窗口一次办完

两者目的都是减少不必要的锁竞争和上下文切换开销。

# 5. 什么是适应性自旋锁？

适应性自旋锁相比传统自旋锁有什么改进？

**原理分析**

**适应性自旋锁**是JDK1.6引入的改进。传统自旋锁的自旋次数是固定的（如10次），而适应性自旋锁的自旋次数是**动态变化的**：

- 如果在同一个锁对象上，自旋等待刚刚成功获得过锁，JVM认为这次自旋成功的可能性大，会**允许自旋更多次数**
- 如果对于某个锁，自旋很少成功获得锁，JVM会**减少自旋次数甚至直接省略自旋**，避免浪费CPU

这种自适应的机制使得自旋锁能够在竞争激烈时自动退化为阻塞，在竞争不激烈时保持高效。

# 6. 什么是偏向锁？偏向锁的原理和撤销过程？

偏向锁的核心思想是什么？什么情况下会撤销偏向锁？

**原理分析**

偏向锁是JDK 1.6引入的锁优化，核心思想：**锁会偏向于第一个获取它的线程，在Mark Word中记录该线程ID**。之后该线程再次进入同步块时，无需任何CAS或互斥操作，直接进入。

**获取过程：**

- 线程访问同步块时，检查对象头Mark Word中偏向线程ID是否为当前线程
- 如果是，直接进入同步块，**无需任何同步操作**
- 如果否，通过CAS将Mark Word的偏向线程ID指向当前线程
- CAS成功 → 获得偏向锁
- CAS失败（存在竞争） → 撤销偏向锁，升级为轻量级锁

**撤销过程：**

- 偏向锁**不会主动释放**，只有遇到竞争时才撤销
- 需等待**全局安全点（STW）**，暂停所有线程
- 检查持有偏向锁的线程是否存活
- 线程不存活 → 对象头置为无锁态
- 线程存活 → 膨胀为轻量级锁或重量级锁
- 唤醒原持有线程，从安全点继续执行

**优缺点：**

- **优点**：同一线程反复获取锁时性能极高，无CAS开销
- **缺点**：撤销偏向锁需要STW，高竞争场景下反而增加开销

**JDK 15默认禁用偏向锁，JDK 21已正式移除偏向锁实现。**

# 7. 什么是轻量级锁？轻量级锁的原理？

轻量级锁如何实现无竞争时的高效同步？轻量级锁和偏向锁有什么区别？

**原理分析**

**轻量级锁**是JDK 1.6引入的优化，核心思想：**无竞争时通过CAS操作避免使用操作系统互斥量（Mutex）**。

**加锁过程：**

- 线程进入同步块时，如果对象处于无锁态，JVM在当前线程的栈帧中创建**锁记录（Lock Record）**空间
- 将对象头Mark Word复制到锁记录中（**displaced mark word**）
- 使用CAS将对象头Mark Word更新为指向锁记录的指针
- CAS成功 → 获得轻量级锁，Mark Word标志位变为00（轻量级锁）
- CAS失败 → 存在竞争，**锁膨胀**为重量级锁

**解锁过程：**

- 使用CAS将锁记录中的Mark Word替换回对象头
- 成功 → 解锁完成
- 失败 → 锁已膨胀为重量级锁，释放时需要唤醒阻塞队列中的线程

**与偏向锁的区别：**

- **偏向锁**：避免CAS操作，适合单一线程反复获取
- **轻量级锁**：通过CAS避免互斥量，适合少量线程**交替获取**锁

# 8. 什么是重量级锁？synchronized 底层如何实现重量级锁？

重量级锁的底层实现是什么？ObjectMonitor 如何工作？

**原理分析**

**重量级锁**是synchronized最传统的实现方式，JDK 1.6之前的synchronized默认就是重量级锁。底层依赖**操作系统的Mutex Lock（互斥量）**实现，通过ObjectMonitor（C++对象）完成。

**ObjectMonitor关键结构：**

- **_owner**：指向持有锁的线程
- **_cxq**：竞争队列，新竞争失败的线程先入_cxq
- **_EntryList**：阻塞队列，等待获取锁的线程列表
- **_WaitSet**：调用wait()方法后进入的等待队列

**加锁/解锁流程：**

- 线程调用`ObjectMonitor::enter`尝试获取锁
- **_owner为空时**，CAS将_owner指向当前线程，获得锁
- **_owner已被占用时**，线程进入_cxq或_EntryList阻塞
- 释放锁时，从_cxq或_EntryList中唤醒等待线程
- 线程阻塞和唤醒需要从**用户态切换到内核态**，开销大

**特点：**

- **优点**：竞争激烈时线程阻塞，不消耗CPU
- **缺点**：线程切换需要内核态用户态切换，**开销大**

**轻量级锁和重量级锁的关系：** 轻量级锁通过CAS乐观自旋避免互斥；自旋失败或超过阈值时**膨胀为重量级锁**，使用Mutex进行互斥阻塞。

# 9. 什么是锁膨胀？锁升级的过程是怎样的？

锁膨胀经历了哪些阶段？各阶段如何转换？

**原理分析**

**锁膨胀（Lock Inflation）**也叫锁升级，指synchronized的锁状态从低到高逐步升级的过程。锁只能升级，不能降级（GC的STW阶段除外）。

**完整锁升级路径：** 无锁 → 偏向锁 → 轻量级锁 → 重量级锁

**各阶段转换：**

**无锁 → 偏向锁：**
- 第一个线程获取锁时，JVM通过CAS将偏向线程ID写入Mark Word
- 锁标志位设为01，偏向位设为1

**偏向锁 → 轻量级锁：**
- 第二个线程尝试获取偏向锁时，CAS失败
- 等待**全局安全点**，撤销偏向锁
- 恢复为无锁态或直接升级为轻量级锁

**轻量级锁 → 重量级锁：**
- 多个线程同时竞争轻量级锁，CAS失败
- JIT的自旋策略尝试自旋等待
- 自旋超过阈值或等待线程数过多 → **膨胀为重量级锁**
- Mark Word指向ObjectMonitor，锁标志位变为10

**关键参数：**

- **`-XX:BiasedLockingStartupDelay=0`**：关闭偏向锁延迟，应用启动后立即启用
- **`-XX:-UseBiasedLocking`**：禁用偏向锁（JDK 15后默认禁用）
- **自旋次数**：由适应性自旋动态决定，不再固定

**为什么锁不能降级：** 避免频繁的膨胀和收缩带来的性能抖动。重量级锁释放后仍保持重量级锁标记，只有GC的STW阶段才可能触发锁降级（偏向锁→无锁）。
