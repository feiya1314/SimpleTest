# 接入标准

**需求描述**

明确需求范围： 阵地：国内商城、国内亲选、亚太商城、..等 端侧：apk,wap,mp,web,los等

如涉及到流程变更的需求，应明确需求的业务场景、业务流程、相关干系人：

1. 从业务视角描述整体的流程：各部门/角色间如何协作，操作的条件，每个动作的结果等
2. 规则描述要明确，比如：要明确涉及到的订单的详细类型（普通订单、订金订单、代销类的订单等），而不能泛泛的说：订单；
3. 特别说明：针对每个环节的异常场景，需要给业务的处理建议（比如说 用户签到失败，应给用户一个什么样的提示；申请给用户返现，如财务审核不通过，应如何处理 等等）

**产品规格及解决方案设计**

高阶系统交互流程图：（可以由应用SE协助输出）

1. 需写到应用服务间的交互，明确应用服务间的交互；交互接口的说明，接口传递的主要信息，不需要把所有属性列出来。
2. 需基于现有应用服务间的交互关系，明确是对某个接口的升级，还是需新增接口。

核心对象状态流转图： 对业务流程的进一步细化：抽象出业务对象，解析业务对象的状态

# 2. 设计规范

## 2.1 微服务设计规范

电商产品根据人、货、场、内容等领域共划分为九大应用，每个应用又被细分为多个应用服务，每个应用服务则是由一个或多个微服务组成。

本规范包括了微服务设计原则、接口设计规范、数据一致性与事务、服务部署与运维以及开发实践与工具等方面的内容，也包括了电商产品的应用分层架构、公共框架设计、当前的应用服务列表等内容。

请参考： 电商微服务设计规范.docx

## 2.2 数据相关应用开发规范

主要针对我们电商各应用用到的数据相关的基础设施，结合以往的研发经验，给出简明、实用的设计&开发规范。 主要涉及 mysql表设计及SQL开发规范、mongo表设计及开发规范、数据缓存（redis）的设计及开发规范、消息队列应用开发规范等。

### 2.2.1 mysql表设计及SQL开发规范

包括建表的设计规范，以及表的查询、数据修改等SQL开发规范等。

有些非常基本的规则，是要求每个人都要记在心里的：

1. 统一用utf8字符集；如需要存储 表情符号、数学符号和其他特殊字符（一般是存储UGC明文场景），则需要将字符集改为 utf8mb4
2. 对象（表、字段、索引等）名称统一用小写字母
3. 不要用触发器，不要建外键，不要用视图，不要用存储过程
4. 字段类型禁止使用枚举类型（enum）和大对象类型（clob, blob）
5. 不要删除字段 \~你可能真的不知道会影响谁
6. 预估表的规模，随事务持续增长的表要考虑分库分表、转储、老化等
7. 新增字段，应尽可能复用现有主表中的字段设计，比如user_id 应跟tbl_customer的定义保持一致

# 2.2.4 消息队列应用开发规范

消息队列是实现系统间的解耦、处理瞬时高流量业务（削峰填谷）的有效手段。

电商中的多个应用服务使用了rocketMQ，基本的设计原则如下：

1. Topic名称应明确表达业务域，Tag名则需明确表达信息的主题。
2. 消息内容应使用结构化的格式，如采用竖线分割的二维表或JSON格式
3. 兼容性：不能删除已有字段，不能修改现有字段的数据类型
4. 消息的目的是高效率的告知上下游模块发生了某个事，所以消息应尽可能的简洁，大小应控制在1KB以内
5. 消息的生产和消费均需要考虑幂等性

详细的规范和宝贵的经验，请参考： 消息队列应用开发规范.docx

# 2.3 配置规范

我们一般有两大类配置：

一类是环境相关的配置，比如站点的域名、数据库的密码、三方服务地址 等；这类配置在Apollo中管理，由运维人员负责管理。

# 2.4 DFx设计

## 2.4.1 高性能

高性能是设计出来的。 高性能一般会伴随着成本的上升。

提升性能一般从如下角度着手：

1. 水平扩容：设计无状态的服务，支持水平扩容（一个不行，那就两个，两个不行，那就再来一个）；服务可以扩容，但数据能力的扩容比较麻烦，所以，要提前考虑分库、分表，为水平扩容做准备
2. 垂直扩容：服务实例要支持硬件配置的扩容（2C4G不够，那就4C8G…）
3. 应用优化：扩容解决性能问题是最直接的，也是开发人员本能会想到的解决方法（毕竟是没有开发成本）；但是，老板们则会把应用程序优化作为最优解：是不是没有索引啊、是不是有内存泄漏啊、是不是缓存被击穿了啊、代码逻辑能不能再优化一下啊、对业务流程稍作简化都行… 这部分内容比较多，数据应用开发规范的章节中有些内容涉及到了高性能的经验、java的高性能开发经验等，请大家移步到《电商IT开发规范》中学习
4. 缓存方案：这个很关键，电商产品从接入层、服务层、数据层等全方位应用了不同的缓存技术；请通过如下文章了解详情：电商缓存方案.docx
