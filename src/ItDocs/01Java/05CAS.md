# 1. CAS是什么

CAS（Compare And Swap，**比较并交换**）是实现并发算法时常用到的一种技术。**CAS 是一个原子操作**，包含三个操作数：内存位置、预期原值及新值。执行 CAS 操作时，**将内存位置的值与预期原值比较，如果相匹配，处理器会自动将该位置值更新为新值；否则处理器不做任何操作**。

CAS 需要 3 个操作数：

- **V（内存地址）**：要操作的内存位置
- **A（旧的预期值）**：上一刻从此内存地址读出来的值
- **B（新值）**：即将要更新的目标值

CAS 指令执行时，**当且仅当内存地址 V 的值与预期值 A 相等时**，才会将内存地址 V 的值修改为 B，否则什么都不做。整个"比较并交换"的过程由一条指令完成，因此是一个**原子操作**（处理器层面保证了这一条指令的比较交换过程不可分割）。

# 2. CAS 更新值时如何保证线程安全

CAS 的**比较并交换**在 CPU 层面是一条原子指令，底层使用了 **cmpxchg 指令**（汇编版的"比较并交换"）。但多核环境下，这一条"读-改-写"指令需要与其它核的访问串行化，所以在 cmpxchg 之前，**如果是多核 CPU，会添加 LOCK 前缀**，从而保证 CAS 的线程安全性。同时，Atomic 类中使用了 **volatile**，保证 CAS 操作后其他线程能立即看到修改后的值。

**LOCK 前缀是如何实现的：**

1. **早期实现（总线锁）**：直接将 CPU 的总线阻塞，其他处理器暂时无法通过总线访问内存，实现效率很低
2. **后期优化（缓存锁）**：X86 CPU 依赖缓存一致性协议（如 MESI）在 cache line 粒度上实现原子性：只有持有锁的核能修改该缓存行，其他核看到一致的数据视图，LOCK# 信号不再发出，开销大幅降低

**添加 lock 前缀的判断逻辑：**

1. 如果通过 `mp` 判断当前系统是多处理器（即 mp 值为 1），则为 cmpxchg 指令添加 lock 前缀，即 `lock cmpxchg`
2. 否则，不加 lock 前缀

这是一种优化手段：**单处理器的环境没有必要添加 lock 前缀**，只有在多核情况下才会添加，因为 lock 会导致性能下降。cmpxchg 是汇编指令，作用是比较并交换操作数。简单来说，**单核 CPU 下 cmpxchg 是原子的**（多核不添加 lock 指令时，两个 core 同时执行针对同一地址的 CAS 指令，其实是在试图修改每个 core 自己持有的 Cache line）。

**为什么多核需要 lock 前缀：**

内存总线只有一条，是独占的，不管是多核还是单核，同一时间只能有一个占用总线。cmpxchg 指令读取目的内存操作数，与寄存器中的值比对，如果相同，则将新值写到目的内存地址。加上 lock 后，读内存时会对内存总线发出 LOCK 信号，锁住总线，**这个锁要到将新值写到目的内存地址后才会解除**。因此，加上 lock 前缀的 cmpxchg 指令在读与写之间不会有其他元器件访问内存，所以是原子的。

**为什么单核不需要 lock 前缀：**

当 CPU 为单核时，尽管 cmpxchg 要访问两次内存，但在该指令执行过程中不会有其他核打断指令执行过程（中断不会发生在单条指令执行过程中，只会发生在指令执行前后，不会在指令中间发生），因此读与写之间也就不会有其他核访问内存，所以单核 CPU 不用加 lock 前缀就已经是原子的了。单处理器自身会维护单处理器内的顺序一致性，不需要 lock 前缀提供的内存屏障效果。

**从总线锁到缓存锁：**

早期 CPU 的 lock 是通过锁内存总线来实现原子性的。目前 CPU 一般都采用了很好的**缓存一致性协议**，在很多情况下能够防止锁总线的发生，其中最著名的就是 Intel CPU 中使用的 **MESI 缓存一致性协议**。

Intel 开发者手册 8.1.4 中描述：**在 P6 以后的 x86 处理器中，原子操作（例如 cmpxchg）不再发出任何 lock 信号，一切都由缓存一致性协议来完成**。

**Atomic::cmpxchg 方法解析：**

1. `mp` 是 `os::is_MP()` 的返回结果，`os::is_MP()` 是一个内联函数，用来判断当前系统是否为多处理器
2. 如果当前系统是多处理器，该函数返回 1；否则返回 0
3. **LOCK_IF_MP(mp)** 会根据 mp 的值决定是否为 cmpxchg 指令添加 lock 前缀：
   - 如果通过 mp 判断当前系统是多处理器（即 mp 值为 1），则为 cmpxchg 指令添加 lock 前缀，即 `lock cmpxchg`
   - 否则，不加 lock 前缀

这是一种优化手段：认为单处理器的环境没有必要添加 lock 前缀，只有在多核情况下才会添加，因为 lock 会导致性能下降。cmpxchg 是汇编指令，作用是比较并交换操作数。简单来说，**单核 CPU 下 cmpxchg 是原子的**（多核不添加 lock 指令时，两个 core 同时执行针对同一地址的 CAS 指令，其实是在试图修改每个 core 自己持有的 Cache line）。

**intel 手册对 lock 前缀的说明：**

1. **确保对内存的读-改-写操作原子执行**。在 Pentium 及 Pentium 之前的处理器中，带 lock 前缀的指令在执行期间会锁住总线，使得其他处理器暂时无法通过总线访问内存，这会带来昂贵的开销。从 P6（Pentium Pro）及其后续家族（Pentium 4、Intel Xeon 等）处理器开始，intel 在原有总线锁的基础上做了一个很有意义的优化：如果要访问的内存区域（area of memory）在 lock 前缀指令执行期间已经在处理器内部的缓存中被锁定（即包含该内存区域的缓存行当前处于独占或以修改状态），并且该内存区域被完全包含在单个缓存行（cache line）中，那么处理器将直接执行该指令。由于在指令执行期间该缓存行会一直被锁定，其他处理器无法读/写该指令要访问的内存区域，因此能保证指令执行的原子性。这个操作过程叫做**缓存锁定（cache locking）**，缓存锁定将大大降低 lock 前缀指令的执行开销。但是当多处理器之间的竞争程度很高，或者指令访问的内存地址未对齐时，仍然会锁住总线。现代处理器，在内存可缓存（write-back 模式）且锁定区域完整包含在单个缓存行内时，不发 LOCK# 信号；否则（跨越缓存行，或访问不可缓存 uncacheable 的内存区域）才会在总线上发 LOCK# 信号
2. **禁止该指令与之前和之后的读和写指令重排序**
3. **把写缓冲区中的所有数据刷新到内存中**

上面的第 1 点保证了 CAS 操作是一个原子操作，第 2 点和第 3 点所具有的内存屏障效果，保证了 CAS 同时具有 volatile 读和 volatile 写的内存语义。

**多核同时执行 CAS 的过程（缓存一致性）：**

当两个 core 同时执行针对同一地址的 CAS 指令时，其实它们是在试图修改每个 core 自己持有的 Cache line。假设两个 core 都持有相同地址对应的 cacheline，且各自 cacheline 状态为 S（共享）：

1. 要想成功修改，首先需要把 S 转为 E 或 M，则需要向其他 core 发出 invalidate（失效）这个地址的 cacheline 的操作
2. 两个 core 都会向 ring bus 发出 invalidate 操作
3. ring bus 会根据特定的设计协议仲裁是 core0 还是 core1 能赢得这次 invalidate
4. 胜者完成操作，失败者需要接受结果，invalidate 自己对应的 cacheline，再读取胜者修改后的值，回到起点

这里需要区分两种场景：**片内多核**通常使用 ring bus 互联，一致性由 **MESI** 协议维护；而 **MESIF** 协议（在 MESI 基础上增加 F 转发态）用于 **QPI 跨 socket（多路）**互联，F 态允许 cache-to-cache 直接转发，大大降低了读操作的时延，同时保持了一致性。那么对于 CAS 操作来说，**锁并没有消失，只是转嫁到了总线仲裁协议中**。而且大量的多核同时针对一个地址的 CAS 操作会引起反复的互相 invalidate 同一 cacheline，造成 **pingpong 效应**，同样会降低性能。只能说基于 CAS 的操作仍然不能滥用，不到万不得已不用，通常情况下还是使用数据地址范围分离模式更好。

# 4. 为什么不用lock，而是用CAS

直接加 Lock 是**悲观锁思路**，CAS 比较再交换是**乐观锁思路**。

**CAS 的执行流程：**

1. 读取内存当前值作为预期值 A
2. 用一条 `cmpxchg` 原子指令完成"比较 + 交换"：将内存值 V 与预期值 A 比较，相等则写入新值 B
3. 相等 → CAS 成功，返回 true
4. 不相等 → CAS 失败，重新读取当前值，自旋重试

**注意**：cmpxchg 是**一条指令**，比较和交换不可拆分。在多处理器上，HotSpot 会对每次 CAS **无条件**添加 LOCK 前缀（`LOCK_IF_MP`），与是否有竞争无关。**无竞争时开销低**的真正原因是**缓存锁**：无竞争时目标缓存行已被本核独占（E/M 态），LOCK# 信号不会发出，原子操作只在 cache 内完成；有竞争或跨缓存行时才升级为总线锁。

**为什么不直接用 Lock：**

1. 直接 Lock（如 synchronized）走锁升级路径，重量级锁会涉及 OS 互斥与线程阻塞/唤醒，开销大
2. 现实中写冲突是小概率事件，CAS 先比较、乐观尝试，能不加锁就不加锁
3. CAS 失败只是用户态自旋重试，不阻塞线程、不上下文切换
4. CAS 采用乐观策略，真正昂贵的总线锁只在发生缓存竞争时才会触发，兼顾安全和高性能

**CAS 的性能瓶颈：**

性能瓶颈主要来自于：多核环境下，上次执行 CAS 更新的 CPU 和本次执行 CAS 更新的 CPU 不是同一个 CPU。例如：

1. CPU 1 执行了某个内存地址 X 的 CAS 更新，那么 X 对应的内存会被载入 CPU 1 的高速缓存中
2. 这时候 CPU 2 需要 CAS 更新 X，发现 CPU 2 的高速缓存中没有 X
3. 查询总线，发现 CPU 1 有
4. CPU 1 将 X 发送给 CPU 2，并且刷新自己高速缓存中的缓存线
5. CPU 2 可以执行 CAS 更新了

# 5. CAS的问题

**1. ABA问题**

因为 CAS 会检查旧值有没有变化，这里存在一个有意思的问题。比如一个旧值 A 变为了 B，然后再变成 A，刚好在做 CAS 时检查发现旧值并没有变化依然为 A，但是实际上确实发生了变化。解决方案可以沿袭数据库中常用的乐观锁方式，**添加一个版本号**可以解决。原来的变化路径 A->B->A 就变成了 1A->2B->3A。java 1.5 后的 atomic 包中提供了 **AtomicStampedReference** 来解决 ABA 问题，解决思路就是这样。

**2. 自旋时间过长**

使用 CAS 时是非阻塞同步，也就是说不会将线程挂起，会**自旋**（无非就是一个死循环）进行下一次尝试，如果这里自旋时间过长，对性能是很大的消耗。如果 JVM 能支持处理器提供的 pause 指令，那么在效率上会有一定的提升。

JDK 1.6 引入了更加聪明的自旋锁，即**自适应自旋锁**：线程如果自旋成功了，那么下次自旋的次数会更加多，因为虚拟机认为既然上次成功了，此次自旋也很有可能会再次成功，那么它就会允许自旋等待持续的次数更多。

**3. 只能保证一个共享变量的原子操作**

当对一个共享变量执行操作时，CAS 能保证其原子性；如果对多个共享变量进行操作，CAS 就不能保证其原子性。有一个解决方案是**利用对象整合多个共享变量**，即一个类中的成员变量就是这几个共享变量，然后将这个对象做 CAS 操作就可以保证其原子性。atomic 中提供了 **AtomicReference** 来保证引用对象之间的原子性。

**4. 高并发场景下的自旋性能问题**

如果大量的线程同时并发修改一个 AtomicInteger，这些线程不停地获取值，然后发起 CAS 操作，但是发现这个值被别人改过了，于是再次进入下一个循环：获取值、发起 CAS 操作又失败，如此反复，就会产生很多线程不停自旋，进入一种无限重复的循环状态。在大量线程高并发更新 AtomicInteger 的时候，这种问题可能会比较明显，导致大量线程空循环、自旋，性能和效率都不是特别好。

为了解决这个问题，**Java 8 对 CAS 进行了优化**，推出了一个新的类 **LongAdder**，它尝试使用**分段 CAS 以及自动分段迁移**的方式来大幅度提升多线程高并发执行 CAS 操作的性能。

# 6. CAS的ABA问题

CPU 的 CAS 指令（cmpxchg）本身是原子的，一次"比较 + 交换"不会被拆散。但**基于 CAS 的算法**会产生 ABA 问题：单条指令的原子性只保证比较和交换不被拆散，却防不住"值在两次操作之间被别的线程改成 B、又改回 A"——它无法区分"从未变过"和"变回原值"两种情况。**原子性和 ABA 是两回事**。

**什么是 ABA 问题：**

ABA 问题是指在 CAS 操作时，其他线程将变量值 A 改为了 B，但是又被改回了 A。等到本线程使用期望值 A 与当前变量进行比较时，发现变量 A 没有变，于是 CAS 就将 A 值进行了交换操作，但是实际上该值已经被其他线程改变过。

**是 CAS 本身有问题吗？**

当然不是。并不是 CAS 的问题导致了 ABA，而是 ABA 问题在 CAS 下发生时不是很容易被联想到。CAS 只是简单的比较并交换，只要是符合 compare 条件（没有被其他线程修改过预期值）就会被 swap（设置为我想要的值），本身是没有问题的。所以我们应该把问题描述清楚：**如果在用 CAS 的时候发生了 ABA 问题，我们应该怎么解决？**

**Java 的 CAS 实现：**

CAS 是一条 CPU 的原子指令（cmpxchg 指令），不会造成所谓的数据不一致问题，Unsafe 提供的 CAS 方法（如 compareAndSwapXXX）底层实现即为 CPU 指令 cmpxchg。

**ABA 影响业务的例子：**

假设现有一个用单向链表实现的堆栈，栈顶为 A，此时线程 T1 已经知道 A.next 为 B，然后希望用 CAS 将栈顶替换为 B：

```java
head.compareAndSet(A, B);
```

1. 在 T1 执行上面这条指令之前，线程 T2 介入，将 A、B 出栈（栈顶变为 C），再依次 push D、C、A，栈变为 A→C→D；此时 B.next 仍指向 C（出栈操作不会清空节点的 next 引用）
2. 此时轮到线程 T1 执行 CAS 操作，检测发现栈顶仍为 A，所以 CAS 成功，将栈顶替换为 B
3. 由于 B.next 仍指向 C，链表变为 B→C→D，看起来仍然"自洽"，C 和 D 并没有丢失
4. 但 T2 刚重新入栈的节点 A 已经不在链表上，**A 被丢弃（内存泄漏）**，栈数据发生了丢失——这就是 ABA 造成的错误结果

**ABA 的解决方法：**

1. **版本号**：比如，上面的栈结构增加一个版本号用于控制，每次 CAS 的同时检查版本号有没有变过。还有一些数据结构喜欢使用高位存储一个邮戳来保证 CAS 的安全
2. **不重复使用节点的引用**：比如，上面的栈结构在线程 2 执行 push() 入栈操作的时候新建一个节点传入，而不是复用节点 1 的引用

**AtomicStampedReference 解决 ABA：**

使用 CAS（也就是使用 compareAndSet(current, next) 方法）进行无锁自加或者更换栈的表头之类的问题时会出现 ABA 问题，Java 中使用 **AtomicStampedReference** 来解决 CAS 中的 ABA 问题。它不再像 compareAndSet 方法中只比较内存中的值和当前值是否相等，而是**先比较引用是否相等，然后再比较值是否相等**，这样就避免了 ABA 问题。

**AtomicStampedReference 常用方法：**

- 构造方法，传入引用和戳：`public AtomicStampedReference(V initialRef, int initialStamp)`
- 返回引用：`public V getReference()`
- 返回版本戳：`public int getStamp()`
- 如果当前引用等于预期值且当前版本戳等于预期版本戳，将更新新的引用和新的版本戳到内存：`public boolean compareAndSet(V expectedReference, V newReference, int expectedStamp, int newStamp)`
- 如果当前引用等于预期引用，将更新新的版本戳到内存：`public boolean attemptStamp(V expectedReference, int newStamp)`
- 设置当前引用的新引用和版本戳：`public void set(V newReference, int newStamp)`

**AtomicStampedReference 实现原理：**

1. 首先，使用版本号控制
2. 其次，不重复使用节点（Pair）的引用，每次都新建一个新的 Pair 来作为 CAS 比较的对象，而不是复用旧的
3. 最后，外部传入元素值及版本号，而不是节点（Pair）的引用

# 7. AtomicInteger 有 ABA 问题吗

**有。AtomicInteger 存在 ABA 问题。**

**1. 为什么会有**

`AtomicInteger.compareAndSet(int expect, int update)` **只对比数值**，不记录版本。 流程示例：

1. 初始值 `x = A = 10`
2. 线程 1 读取 `x=10`，准备 CAS；此时被 CPU 挂起
3. 线程 2：把 `10 → 20`，再把 `20 →10`
4. 线程 1 恢复，执行 `compareAndSet(10, 30)`
   - 当前内存值确实是 10，CAS 执行成功。
   - 线程 1**感知不到中间发生过修改**，这就是 ABA。

AtomicInteger 底层就是单纯数值比较，**没有版本戳，天然无法区分 “一直是 A” 和 “A 被改过又变回 A”**。

**那平时使用 AtomicInteger，ABA 一定会出 bug 吗？**

**不一定，要看业务场景：**

1. **单纯数值自增场景（例如计数器** `incrementAndGet`**）** ABA 几乎不会造成问题。

   > 计数器只关心最终数值，不在乎中间经历了多少次变化，即使 A→B→A，自增语义不受破坏。这也是日常 AtomicInteger 最常用场景。
2. **引用对象、状态流转场景（状态 A→B→A）** ABA 会产生严重逻辑错误。

   > 例如：对象状态、队列节点操作（经典的无锁链表节点删除场景），这时必须用 `AtomicStampedReference`。

> 一句话总结： AtomicInteger **具备 ABA 漏洞**，但在单纯数字计数场景，ABA 一般不影响业务； 如果是状态 / 对象引用的逻辑，不能用它，要带版本戳。

**自旋锁的实现，**自旋CAS，是一个自旋锁**：**

```
AtomicInteger：
	public final int getAndIncrement(){
		return unsafe.getAndAddInt(this,valueOffset,1);
	}
	
	进入unsafe 方法中，可以发现，保证线程安全的方式就是 自旋CAS，是一个自旋锁
	public final int getAndAddInt(Object var1, long var2, int var4) {         
	    int var5;                                                             
	    do {                                                                  
	        var5 = this.getIntVolatile(var1, var2);                           
	    } while(!this.compareAndSwapInt(var1, var2, var5, var5 + var4));      
	                                                                           
	    return var5;                                                          
}
```

# 8. CAS 能保证线程安全吗

单纯 CAS 指令本身只能保证「单次比较交换这一步原子性」；不能无条件保证一段业务逻辑线程安全，要看你怎么用。

1. **硬件层面：CAS 指令本身是原子的**`比较 + 交换` 这一个 CPU 指令不可被打断，多线程并发执行这条指令不会出现 “一半执行完” 的情况。 👉 **单个变量单次 CAS 操作具备原子性。**
2. **业务层面：一段逻辑只用一次 CAS 不一定线程安全** 典型反面例子：`x++`

```
old = get(x);        // 步骤1 读
newVal = old + 1;   // 步骤2 计算
cas(old, newVal);   // 步骤3 CAS更新

```

整个 `读→计算→CAS` **不是原子的**。 两个线程可以先后读到同一个 old 值，计算出相同 newVal，先后执行 CAS，后一次覆盖前一次，产生**更新丢失**。

**正确用法：自旋 CAS（AtomicInteger 的实现）这种写法下，可以保证单个变量线程安全。**

```
do {
    old = get();
    newVal = old + 1;
} while (!cas(old, newVal));

```

逻辑：

- 如果 CAS 失败，说明期间被其他线程修改，重新读取最新值，重新计算，再次尝试；
- 直到 CAS 成功退出循环。
