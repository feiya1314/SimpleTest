# 1. SOLID 五大设计原则 + 额外两大原则分别是什么？

面向对象设计的 **7 大原则**，前 5 个合称 SOLID：

**S** — **单一职责原则**（Single Responsibility）：一个类只负责一件事。

**O** — **开闭原则**（Open/Closed）：对扩展开放，对修改关闭。

**L** — **里氏替换原则**（Liskov Substitution）：子类必须能替换父类且不破坏逻辑。

**I** — **接口隔离原则**（Interface Segregation）：接口要小而专，不强迫实现类依赖不需要的方法。

**D** — **依赖倒置原则**（Dependency Inversion）：依赖抽象，不依赖具体实现。

**迪米特法则**（Law of Demeter）：最少知道原则，一个对象应尽量少地了解其它对象。

**合成复用原则**（Composite Reuse）：优先使用组合/聚合，而不是继承来复用代码。

# 2. 单一职责原则如何把握粒度？

**定义**：一个类 / 一个方法只应该有一个引起它变化的原因。

粒度把握的 **关键判断依据**：

1. **从变化维度出发** — 如果两个功能因为不同的原因被修改，就应该拆开。
2. **从职责语义出发** — 如果你无法用一句话说清这个类负责什么，大概率违反 SRP。
3. **从类的方法数量出发** — 方法过多通常意味着职责过重（仅参考，不是绝对）。

例子：

```java
// ❌ 违反：既负责订单逻辑，又负责日志、通知
class OrderService {
    void createOrder(Order order) {
        // 订单校验
        // 写入DB
        // 写日志
        // 发短信通知
    }
}

// ✅ 符合：拆分后各司其职
class OrderService {
    void createOrder(Order order) { ... }
}
class Logger { void log(String msg) { ... } }
class Notifier { void notify(User user) { ... } }
```

**面试口述要点**：不要过度拆分也不要过于聚合，判断标准是"变化来源"——如果两个功能因为完全不同的需求变更而修改，就应该拆分。

# 3. 开闭原则在架构中如何体现？

**定义**：软件实体（类、模块、函数）应该 **对扩展开放，对修改关闭**。

架构层面的 **体现方式**：

1. **策略模式 + 接口抽象** — 新增支付方式只需新增实现类，不改核心逻辑。
2. **插件化架构** — Spring 的 Bean 机制，新增功能通过扩展点注入，不需改框架代码。
3. **SPI 机制** — JDBC 驱动、Dubbo 扩展点，都基于接口编程，运行时加载实现。
4. **AOP 切面** — 不修改业务代码，通过切面统一增加日志、事务、权限。

典型例子：支付系统

```java
// 定义抽象
interface Payment { void pay(Order order); }

// 原有实现
class WechatPay implements Payment { ... }

// 新增实现——不改老代码，只新增类
class AliPay implements Payment { ... }
```

**面试口述要点**：核心是多态和抽象，**扩展不修改**是架构稳定性的基石。Spring IoC 容器就是开闭原则的最佳实践。

# 4. 里氏替换原则有哪些约束？

**定义**：所有引用父类的地方必须能透明地使用其子类对象。

**具体约束**：

1. **子类不能重写/修改父类的已有方法行为**（覆盖后行为必须一致）。
2. **子类不能抛出父类没有声明的异常**（可以更少或更具体，不能更多）。
3. **子类方法的前置条件不能比父类更严格**（参数范围不能缩小）。
4. **子类方法的后置条件不能比父类更宽松**（返回值范围不能扩大）。
5. **子类不能改变父类的不可变属性**（如 final 语义）。

经典反例：正方形继承矩形

```java
class Rectangle {
    int w, h;
    void setW(int w) { this.w = w; }
    void setH(int h) { this.h = h; }
}
class Square extends Rectangle {
    void setW(int w) { this.w = w; this.h = w; } // ❌ 改变了行为
}
// 调用方期待 setW 只改宽度，Square 却连高度一起改了
```

**面试口述要点**：不要被继承的"is-a"迷惑，要看行为语义是否一致。**组合优于继承**往往是避免 LSP 违背的最好方式。

# 5. 接口隔离原则与单一职责原则的区别是什么？

**SRP** 关注的是 **类的内聚性** — 一个类职责是否单一。

**ISP** 关注的是 **接口的粒度** — 接口是否够小，实现类是否不需要实现无用方法。

**核心区别**：

- SRP 是面向 **实现** 的角度，解决"类该干什么"。
- ISP 是面向 **调用者** 的角度，解决"接口要暴露什么"。
- SRP 拆分后可能得到一个类 + 多个方法；ISP 拆分后得到多个小接口。
- 违反 SRP 的类臃肿难改；违反 ISP 的接口导致调用方被迫依赖不需要的东西。

例子：

```java
// ❌ 违反 ISP：大接口
interface Worker {
    void work();
    void eat();
    void sleep();
}
class Robot implements Worker {
    void eat() { throw new UnsupportedOperationException(); } // 被迫实现
}

// ✅ 符合 ISP：拆分
interface Workable { void work(); }
interface Eatable { void eat(); }
interface Sleepable { void sleep(); }
class Robot implements Workable { ... }
class Human implements Workable, Eatable, Sleepable { ... }
```

**面试口述要点**：SRP 管"类的职责边界"，ISP 管"接口的契约粒度"。

# 6. 依赖倒置与依赖注入/IoC 的关系？

**依赖倒置（DIP）** 是设计原则——**高层不依赖低层，都依赖抽象**。

**IoC（控制反转）** 是一种思想——将对象创建和依赖管理的控制权从应用代码中反转给容器。

**依赖注入（DI）** 是 IoC 的具体实现方式——容器在创建对象时自动注入它依赖的对象。

**三者的关系**：

1. DIP 是 **目标**：我们要让代码依赖抽象而非具体实现。
2. IoC 是 **手段**：通过反转控制权来达到 DIP。
3. DI 是 **具体做法**：通过构造器注入、Setter 注入、接口注入来解耦。

```java
// ❌ 违反 DIP：业务直接依赖具体实现
class UserService {
    private MysqlRepo repo = new MysqlRepo();
}

// ✅ 符合 DIP：依赖抽象 + DI 注入
class UserService {
    private final UserRepo repo; // 依赖抽象
    UserService(UserRepo repo) { // 构造器注入
        this.repo = repo;
    }
}
```

**面试口述要点**：Spring 的 IoC 容器就是 DIP 原则的工程实践典范，通过 DI 让所有 Bean 面向接口编程。

# 7. 迪米特法则（最少知道原则）是什么？

**定义**：一个对象应该对其它对象保持最少的了解，**只与其直接的朋友通信**。

**核心规则**：

1. **不向陌生人发消息** — 不要通过链式调用深入访问一个对象的内部对象。
2. **方法内只调用**：自身方法、参数对象方法、成员变量方法、创建的对象方法。
3. **避免长方法链** — `a.getB().getC().doSomething()` 就是典型违反。

```java
// ❌ 违反：Order 依赖 OrderDetail 再依赖 Product
class OrderService {
    void process(Order order) {
        order.getDetail().getProduct().getPrice(); // 链式调用太深
    }
}

// ✅ 符合：把逻辑移到 Order 内部
class Order {
    void process() { this.detail.process(); }
}
```

**面试口述要点**：迪米特法则是**降低耦合**的实战法则，核心是"只和直接朋友说话，不要隔层操作"。

# 8. 合成复用原则是什么？

**定义**：尽量使用 **组合/聚合** 实现代码复用，而不是继承。

**理由**：

1. **继承破坏封装** — 子类依赖父类实现细节，父类变更可能影响所有子类。
2. **组合更灵活** — 运行时可以动态替换行为。
3. **组合不暴露内部实现** — 符合接口隔离和迪米特法则。

```java
// ❌ 继承复用
class DBQuery extends MysqlConnection { ... }

// ✅ 组合复用
class DBQuery {
    private final Connection conn; // 组合
    DBQuery(Connection conn) { this.conn = conn; }
}
```

**面试口述要点**：GOF 的"**组合优于继承**"就是合成复用原则的体现，Spring 大量使用组合来扩展功能。

# 9. 模板方法模式

**定义**：在父类中定义一个算法的 **骨架**，将某些 **步骤延迟到子类** 实现。

**核心要点**：

1. 父类定义不可变的执行流程（用 `final` 修饰）。
2. 父类提供默认实现或抽象方法让子类实现。
3. 子类不改变流程结构，只重写特定步骤。

```java
abstract class AbstractProcessor {
    // 模板方法，定义流程
    public final void process() {
        step1();
        step2();
        step3();
    }
    abstract void step1();
    void step2() { /* 默认实现 */ }   // hook
    abstract void step3();
}
class XmlProcessor extends AbstractProcessor {
    void step1() { /* read XML */ }
    void step3() { /* parse XML */ }
}
```

**应用场景**：AQS（AbstractQueuedSynchronizer）、Spring JdbcTemplate、Servlet 的 `doGet`/`doPost`。

**面试口述要点**：模板方法适合"流程固定，细节可变"的场景，核心是 **好莱坞原则——不要调用我，我来调用你**。

# 10. 策略模式

**定义**：定义一系列算法，将每个算法封装起来，使它们可以 **互相替换**。

**核心组成**：

1. **Context** — 持有策略引用，负责调用策略。
2. **Strategy 接口** — 定义算法族。
3. **ConcreteStrategy** — 具体算法实现。

```java
interface CompressionStrategy {
    byte[] compress(byte[] data);
}
class ZipStrategy implements CompressionStrategy { ... }
class RarStrategy implements CompressionStrategy { ... }

class Compressor {
    private CompressionStrategy strategy;
    void setStrategy(CompressionStrategy s) { this.strategy = s; }
    byte[] compress(byte[] data) { return strategy.compress(data); }
}
```

**与状态模式的区别**：

- **策略模式**：客户端 **主动选择** 算法，各策略之间**互相独立、可替换**。
- **状态模式**：对象 **内部状态驱动行为变更**，状态之间**会转换**，客户端不感知。

**应用场景**：支付方式选择、登录认证方式、优惠券打折、Comparator。

**面试口述要点**：策略模式就是**开闭原则的最典型应用**，新增算法只需要新增实现类，不要改上下文。

# 11. 责任链模式

**定义**：将请求沿着一条 **处理链** 传递，每个处理器决定自己处理还是传递给下一个。

**核心组成**：

1. **Handler 接口** — 定义处理方法和设置下一个处理器的方法。
2. **ConcreteHandler** — 具体处理器，处理成功或传给下一个。
3. **Client** — 组装链并发送请求。

```java
abstract class Filter {
    Filter next;
    void setNext(Filter next) { this.next = next; }
    abstract void doFilter(Request req);
}
class AuthFilter extends Filter {
    void doFilter(Request req) {
        if (!auth(req)) return; // 拦截
        if (next != null) next.doFilter(req);
    }
}
class RateLimitFilter extends Filter { ... }
class LogFilter extends Filter { ... }

// 组装
Filter chain = new AuthFilter();
chain.setNext(new RateLimitFilter());
chain.setNext(new LogFilter());
chain.doFilter(request);
```

**应用场景**：Servlet Filter、Spring Interceptor、Netty Pipeline、MyBatis 插件、网关过滤器。

**面试口述要点**：核心是 **解耦请求处理者**，每个处理器只关心自己职责，灵活增删处理器。相比 if-else 链，维护性大幅提升。

# 12. 单例模式（多种实现方式）

**定义**：确保一个类 **只有一个实例**，并提供全局访问点。

**多种实现方式**（从优到劣）：

1. **枚举单例**（最佳） — JVM 天然保证，防反射防序列化：
```java
enum Singleton { INSTANCE; }
```

2. **静态内部类**（懒加载 + 线程安全）：
```java
class Singleton {
    private Singleton() {}
    static class Holder { static Singleton INSTANCE = new Singleton(); }
    static Singleton getInstance() { return Holder.INSTANCE; }
}
```

3. **双重检查锁（DCL）**（volatile + synchronized）：
```java
class Singleton {
    private static volatile Singleton instance;
    static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
}
```

4. **饿汉式**（类加载就创建） — 简单但可能浪费资源。
5. **懒汉式 synchronized** — 性能差，不推荐。

**破坏单例的方式及防范**：

- **反射** → 构造器中加标志位，第二次抛异常。
- **序列化** → 实现 `readResolve()` 返回同一实例。
- **克隆** → 不实现 Cloneable。

**应用场景**：线程池、配置管理器、连接池、Logger。

**面试口述要点**：**枚举单例最安全**，但实际项目中 DCL 或静态内部类更常用。面试记得把"防反射、防序列化"也讲出来。

# 13. 工厂模式（简单工厂 / 工厂方法 / 抽象工厂）

**简单工厂（Simple Factory）**：

```java
class PaymentFactory {
    static Payment create(String type) {
        return switch (type) {
            case "wechat" -> new WechatPay();
            case "alipay" -> new AliPay();
            default -> throw new IllegalArgumentException();
        };
    }
}
```
- **不是 GOF 23 种**，本质是"将 if-else 集中管理"。
- 缺点：新增类型需要改工厂类，违反开闭。

**工厂方法（Factory Method）**：

```java
interface PaymentFactory { Payment create(); }
class WechatPayFactory implements PaymentFactory { ... }
class AliPayFactory implements PaymentFactory { ... }
```
- **将对象创建延迟到子类**，符合开闭原则。
- 每新增一个产品就新增一个工厂类，类多。

**抽象工厂（Abstract Factory）**：

```java
interface UIFactory {
    Button createButton();
    TextBox createTextBox();
}
class WinUIFactory implements UIFactory { ... }
class MacUIFactory implements UIFactory { ... }
```
- 创建 **一族产品**（配套组件）。
- 新增产品族容易，新增产品种类难。

**三者的选择**：

- 简单工厂：产品少，不需要扩展。
- 工厂方法：需要扩展产品，但单条产品线。
- 抽象工厂：需要创建一组关联产品。

**面试口述要点**：Spring 的 BeanFactory 是工厂方法模式的典例，MyBatis 的 SqlSessionFactory 用了抽象工厂思想。

# 14. 代理模式（静态 / JDK 动态 / CGLIB）

**定义**：为另一个对象提供一个 **替身/代理** 以控制对该对象的访问。

**三种实现**：

1. **静态代理** — 手动编写代理类，实现和目标类相同的接口：
```java
class UserServiceProxy implements UserService {
    UserService target;
    void save() {
        log("before");
        target.save();
        log("after");
    }
}
```
缺点：每个目标类要写一个代理类，维护成本高。

2. **JDK 动态代理** — 基于接口，运行时生成代理类：
```java
class LogHandler implements InvocationHandler {
    Object target;
    Object invoke(Object proxy, Method m, Object[] args) {
        log("before");
        Object r = m.invoke(target, args);
        log("after");
        return r;
    }
}
UserService proxy = (UserService) Proxy.newProxyInstance(
    loader, interfaces, new LogHandler(target));
```
要求：目标类**必须有接口**。

3. **CGLIB 动态代理** — 基于子类继承，字节码增强：
```java
class LogInterceptor implements MethodInterceptor {
    Object intercept(Object obj, Method m, Object[] args, MethodProxy mp) {
        log("before");
        Object r = mp.invokeSuper(obj, args);
        log("after");
        return r;
    }
}
```
要求：目标类**不能是 final**。

**Spring AOP 的选择策略**：

1. 目标类实现接口 → **JDK 动态代理**（默认）。
2. 目标类没实现接口 → **CGLIB**。

**应用场景**：AOP（事务/日志/权限）、远程代理（RPC）、延迟加载（Hibernate）。

**面试口述要点**：代理的核心是**不改原代码增强功能**——正是开闭原则的体现。重点讲清楚 JDK 和 CGLIB 的差异："JDK 必须基于接口，CGLIB 基于继承"。

# 15. 适配器模式

**定义**：将一个类的接口转换成客户端期望的另一个接口，让**不兼容的接口能够合作**。

**三种形式**：

1. **类适配器**（继承）：
```java
class VoltageAdapter extends Voltage220V implements Voltage5V { ... }
```

2. **对象适配器**（组合，推荐）：
```java
class VoltageAdapter implements Voltage5V {
    private Voltage220V v220; // 组合
    int output5V() { return v220.output220V() / 44; }
}
```

**与代理模式的对比**：

- **代理**：接口相同，**不改变功能**，只控制访问或增强。
- **适配器**：接口不同，**转换接口**让不兼容的类能协作。

**与装饰器的对比**：

- **装饰器**：接口相同，**动态增加功能**，递进增强。
- **适配器**：接口不同，**转换匹配**，解决兼容问题。

**应用场景**：

- `java.io.InputStreamReader`（InputStream → Reader）
- `java.util.Arrays#asList()`（数组 → List）
- Spring 的 `@Controller` 适配各种 HTTP 请求。
- Spring MVC 中的 HandlerAdapter。

**面试口述要点**：适配器模式解决的是"**接口不匹配**"问题，就像电源转换插头。记住三个模式的区别：代理不改接口只增强，装饰器同接口累加功能，适配器异接口做转换。

# 16. 装饰器模式

**定义**：**动态地** 给一个对象 **添加额外职责**，比继承更灵活。

**核心结构**：

1. **Component** — 抽象组件接口。
2. **ConcreteComponent** — 被装饰的原始对象。
3. **Decorator** — 装饰器抽象，持有 Component 引用。
4. **ConcreteDecorator** — 具体装饰器，在调用前后增强。

```java
interface Coffee { double cost(); }
class Espresso implements Coffee { double cost() { return 5.0; } }

abstract class CoffeeDecorator implements Coffee {
    Coffee coffee;
    CoffeeDecorator(Coffee coffee) { this.coffee = coffee; }
}
class MilkDecorator extends CoffeeDecorator {
    double cost() { return coffee.cost() + 2.0; }
}
class SugarDecorator extends CoffeeDecorator {
    double cost() { return coffee.cost() + 1.0; }
}

// 用起来像叠 Buff
Coffee c = new SugarDecorator(new MilkDecorator(new Espresso()));
```

**应用场景**：

- `java.io.BufferedInputStream`（为 FileInputStream 加缓冲）
- `java.io.BufferedReader`（为 FileReader 加行读取）
- `javax.servlet.http.HttpServletRequestWrapper`（包装请求）
- Spring 的 `TransactionAwareCacheDecorator`。

**面试口述要点**：装饰器**同接口、递进包装、层层增强**，像俄罗斯套娃。核心优势是比继承更灵活——运行时组合，避免类爆炸（如果每种组合都写子类）。

# 17. 观察者模式（与发布订阅对比）

**定义**：定义对象之间 **一对多依赖**，当一个对象状态变化，所有依赖者自动收到通知。

**核心组成**：

1. **Subject**（被观察者）— 维护观察者列表，提供 attach/detach/notify。
2. **Observer**— 观察者接口，定义 update 方法。
3. **ConcreteSubject** — 具体主题，状态变化时通知。
4. **ConcreteObserver** — 具体观察者，收到通知后处理。

```java
interface Observer { void update(String msg); }
class Subject {
    List<Observer> observers = new ArrayList<>();
    void attach(Observer o) { observers.add(o); }
    void notifyAll(String msg) {
        for (Observer o : observers) o.update(msg);
    }
}
class UserObserver implements Observer {
    void update(String msg) { System.out.println("收到: " + msg); }
}
```

**与发布订阅（Pub-Sub）的区别**：

- **观察者模式**：Subject 直接通知 Observer，**两者知道对方**（紧耦合）。
- **发布订阅**：通过 **消息中间件/Broker** 转发，发布者和订阅者**互不知道对方**（完全解耦）。

**对比图**：

- Observer：Subject → Observer（直接）。
- Pub-Sub：Publisher → EventBus/MessageQueue → Subscriber（间接）。

**应用场景**：

- `java.util.Observer` / `Observable`（JDK 9 后废弃）。
- Spring 的 `ApplicationListener` / `ApplicationEvent`（事件机制）。
- Guava 的 EventBus。
- 消息队列（Kafka/RabbitMQ）本质是跨进程的发布订阅。
- Swing/AWT 的事件监听。

**面试口述要点**：观察者模式是**事件驱动架构的基石**，Spring 事件机制就是典型应用。如果面试官追问，要说出"观察者紧耦合"和"发布订阅松耦合"的区别。

# 19. 总结：如何在实际项目中合理运用设计模式？

**核心原则**：

1. **不能为了用模式而用模式** — 模式是解决特定问题的工具，不是装饰品。
2. **优先满足 SOLID 原则** — 满足七大原则的代码自然贴合设计模式。
3. **KISS 优先** — 简单方案能解决就不要强行上设计模式。
4. **识别变化点** — 找到系统中"频繁变化"的地方，用模式封装变化。
5. **与框架结合** — Spring 已经大量内置了设计模式（AOP/事件/模板），优先用框架现成的。

**实战判断方法**：

1. **条件分支经常变** → 策略模式 / 工厂模式。
2. **处理流程固定、步骤频繁变** → 模板方法模式。
3. **需要对调用前后增强** → 代理模式 / 装饰器模式。
4. **解耦一对多通知** → 观察者模式 / 事件机制。
5. **避免多层 if-else 判断** → 责任链模式 / 策略模式。
6. **确保全局唯一实例** → 单例模式。
7. **接口不兼容需要转换** → 适配器模式。

**面试口述要点**：面试官期望的不是背模式，而是**在场景中选择模式的判断力**。回答时先说"我会先分析变化点在哪里"，再说"基于变化点选择对应的设计模式"。
