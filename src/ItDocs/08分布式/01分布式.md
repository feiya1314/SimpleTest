# 1. 什么是CAP理论？

**核心回答：** CAP理论指出分布式系统无法同时满足**一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance）**三个特性，最多只能同时满足两个。

**原理分析：**

1. **一致性（C）**：所有节点在同一时刻看到的数据是相同的，即数据强一致。
2. **可用性（A）**：每个请求都能在有限时间内得到响应（成功或失败）。
3. **分区容错（P）**：系统在网络分区（节点间通信中断）时仍能运行。

**组合分析：**

- **CA**：放弃分区容错，不适合分布式环境
- **CP**：放弃可用性，网络分区时可能无法响应（如Zookeeper）
- **AP**：放弃强一致性，保证最终一致性（如Eureka、Cassandra）

**CAP三者制衡关系**

1. 单节点存数据：数据只保存在一个节点，出现分区后，断开连接的区域无法访问该数据，系统不具备分区容错能力。
2. 多副本存数据（解决分区问题）：将数据复制到多个节点，分区发生后，数据可以分布在各个区域，提升分区容错性。但同时带来新的矛盾：

- 想要保证一致性：每次写操作必须等待所有节点写入完成，等待耗时增加，会降低系统可用性
- 想要保证可用性：不用等待全部节点同步完成，服务可快速响应，但多个节点之间会出现数据不一致

**什么是分区**

- 分布式系统中所有节点原本网络是连通的，一旦出现故障，部分节点之间无法互通，整个网络被分割成多个独立区域，数据分散在这些互不连通的区域中，这个现象就是分区。

**分区产生的原因**

- 网络层面：节点之间网络不可达
- JVM层面：GC的Stop The World阻塞时间过长
- 服务器层面：CPU死循环卡死

**为什么分布式系统无法放弃P（分区容错）**
网络分区是分布式系统必然会发生的硬件/网络客观故障，无法彻底避免：

- 分布式系统由多台服务器、多节点跨网络部署，网络延迟、断连、机器卡顿都是客观存在的故障，人力无法百分百杜绝
- 一旦放弃P，意味着系统不允许出现任何网络分区，只要发生分区，整个系统直接不可用
- 所以分布式系统必须保留分区容错P，我们只能在C（一致性）和A（可用性）之间做取舍，无法选择CA组合

**延展思考：**
CAP理论中P是必然发生的（网络不可能100%可靠），所以实际是在CP和AP之间选择。多数互联网业务选择AP，通过最终一致性保证高可用。BASE理论是AP的实现基础。

# 2. 什么是BASE理论？

**核心回答：** BASE理论是**Basically Available（基本可用）、Soft State（软状态）、Eventually Consistent（最终一致性）**的缩写，是对CAP中AP方案的实践指导。

**原理分析：**

1. **基本可用**：允许系统在故障时降级，保证核心功能可用（如降级页面、非核心功能关闭）。
2. **软状态**：允许系统数据存在中间状态，不要求强一致性。
3. **最终一致性**：系统在一段时间后达到一致状态。

**实践策略：**

- **分区降级**：故障时关闭非核心功能，保证核心流程
- **数据补偿**：通过异步消息或定时任务修复数据不一致
- **延迟敏感**：对延迟敏感的业务提供兜底方案

**延展思考：**
BASE理论是多数互联网分布式系统的理论基础。典型应用：淘宝库存扣减（高并发时允许暂时不一致，后续补偿）、12306订票（库存最终一致，允许部分请求失败重试）。

# 3. 分布式事务有哪些解决方案？

**核心回答：** 分布式事务解决方案包括**2PC、3PC、TCC、Saga、可靠消息**。

**原理分析：**

1. **2PC（两阶段提交）**：
   - 准备阶段：协调者向所有参与者发送准备请求，参与者执行事务但不提交
   - 提交阶段：所有参与者准备成功则提交，失败则回滚
   - 问题：协调者单点故障、数据不一致风险（部分参与者提交成功）
2. **3PC（三阶段提交）**：
   - 引入预提交阶段，减少阻塞时间
   - 协调者超时后参与者自动提交，降低数据不一致概率
3. **TCC（Try-Confirm-Cancel）**：
   - Try：预留资源
   - Confirm：确认使用资源
   - Cancel：取消预留
   - 优点：性能较高，不阻塞；缺点：业务侵入性强，需要实现三个接口
4. **Saga模式**：
   - 事务链中每个服务执行本地事务，失败则执行补偿操作
   - 适用于长流程业务，如订单处理
5. **可靠消息**：
   - 发送方确保消息一定能送达，通过本地消息表或RocketMQ事务消息
   - 接收方做好幂等处理

**选型建议：**

- 强一致性要求：2PC/3PC（但不推荐，有单点问题）
- 性能要求高、业务可拆分：TCC
- 长流程业务：Saga
- 最终一致性：可靠消息

# 4. 分布式锁有哪些实现方式？

**核心回答：** 常见分布式锁实现包括**数据库锁、Redis锁、Zookeeper锁**。

**原理分析：**

1. **数据库分布式锁**：
   - 基于唯一索引或排他锁实现
   - 实现简单但性能差，无失效机制
2. **Redis分布式锁**：
   - 基于SET key value NX PX timeout实现
   - 需考虑Lua脚本保证原子性
   - Redisson提供了完整的分布式锁实现
3. **Zookeeper分布式锁**：
   - 基于临时顺序节点和Watch机制
   - 可靠性高但性能低于Redis

**Redis锁关键点：**

- 锁值需包含唯一标识（如UUID），释放锁时需验证
- Lua脚本保证原子性：if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end
- 需考虑锁重试、锁超时自动释放、死锁检测

**方案设计：**

- Redis + Lua：性能高，支持集群，但可能有数据不一致风险
- Zookeeper：可靠性高，顺序锁支持公平锁，但性能较低
- 数据库：简单场景，不推荐生产环境使用

# 5. 什么是分布式ID？如何生成？

**核心回答：** 分布式ID是**在分布式系统中唯一标识数据**的ID，要求唯一性、递增性、可读性。

**常见方案：**

1. **UUID**：简单但无序、长度过长、字符串存储空间大
2. **数据库自增**：单点数据库有瓶颈，可通过设置step实现多节点自增
3. **雪花算法（Snowflake）**：Twitter开源的分布式ID生成算法，64位long型ID，趋势递增、性能高；缺点是依赖系统时钟（详见下方详解）
4. **Leaf（美团）**：号段模式，每次批量获取ID，避免数据库单点瓶颈

**雪花算法（Snowflake）详解：**

雪花算法是Twitter开源的分布式ID生成算法，由**时间戳、机器ID、序列号**三部分组成一个64位long型ID，整体趋势递增，是当前最主流的分布式ID方案之一。

**位结构（64位）：**

```
符号位(1) | 时间戳(41) | 数据中心ID(5) | 机器ID(5) | 序列号(12)
```

| 部分 | 位数 | 说明 |
| --- | --- | --- |
| 符号位 | 1位 | 固定为0，保证ID为正数 |
| 时间戳 | 41位 | 记录毫秒级时间戳，2^41毫秒约等于**69年**；可自定义起始时间，从而延长算法的可用时长 |
| 数据中心ID | 5位 | 标识数据中心，最多支持32个（2^5），如按机房划分 |
| 机器ID | 5位 | 标识数据中心内的机器，最多支持32台（2^5）；与数据中心ID组合，共可支持**1024台机器** |
| 序列号 | 12位 | 同一毫秒内的递增序号，单机每毫秒最多生成**4096个**（2^12）ID |

**生成流程：**

1. 取当前毫秒级时间戳，减去自定义的起始时间，得到41位时间戳部分
2. 获取当前机器的数据中心ID和机器ID（通过Zookeeper或配置中心分配）
3. 同一毫秒内，序列号从0开始自增：如果序列号达到上限4095，则等待进入下一毫秒，序列号重新从0开始
4. 将时间戳、数据中心ID、机器ID、序列号四部分按位拼接，得到一个64位ID

**优点：**

- **趋势递增**：时间戳在最高位，生成的ID整体随时间的推移单调递增，对数据库索引（B+树）友好，插入性能好
- **性能高**：纯内存位运算生成，不依赖数据库、不依赖网络，单机每毫秒最多可生成4096个ID
- **全局唯一**：不同机器使用不同机器ID，同一机器不同毫秒时间戳不同，同一毫秒由序列号区分，因此不会重复

**缺点与注意点：**

- **依赖系统时钟**：ID中的时间戳取自系统当前时间，一旦系统时钟发生回拨（如NTP同步、手动改时间），就可能生成重复的ID
- **时钟回拨的处理**（常见方案）：
  - **拒绝服务**：检测到时间回拨时暂停生成ID，等待时钟追平后再恢复
  - **序列号补偿**：利用序列号继续递增来避开回拨前已生成的ID
  - 更完善的实现（如美团Leaf的雪花模式）会记录上次生成的时间，发现回拨时抛异常或延迟等待
- **机器ID需要分配管理**：每台机器需要唯一的机器ID（数据中心ID+机器ID），机器数量多时需要借助Zookeeper、配置中心统一分配

**选型建议：**

- 小型系统：UUID或数据库自增
- 中大型系统：雪花算法或Leaf
- 需要趋势递增：雪花算法

# 6. 一致性Hash算法是什么？

**核心回答：** 一致性Hash算法用于**解决分布式缓存和数据分片的负载均衡问题**，在节点增减时尽可能减少数据迁移。

**原理分析：**

1. **Hash环**：将Hash值空间映射到0-2^32-1的环上
2. **数据定位**：数据Hash值顺时针找到第一个节点
3. **虚拟节点**：为每个物理节点创建多个虚拟节点，解决数据倾斜问题

**优势：**

- 节点增加/删除只影响相邻节点的数据
- 虚拟节点解决负载不均问题

**适用场景：**

- 分布式缓存（Redis Cluster的Hash Slot类似）
- 分布式存储的数据分片

**调优实践：**

- 虚拟节点数：通常每个物理节点100-200个虚拟节点
- 需监控节点负载，及时调整虚拟节点数

# 7. 什么是拜占庭将军问题？

**核心回答：** 拜占庭将军问题研究**分布式系统中存在恶意节点时如何达成共识**。

**原理分析：**

1. **问题描述**：多个将军围攻敌人，需要协调进攻时间，但其中可能有叛徒传递假消息。
2. **核心挑战**：如何在不可靠的通信下，让忠诚的将军达成一致。
3. **解决方案**：实用拜占庭容错（PBFT）、Raft、Paxos等共识算法。

**共识算法对比：**

- **Paxos**：理论共识算法，晦涩难懂，Lamport提出
- **Raft**：简化的共识算法，适用于非拜占庭环境（允许节点故障，不允许恶意）
- **PBFT**：拜占庭容错算法，适用于存在恶意节点场景

**延展思考：**
区块链是拜占庭将军问题的实际应用，通过工作量证明（POW）、权益证明（POS）等机制在不可信网络中达成共识。

# 8. 分布式系统如何保证数据一致性？

**核心回答：** 分布式数据一致性分为**强一致性、最终一致性**，实现方式包括**同步复制、异步复制、混合复制**。

**原理分析：**

1. **同步复制**：主节点写入后同步到从节点，全部成功才返回，延迟高但一致性强（如Zookeeper）。
2. **异步复制**：主节点写入后立即返回，后台异步复制到从节点，性能高但可能丢失数据。
3. **半同步复制**：主节点写入后至少一个从节点成功即返回，平衡性能和数据安全。

**最终一致性方案：**

1. **版本控制**：每次更新增加版本号，冲突时基于版本号合并
2. **向量时钟**：记录每个节点的逻辑时间，用于检测冲突
3. **CRDT**：支持合并的数据结构，保证最终一致性

**调优实践：**

- 金融级系统：同步复制或半同步复制
- 普通业务：异步复制 + 对账补偿
- 缓存和DB：延迟双删、订阅binlog保证最终一致

# 9. 什么是Paxos算法？

**核心回答：** Paxos是**分布式共识算法**，用于在存在故障的分布式系统中达成一致性。Raft算法是其工程实现。

**原理分析：**

1. **角色**：Proposer（提案者）、Acceptor（接受者）、Learner（学习者）
2. **两个阶段**：
   - Prepare阶段：提案者向多数派发送提案编号，获取承诺
   - Accept阶段：提案者发送提案内容，接受者接受多数派提案
3. **约束**：提案编号必须递增，接受者只能接受编号最大的提案

**特点：**

- 属于少数派多数获胜模型
- 只能达成一致，不能保证提案被选中

**延展思考：**
Paxos难以理解，Raft通过选举Leader简化了Paxos。Zookeeper的ZAB协议类似Paxos。实际工程中通常使用Raft（Etcd、Consul）或ZAB（Zookeeper）。

# 10. 什么是Raft算法？

**核心回答：** Raft是**工程化的共识算法**，通过选举Leader简化了分布式一致性问题。

**原理分析：**

1. **三种角色**：Leader（领导者）、Follower（跟随者）、Candidate（候选者）
2. **Leader选举**：Follower超时未收到心跳则转为Candidate，发起选举，获得多数票成为Leader
3. **日志复制**：Leader接收客户端请求， AppendEntries消息复制到Follower，超过半数成功则提交
4. **任期机制**：每个任期有唯一任期号，任期大的节点更新任期小的节点

**核心机制：**

- **心跳**：Leader定期发送心跳维持统治
- **选举超时**：Follower随机超时，防止选举僵持
- **日志复制**：线性一致性保证

**适用场景：**

- 分布式协调服务（Etcd、Consul）
- 分布式存储（Redis Cluster的Sentinel）

**延展思考：**
Raft相比Paxos更容易理解和实现，是当前分布式系统的主流共识算法。需注意网络分区时的脑裂问题，Raft通过多数派选举避免。

# 11. 如何保证接口幂等

**核心回答：** 幂等（Idempotent）指：**同一个操作，无论执行一次还是执行多次，产生的影响都和只执行一次相同**（使用相同参数重复执行，能获得相同结果）。比如"把订单状态改为已支付"，执行一次和执行十次，订单最终都是已支付状态。接口幂等是系统服务对外的一种承诺——**承诺只要调用成功，外部多次调用对系统的影响是一致的**。除了天然幂等的查询、删除操作外，新增、更新、删除都需要保证幂等。

**为什么需要幂等（重试是常态）：**

- 分布式环境下网络超时是常态：客户端拿到TimeoutException时，服务端可能已经执行成功了，此时客户端会发起重试（用MQ处理时，MQ也会重试）
- 服务端应该默认"外部调用失败是常态，失败之后必然会有重试"
- 重复消息是SOA服务实现中非常常见的问题，永远不要指望调用方每次请求的消息都不一样：对于读操作，重复消息可能无害；对于写操作，重复消息很可能就是灾难
- 举例：客户账户Account1有100元，执行一次交易（Order01）扣款10元变成90元。但如果服务端扣款成功、响应却超时，客户端拿到TimeoutException后重试，就会再次扣款10元变成80元；重试多次余额甚至会被扣成负数。理想情况是多次重复处理的结果不变，始终是90元

**核心思路：** 不管哪种方案，本质上都围绕两点：

1. 给每次操作一个**唯一标识**（业务ID、token、唯一索引、版本号等），用它标识一个工作单元，这个工作单元只应执行一次
2. 执行前**先判断该操作是否已经执行过**：已执行过就直接返回原有结果；未执行过才真正执行业务

**常见技术方案：**

 1. **查询操作（天然幂等）**：在数据不变的情况下，查询一次和查询多次结果一样，select是天然的幂等操作
 2. **删除操作（天然幂等）**：删除一次和删除多次都是把数据删除（注意：返回值可能不一样——删除不存在的数据返回0，删除多条数据返回多条的删除数，但最终的数据状态一致）
 3. **唯一索引 / 唯一主键（防止新增脏数据）**：
    - 给数据库表中容易重复的字段加唯一索引或唯一组合索引，重复插入时数据库会抛唯一约束异常，保证一条记录只会被创建一次
    - 例子：支付宝资金账户——每个用户只能有一个资金账户，给资金账户表的用户ID加唯一索引，防止给同一个用户创建多个资金账户
    - 要点：当表存在唯一索引、并发新增报错时，再查询一次即可返回结果（数据应该已经存在了）
    - 唯一主键注意：主键不能是自增的，需要业务生成全局唯一主键；如果是分库分表场景，路由规则要保证相同请求落在同一个库、同一张表，否则不同库表之间的主键约束互不相关，就不起作用
 4. **防重表 / 去重表（有唯一标识的插入场景）**：
    - 适用场景：业务中有唯一标识的插入场景，比如一个订单只会支付一次，订单号就可以作为唯一标识
    - 实现：建一张去重表，把唯一标识（如订单号orderNo）作为唯一索引；把"写入去重表"和"业务操作"放在同一个事务中。重复请求时，去重表唯一约束导致插入失败，事务回滚
    - 注意：去重表和业务表应该放在同一个库中，这样才能保证处于同一个事务；即使业务操作失败，去重表的数据也会回滚，保证数据一致性
 5. **插入或更新（Insert Or Update）**：适用于"插入并且已有唯一索引"的场景，利用数据库的ON DUPLICATE KEY UPDATE，重复插入时改为更新：

    ```sql
    insert into goods_category (goods_id,category_id,create_time,update_time) 
           values(#{goodsId},#{categoryId},now(),now()) 
           on DUPLICATE KEY UPDATE
           update_time=now()
    ```
 6. **悲观锁（获取数据时加锁）**：

    ```sql
    select * from table_xxx where id = 'xxx' for update;
    ```
    - 注意：id字段一定是主键或者唯一索引，否则会锁表，性能很差
    - 悲观锁一般伴随事务一起使用，数据锁定时间可能很长，要根据实际情况选用
 7. **乐观锁（版本号控制）**：只在更新数据那一刻生效，其他时间不锁表，相对悲观锁效率更高。实现方式：通过version字段或者其他状态条件

    ```sql
    update t_goods set count = count - 1, version = version + 1 where good_id = 2 and version = 1;
    ```
    - 原理：操作库存前先获取当前version（比如1），更新时带上version条件（version=1）。第一次更新成功后version变成2；如果返回给订单服务时出现问题，订单服务再次调用时传入的version还是1，where条件不成立，SQL不会执行。这样不管调用几次，只会真正处理一次
    - 另一种写法（多版本控制）：`update goods set name=#{newName},version=#{version} where id=#{id} and version<${version}`——更新商品名字时在接口中增加版本号参数，只有当当前版本小于传入版本时才允许更新
    - 适用场景：读多写少的场景
 8. **状态机幂等**：适用于单据类、任务类业务（如订单的状态流转）
    - 业务单据上有一个状态，状态在不同情况下会发生变更，一般情况下是有限状态机
    - 如果状态机已经处于下一个状态，这时来了上一个状态的变更请求，理论上是不允许变更的，这样就保证了幂等
    - 实现：状态字段使用int类型，通过值的大小做幂等，比如订单创建为0、付款成功为100、付款失败为99

    ```sql
    update `order` set status=#{status} where id=#{id} and status<#{status}
    ```
    - 注意：订单等单据类业务存在很长的状态流转，一定要深刻理解状态机，这对业务系统设计能力的提升有很大帮助
 9. **分布式锁**：当难以确定唯一性字段、难以构建全局唯一索引时使用
    - 通过第三方系统（redis或zookeeper）在业务系统插入或更新数据前获取分布式锁，操作完成后释放锁
    - 本质：把多线程并发的锁思路，引入到多个系统（即分布式系统）中解决
    - 要点：某个长流程处理过程要求不能并发执行时，可以在流程执行前根据某个标志（用户ID+后缀等）获取分布式锁；其他流程执行时获取锁就会失败，即同一时间该流程只能有一个执行成功；执行完成后释放分布式锁（分布式锁需要第三方系统提供）
10. **token机制（防止页面重复提交）**：
    - 业务要求：页面的数据只能被点击提交一次
    - 发生原因：重复点击、网络重发、nginx重发等情况会导致数据被重复提交
    - 处理流程：
      1. 数据提交前先向服务端申请token，token放到redis（集群环境）或jvm内存（单JVM环境），并设置有效时间
      2. 提交后后台校验token，同时删除token，生成新的token返回
    - token特点：要申请、一次有效性、可以限流
    - 注意：redis要用"删除"操作来判断token——删除成功代表token校验通过；如果用select + delete两步校验token，存在并发问题，不建议使用
    - 先删除还是后删除token：
      - 后删除：业务处理成功后删除redis中的token失败，token没被删除，就会导致重复请求。这本质是数据库和缓存redis的数据不一致问题
      - 先删除：如果业务处理出现异常没有成功，调用方重试时token已被删除，服务端判断token不存在、认为是重复请求而直接返回，无法执行业务。但先删除可以保证不会因为重复请求导致业务数据出错；出现业务异常时，让调用方重新获取新的token，再次发起重试即可
    - 缺点：每次请求都会多出额外请求（一次获取token请求 + 一次判断token的请求）。真实生产环境中，1万请求也许只会存在10个左右的请求发生重试，却让9990个请求都多付出了额外开销
11. **select + insert（先查后插）**：适用于并发不高的后台系统或任务JOB
    - 先查询一些关键数据，判断是否已经执行过，再进行业务处理，从而支持重复执行
    - 注意：核心高并发流程不要用这种方法
12. **对外API接口的幂等（source + seq）**：如银联提供的付款接口
    - 接入商户提交付款请求时须附带：source（来源）、seq（序列号），这两个字段在提供方系统里做联合唯一索引，防止多次付款（并发时只能处理一个请求）
    - 重点：对外提供接口为了支持幂等，接口有两个字段必须传——一个是来源source，一个是来源方序列号seq，两个字段在提供方系统里做联合唯一索引
    - 流程：第三方调用时，先在本方系统查询该笔业务是否已经处理过——处理过则返回相应处理结果；没有处理过再进行业务处理，返回结果
    - 注意：为了幂等友好，一定要先查询是否处理过该笔业务。不查询直接插入业务系统会报错，但实际已经处理了

**通用方案：全局唯一ID**

- 思路：根据业务的操作和内容生成一个全局唯一ID，执行操作前先根据这个全局ID是否存在，判断操作是否已执行：不存在则把全局ID存储到存储系统（数据库、redis等）；存在则说明该方法已经执行过
- 具体到redis实现：调用接口时生成一个唯一id，用redis的集合（Set）去重——添加成功说明是第一次处理，添加失败说明已处理过
- 支持插入、更新、删除业务操作，是一个通用方案；但它实现起来比较麻烦，上面针对特定场景的方案实现起来更简单
- 工程角度：使用全局ID做幂等可以作为业务的基础微服务存在，很多微服务都会用到；如果在每个微服务里都各自实现，存在工作量重复
- 注意：打造高可靠的幂等服务还要考虑很多问题，比如一台机器把全局ID先写入存储之后挂了，就需要引入全局ID的超时机制

**具体业务案例：**

- **订单类超时重试场景**：
  - 订单创建接口第一次调用超时，调用方重试——要保证不会创建出两个订单
  - 订单创建时需要扣减库存，接口超时后调用方重试——要保证库存不会重复扣减
  - 订单开始支付，支付请求发出后服务端已扣钱但响应超时，调用方重试——要保证不会重复扣钱
  - 订单状态更新接口，调用方连续发送两个消息（已创建、已付款），但接收方先收到"已付款"再收到"已创建"——要保证乱序消息不会把订单状态改错
  - 支付完成后需要发送一条短信，一台机器接收短信消息后处理较慢，消息中间件又把消息投递给另一台机器处理——要保证短信不会重复发送
- **代扣接口**：执行业务操作前，先查询代扣请求参数中的商户自定义orderid是否已经存在，存在说明已处理过
- **云卡充值（用更新影响行数判断幂等）**：先更新card状态为"处理中"、更新flow为"支付中"。业务处理完成后调用收单平台，等待kafka回调收单结果。kafka回调返回Success时，先执行"将flow从paying更新为success"的更新语句并校验影响行数：若更新影响行数大于0，说明是首次更新，继续执行后续操作；若影响行数小于等于0，说明该flow可能已被更新过，即可能是重复调用接口，以此判断接口幂等

**方案选型总结：**

- **新增（插入）场景**：唯一索引/唯一主键、防重表、插入或更新、全局唯一ID
- **更新场景**：乐观锁（版本号）、状态机
- **防止页面重复提交**：token机制
- **跨系统并发控制**：分布式锁
- **对外提供的接口**：source + seq 联合唯一索引
- **低并发后台任务**：select + insert

# 12. 分布式session

**核心回答：** Session是客户端与服务器的会话跟踪技术：服务端生成sessionId并让客户端存入cookie，之后的请求带上它来识别会话。在分布式集群环境下，同一用户的多次请求可能被负载均衡分发到不同服务器，导致session无法共享，这就是分布式session要解决的问题。常见解决方案有四种：**session复制、session绑定、cookie记录session、独立session服务器**，其中**独立session服务器（用redis等集中存储）**是主流推荐方案。

**Session的作用（先搞清楚Session是什么）：**

Session是客户端与服务器通讯的会话跟踪技术，服务器用它保持与客户端整个通讯过程中的会话基本信息。工作流程：

1. 客户端第一次访问服务端时，服务端响应一个sessionId，并将它存入本地cookie
2. 之后的访问，客户端会把cookie中的sessionId放入请求头中去访问服务器
3. 服务器通过sessionId查找对应的会话数据：找到则继续使用；如果通过sessionId没有找到对应数据，就创建一个新的sessionId并响应给客户端

**分布式Session存在的问题（为什么不能直接用）：**

- 单服务器web应用中，session信息只需存在该服务器上，不存在共享问题
- 但随着分布式系统的流行、百万级用户规模的增长，单系统已经不能满足需求，应用以集群方式部署：高并发请求到达服务端后，通过负载均衡分发到集群中的某个服务器，同一个用户的多次请求可能被分发到集群的不同服务器上，就会取不到session数据
- 举例：第一次访问服务A生成一个sessionId并存入cookie；第二次访问服务B，客户端从cookie中读取sessionId加入请求头，但服务B通过sessionId找不到对应数据，就会创建一个新的sessionId返回给客户端——Session无法共享，达不到预期目的
- 于是session的共享成了一个问题，这时就需要解决**Session一致性**

**常见解决方案：**

1. **session复制（早期方案）**：
    - 做法：应用服务器开启web容器的session复制功能，在集群中的几台服务器之间同步session对象，使每台服务器上都保存所有session信息
    - 效果：任何一台宕机都不会导致session数据丢失；服务器使用session时直接从本地获取
    - 简介：将一台机器上的Session数据广播复制到集群中其余机器上
    - 使用场景：机器较少、网络流量较小
    - 优点：实现简单、配置较少、网络中有机器宕机时不影响用户访问
    - 缺点：广播式复制到其余机器有一定延时，带来一定网络开销；应用集群达到数千台时会出现瓶颈——每台都需要备份session，内存不够用

2. **session绑定（黏性会话）**：
    - 做法：利用hash算法（如nginx的ip_hash），使得同一个IP的请求都被分发到同一台服务器上
    - 使用场景：机器数适中、对稳定性要求不是非常苛刻
    - 优点：实现简单、配置方便、没有额外网络开销
    - 缺点：网络中有机器宕机时，用户session会丢失，容易造成单点故障；这种方式不符合系统高可用要求——一旦某台服务器宕机，该机器上的session就不复存在，用户请求切换到其他机器后没有session，无法完成业务处理

3. **利用cookie记录session**：
    - 做法：session记录在客户端（cookie），每次请求服务器时把session放在请求中发送给服务器，服务器处理完请求后再将修改后的session响应给客户端
    - 优点：cookie简单易用、可用性高、支持应用服务器的线性伸缩；大部分需要记录的session信息比较小，因此事实上许多网站多多少少在使用cookie记录session
    - 缺点：
      - 受cookie大小的限制，能记录的信息有限
      - 每次请求响应都需要传递cookie，影响性能
      - 用户关闭cookie后，访问就不正常

4. **独立session服务器（推荐方案）**：
    - 做法：利用独立部署的session服务器（集群）统一管理session，服务器每次读写session时都访问session服务器，可以解决上面的所有问题
    - 本质：应用服务器的状态分离——分为无状态的应用服务器和有状态的session服务器，然后针对这两种服务器的不同特性分别设计架构
    - 实现：对于有状态的session服务器，一种比较简单的方法是利用分布式缓存（redis、memcached），或者存储在数据库（如MySQL）等，在这些产品的基础上进行包装，使其符合session的存储和访问要求
    - 进阶：如果业务场景对session管理有比较高的要求，比如利用session服务实现单点登录（SSO）、用户服务器等功能，需要开发专门的session服务管理平台
    - 使用场景：集群中机器数多、网络环境复杂
    - 优点：可靠性好
    - 缺点：实现复杂、稳定性依赖于缓存的稳定性、Session信息放入缓存时要有合理的策略写入

**方案选型总结：**

- **机器少、网络流量小（早期/小规模）**：session复制
- **机器数适中、稳定性要求不高**：session绑定
- **记录信息量小、简单场景**：cookie记录session
- **生产环境主流（机器多、高可用、网络复杂）**：独立session服务器（redis等集中存储）
