## 功能说明

`to-spec` 将你刚刚完成的对话整理成一份**需求规格文档（spec）**，并作为一条工单发布到你的任务追踪系统。

它**不会向你发起新一轮问询**。当你调用这条指令时，关键决策应当已经完成。它只会整合已有信息：对话记录、代码库内容、`CONTEXT.md` 以及架构决策记录（ADR），不会开启新一轮提问。 规格文档是**已完成决策的存档**，而不是用来产生新决策的载体。

## 何时使用

你需要手动输入 `/to-spec` 进行调用，Agent 不会自动执行该指令。

适用场景：开发工作量超出单次 Agent 会话上限，需要拆分多次执行。这是使用它的核心判断标准：

| 当前所处阶段 | 应当执行指令 |
| --- | --- |
| 尚未完成任何决策 | 先执行 `grill-with-docs` |
| 决策已定，工作量能放入单个上下文窗口 | 直接使用 `implement`，跳过生成规格文档步骤 |
| 决策已定，需要跨多个会话完成开发 | 先执行 `/to-spec`，再执行 `to-tickets` |
| `wayfinder` 任务规划地图梳理完毕 | `/to-spec #<地图工单编号>` |

## 前置条件

`to-spec` 会把规格文档发布为工单，因此必须先通过 `setup-matt-pocock-skills` 为本仓库配置好任务追踪工具以及工单评审标签词汇表。 两种模式均支持：GitHub 这类线上追踪平台，或是存放在 `.scratch/` 目录下的本地 Markdown 文件（开箱即用）。

## 规格文档 = 决策记录

设置规格文档的根本原因：大模型上下文窗口存在上限。 你在深度质询（grilling）过程中敲定的所有内容——最终方案形态、反复权衡得出的选择、明确决定不做的需求——全都保存在一段即将被清空的对话里。规格文档用来永久留存这些结论。

因此，它不会校验方案，也不会做出任何新决策。它使用项目自有术语记录已定方案，保证新开会话时无需你重复讲解需求。 如果规格文档中出现了你从未确认过的内容，那属于文档缺陷。

## 先确定测试边界，再撰写正文

在输出任何文字之前，`to-spec` 会先梳理该功能对应的**测试边界（seams）**，并与你确认。 优先复用现有边界，尽可能选用层级最高的边界；一次改动理想情况下只定义一处边界。

确认后的测试边界会贯穿后续流程： `tdd` 只会在双方约定好的边界开展测试；`code-review` 对照规格文档评审代码变更。一旦出现未经确认的边界，评审阶段就会标记出来。 这种关联是间接依托这份规格文档建立的。正因如此，测试边界的讨论应当在此处落实，不要推迟到开发阶段。

## 常见问题解答

### `/to-prd` 去哪里了？

该能力就是现在的 `to-spec`，在 v1.1 版本完成更名。 目前统一使用术语 Spec（规格文档），旧指令 `to-prd` 已废弃，需要重新安装使用新名称。 新的术语配对为：**spec（规格文档）+ tickets（开发工单）**。 规格文档定义最终目标与固定决策；工单是抵达目标的执行步骤。 如果后续方案发生调整，可以删除未完成工单，保留规格文档。

### 为什么规格文档会打上 `ready-for-agent` 标签？我不希望 Agent 直接依据文档开发。

这个标签含义是「无需进一步需求评审」，代表文档信息完整，可以作为 Agent 的工作输入，它仅仅是标识文档状态，不等同于开发任务单。

但如果你启用了后台轮询任务的 AFK 自动化 Agent，Agent 无法区分这个差异，会尝试一次性实现完整规格文档，而不是拆分到各个工单分步开发。 这是该技能反馈最多的痛点。在功能优化前，有两种方案：

1. 在 AFK Agent 的提示词中明确排除规格主工单；
2. 执行完 `/to-tickets` 之后移除该标签。

### 能不能直接从深度质询跳到 `/to-tickets`，省略规格文档？

很多场景下完全可以。**只有跨多会话的大型开发，规格文档才有存在价值。** 工单是可丢弃的，规格文档需要长期留存：每张工单适配单次上下文窗口，完成后关闭或删除；规格文档统一承载全部设计思路。 如果只是单次会话就能完成的改动，生成规格文档不会带来收益，反而额外增加一轮模型整理步骤，存在信息失真风险。 推荐链路：深度质询 → `/implement`。

### 我刚完成 wayfinder 规划地图，调用时传入什么内容？

传入主规划地图工单：`/to-spec #<地图工单编号>`，不要传入零散的决策子工单。 `wayfinder` 产出的是分散在规划图中的各项决策，而非可直接开发的交付方案；`to-spec` 的作用就是把零散决策整合为一份完整可落地文档。 如果直接把规划地图交给 `/implement`，就会跳过整合步骤。

### 这份文档是给我审阅，还是专供 Agent 使用？

主要面向 Agent，行文风格偏向完整、信息密集、大量引用参考。 你重点审阅**测试边界**和\*\*需求范围外（out-of-scope）\*\*两个板块：这两处如果决策出错，早期修正成本最低，等到开发后期发现代价极高。

不少使用者反馈通读全文负担很重，但目前没有精简摘要模式。坦诚来说： 如果你看完规格文档感到意外、发现大量陌生结论，问题根源是前期深度质询不够充分，而非文档篇幅过长。

### 工单启动开发后，规格文档需要固定不再改动，还是允许 Agent 更新？

没有机制保障文档与开发进度自动同步。实际使用中，它只是某一时间点的快照，一旦开发过程获得新认知，文档立刻开始滞后。 项目上线后就可以视作临时文档。 需要长期保留的内容应当写入 `CONTEXT.md` 和 ADR；开发阶段得出的重要新知，记录到这两份文件，不要反复修改规格文档。

### 如果我的工作是重构、调整模块边界，而非新增功能，这套模板适用吗？

适配度一般，这是已知局限。模板重度依赖用户故事，但架构调整类工作并不适合这套表述方式。强行填写会衍生出大量无关用户故事，掩盖接口、不变量相关的核心架构决策。

建议重点填写「实现决策」「测试决策」板块；长期性架构结论尽量通过 `grill-with-docs` 输出为 ADR，不要依靠规格文档承载。

### 它会自动检索工单系统里相关任务、自动引用遵循的 ADR 吗？

两者都不会。 它会读取并遵守改动范围内的 ADR，但不会自动添加链接引用；起草文档前也不会检索任务系统排查重复需求，有可能出现和已有工单重复开发的情况。 如果改动模块业务比较密集，建议你手动提前检索工单。

### `/to-tickets` 读取规格文档时内容被截断怎么办？

超大规格文档可能超出工单系统完整返回文本的上限，并且没有本地备用副本。 解决方案：做好上下文管理，**不要在执行** `/to-spec` **和** `/to-tickets` **之间清空或压缩对话上下文**。两条指令在同一个会话窗口连续运行，就无需重新拉取规格文档。

## 判断运行正常的标准

满足下面所有特征，代表技能执行符合预期：

1. 直接开始撰写文档，而不是抛出新一轮问题向你确认；
2. 正式撰写前先和你确认测试边界，尽可能精简边界数量；
3. 使用项目自有业务名词行文，而非通用产品管理套话；
4. 文档内每一项决策你都有印象，不存在为填充板块凭空编造的内容；
5. 「需求范围外」板块有实质内容；你明确放弃不做的条目，往往是文档最有价值的部分。

## 在工作流中的位置

`to-spec` 属于主开发链路的一环，仅用于跨多会话开发分支：

```
grill-with-docs → to-spec → to-tickets → implement → code-review

```

上游前置技能：

- `grill-with-docs`：负责完成决策，`to-spec` 只负责记录决策；
- `wayfinder`：完成规划地图后接入当前链路。

下游技能： `to-tickets` 将规格文档拆解为验证性子工单，交由 `implement` 执行开发。

如果你不确定选用哪条技能、走哪套流程，可以调用 `ask-matt` 获取推荐。
